# Course 12 · Chapter 12.4: Context and memory in long sessions: stateless calls, tool-result hygiene, stale data, resume vs fork vs fresh, exploration, subagents

_Andrey Popov's project notes: how it works, why it was built this way, and the theory behind it._

**In short:** Keeping long agent sessions accurate: stateless API calls, context rot, offloading and trimming tool results, structured case facts, stale data for returning users, resume versus fork versus fresh sessions, code exploration tactics and subagents.

## 2. The problem (business view, plain English)

Long agent sessions degrade. After 30 minutes of exploration the agent says "typical rendering patterns" instead of the class names it found; a support agent at turn 48 cannot recall the refund from turn 5; a returning customer is told "your refund is still pending" because a four-hour-old tool result is still in the transcript. Bigger context windows do not fix this: more tokens means more noise to attend over, higher cost, and old facts competing with new ones.

Finance analogy: a case file. A good case handler does not re-read every email each morning; they keep a one-page case summary (parties, amounts, status, next step), file the evidence, and pull the current account statement before calling the client, instead of quoting yesterday's.

## 4. How it works (the context budget of one session)

```
 ┌──────────────── what the model sees on turn N ─────────────────┐
 │ system prompt + tool defs (stable, cached)                     │
 │ pinned facts: case file {ids, amounts, statuses, decisions}    │ ← write / select
 │ recent turns, verbatim                                         │
 │ older turns: compacted summary                                 │ ← compress
 │ tool results: trimmed fields; old ones cleared                 │ ← compress
 └────────────────────────────────────────────────────────────────┘
        outside the window: files (scratchpad, decisions log), git,
        memory store, MCP resources, subagent contexts                ← write / isolate
```

Each turn: read current truth (fresh tool calls, files), act, write durable findings to the case file or scratchpad, and let compaction or context editing remove what is no longer needed.

## 5. Why it is done this way (decisions and trade-offs)

| Decision | Alternatives | Why this one | Cost / risk |
|---|---|---|---|
| Trim tool results to task fields | Keep raw; prose summary; vector store | Precise, cheap, keeps IDs exact | Must know which fields matter |
| Structured case file pinned in context | Narrative summary; sliding window | Survives compaction; exact values | Needs a schema and update discipline |
| Fresh session + summary + fresh calls for returning users | Resume with stale results | Removes anchors on outdated data | Some prior nuance lost |
| Resume + "these two functions were renamed" | Fresh subagent; resume silently | Keeps 30 minutes of valid analysis, fixes the stale part | Must know what changed |
| Fork for alternative approaches | Sequential in one thread; two fresh sessions | Both branches start from the same analysis without contaminating each other | Two contexts to pay for |
| Scratchpad file of findings | Bigger window; periodic wipe | Findings persist and can be re-read | The agent must keep it current |
| Subagent with a summary for a new topic | Continue in a saturated context; /clear | Clean context for the new topic, prior knowledge carried in | Summary quality limits the subagent |

## 6. Theory (the lecture)

### 6.1 Statelessness and context rot
The Messages API (and Bedrock's Converse API) is stateless: the client sends the full message list every turn, including previous tool calls and results. Session "memory" is whatever your code sends. **Context rot** is the decline in output quality as stale, redundant or irrelevant tokens accumulate: early drafts contradict later decisions, old tool results compete with new ones, and attention over long inputs is weaker in the middle ("lost in the middle"). The goal is the minimum sufficient context for the next step, not the maximum.

### 6.2 The four moves
- **Write (offload):** move anything that must survive into storage: a decisions log, a scratchpad of findings, a case file, git commits. "A decision not written to a file does not exist."
- **Select (retrieve):** at the start of each cycle read the current truth (task list, latest spec, fresh tool results), not what the model remembers.
- **Compress:** trim tool outputs, clear old ones, summarise old turns into structured summaries while keeping pinned facts verbatim.
- **Isolate:** give sub-tasks their own context (subagents) and return only a summary.

### 6.3 Tool-result hygiene
Tool outputs are usually the largest part of an agent's context. Rules: return only the fields the task needs (12.2); after a lookup, keep the relevant fields (items, purchase date, return window, status) and drop the rest; clear tool results once their content has been used. In the Claude API, **context editing** (`clear_tool_uses_20250919`) clears old tool results automatically; **compaction** (beta) summarises earlier context when a threshold is reached, and the compaction block must be appended back to the history each turn. For multi-issue sessions, keep a **structured case layer**: per issue, the order IDs, amounts, statuses and outcomes, injected each turn. A narrative summary loses the exact numbers; a sliding window loses issue 1 entirely.

### 6.4 Stale data and returning users
A tool result is a snapshot with a timestamp, not a fact. When a customer returns hours later, the old "Status: PENDING" is wrong but persuasive: models tend to repeat it even after a fresh call returns something else. The reliable pattern: start a new session, inject a structured summary of the previous interaction (issue type, actions taken, resolution status, IDs), and make fresh tool calls before replying. Instructions like "prefer the newest result" do not remove the anchor. Re-calling every previous tool automatically at start wastes calls on data nobody needs.

### 6.5 Resume, inform, fork, or start fresh
| Situation | Best move |
|---|---|
| Continue the last session in this directory | `claude --continue` (check current) |
| Continue a specific named or older session | `claude --resume <name or id>` (check current) |
| Prior analysis valid, small known change (two functions renamed) | Resume and tell the agent exactly what changed so it re-reads those files |
| Prior analysis valid, explore two alternatives independently | Fork from the analysis session (`--fork-session` with resume; check current), one branch per approach |
| Context degraded or largely stale, or a different topic | Fresh session or subagent with a structured summary of the findings |
| One topic finished, next is unrelated | `/clear`; or `/compact` with instructions to keep the key findings |

Exporting findings to a file and starting two sessions from it is a valid fallback when forking is not available; it costs the nuance that is not in the file.

### 6.6 Exploring a large codebase
- **Find the source of an error message:** search for its distinctive literal ("SYNC_CONFLICT", "entity version mismatch"), then read the hits. Not directory guessing, not reading the README first.
- **Understand a subsystem spanning 15 files:** find the base class or interface, read it, then trace the specific implementations you need (invalidation paths). Grepping keywords and reading fragments misses structure; reading all 8,000 lines fills the context.
- **Find all callers before deleting a function:** first discover every exported name (wrappers rename `calculateTax` to `computeOrderTax`), then search for each name. Searching the original name only misses aliases; reading every importer is slow.
- **Prioritise:** map with cheap tools (Glob, Grep), read narrowly with line ranges, write findings to a scratchpad as you go.

### 6.7 Subagents for isolation
Use a subagent when a sub-task would flood the main context with reading (exploring physics after 25 minutes of rendering), when tasks are independent, or when least-privilege tools matter. Give it a focused prompt and a summary of what is already known; get back a summary, not a transcript. Spawning a subagent with no summary and synthesising later by hand loses the cross-links. A fresh subagent receiving the full prior transcript defeats the point.

### 6.8 Orientation through MCP resources
When an agent spends 8-10 calls asking what each server contains, expose **catalogs as resources**: issue summaries, documentation hierarchy, database schemas. The client can attach them up front, so the agent starts oriented and makes targeted tool calls. Adding a "prepare_investigation" summariser tool to each server, or merging the servers, hides the structure instead of exposing it.

### 6.9 Memory across sessions
Three layers: **instructions** that always load (CLAUDE.md / AGENTS.md: project rules, commands, conventions; keep them short); **files** the agent reads on demand (decisions log, scratchpad, failure patterns, project status); and an API-level **memory tool** (`memory_20250818`) that lets the model read and write a memory directory you host. Memory is data: version it, review it, and delete what is wrong.

### 6.10 Caching interplay (2026)
Prompt caching is a prefix match: tools, then system, then messages. Append-only histories keep the cache warm; editing an early turn invalidates everything after it, and on the newest Claude models also invalidates thinking blocks ("preserved thinking"). So compaction and context editing should be done by the mechanisms built for it, not by rewriting history ad hoc.

## 8. Glossary

| Term | One-line definition |
|---|---|
| Stateless API | Each call carries the full conversation; the server keeps no session |
| Context rot | Quality loss as stale or irrelevant context accumulates |
| Lost in the middle | Weaker attention to content in the middle of long inputs |
| Offloading | Moving durable facts out of the window into files or stores |
| Compaction | Summarising earlier context to free space |
| Context editing | Clearing old tool results or thinking blocks from the request |
| Case file / pinned facts | Structured facts re-injected every turn and never summarised away |
| Scratchpad | File where the agent records findings during exploration |
| Resume / fork | Continue a saved session / branch a copy of it |
| Subagent | Separate agent with its own context that returns a summary |
| MCP resource | Read-only content (schema, catalog) a client can attach |
| Memory tool | API tool that lets the model read and write a persistent memory directory |

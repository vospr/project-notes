## 2. The problem (business view, plain English)

In January 2026 I built an ML pipeline to show the full MLOps lifecycle: ingest, features, tuning, registry, serving, monitoring, CI. It ran end to end. But the model on top predicted labels that were **random numbers**, so it could not learn anything, and the project documents still said it classified "geological formations" and would "exceed 85%" with more data. Anyone who opened one line of the sampling script saw the problem in two minutes.

Finance analogy: a back-testing report on a trading strategy where the "signal" was a random-number generator. The plumbing (data feed, risk checks, reporting) can be perfect and the report still worthless, and if the report says "expected Sharpe above 2 with more data" it is also misleading. A reviewer asks one thing first: what is the benchmark, and does the strategy beat it?

## 4. How it works (what v1 did, and where it broke)

```
v1 flow:
F3 SEG-Y (600,515 traces) -> stage0 sample 500 -> assign label = f(trace_id)   <-- RANDOM
   -> stage2 features (8 stats + 32 PCA, scaler/PCA fit on ALL rows)
   -> stage3b Optuna (4 families x 30 trials, 5-fold CV)  -> stage3 train -> stage4 eval
   -> stage5 MLflow register -> stage6 FastAPI (re-implements features) -> stage7 "drift"
```

**The label function**:

```python
def _generate_class_label(self, trace_id: int) -> int:
    np.random.seed(trace_id)
    rand = np.random.random
    if rand < 0.5:  return 0   # Normal
    elif rand < 0.8: return 1  # Anomaly
    else:            return 2  # Boundary
```
It is applied per row at, with `trace_id` set to a sequential counter at *:146*. The label is a deterministic function of the row number only. The features (amplitude statistics, PCA of the waveform) never see it, so the label is **statistically independent of the features**. Side effect: it reseeds NumPy's global generator on every call.

**What the numbers said** (all from):

| Metric | Value | Chance level for these labels |
|---|---|---|
| Accuracy (test, n = 100) | 0.49 | 0.52 (always predict "normal") |
| Macro-F1 | 0.337 | 1/3 for a prior-matched random guesser (my derivation, §6.3) |
| Weighted-F1 | 0.435 | about 0.39 = Σπ² for a prior-matched guesser |
| ROC-AUC macro | 0.490 | 0.5 |
| Best tuning score (LogisticRegression, CV weighted-F1) | 0.4218 | about 0.39 plus the winner's curse of 120 trials |

Four metrics, same message: chance. Note the trap: the **macro-F1 of the majority-class baseline is only 0.228** (0.684 for one class, 0 for two). A model that merely spreads its guesses over all classes "beats" that baseline with macro-F1 0.337 while having no skill. Only the accuracy comparison (0.49 < 0.52) exposes it. This is why the redo's gate requires beating the baseline on **both** accuracy and macro-F1 (*gate.py:29-31*, chapter 4.5).

**The drift check**: it takes the predictions file, splits it at the midpoint, calls the first half "reference" and the second half "current", and runs a KS test per feature (*:170-216*, α = 0.05, 40 features). The rows come from one random sample, so the two halves are exchangeable. The null hypothesis is true by construction. Result: 0 of 40 drifted, largest KS statistic 0.112. With 250 vs 250 rows the 5% critical value is 1.358·√(500/62500) ≈ 0.121, so everything sits just under it. The check cannot say anything about the world, because real drift is a difference between the **training data** and **later data**, and neither ever enters.

**The serving code** re-implemented feature extraction (:180-246). By my reading it had two further skew problems that the redo's one-Pipeline design removes (chapter 4.3): the PCA path default `data/silver/pca_model.pkl` (:94) does not match where stage 2 saved it, `data/silver/embedder/pca.pkl`, and a missing PCA silently returns 32 zeros (:229-231).

## 5. Why it was built this way (decisions and trade-offs)

| Decision | Alternatives | Why it was done | Cost / risk |
|---|---|---|---|
| Breadth first: every box of an MLOps diagram | A narrow, deep slice || Islands (Feast, RAG, agents) never wired; hollow core |
| Classical ML on 500 traces | PyTorch CNN on GPU as planned | Laptop capacity | Fine for the demo; not the problem |
| Keep placeholder labels | Real facies labels | Not a decision; it was inherited from the synthetic-data stage | Misleading docs, chance-level model |
| Hand-rolled KS drift on first vs second half | Evidence of drift against a training reference; Evidently as planned | Simplest thing that "ran" | Cannot fail; gives false comfort |
| Graceful fallbacks everywhere | Fail loudly | "Hard to crash" | Missing pieces fail silently (zero embeddings) |
| CI = `py_compile` of 5 files; pipeline job manual with `continue-on-error: true` on every stage | CI that runs the pipeline and fails | Make the badge green | CI cannot fail |

## 6. Theory behind it (the "lecture" part)

### 6.1 Irreducible error and the independence of labels
For a classifier with features X and label Y, the best achievable accuracy is the **Bayes accuracy** E[max_c P(Y=c | X)]. If Y is independent of X, then P(Y=c | X) = π_c for all X, and the best any model can do is predict the most frequent class: accuracy = max_c π_c. Everything above that on a large test set would be a bug (leakage); everything at or below it is expected.

A cheap **sanity test** for any new pipeline: train on shuffled labels. If the score is not at chance, you have leakage. If the score on the real labels equals the score on shuffled labels, you have no signal. (Also called a permutation or negative-control test.)

*In my project:* the v1 labels were independent of X by construction, so the ceiling was 0.51–0.52 accuracy, and tuning 120 configurations could not change that.

### 6.2 Label noise versus leakage (they look opposite)
| | Label noise | Leakage |
|---|---|---|
| What it is | The label carries little or no information about X | Information about the label reaches the model through a path that is not available at prediction time |
| Typical symptom | Scores near chance, unstable between runs | Scores **too good**, collapse in production |
| Examples | Random or inconsistent labels, weak annotators | Target in a feature; scaler/PCA fitted before the split; the same patient/location in train and test; selecting the model on the test set |
| Fix | Fix the labels | Fix the pipeline (split first, fit inside the fold) |

*In my project:* v1 had **noise** (random labels) plus a small **preprocessing leak** (fit on all rows) that was harmless only because of the noise. "Random labels broke everything" is a noise story. Saying "label leakage" would be wrong.

### 6.3 Chance levels for common metrics
With K classes, class shares π_c, and a guesser that predicts class c with probability q_c independently of X:
- Accuracy of the majority class: max π_c. Prior-matched random guess (q = π): Σ π_c².
- Per-class F1 of the prior-matched guesser = π_c, so **macro-F1 = 1/K** and **weighted-F1 = Σ π_c²**.
- Majority-class predictor: F1 for that class = 2p/(1+p) with p = π_max; zero for the others; macro-F1 = 2p/(1+p)/K. For p = 0.52, K = 3: 0.228.
- ROC-AUC of any score independent of the label: 0.5.

A baseline is only useful if you know what it scores. Always report model and baseline on the same metrics, and say which metric the decision uses.

*In my project:* the v1 numbers 0.49 / 0.337 / 0.435 / 0.490 are all within noise of 0.52 / 0.333 / 0.39 / 0.5.

### 6.4 Uncertainty of a score, and the winner's curse
An accuracy on n independent test cases has standard error √(p(1−p)/n): about 0.05 for n = 100, 0.007 for n = 5,000. Differences smaller than about two standard errors are not evidence.

Picking the best of k noisy scores is biased upward. For k independent estimates with noise σ and no true differences, the expected maximum is about σ·√(2 ln k) above the mean (a standard approximation). Hyperparameter search reports the maximum.

*In my project:* the best of 120 Optuna trials had CV weighted-F1 0.4218 against about 0.39 chance. That gap is the size of noise plus selection, not skill.

### 6.5 Two-sample tests and why a drift check needs a reference
The Kolmogorov–Smirnov two-sample statistic is D = sup_x |F₁(x) − F₂(x)|. At level α the critical value is c(α)·√((n+m)/(nm)), with c(0.05) ≈ 1.358. Running it on 40 features at α = 0.05 gives about 2 false alarms per run if features were independent and the null true; features are correlated, so the count is lumpy.

**Drift** means the data the model sees now differs from the data it was trained on: *covariate shift* (P(X) changes), *prior shift* (P(Y) changes), or *concept drift* (P(Y|X) changes). A drift test needs a **reference** that is the training distribution (or an earlier healthy window) and a **current** window from live data. Two halves of the same random sample are the same distribution by definition, so the test has zero power.

*In my project:* the v1 check compared two halves of one file; see chapter 4.6 for what a real one needs.

### 6.6 Post-mortems that help
A good post-mortem separates *what happened*, *why the checks missed it*, and *what check would have caught it*. The last item is the useful one. Here: a baseline row in the results table, a shuffled-label run, a reviewer who opens the label code, a CI that can fail. The redo's acceptance tests are exactly these checks (chapters 4.3–4.6).

*In my project:* the redo turned each v1 failure into a test or a gate.

## 8. Glossary

| Term | One-line definition |
|---|---|
| Label noise | Labels that carry little or no information about the features |
| Target / label leakage | Information about the label reaching the model through a path unavailable at prediction time |
| Preprocessing leakage | Fitting scaler, PCA or imputer on data that includes the test rows |
| Bayes accuracy | The best accuracy any model can reach given the true P(Y given X) |
| Majority-class baseline | Always predict the most frequent training class |
| Chance level | The score a guesser with no information achieves, for a given metric |
| Prior-matched random guesser | Predicts each class with its training frequency, ignoring X |
| Winner's curse | The best of many noisy scores overstates the true quality |
| KS test | Two-sample test on the largest gap between two empirical CDFs |
| Tautological test | A test whose result is fixed by how it is set up, not by the thing under test |
| Negative control | A run that must fail (for example shuffled labels) to prove the pipeline is not leaking |
| Medallion layout | Bronze (raw), silver (cleaned/features), gold (results) tables |

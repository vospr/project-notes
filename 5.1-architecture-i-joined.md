# Course 5 · Chapter 5.1: The architecture I joined: Functions v4 on Container Apps, same origin, provider seam, LLM tiering

_Andrey Popov's project notes: how it works, why it was built this way, and the theory behind it._

## 2. The problem (business view, plain English)

A leadership-coaching company wanted to rebuild its AI coaching assistant from scratch, next to a legacy low-code platform that keeps running. The rebuild had to be safe for many client organisations at once and cheap to change, while a small team shipped several changes a day with AI coding agents. The architecture answers three practical questions. Where does the code run, cheaply and the same everywhere (laptop to production)? How does the browser talk to the API without a security headache? How do we use Claude without being locked to one billing route or one model?

Finance analogy: a company that pays suppliers through one treasury gateway. The gateway has a switch between two banks (direct bank, or the group's cash-pool bank). Treasury can flip the switch in one line if one bank has an outage, and the switch refuses to run if the second bank's credentials are not loaded, rather than quietly paying from the wrong account.

## 4. How it works (technical walkthrough)

```
 Browser (SPA)                        Slack
     │  one hostname                    │ Events API (HMAC)
     ▼                                  ▼
┌─────────────── Container Apps environment ─────────────────┐
│  app "<env>"  (one revision, one ingress → port 80)        │
│   ┌──────────────┐  localhost:8080  ┌──────────────────┐   │
│   │ frontend     │ ───────────────► │ api container    │   │
│   │ nginx + SPA  │   /api/*         │ Functions v4 host│   │
│   └──────────────┘                  │ (Node/TS)        │   │
│                                     └───────┬──────────┘   │
│  app "<env>-slackbot" (own ingress :3000)   │              │
│  job  "<env>-migrate" (staging/prod only)   │              │
└─────────────────────────────────────────────┼──────────────┘
                     Postgres ◄────────────────┤  the model-client factory
                                              ▼  the provider switch = direct | azure
                                     Claude API / Azure AI Foundry
```

**Hosting.** The API is written in the Azure Functions v4 programming model (`app.http(...)`, `app.timer(...)`; 128 HTTP registrations plus 6 timers, loaded by `api/src/index.js`) but runs as a container on Azure Container Apps. The image uses the Functions runtime base image. Frontend and API are sibling containers in **one** Container App. Ingress points at the frontend (nginx, port 80) and nginx proxies `/api/*` to `localhost:8080`. Sibling containers share one network namespace, hence `localhost`.

**Same origin.** The SPA and the API share one hostname, so there is no CORS and no cross-site cookie problem. The refresh token is an HttpOnly cookie that the SPA never touches. nginx also forwards the `Authorization` header unchanged, which removed the need for the old API gateway. Root-level OAuth paths (`/register`, `/authorize`, `/token`, `/.well-known/*`) are rewritten to `/api/...` because some MCP clients assume issuer-relative paths.

**Adapters are separate apps.** Slack runs as its own Container App, same environment, same image registry and pipeline. Reasons given: failure isolation, independent scaling, and Slack's 3-second acknowledgement budget.

**Provisioning and pipeline.** One parameterised Bicep template for QA, UAT and per-PR previews (`<app>-pr-<N>`); images built in GitHub Actions, pushed to a private registry; secrets are Container Apps secrets, injected by `secretRef`. Staging and prod sit on a private network: images are built on a registry agent pool and migrations run as a Container Apps job.

**Provider seam.** All Claude calls go through the model-client factory. It is lazy (built on first use, the cold-start pattern) and cached. the provider switch unset means `direct`; `azure` is never the default; any other value throws. the provider-config check throws if the Foundry key or base URL is missing and **never** falls back to the other provider, because a silent fallback would bill the wrong account. On `azure`, the client rewrites the canonical model id to the Foundry deployment name inside `messages.create`, on a copy of the params. That mapping sits downstream of the record/replay layer, so recorded test cassettes stay keyed on canonical ids.

**Tiering.** Model ids live only in a single model-configuration module. Chat uses the Sonnet tier (default Sonnet 5, per-environment override a per-environment model override variable, validated against an allowlist); generation uses Haiku. Sonnet 5 runs adaptive thinking when the parameter is omitted, so the code sends `thinking: disabled` as a standing cost and latency decision. Two documented exceptions use Sonnet for generation: the composed assessment report (#1632) and the weekly nudge (#2248). The nudge was measured on one frozen prompt, n=90 per arm: Haiku 66.7% good, Sonnet with thinking 79.5%, Sonnet without thinking 85.1%. The cost was accepted as about 3x the per-token rate, once a week, to a named person.

## 5. Why it was built this way (decisions and trade-offs)

| Decision | Alternatives | Why this one | Cost / risk |
|---|---|---|---|
| Keep Functions v4 code, run in a container | Rewrite 28 endpoints as plain Node/Express | Zero code change at cutover; timers and streaming are first-class when you own the host. Stated as "ergonomics, not capability" ||
| One app, two sibling containers, same origin | Two apps (frontend, API) with CORS | Mirrors local Docker Compose; no CORS or cookie surface | Both scale together (accepted for QA/UAT/PR) |
| Slack as its own app | Sidecar in the API app | Failure isolation, own scaling, 3 s ack budget | One more app per adapter |
| Provider seam with no fallback | Auto-fallback to direct on error | A silent fallback mis-bills during a billing migration | Needs a human to flip the switch in an incident |
| Model allowlist, ids in one file | Free-text model per endpoint | One place to audit and to flip a default | Exceptions need a named constant (visible deviation) |
| Thinking disabled on Sonnet 5 | Leave the default (adaptive) | A leading `thinking` block in about 1 of 3 calls broke consumers reading `content[0]` and added cost | Less reasoning on chat; flip only as a budgeted eval axis |
| Bicep for every environment | Ad-hoc `az` commands | Environments stay reproducible; learned the hard way that imperative custom-domain binding was wiped by the next deploy | Template has to stay generic |
| Deny-by-default module boundaries | Convention only | A convention-only barrel measurably failed (0 uses vs 89 deep imports) | Tooling to maintain |

## 6. Theory behind it (the "lecture" part)

### 6.1 Programming model versus hosting model
A *programming model* is the shape of your code (functions with triggers). A *hosting model* is where and how it runs (a managed serverless plan, or a container you operate). They can be chosen independently. Serverless plans trade control for convenience: scale-to-zero and per-execution billing, but cold starts, timeouts and platform quirks. Containers trade the other way: you own the process and its lifetime, so long-lived listeners, timers and streaming work, at the price of operating the platform. Cold start is the delay to start a new instance; scale-to-zero makes it visible to users.
*In my project:* Functions v4 is only the programming model; Container Apps is the host, so the same image runs on a laptop, in a PR preview and in production.

### 6.2 Same-origin policy, CORS and cookies
An origin is scheme + host + port. A browser blocks a page from reading responses of another origin unless the server opts in via CORS headers. Cross-origin requests that carry credentials need explicit allow-lists and `SameSite` care. Serving the SPA and the API behind one hostname through a reverse proxy removes the whole class: same origin, one cookie jar. The cost is that the proxy becomes a routing seam that you must configure and test.
*In my project:* nginx routes `/api/*` to the sibling container, so the SPA needs no API base URL and the refresh cookie stays HttpOnly.

### 6.3 Adapter / strategy seam and fail-fast configuration
A *seam* is a place where behaviour can be changed without editing the callers. The *adapter* pattern puts one interface in front of different providers; *strategy* selects which one at run time. Good seams share three properties: one chokepoint (so cross-cutting rules like a kill switch or a cost log live once), explicit selection (no hidden default for the risky option), and **fail-fast** validation (a missing setting throws at first use, with the name of the variable). The opposite, a silent fallback, hides a billing or data-residency change.
*In my project:* the model-client factory is the chokepoint for every Claude call, and a chat call on a mis-configured `azure` provider throws instead of quietly using the direct key.

### 6.4 Model tiering and the cost of a call
Cost of one LLM call = input tokens × input price + output tokens × output price (+ cached-input tokens at a discounted price). A *tiering* (or cascade) policy sends each task to the cheapest model that meets its quality bar. If a fraction s of calls goes to the expensive tier, the blended cost per call is C = s·C_big + (1 − s)·C_small. With a roughly 3x price ratio, even a small s dominates spend, which is why exceptions are named, measured and documented. Quality needs a metric on a fixed test set: comparing 66.7% (n=90) with 85.1% (n=90) gives a standard error of about 6 points on the difference, so an 18-point gap is clear, a 6-point gap would not be.
*In my project:* chat on Sonnet, generation on Haiku, and exactly two Sonnet generation surfaces, each with a written reason.

### 6.5 Architecture decision records and status
An ADR records a decision, its context, alternatives and consequences, and a status. This repo uses `locked`, `locked-deferral` (decide later, with a stated trigger) and `open`, and a rule that a sub-ticket that contradicts the doc must update the doc. The value is that a reader six months later can see not only what was chosen but what would make you change it (for example: "abstraction overhead becomes friction worth 28 endpoint rewrites").
*In my project:* the ACA doc is the reference I used to explain why things are as they are, and my environment-mapping ADR for the coaching integration follows the same habit (5.4).

### 6.6 Bulkhead and independent scaling
A *bulkhead* isolates components so that one failing or overloaded part does not take down others (ship compartments). In services it means separate processes, pools or replicas. Related: scaling is per deployable unit, so what must scale together should live together.
*In my project:* Slack events (bursty, 3 s deadline) are in a separate Container App from API requests.

## 8. Glossary

| Term | One-line definition |
|---|---|
| Functions v4 | Node programming model for Azure Functions: handlers registered in code with `app.http` / `app.timer` |
| Container Apps (ACA) | Azure's managed container platform with ingress, revisions, scale rules |
| Revision | An immutable snapshot of a Container App's template; changing env vars creates a new one |
| Sibling containers | Containers in one app that share a network namespace (`localhost`) |
| Same origin | SPA and API served from one scheme + host + port |
| Provider seam | The single function that decides which route to Claude is used (the provider switch) |
| Foundry | Azure AI Foundry: Azure-hosted route to Claude with Azure billing |
| Break-glass | A switch used only in an emergency, with a documented procedure |
| Tiering | Sending each task to the cheapest model that meets its quality bar |
| Adaptive thinking | A mode where the model decides whether to emit a reasoning block; disabled here for Sonnet 5 |
| Cassette | A recorded LLM round-trip replayed offline in tests and seed data |
| ADR | Architecture decision record |
| Bicep | Azure's declarative infrastructure-as-code language |

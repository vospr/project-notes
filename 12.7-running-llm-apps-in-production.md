## 2. The problem (business view, plain English)

A demo calls a model once; a product calls it thousands of times an hour, during spikes, across regions, with a budget. The production questions in the exams are all variants of: it is slow at peak, it is throttled, it costs 40% more than planned, a new model version made answers worse, nobody noticed until customers complained. The answers are ordinary reliability engineering plus a few LLM-specific levers (prompt caching, batch pricing, model routing, token accounting).

Finance analogy: running a trading desk's market-data feed. You size capacity for peaks, keep a fallback venue, throttle gracefully, measure cost per trade not per message, roll out new pricing models to a slice of flow first, and alert on deviations from a moving baseline rather than a fixed number.

## 4. How it works (the request path with its controls)

```

            │
            ▼

            │
            ├─► response cache (exact match) ── hit ─► reply

            │

            │          └─ capacity: on-demand | provisioned (call its ID) | geo inference profile | batch

            │
            ▼

```

## 5. Why it is done this way (decisions and trade-offs)

| Decision | Alternatives | Why this one | Cost / risk |
|---|---|---|---|
| Stream end to end | Wait for the full answer | Users see progress; partial results usable | Error handling mid-stream; harder retries |
| On-demand + geo inference profile for spiky traffic | Provisioned for peak | No idle cost; spreads load within a compliant geography | Throttling still possible at extreme peaks |
| Provisioned capacity for steady high volume | On-demand | Predictable throughput and latency | Fixed cost; must be addressed explicitly |
| Prompt caching for shared prefixes | No caching | Cache reads cost about a tenth of input (a twentieth on Opus 5.5); lower latency | 1.25x write cost; prefix must be byte-stable |
| Batch for non-urgent volume | Real-time for everything | 50% cheaper | Up to 24 h; not for users waiting |
| Model routing by complexity | One big model | Simple traffic on cheap models | Router errors; caches are per model |
| Model and prompt as validated config with flags | Hard-coded in code | Switch without redeploy; staged rollout; rollback | Config is now production code: review it |
| Canary with automatic rollback | Big-bang release | Limits blast radius | Needs metrics that move fast enough |
| Adaptive anomaly alerts | Fixed thresholds | Follows traffic changes | Needs history; can learn bad baselines |

## 6. Theory (the lecture)

### 6.1 Latency
End-to-end latency = queueing + time to first token (TTFT, grows with input length) + output tokens ÷ decode speed + tool and network time. Output tokens dominate long answers, so shorter outputs are the strongest latency lever. **Streaming** does not reduce total time; it improves perceived latency and lets downstream work start early. For live assistance (call-centre suggestions) stream at every hop: streaming transcription with partial results, streaming model responses, and a bidirectional channel (WebSocket) to the screen. Batch transcription or publish/subscribe fan-out breaks the "while the customer is still speaking" requirement. Report p50 and p95 (or p99), never the mean.

Independent calls should run **in parallel** (five report analyses in parallel states rather than one after another). Between workflow steps, pass **references** (an object-store URI) rather than large payloads; this "claim check" pattern avoids payload limits such as 256 KB between workflow states and keeps the audit copy in one place.

### 6.2 Capacity and quotas
Providers limit requests and tokens per minute; exceeding them returns throttling errors (HTTP 429). Options:
- **On-demand**: pay per token, shared capacity, throttling at peaks.
- **Provisioned / reserved throughput**: fixed hourly cost for guaranteed capacity; only used if requests target the provisioned identifier.
- **Cross-region inference within a geography** (AWS inference profiles with a geographic prefix such as `eu.`): the platform spreads requests over regions in that geography, raising throughput without leaving the data-residency boundary.
- **Batch**: half price, asynchronous, for offline volume.
- **Load shedding and queues**: reject or defer low-priority work early rather than time out everything.

Monitor throttles explicitly (invocations, input and output tokens, throttle count), not only errors and latency.

### 6.3 Retries done right
Classify first: **retry** timeouts, 429, 5xx and connection errors; **do not retry** 400-class validation or permission errors. Use **exponential backoff with jitter** (randomised delays) so clients do not retry in lockstep; respect `retry-after`; cap attempts and total time (a **retry budget**, e.g. retries ≤ 10% of traffic). Add a **circuit breaker** that stops calling a failing dependency for a cool-down and fails fast or falls back. Make side-effecting calls **idempotent** (idempotency keys) so a retry does not double-book. SDKs already retry (the Anthropic SDKs retry 408/409/429/5xx and connection errors twice by default, and wall-clock time can reach timeout × attempts); know the defaults before adding your own layer. Trace with annotations so you can filter by component.

**Broken streams**: detect stalls (no chunk for N seconds), keep what was received, and retry the request; show the user that the answer restarted. Token-aware handling means counting or estimating tokens before sending, trimming inputs to fit, and setting `max_tokens` high enough that answers are not cut (check `stop_reason`).

### 6.4 Cost levers (in the order to try them)
1. **Prompt caching** for repeated prefixes (system prompt, tool definitions, shared documents). Claude: cache reads cost about 0.1x the base input price (0.05x on Opus 5.5); writes cost 1.25x with the 5-minute TTL or 2x with the 1-hour TTL. Break-even: 5-minute TTL pays off from the second request (1.25 + 0.1 = 1.35 vs 2.0 uncached); 1-hour TTL from the third (2 + 0.2 = 2.2 vs 3.0). Caches are prefix matches and per model; any byte change in the prefix (a timestamp in the system prompt) silently disables them.
2. **Output hygiene**: shorter outputs, structured outputs, no preamble; output tokens cost 4-5x input tokens.
3. **Batch** for anything that can wait (50% off).
4. **Effort / reasoning depth** per route: low for classification and chat, higher for hard agentic work. On current Claude models, try the strongest model at lower effort before building a multi-model cascade.
5. **Model routing**: small model for simple traffic (70% simple product questions), large model for complex reasoning (30% return-policy cases). Least effort is a managed prompt router; otherwise rules plus a classifier, measured on a labelled set (7.2, 7.3).
6. **Context hygiene** (12.4): fewer, smaller tool results and trimmed histories.

Judge by **cost per completed task**, not per call. For governance, estimate tokens before sending (with the model's tokenizer or token-count endpoint), alert when requests approach model limits, and attribute cost by tenant or business unit through tags or request metadata.

### 6.5 Consistency
For "identical inputs must give identical outputs", the reliable tool is an **exact-match response cache** keyed on the normalised input and the model and prompt version, with a TTL. It also cuts latency at peak. Pinned versions and structured outputs reduce variance; temperature is not a guarantee and is not available on the newest Claude models (12.1). Semantic caching (similar, not identical, inputs) risks wrong answers and needs a strict threshold and an eval.

### 6.6 Configuration, rollout and rollback
Model ID, prompt version, temperature/effort, token limits and routing rules are **configuration**: store them in a config service with schema validation, feature flags (per tier: premium vs standard customers), staged deployment and rollback, and read them at runtime so a switch needs no redeploy. Treat prompts like code: a versioned repository, a test suite of hard cases with quantitative metrics, automated comparison of versions, and a record of results (10.1). For model upgrades use a **canary**: shift traffic in steps, watch latency, error and quality metrics, and roll back automatically below thresholds. For multilingual assistants, the regression suite includes the same question in every language with blocking thresholds in CI. For custom models, log with lineage and register in a model registry before serving (MLflow, with aliases for champion and challenger, 4.5).

### 6.7 Observability
| Signal | Examples |
|---|---|
| Logs | Prompt and response (or hashes and samples, under privacy rules), model and prompt version, tool calls, retrieved IDs, `stop_reason` |
| Metrics | Requests, TTFT, p50/p95 latency, input/output/cached tokens, cache hit rate, throttles, errors by class, cost per tenant, escalation rate, grounding failures, thumbs-down rate |
| Traces | One trace across gateway, app, retriever, model and tools (OpenTelemetry GenAI conventions) |
| Alerts | Adaptive anomaly detection on tokens and cost per tool or tenant; quality drift; SLO burn |

Managed platforms log every request and response to a table (Databricks inference tables, Bedrock invocation logging), which also becomes the source for evals. Correlate model behaviour with operational metrics in one place, with dimensions such as request type and user segment, so "recommendations got worse" can be tied to a release, a tenant or a latency spike. A token surge with flat traffic usually means a tool returning more data or a loop: alert per tool integration.

## 8. Glossary

| Term | One-line definition |
|---|---|
| TTFT | Time to first token |
| p95 latency | Latency that 95% of requests beat |
| Throttling (429) | Rejection when rate or token limits are exceeded |
| Provisioned throughput | Reserved model capacity at a fixed hourly price |
| Cross-region / geo inference | Platform spreads requests across regions within a geography |
| Exponential backoff with jitter | Growing, randomised waits between retries |
| Retry budget | Cap on retries as a share of traffic |
| Circuit breaker | Stops calls to a failing dependency for a cool-down |
| Idempotency key | Ensures a retried action executes once |
| Prompt caching | Reusing a processed prompt prefix at reduced price |
| Response cache | Returning a stored answer for an identical request |
| Model router | Chooses a model per request by difficulty or type |
| Feature flag | Runtime switch for behaviour without redeploying |
| Canary release | Gradual traffic shift with automatic rollback |
| Claim-check pattern | Passing a storage reference instead of a large payload |
| Inference table / invocation logging | Managed log of requests and responses |

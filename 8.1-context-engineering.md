# Course 8 · Chapter 8.1: Context engineering: window economics, memory files, role separation

_Andrey Popov's project notes: how it works, why it was built this way, and the theory behind it._

**In short:** How the template works: a stateless dispatcher in CLAUDE.md, state in files, the write/select/compress/isolate moves and sized pipelines (Micro to Large). The full pipeline used 613,670 tokens on a small task versus an estimated under 100k for one prompt.

## 2. The problem (business view, plain English)

An AI coding agent given an empty folder forgets decisions between sessions, skips review and drifts on long tasks. The template is a drop-in setup that tries to fix this with files and roles: decisions are written down, work is split between specialists, and review loops have stop conditions.

Finance analogy: a small fund with no process. Every analyst keeps positions in their head, the same person books and approves a trade, and nothing survives a holiday. The template is the middle-office: a trade blotter (memory files), maker and checker (implementer and reviewer), limits and escalation (circuit breakers).

## 4. How it works (technical walkthrough)

```
User goal
   │
   ▼
CLAUDE.md = Main agent (stateless dispatcher, 239 lines, cap 300)
   │ 1 read state  ─► planning-artifacts/pipeline-state.md (1h cache), TaskList, git log
   │ 2 pick task, 3 match agent (score ≥4/6), 4 size: Micro/Small/Medium/Large
   │ 5 dispatch  ─► subagent (own context window) + injected warnings (≥3 occurrences, ≤500 tokens)
   │ 6 process   ◄─ result file + "Machine-Readable Summary" YAML  ─► update state file
   ▼
planning-artifacts/ + implementation-artifacts/  (the memory; git = fault tolerance)
```

- **Stateless means state lives in files.** Principle 1 and 3: hold no project state, write every decision to a file "before proceeding". Step 1 reads `pipeline-state.md` and treats it as a cache: valid under one hour, otherwise rebuild from TaskList + git log (; the file itself calls it "a fast recovery cache (ADR-004), NOT the sole source of truth", *PA pipeline-state.md* line 3).
- **The dispatcher never implements**. It routes: match the task to an agent by scoring two candidates on task type, tool access and output format (0–2 each, dispatch at 4/6 or more).
- **Size sets depth and model.** Micro: haiku, implementer only. Small: sonnet, implementer then reviewer. Medium: planner, implementer, reviewer plus blind reviewer in parallel, tester. Large: opus architect, then the full pipeline. A step-sizing gate sub-slices big steps.
- **Context-saving moves in the loop:**
  - *Isolate:* research pre-flight with up to 10 haiku scouts who return summaries, not raw files; "up to 30 haiku agents" for multi-file reading.
  - *Select:* inject at most 5 patterns, 500 tokens; give each role a spec view with irrelevant fields stripped.
  - *Compress:* observation masking of stale tool output and compaction at 80k into `session-context.md`.
  - *Write:* decisions to `decisions.md` immediately.
- **Structured output is the contract between agents.** Every agent ends with a `Machine-Readable Summary` YAML block; the dispatcher parses it and "never scan[s] free text for machine signals"; a missing block is a PARSE_ERROR.
- **Role separation** is by tool lists and instruction text (details in 8.2). **Hooks** are the only parts a machine enforces (8.3). README states it: apart from the hooks, "nothing enforces them mechanically".
- **Comparison data.** A: full template, 13 subagent dispatches, 613,670 tokens logged, 246 lint errors fixed afterwards. B: bare, tokens not recorded. C: one prompt with the template assets, cleanest, "est. <100k". D: a different, smaller task.

## 5. Why it was built this way (decisions and trade-offs)

| Decision | Alternatives | Why this one | Cost / risk |
|---|---|---|---|
| Stateless dispatcher, state in files | Long chat session holding state | Survives resets and compaction; git gives recovery | Many file reads and writes; stale cache risk (1h TTL rule) |
| Dispatcher never implements | Main agent codes directly | Keeps the main context small; clear separation | Every change pays a dispatch round-trip |
| Seven narrow roles | One general agent | Smaller prompts per role, different tool rights, independent review | 614k tokens on a todo API; rules between roles to maintain |
| Sizing Micro to Large | Same pipeline for all tasks | Cost control by task size | Classification is itself a model judgement; the plan-file hook ignores tiers |
| Haiku scouts return summaries | Main agent reads files | Keeps main context lean | Total tokens are not lower, only moved; saving "15-20k" is unmeasured |
| Compaction at 80k plus masking | Rely on platform compaction | Needed in early 2026 for smaller windows | Hand-written, unmeasured; obsolete today |
| Inject top failure patterns (≥3) | Always inject all, or none | Bounded cost (≤500 tokens) and relevance | Shipped seeds never reach 3 |
| Claude Code as sole runtime | Portable across tools | Richest agent, hook and skill primitives in Feb 2026 | Deliberate lock-in |

## 6. Theory behind it (the "lecture" part)

### 6.1 The context window as a budget
A model reads a fixed-size window of tokens. Three costs depend on how full it is:
1. **Money.** An agent loop re-sends the whole context every turn. If the context starts at c₀ tokens and grows by Δ per turn, input tokens over T turns are Σ(c₀ + tΔ) = T·c₀ + Δ·T(T+1)/2. The total is **quadratic in T**. Illustration (not from the project): c₀ = 10k, Δ = 2k, T = 20 gives 200k + 420k = 620k input tokens. Prompt caching makes the repeated prefix cheaper per token but not free, and it does not shorten the window.
2. **Compute.** Self-attention work grows roughly with n² for context length n (standard result for the transformer), and key-value cache memory grows with n.
3. **Quality.** Models use information at the start and end of a long context better than the middle (Liu et al., "Lost in the Middle", 2023). Irrelevant text also distracts. The practitioner's name for the decay is "context rot".

So the aim is the smallest context that holds what the next step needs. Finance analogy: working capital. Holding cash costs something, and so does holding too little.

*In my project:* the 80k/128k limits, masking and compaction are attempts at this budget, but they are instructions with no measurement.

### 6.2 Four moves: write, select, compress, isolate
A common taxonomy for agent context (popularised in LangChain's "Context Engineering for Agents" writing; the *Review §3* says the March article cites LangChain):
- **Write:** put information outside the window (scratchpads, files, memory).
- **Select:** pull in only what is relevant now (retrieval, rules matched to the task).
- **Compress:** shrink what stays (summaries, trimming old tool output).
- **Isolate:** give sub-tasks their own window and return only a summary.

Isolation trades one cost for another. The main window stays small but the sub-agents each pay for their own, so **total tokens across all windows usually go up**; what you buy is a cleaner main context and parallelism.

*In my project:* write = `planning-artifacts/`; select = pattern injection and spec views; compress = masking and compaction; isolate = subagents and haiku scouts. Scenario A shows the total-token side: 13 dispatches, 613,670 tokens.

### 6.3 External memory and stateless controllers
If the controller keeps no state, it can crash, restart or be compacted and resume from storage. This is the same idea as an event log or a write-ahead log: durable state first, in-memory view second. Two rules follow: write before acting ("decision persistence rule") and treat any cache as rebuildable with a TTL. Weak points: stale caches, two writers to one file, and **memory that is never read back**. A file nobody injects is a diary.

Compaction is lossy by design. What must not be lost has to live in a file that is not summarised. That is why `spec_packet` and `failure_patterns` are "never compress" entries.

*In my project:* state sits in markdown files plus git; the 1-hour `pipeline-state` cache is rebuildable from TaskList and git log.

### 6.4 Role separation, least privilege, maker–checker
Two classical controls:
- **Least privilege** (Saltzer and Schroeder, 1975): each component gets only the rights its job needs. Details in 8.2.
- **Separation of duties / maker–checker:** the person who produces does not approve. In finance: the trader books, the middle office confirms.

A review adds value only if the reviewer's errors are not the same as the author's. If two checks each catch a defect with probability p and are **independent**, the chance both miss is (1−p)². With p = 0.6 that is 0.16. If they are fully correlated (same context, same blind spots) the miss chance stays 1−p = 0.4. Giving the second reviewer less context (diff only) is a way to lower the correlation. The price is that it also loses information.

*In my project:* the blind reviewer is the "low-correlation" check; whether it is really blind is a configuration question (8.

### 6.5 Evaluating a scaffold honestly
To claim "structure X improves outcome Y" you need a comparison with controlled inputs: same task, same model, several runs per arm (because LLM output varies), a measured outcome for every arm, and a grader who is not the author. With n = 1 per arm, you cannot separate effect from noise. Also report ratios only between **measured** numbers. A ratio of a measured number to an estimate is a bound at best: here 613,670 ÷ 100,000 is at least 6.1× if C's "<100k" holds (*BENCH* Limits 4).

*In my project:* one run per scenario, self-assessed, tokens logged for A only. Honest claim: "the full pipeline bought scope and traceability, not better first-pass code, and cost an order of magnitude more tokens than estimated for the single prompt."

## 8. Glossary

| Term | One-line definition |
|---|---|
| Context engineering | Deciding what goes into the model's window, when, and in what form |
| Context window | The maximum tokens the model can read in one call |
| Dispatcher | The main agent that only routes work to subagents |
| Subagent | A role agent with its own window, tools and model, defined in `.claude/agents/` |
| Skill | A packaged instruction file, `.claude/skills/<name>/SKILL.md`, loaded on demand or preloaded |
| Pipeline sizing | Choosing agents and model by task size (Micro to Large) |
| Memory file | A markdown or JSON file that carries state across sessions |
| Compaction | Replacing old turns by a summary to free window space |
| Observation masking | Replacing stale tool output by a one-line placeholder |
| Failure pattern | A recorded recurring mistake; injected as a warning at 3 or more occurrences |
| Circuit breaker | A hard stop (3 review cycles, cascade, dispatch loop, plan explosion) |
| SDD | Spec-driven development: specs and assertions written before code |
| ADR | Architecture Decision Record |
| Prompt caching | Provider feature that bills repeated prompt prefixes at a lower rate |

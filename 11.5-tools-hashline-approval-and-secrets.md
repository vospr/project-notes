# Course 11 · Chapter 11.5: Tools, hashline edits, the approval gate and secrets

_Andrey Popov's project notes: how it works, why it was built this way, and the theory behind it._

**In short:** Tools and safety in the harness: approval tiers, modes and resolution order, critical bash patterns, hashline compare-and-swap edits, parameter validation, background shell jobs, the eleven-layer redaction pipeline with request_secret, and TTSR mid-stream rules.

## 2. The problem (business view, plain English)

Tools turn a chatty model into something that can change your machine. Three risks follow. (1) **Wrong action**: the model deletes the wrong directory, force-pushes, pipes a download into a shell. (2) **Wrong edit**: the model edits a file from its memory of an old version and overwrites newer changes. (3) **Leak**: an API key shows up in a command output, enters the model context, then the transcript, then the session file on disk, and from there to a provider's logs.

A good harness answers with layers that do not depend on the model behaving: a gate before execution, an edit format that fails loudly on drift, and a filter on everything that flows back.

Finance analogy: the approval gate is the order-limit system with a four-eyes rule for large tickets; hashline edits are a trade amendment that carries the version number of the trade it amends (rejected if someone changed it meanwhile); redaction is the data-loss-prevention filter on outgoing mail.

## 4. How it works (technical walkthrough)

### 4.1 The tool surface (*README*, `lib/src/tools/`)
| Family | Tools | Notes |
|---|---|---|
| Files | `read`, `write`, `edit`, `ls` | `read` takes trailing selectors, reads archives and SQLite; `edit` can use hashline |
| Shell | `bash`, `bash_job` | foreground with timeout, background jobs, status/output/stop |
| Delegation | `task`, task-monitoring tools | chapter 11.6 |
| Code intelligence | `lsp` | diagnostics, definition, references, rename |
| Integration | MCP tools, A2A, `web_search`, `web_fetch` | chapter 11.6 |
| State | `checkpoint`, `rewind`, `memory_*`, `ask`, `request_secret`, `compact_expand` | session and memory |
| Media | `inspect_image`, `generate_image`, `generate_video`, `transcribe_audio` | some are plugins |
Each tool has a JSON schema, an approval tier, and a prompt file in `prompts/tools/`. Tools that do not declare a tier default to **exec**, "the safe choice" (*AP* lines 14-18).

### 4.2 The read tool's selector grammar
`path:50-100`, `path:50+20` (20 lines from 50), `path:30-` (open-ended), `path:10-20,40-60` (multiple, merged), `path:raw` (no line numbers, no hashline header). Unrecognised `:...` text stays in the path, so `a.zip:inner/file` and `db.sqlite:table` can use their own colon syntax. Line 0 is an error: lines are 1-indexed. Purpose: "the agent reads exactly the lines it needs", which saves context.

### 4.3 The bash tool and background jobs
- Timeout is validated (finite, positive, below a maximum); a timeout error is detected and reported with the effective seconds; transient failures are retried.
- A foreground command that runs long can **yield** to a background job (the soft-yield path from chapter 11.3). Background jobs stream stdout and stderr into a log file under `.fah/bash_jobs/`, which the model reads with `bash_job output` or the `read` tool. Bench and unattended runs relocate that directory (`FAH_JOB_LOG_DIR`) so the harness's artifacts never land in the graded workspace, and pass writes through a redactor so secrets never rest in logs (issue #1408).
- When a job settles, the registry's `onSettled` hook lets the host steer a message into the run, so the model learns about completion at the next step boundary without polling.
- Session variables (`FAH_SESSION_ID`, `FAH_SESSION_FILE`, `FAH_PROVIDER`, `FAH_MODEL`) are injected into shell executions by an `ExecutionEnv` decorator; never secrets.

### 4.4 Hashline edits
The model does not send "replace this text with that text". It sends a small patch language anchored on **line numbers plus a content tag**:
- A `read` in hashline mode (or a previous edit) returns the file with a header `[path#TAG]`, where TAG is a **4-hex-digit hash of the whole file content** (the folder has `xxhash32.dart`).
- An edit section starts with that same header and uses 1-indexed line anchors: `SWAP N.=M:` replaces lines N to M, `DEL N.=M` deletes them, `INS.PRE|POST|HEAD|TAIL:` inserts.
- If the file changed since the tag was minted, the tag no longer matches and **the edit is rejected before any write**: "an edit can never silently land on drifted content." The snapshot store keeps the earlier versions to help report a mismatch.
- Ported subset: tokenizer, parser, applier, snapshot store and patcher for the line-range operations. Skipped: tree-sitter block operations, file operations (`REM`, `MV`), boundary-repair and landing-shift leniency, and diff-based stale-anchor auto-remap.
Why: text-match edits ("old string" must appear exactly once) fail on whitespace and repeated code, and silently succeed on the wrong occurrence; whole-file rewrites cost output tokens and clobber concurrent changes.

### 4.5 Parameter validation
Before a tool runs, its arguments are validated and **coerced** against a JSON-schema subset: types and unions, `required`, `properties`, `items`, `enum` (checked after coercion), `default` injection. Coercion examples: `"42"` → `42`, `"true"` → `true`, `1`/`0` → booleans, numbers to strings. Undeclared keys pass through. Keywords such as `pattern`, `minimum`, `anyOf`, `additionalProperties` are **ignored, not enforced**. A hand-rolled subset instead of a full validator keeps the pure-Dart core small and web-safe.

### 4.6 The approval gate
Every tool has a **tier**: `read` (reads data), `write` (changes workspace state), `exec` (runs code). The session has a **mode**:
| Mode | CLI label | Behaviour |
|---|---|---|
| `alwaysAsk` | always-ask | prompt for every call, reads too |
| `write` | write | auto-allow reads; prompt for write and exec |
| `yolo` | yolo | auto-allow everything; critical bash still prompts |
| `unattended` | autopilot | auto-allow everything, critical bash included; never blocks on a prompt |

The resolution order in `authorize` (*AP* lines 142-157, 254-285):
1. explicit per-tool `deny` override → refuse (wins over everything, including the interceptor)
2. a skill's `disallowed-tools` for this turn → refuse
3. **critical bash pattern** → forced prompt in every mode except `unattended`
4. remaining per-tool overrides (`allow` / `prompt`)
5. a skill's `allowed-tools` for this turn → allow
6. the session "approve always" set
7. the mode compared with the tool's tier
If the result is `prompt` and no prompt UI is installed, the call is **denied** ("no approval UI"), the safe default for headless runs. A denied call never executes: it becomes an error tool result the model can react to. The check runs in the loop's `beforeToolCall` phase and is installed first.

**Critical patterns** include: recursive delete, chmod or chown from a root-like path (`/`, `/*`, `~`, `$HOME`, a drive root or a single top-level directory; `rm -f /tmp/x` and `chmod -R 755 /var/www` do not match, issue #460), `sudo rm`, a fork bomb, writing to a disk device, `mkfs`, `dd` to a device, `shred` on a device, overwriting `/etc/passwd`, `/etc/shadow`, `/etc/sudoers`, and **remote fetch piped to a shell** (`curl ... | bash`). The response is a *prompt*, not a block: "the user decides". The same list covers the mobile shell tool because it runs with elevated privileges. A companion `bash_shape_redaction` file redacts the command shape shown in prompts (not read in detail).

### 4.7 Secrets and redaction
Two systems run side by side:
- **`SecretRedactor`** (exact values): holds named secret values (API keys, `request_secret` grants) and replaces any occurrence with `***` in tool results before it enters the transcript, the provider context or the session JSONL. Values shorter than 8 characters are never registered (false-positive guard). Only names are ever exposed, never values.
- **Layered `RedactionPipeline`** (issue #24): eleven pure layers in strict priority order, `registered → path → credential → vendor → prefix → pem → asn1 → connection → context → entropy → pii`. Higher-priority spans win overlaps; output markers are `[REDACTED:<kind>]`; rewriting is idempotent and preserves line count. Examples: credential file paths and whole-file dumps (`.env`, `id_rsa`, `.aws/credentials`), vendor tokens (GitHub, AWS, OpenAI, JWT), PEM and ASN.1 blobs, connection strings, context keywords (`password=`, `api_key:`, JSON `"password": "..."`, only the value is masked), a Shannon-entropy heuristic (excludes UUIDs, hex, ISO timestamps, SRI hashes, and path components), and opt-in PII (email, phone, Luhn-valid card numbers, SSN, IBAN).
- **`request_secret` tool**: when a credential is missing the agent asks the *user* through a UI (never in chat text); a grant returns a host-adjusted name and value, is persisted, injected into the live shell environment, and registered with the redactor, so `$NAME` works in bash while the value never reaches the model. Provider tokens live in the OS secure store (Keychain, Secret Service), and `config.yaml` carries names only.

### 4.8 TTSR: time-traveling stream rules
A rule is one or more regexes plus a body. While the model streams, each delta is appended to a per-stream buffer (`text`, `thinking`, or the tool-call id) and **every rule is re-tested on the whole buffer** (so a pattern split across chunks still matches). On a match the controller: aborts the current generation mid-stream, drops (or keeps) the partial output, injects the rule body as a hidden `<system-interrupt>` user message, persists it as a `ttsr-injection` custom message, and retries the turn with `continueRun`. Rules live in `~/.fah/config.yaml` or `.fah/rules.yaml`; a malformed section is a hard config error, an invalid regex inside a valid rule is a warning and skipped. It is a way to enforce a convention **at the moment the model is about to violate it**, without paying for a long system prompt on every turn.

### 4.9 Other tool pieces worth knowing
`lsp` (a pure-Dart JSON-RPC client over a transport: initialize handshake, diagnostics cache, per-request timeouts, spec-compliant replies to server requests), `web_search` (keyless DuckDuckGo first, keyed Brave/Tavily behind secrets) and `web_fetch` (pages to markdown), `memory_*` (git-backed long-term memory, project and user scope; chapter 11.6), and **tool availability** scoping per project or session through `.fah/config.yaml` and `.tools/<id>.yaml`.

## 5. Why it was built this way (decisions and trade-offs)

| Decision | Alternatives considered | Why this one | Cost / risk |
|---|---|---|---|
| Static tier per tool + session mode | Per-call risk scoring by an LLM | Predictable, explainable, no extra model call (*AP* header) | Coarse: a `bash` read and a `bash` delete share a tier; hence the interceptor |
| Critical patterns **prompt**, not block | Hard block | The user keeps control; false positives stay actionable | Prompt fatigue; in `unattended` nobody answers |
| Interceptor skipped in unattended mode | Always on | An unattended run must never wedge on a prompt (*AP* lines 270-273) | The mode relies on external isolation |
| Unknown tools default to `exec` | Default to read | Safe by default for plugins and custom tools | Friction for harmless custom tools |
| Deny wins over everything | Mode wins | Explicit user policy must be unbreakable | Misconfigured deny blocks silently-ish; reason is surfaced |
| No prompt UI means deny | No prompt UI means allow | Headless safe default | Headless runs need an explicit mode or allow list |
| Hashline compare-and-swap edits | Search-and-replace; whole-file write | Detects drift; cheap in tokens | Model must learn a patch language; the `read` must mint the tag first |
| Redaction by many small layers with priority | One big regex | Each layer is testable and tunable; overlaps resolved by priority | Heuristics; entropy layer trade-off between misses and mangling |
| Secrets as named variables (`$NAME`) | Put values in the prompt | Model can use secrets it never sees | Output can still echo a secret; hence output redaction |
| TTSR rules instead of a longer system prompt | More prompt text | Pay only when a violation starts; strong correction | Abort and retry cost; regex rules only (no AST conditions ported) |

## 6. Theory behind it (the "lecture" part)

### 6.1 Least privilege and capability tiers
The principle of least privilege gives a component only the access it needs. Tiering tools into read, write and exec is a coarse capability model: reading is cheap and reversible, writing is local and often recoverable, execution is open-ended. Policy engines combine rules by precedence; the common safe design is **deny overrides** (any deny wins). Defaults should fail closed: unknown means exec, no prompt UI means deny.

*In my project:* Course 8.2 (subagents with least-privilege tool lists) is the same idea at the agent-definition level.

### 6.2 Defence in depth, and where the sandbox must come from
No single control is enough: the tier policy, the pattern interceptor, redaction, the workspace boundary and the OS sandbox each cover different failures. A pattern interceptor is a **blocklist** and can always be bypassed (an interpreter, an obfuscated command). It catches accidents, not attacks. Real containment for autonomous runs comes from the environment (container, restricted user, no network) — which is exactly where an unattended mode puts the burden.

*In my project:* my hooks in the context-engineering template (Course 8.3) are the same class: a guard against accidental out-of-scope edits, not a sandbox.

### 6.3 Optimistic concurrency and compare-and-swap
Optimistic concurrency lets several writers proceed and checks at commit time that the data has not changed (a version number or hash). A compare-and-swap (CAS) updates only if the current value equals the expected one. HTTP's `If-Match` with an ETag is the same pattern. Hashline gives each edit the file's content hash as its "expected version". The failure mode is a clean rejection, which the agent handles by re-reading.

*In my project:* the risk it addresses is the agent editing from a stale view, which also happens when two agents or a human share a checkout (chapter 11.8).

### 6.4 Prompt injection and tool results as untrusted input
Anything a tool returns (a web page, a file, an issue body) is untrusted text that can contain instructions. Defences are layered: privilege separation (the approval gate sits outside the model), output filtering, quarantining untrusted content, and never giving one tool call the combination of private data, untrusted content and an exfiltration channel. An approval gate limits damage even when the model has been fooled.

*In my project:* Course 6.3 (what to expose before identity and GDPR) argues the same boundary for MCP.

### 6.5 Secret scanning: patterns, entropy, context
Three detection families: **known formats** (vendor prefixes such as `ghp_`, `AKIA`, JWT structure), **context** (a value after `password=`), and **entropy** (random-looking strings have high Shannon entropy, H = −Σ p_i log₂ p_i per character). Known formats have high precision; entropy finds the unknown at the price of false positives, so allowlists (UUIDs, git SHAs, hashes) are essential. Masking must be idempotent and must not corrupt structure (line counts preserved here), because the output feeds a model.

*In my project:* the order of layers by priority is the standard way to resolve overlapping findings.

### 6.6 Mid-stream interruption (TTSR) as a control technique
Most guardrails act before (system prompt) or after (output check) generation. Interrupting a stream when a pattern appears is a **streaming guardrail**: lower latency to correction, and a retry can inject a precise reminder. The cost is wasted tokens and the risk of oscillation (the model produces the pattern again), which hosts bound through settings.

*In my project:* it is the runtime counterpart of a PreToolUse hook in Claude Code, but triggered by generated text instead of tool calls.

## 8. Glossary

| Term | One-line definition |
|---|---|
| Tier | `read`, `write` or `exec`: the capability class of a tool |
| Mode | Session approval posture: always-ask, write, yolo, unattended (autopilot) |
| Critical pattern | Destructive shell shape that forces a prompt |
| Approve always | Session allow for a tool after one approval |
| Turn grant | Allow or deny that a skill applies to one turn |
| Hashline | Line-anchored patch language carrying a content hash of the file |
| Tag | Short hash of the whole file content minted by `read` or a prior edit |
| CAS | Compare-and-swap: write only if the current value matches the expected one |
| Selector | Trailing `:range` or `:raw` part of a read path |
| Background job | Shell command running detached with a log file |
| Redaction pipeline | Eleven priority-ordered layers masking secret-shaped text |
| `SecretRedactor` | Exact-value masker for registered secrets |
| `request_secret` | Tool that asks the user for a credential through a UI |
| TTSR | Rules that abort and retry a generation when its text matches a pattern |
| Shannon entropy | Measure of randomness of a string, used to spot keys |

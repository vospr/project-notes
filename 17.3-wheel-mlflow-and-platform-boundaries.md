## 4. How it works (technical walkthrough)

### 4.1 Source becomes an installed interface

`pyproject.toml` declares project `forecast`, Python >=3.10 and dependencies on MLflow, NumPy, pandas and scikit-learn. Hatchling builds the package from `src/forecast`; the version comes from `_build_version.py`, using a time-based PEP 440 post-release value. The optional agent prototype pins framework core 1.24.0 only for Python >=3.11. The metadata's broad base dependency names are not the same as a fully pinned production environment.

The scripts table maps `forecast-prepare` to `forecast.cli:prepare_main`, with equivalent mappings for train/register/score/monitor. Installation creates command wrappers that import those callables. `cli.py` accepts argv or keyword strings, rejects mixed invocation, duplicate options, unresolved selectors and conflicting explicit versus pipeline selectors. Historical Databricks logs observed argv invocation; local tests support keyword-call behavior, so these are distinct evidence claims.

```text
reviewed source -> wheel + hash -> installed distribution
                                     |
                              named entry point
                                     |
prepare -> train -> register -> score -> monitor
   |         |          |          |         |
   +---------+----------+----------+---------+
                   io.py boundary
                  /              \
           laptop files       managed Spark/registry

journal: started -> effects -> completed + exact handoff
```

The historical Databricks wheel executed; current source includes later changes. Applied Fabric adapters lack a default live managed-context observer, and Fabric model CLI paths stop without validated context. Live LLM and Teams remain deferred.

### 4.2 Keep environment knowledge at the boundary

`io.runtime` honours an explicit runtime override, then checks the Databricks runtime marker, then a Fabric filesystem marker, otherwise laptop (`io.py:112`). Detection chooses a branch; it does not authenticate a managed registry. Laptop demand reads may use CSV or the synthetic generator. Managed table reads collect at most `max_rows+1` rows to pandas and reject beyond the two-million-row limit. This is deliberately small-data orchestration, not a distributed model-training pipeline (`io.py:177`).

Table naming is three-level and parameterised. Databricks registry configuration selects Unity Catalog. Fabric model names are workspace-local and numeric URIs are exact, rather than reusing a Unity Catalog qualified model name. All runtime-specific decisions remain in `io.py`; callers provide explicit context and ports. Existing Spark writes normalise pandas string-extension columns to object strings to avoid the historical Arrow chunk serialization failure, preserving numeric/date columns and the caller's frame (`io.py:211`).

### 4.3 Track a model, then register an identity

Training logs a parent model-family run, child runs, validation metrics, parameters and source-related tags. A run records an experiment execution; it is not itself a registered model version. `NamedPredictionModel` wraps an estimator and returns a pandas frame with exactly one column, `prediction`. Its signature has eight ordered named double inputs and one named double output (`train.py:42`).

`validate_signature` rejects missing signatures, integer inputs, different order/names and tensor-style output before registry mutation (`register.py:12`). The non-Fabric path registers the logged model, tries a champion alias and falls back to a version tag if alias assignment raises. This broad fallback does not mean every exception proves lack of alias support. Fabric follows a separate local-tested tag-only policy and no Fabric alias calls.

### 4.4 Score the exact version and check coverage

`score_registered` resolves an explicit numeric version, loads the model and passes float64 features. In the Fabric branch its IO policy checks supplied context and inventory before loading. Outside Fabric, champion-marker validation belongs to `score_main` through `require_champion_version` before the scorer is called (`cli.py:169`); calling the reusable scorer alone does not perform that marker check. The scorer requires a one-column dataframe, matching row count and finite numeric predictions, then writes part/week/prediction/model_version (`score.py:14`). An all-double signature solves an interface mismatch, not estimator portability across different scikit-learn versions.

`monitor_model` joins predictions to test keys with one-to-one validation, checks complete finite coverage and matching version, then computes metrics. Training-quantile bins define PSI, with small smoothing to avoid zero proportions. Four chronological blocks expose worse periods hidden by an overall average. Historical worst-block WAPE about 0.37460 exceeded 1.25 times validation WAPE, about 0.37289, while both PSI values stayed below 0.2. The task succeeded and the monitoring alert was true: those statements are compatible. No automatic notification, retraining or rollback is demonstrated.

### 4.5 Publish intent before effects

`Pipeline.begin` reads and validates the journal, requires a unique ordered prefix and appends started before the main stage effects. Prepare may ensure the schema before that append. `complete` rereads history, refuses changes and appends completed only after the caller's success conditions. Parent identity first becomes required at train completion; registered version first becomes required at register completion. Null earlier outputs are therefore expected, not automatically failed writes (`pipeline.py:61`).

If registration creates a version but completion publication fails, the started record remains. A second attempt is forbidden even if some effects succeeded. The journal does not roll back model creation or create an atomic transaction across Spark, registry and tracking. The retained historical failed prepare intent must not be repaired or replayed; this chapter authorises no command execution.

## 5. Why it was built this way (decisions and trade-offs)

| Decision | Alternatives considered | Why this one | Cost / risk |
|---|---|---|---|
| Installable wheel and five named commands | Notebook-only orchestration | Reviewable code and explicit execution interfaces | Packaging alone does not reproduce the environment |
| Per-build post-release version | Reuse identical version string | Distinguish artifacts and reduce cache ambiguity | Different names alone do not prove byte identity |
| IO boundary | Runtime checks scattered everywhere | Test pure behavior with explicit dependencies | IO module carries substantial policy complexity |
| Named double signature | Implicit integer/tensor inference | Stable input/output contract for batch consumption | Does not guarantee cross-version serialization |
| Durable no-replay journal | Automatic retry/resume | Preserve uncertain effects and spent evaluation boundary | Manual reconciliation; no general recovery engine |
| Explicit source/evidence scope | Transfer old live proof to new source | Trace what actually executed | Historical DBX proof and local Fabric proof stay separate |
| Guarded Fabric context and inventory | Trust a URI or empty listing | Fail before unsafe adoption/load | Local observer mocks are not live authentication |
| Owner decisions with AI-assisted delivery | Claim personal sole implementation | Accurate contribution account | Provider/Teams still deferred; no production outcome claim |

## 6. Theory behind it (the "lecture" part)

### 6.1 Distribution is not an environment

A wheel is an installation archive containing code and distribution metadata. The [Python packaging specification](https://packaging.python.org/en/latest/specifications/binary-distribution-format/) defines the format. A filename ending `py3-none-any` does not bundle an operating system, Spark or all transitive dependencies. Installation metadata can state dependency requirements; the actual interpreter resolves installed versions, which may differ between laptop and managed runtime. Here the wheel separates application delivery from environment verification.

A version labels a release, a hash fingerprints exact bytes, and a source manifest maps bytes to reviewed modules. A commit alone omits dirty/untracked work; a time-based version does not promise reproducible builds. Here source/wheel matching supports local identity, while live acceptance remains attached to its earlier wheel.

### 6.2 Tracking, registry and serving are different services

Tracking records runs, parameters, metrics and artifacts. A registry organises named model versions and mutable selection markers. Serving makes a chosen model available for requests. A recorded metric does not establish registration; a registered version does not establish an endpoint; an endpoint does not establish safe operational use. The project demonstrates historical batch execution and registry linkage, not a live serving endpoint or reviewed Teams application.

A mutable champion alias is convenient for selection but can move. An explicit numeric version stabilises the load target for an operation; provenance still needs the source/run identity and the intended registry context. Model version, experiment run identifier, pipeline identifier and Delta table version are different types of identity, even when all look like strings. The project's journal carries the precise parent/version handoffs rather than parsing stdout as the source of truth.

### 6.3 Contracts and adapter isolation

An interface contract specifies names, order, types and return shape so independent components can disagree safely rather than silently corrupt results. Eight double inputs plus a named prediction column are a contract. They do not establish that a pickled estimator from one library version behaves correctly under another. The same distinction applies to a fake service adapter: a passing mock proves the code responds to supplied observations, not that the real platform supplies those observations or honours deadlines. This is why actual Fabric integration remains unproven despite applied adapters and local tests.

Dependency inversion means the core receives operations rather than discovering global services itself. A test can inject a loader, writer or registry client and assert call ordering and refusal. The Fabric adapter requires explicit synthetic ports and independently matching tracking/registry context. Equality of URI strings or a managed=true flag cannot substitute for positive service identity. This project's local policy makes missing authority a stop condition.

### 6.4 Partial failures and the replay problem

Suppose an application sends create-model-version, the registry commits it, and the response is lost. Retrying can create a duplicate; claiming failure can conceal a real effect. Exactly-once application behavior requires more than a timeout or request-local flag. Durable intent, unique identities, idempotent service operations where supported, and reconciliation of observed effects are separate techniques.

The project's approach records intent and forbids stage replay. It intentionally trades automatic recovery for evidence preservation. A completed append is not a distributed transaction with the model or table write, and rereading history does not lock out every external writer. The contract assumes one effective writer; whole-history collection is suited to the small synthetic demonstration, not indefinite production retention.

### 6.5 Monitoring is a rule, not a diagnosis

PSI compares binned feature proportions: `sum((observed_share-reference_share) * log(observed_share/reference_share))`. It indicates distribution change under chosen bins; it neither identifies a business cause nor proves a model is inaccurate. WAPE measures observed forecast error after outcomes arrive. The project's strict rule alerts when worst-block WAPE > 1.25 times validation WAPE OR either monitored PSI > 0.2. Equality does not alert. Bin choices, reference period and smoothing affect PSI; a fixed threshold is a local policy rather than universal scientific truth.

### 6.6 Evidence grows in separate steps

Source inspection, unit tests, clean installation, installed metadata, service connectivity, actual stage execution and saved-estimator parity each establish different facts. Success at one step cannot skip the next. Current retained Fabric gaps include full versus skinny MLflow, Arrow constraints, optional framework dependencies, a missing live managed-context observer and estimator portability. A published package list is a declaration; it is not proof of resolved installed bytes. The proposed read-only M0 inspection and separate S1 metadata session would narrow gaps, not establish end-to-end acceptance by themselves.

## 8. Glossary

| Term | One-line definition |
|---|---|
| Wheel | Installable Python distribution archive, not a complete runtime |
| Entry point | Metadata mapping a command to an importable Python callable |
| Artifact hash | Fingerprint of exact bytes, distinct from a friendly version |
| Tracking run | Experiment execution record containing metrics, parameters and artifacts |
| Registered version | A numbered model identity within a registry name |
| Signature | Ordered typed input/output interface contract |
| Delta version | Table history version, not an MLflow model version |
| Durable intent | Persisted started record before the main stage effects |
| Partial failure | Some effects may have committed even when the caller reports failure |
| PSI | Population Stability Index, a binned distribution comparison |
| Local adapter proof | Synthetic supplied-context behavior; actual Fabric integration remains unproven |
| Contribution boundary | Owner framing/review of AI-assisted implementation, not sole manual authorship |
| Deferred delivery | Live provider and Teams work awaits reviewed actual Fabric integration |

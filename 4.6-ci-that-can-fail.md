# Course 4 · Chapter 4.6: CI that can fail, `make demo`, and what is missing (monitoring and drift)

_Andrey Popov's project notes: how it works, why it was built this way, and the theory behind it._

**In short:** CI that can actually fail: make ci runs 27 tests plus a train, gate and serve demo on a committed fixture. Lists what is not built (drift monitoring, retraining, Docker) and what a real monitor needs (PSI, reference window).

## 2. The problem (business view, plain English)

v1 had a CI badge that could not turn red: it only checked that five Python files compile, and the one job that ran the pipeline was manual and set `continue-on-error: true` on every stage. A green check that cannot fail is worse than none, because people trust it. The redo asks: if I break the model, the gate or the serving path, does the build go red?

Finance analogy: a daily reconciliation that always prints "OK". The control exists, auditors see it, and it catches nothing. A control is only real if you have seen it fail on a planted error.

## 4. How it works

```
push to main / pull request ──► GitHub Actions: ubuntu, checkout, setup-uv, `make ci`
                                         │
        make ci ── uv sync --frozen ── pytest (27 tests) ── make demo
                                                             │
        make demo ── uv sync --frozen ── rm -f mlflow.db
                  ── python -m seismic_mlops.train --data fixture --fail-if-not-promoted   (exit 1 if gate rejects)
                  ── python scripts/smoke_serve.py   (start uvicorn, GET /health, POST /predict with 20 patches, assert 20 answers)
```
`make` stops at the first failing recipe line and returns non-zero, so any failing step fails the job. The workflow itself is 12 lines and contains no `continue-on-error`.

**What runs in CI** (27 tests, counted by file: 01 → 5, 02 → 3, 03 → 5, 04 → 3, 05 → 5, 06 → 6):
| Group | Files | Guards |
|---|---|---|
| Data | `test_01` | Real facies in fixture, provenance strings, MD5 check rejects corrupt file, centre-pixel label |
| Pipeline | `test_02` | One Pipeline, fit on train only |
| Gate | `test_03` | Below-baseline, weaker, tied rejected; alias does not move |
| Serving | `test_04` | Served = trained, wrong shape rejected, no feature code |
| Hygiene | `test_05` | No `continue-on-error`, `make ci` content, lockfile present, cut scope absent |
| Selection | `test_06` | Blocks disjoint, gate independent of test1, test1 scored once per run |

**The fixture**: `build_fixture` calls `load_f3` with 600/300/300 and seed 0 and saves a compressed `.npz`. Tests and the demo read it through `load_fixture`. Provenance (source URL, MD5, section ranges) is stored in the file.

**v1 versus the redo**
| | v1 | Redo |
|---|---|---|
| Trigger | push to `main` only if `data/raw/**` changes, or manual | every push to `main` and every pull request |
| Checks | `py_compile` of five files | 27 tests + full train/gate/serve on a fixture |
| Pipeline job | manual, each stage `continue-on-error: true` | `make demo`, any failure fails |
| Dependencies | `requirements.txt` (optuna, feast, faiss missing) | `pyproject.toml` + `uv.lock` |
| Needs data | raw SEG-Y not in repo | fixture in repo |

**What is not built**: drift monitoring against a training reference; API request metrics; any retraining trigger; Docker and separate environments; hyperparameter search; a feature store; retrieval. The page may not claim "drift", "live metrics", "retraining", "Docker", "Optuna".

## 5. Why it was built this way (decisions and trade-offs)

| Decision | Alternatives | Why this one | Cost / risk |
|---|---|---|---|
| CI = `make ci` (same command as local) | Duplicated YAML steps | One definition; what I run is what CI runs | Hides step detail in the Makefile |
| Commit a real-patch fixture | Download 1 GB in CI; synthetic data | CI in minutes without network or secrets | Not representative of rare classes; 2.3 MB binary in git |
| No `continue-on-error`, with a test that bans it | Trust review | Regression guard for v1 habits | Text-level check |
| `--fail-if-not-promoted` in the demo | Print only | Gate failure becomes a red build | Path untested; only first-model branch |
| uv + lockfile | pip + requirements | Reproducible; would have caught the missing optuna/feast/faiss | `--frozen` does not detect drift |
| Cut Feast, RAG, 3 environments, Docker | Keep as islands | Wire fewer things properly | Less to show; honest |
| No monitoring | Half-built monitoring | An honest gap beats a tautological test (chapter 4.1) | A pipeline "after deployment" is not covered |

## 6. Theory behind it (the "lecture" part)

### 6.1 What CI proves, and the false green
Continuous integration runs checks on every change. A check has value only if (a) it runs, (b) it can fail, and (c) failure stops the merge. A check that always passes is a **false green**. The practical test is *red-green*: break the thing on purpose, see the build fail, then fix it. **Mutation testing** automates this idea by changing the code and counting how many mutants the tests kill.

*In my project:* the redo bans the v1 patterns by test, but I have not shown a planted red run.

### 6.2 Testing an ML pipeline
Layers: **unit** (pure functions such as `gate.decide`), **data** (schema, class coverage, no overlap between sets), **integration** (train, log, serve on a tiny dataset), **behavioural** (invariances, for example scrambling test labels must not change the gate; directional and minimum-functionality tests in CheckList style), **parity** (served equals trained), and **evaluation on real data**, which is slow and usually runs on a schedule, not on every commit. CI on a fixture proves that the plumbing works and that decision logic fires. It cannot prove model quality on the real distribution.

*In my project:* unit, data, integration, behavioural and parity tests exist; real-data evaluation is a manual `make f3` with logs committed.

### 6.3 Hermetic, reproducible builds
A build is **hermetic** if it needs nothing outside the repo and the pinned dependencies: no network at test time, fixed seeds, a lockfile. `uv sync --frozen` installs exactly the lockfile; `--locked` additionally fails if the lockfile is stale relative to `pyproject.toml` (my understanding; check the docs). Pinning the Python version (`.python-version` says 3.12; `requires-python` >=3.11,<3.13, *pyproject.toml:6*) and committing small fixtures complete the picture. Float16 storage shrinks the fixture but changes values slightly, so fixture metrics are not comparable to full-data metrics.

*In my project:* fixture + lockfile + seeds; the demo log shows MLflow exporting 93 pinned dependencies into the model.

### 6.4 What to monitor after deployment
Four layers: **system** (latency, errors, throughput), **data** (schema, missing values, ranges, distribution), **predictions** (class histogram, confidence), **performance** (accuracy, needs true labels, usually delayed). Drift types: **covariate** (P(x) changes), **prior/label** (P(y) changes), **concept** (P(y|x) changes). Without labels you can only watch the first three.

Detectors: for a continuous feature, the two-sample KS test (statistic D, critical value c(α)√((n+m)/(nm)), c(0.05) ≈ 1.358); for categories, χ²; for binned distributions, the **Population Stability Index**, PSI = Σᵢ (aᵢ − eᵢ) · ln(aᵢ/eᵢ) over bins with actual share aᵢ and expected (reference) share eᵢ, with the usual rule of thumb: below 0.1 stable, 0.1 to 0.25 some shift, above 0.25 significant. PSI comes from bank scorecard monitoring. Many features mean many tests (multiple comparisons), so alert on a share of features or a PSI summary, not on any single p-value. The **reference** must be the training data (or a vetted earlier window), not the data being tested.

For prior shift without labels, **black-box shift estimation** (Lipton et al. 2018) solves C·w = μ̂, where C is the classifier's confusion matrix on validation (rows: predicted, columns: true) and μ̂ the predicted-class distribution on new data. A raw predicted-class histogram can be blind to a shift in a class the model rarely predicts.

*In my project:* nothing is built. Worked illustration with README numbers I could not verify (class 4 is 3.0% of training patches, 15.6% of test1): the two-bucket PSI "class 4 vs rest" = (0.156 − 0.030)·ln(0.156/0.030) + (0.844 − 0.970)·ln(0.844/0.970) = 0.208 + 0.018 ≈ 0.23, near the 0.25 threshold from one class alone. And the model predicts class 4 for only about 1.8% of test1 patches (91 of 5,000, derived from precision 0.78, recall 0.091), so a predicted-class histogram would hardly show it.

### 6.5 Closing the loop: retraining and rollout
Monitoring feeds a decision: ignore, investigate, retrain. A retraining trigger can be a schedule, a drift alert, or a performance drop once labels arrive. The new model goes through the same gate (chapter 4.5), then a staged rollout: shadow (run alongside, compare), canary (small traffic share), full. Rollback means repointing the alias.

*In my project:* the gate and alias exist; triggers, shadow mode and canary do not. The v1 "retraining" was a text recommendation.

### 6.6 Claims must match evidence
Documentation is a control too. Each claim should be backed by something a reader can check: a log, a test, a run. A claim stronger than its evidence ("CI/CD validated", ">85% expected") damages trust more than an honest gap does.

## 8. Glossary

| Term | One-line definition |
|---|---|
| CI | Automatic checks on every push or pull request |
| False green | A passing check that could not have failed |
| Red-green | Make the check fail once on purpose to prove it works |
| Fixture | A small committed dataset used by tests |
| Hermetic build | Needs nothing from outside the repo and its pinned dependencies |
| `--frozen` / `--locked` | uv flags: use the lockfile as is / also fail if it is out of date |
| `make demo` | Install, train on the fixture, gate, serve, query |
| Smoke test | A quick check that the service starts and answers |
| Covariate / prior / concept drift | P(x) / P(y) / P(y given x) changes |
| PSI | Population Stability Index: Σ (actual − expected) · ln(actual/expected) |
| KS test | Two-sample test on the largest CDF gap |
| Reference window | The healthy data a monitor compares against |
| Shadow / canary | Run a new model beside the old / on a small share of traffic |
| Behavioural test | Change an input, assert how the output may or may not change |

# Course 11 · Chapter 11.8: The AI factory around the repo

_Andrey Popov's project notes: how it works, why it was built this way, and the theory behind it._

**In short:** The AI-run delivery loop around the repo: issue to dev leg, PR, dispatched CI, review leg, bounded rework, merge bot and release bot; controls (concurrency, caps, App token, ownership scope); AGENTS.md and committed memory; case studies of regression #1516 and perf issue #1499; what is not measured.

## 2. The problem (business view, plain English)

A solo maintainer cannot keep up with a 185,000-line, seven-host project that releases a new version on every merge. The answer in this repo is to let **AI agents run the software delivery loop itself**: they read an issue, write a fix on a branch, open a pull request, review each other's pull requests, rework after review, wait for CI, merge and release. The human steers by writing issues and goals, setting rules, and watching outcomes. The same agent product (`fa`) that is the subject of the repo is used to build the repo (the "dogfooding" loop). This chapter is about that process layer, because it is the part of the repo that most directly answers the question "can you run AI agents in production delivery, and with what controls?"

Finance analogy: straight-through processing with exception handling. Orders flow without a human touching them; humans own the limits, the exception queue and the reconciliation.

## 4. How it works (technical walkthrough)

### 4.1 The cast
| Actor | What it is | Evidence |
|---|---|---|
| `ai-teammate` | A GitHub identity (and commit identity `ai.teammate`) under which the dev, review and rework agents act | *TEAM*; *AGENTS* "Commits and releases" |
| Factory | The public repo `dmtools-agents`: reusable workflows `factory-teammate.yml`, `factory-sm.yml`, `factory-merge.yml`, agent configs and JS | *TEAM*, *SM*, *AWF* |
| Dev / review / rework **legs** | Three roles of the teammate workflow, each with a runner config in `.dmtools/runners/` (`fa-bug-dev`, `fa-story-dev`, `fa-review`, `fa-rework`) | *DMT* |
| **Machine SM** | A reconcile tick every 10 minutes; "the engine idles when busy"; dispatches legs and CI validation; the original system calls this agent the *Scrum Master* | *SM*; *AWF* |
| **Merge bot** | A deterministic (non-AI) fast path reacting to CI conclusions, labels, pushes and check runs so approved green PRs merge "within seconds"; idempotent with the SM, "first actor wins" | *MERGE* |
| **Release bot** | The `fa-release-bot` GitHub App, the only identity allowed to push the release bump to protected `main` | *AGENTS* |
| `fa` itself | The agent CLI that runs inside the legs, configured by `.fah/config.yaml` | *TEAM*; `.fah/` |

### 4.2 The loop of one issue
```
issue filed (human or machine), assigned to ai-teammate
        │  trigger: `issues: assigned` (labelled events removed on 2026-10-01 to stop echo runs)
        ▼
 DEV leg   → branch, commits, PR, labels ai_developed, status: In Review
        │
 SM tick   → dispatches CI validation on the PR head ("validate-fresh / validate-armed")
        │      (CI has no pull_request trigger; only this dispatch runs it)
        ▼
 REVIEW leg (PR opened by ai-teammate → review on the linked issue)
        │      labels ai_pr_reviewed, pr_approved  or  rework-round-N
        ▼
 REWORK leg (bounded by MAX_AUTO_REWORK_ROUNDS) → back to review
        │
 MERGE bot → merges approved, green PRs
        ▼
 push to main → CI → auto-release to pub.dev (1.0.<counter>), tag → binaries, stores
```
Control details seen in the stubs and issues:
- **Per-issue concurrency group**: one run per issue; workflow-level concurrency holds duplicates pending, which is why `labeled` triggers were removed (every status-label echo spawned a queued twin run).
- **Ownership by author**: in this phase the loop reacts only to issues and PRs authored by the machine; human-authored ones do not trigger it.
- **Explicit minimal permissions** at the top level; job-level grants carry the real rights (SEC-08). The SM needs `contents: write` to update PR branches, and has `actions: write` to dispatch the teammate workflow.
- **Secrets mapping** is explicit: the factory gets `SOURCE_GITHUB_TOKEN`; provider keys `ZAI_CODE_KEY` and `KIMI_REVIEW_KEY` are optional. The implementer and the reviewer can be **different models** (a z.ai GLM key for coding, a Kimi key for review).
- **Labels as state**: `status:In Development`, `status:In Review`, `status:Blocked`, `ai_developed`, `ai_pr_reviewed`, `ai_validating`, `ai_validated`, `pr_approved`, `agent:review`, `agent:rework`, `rework-round-N`, `priority_blocker`, `sm_story_rework_triggered`. In the original design these double as **distributed locks** (`skipIfLabel` / `addLabel`, released in a post step) and a `wip` label pauses a ticket.
- **Watchdog**: the external watchdog kills a leg after 10 minutes without trace updates, which is why the loop-level stuck-call supervision (chapter 11.3) uses a 300-second floor.
- **Self-filed problems**: workflows file issues for flakes (`flake-watch`), failed daily publishes (`daily-publish` auto-filer with root-cause dedup), low coverage (`coverage-gardener`), and red main. In the sample of 12 newest issues, 8 carry both `ai_developed` and `ai_pr_reviewed`.

### 4.4 Case study: issue #1516, a regression in the agent's own guard
- **Symptom (owner report):** in an interactive TUI session with `approvalMode: autopilot`, a trivial question triggered a "verification ritual": the model wrote its own reply to a temp file, read it back, measured file times, and added a visible "Checklist" section and an unfenced `task-ledger` dump to its answer. A different, smaller model answered normally, so the trigger was universal and the explosion model-dependent.
- **Root cause (owner direction: the prompt, not the wiring):** `prompts/cli/finalize_gate.md` said "Before ANY final summary you MUST ..." with no rule for when it does *not* apply. Secondary: the gate is wired to `approvalMode == unattended` (which the CLI labels `autopilot`), at `agent_cli.dart:649`.
- **Requirements:** (1) the prompt must open with an applicability rule, with two or three negative examples ("weak models follow examples better than abstract rules"); (2) the strip logic must also catch near-miss shapes (an unfenced heading plus bullets), persist them as the hidden record and never leave them in the transcript; (3) a "never-again" regression test: a scripted provider, a trivial question in a gate-active session, zero tool calls and no checklist in the visible transcript.
- **Status in the sample:** labels `ai_developed`, `ai_pr_reviewed`, `agent:review`, `rework-round-1`, `status:In Review` — the loop was working on its own bug.
Lessons: a prompt contract needs a scope clause; "mode implies behaviour" couples two concerns (permission mode and verification ritual); the fix includes a test that fails first.

### 4.5 Case study: issue #1499, a performance hotspot found by profiling
`crap4dart profile` over 42 core test directories showed `buildContextLedger` (the structured-compaction ledger, chapter 11.4) at a **mean 2.0 s and a maximum 58.8 s** per compaction over 32 calls, caused by repeated linear lookups and a full rebuild each time. The issue asks for a benchmark on synthetic 1k and 10k message histories (linear growth, under 1 s at 10k), an index by id, and caching between iterations, with a before and after benchmark in the PR and a byte-equivalent ledger. This is the profile-driven, acceptance-criteria-first style that the agents work from.

### 4.6 `AGENTS.md` as the constitution
`AGENTS.md` (134 KB) is "conventions for AI agents and contributors ... facts: paths, commands, invariants, no essays". It holds: project layout with per-folder invariants, hard architecture rules (no `dart:io` in `lib/`), parallel-work rules, memory rules, golden-test rules, prompts-outside-code rules, the quality gates (chapter 11.7), parity rules, commit and release rules and bench knobs. Selected rules that exist because of past incidents:
- **Shared checkout policy**: do not modify the shared checkout unless asked; do not run heavy commands there; never `git stash` the user's work; worktrees only on request, under `.worktrees/`, created from the remote ref, removed at once.
- **Peer agents talk through the inbox fabric** (`agent_directory`, `agent_message`), never by reading each other's working files; each agent's `memory/note/` files are its own.
- **Commit identity**: contributors commit as `ai.teammate`; release commits as the release bot; any automation touching release paths must use the App token, never a PAT or the default token (gh-1402).
- **Barrel file policy** (gh-1232): grouped, append-only export sections so that parallel edits almost never touch the same line. This is a rule designed for **merge-conflict avoidance between agents**.

### 4.7 Memory as part of the system prompt
- `memory/` is committed in the repo and declared as the project memory in `.fah/config.yaml` (`memory: projectPath: ./memory`), so anyone cloning gets it. It holds **861 notes** (`memory/note/n_0001.md` ...), each with front matter: id, type, title, author (`agent`), date, area (`project`), importance, level, tags. Example (n_0003, 2026-08-16): "flutter_agent root contains install_local.sh that builds and installs fa to ~/.local/bin/fa with ad-hoc macOS code signing." A `DELETIONS.md` and a `deleted/` folder record removals.
- `AGENTS.md` tells agents to `memory_search` before any non-trivial task ("cheap to query, often the difference between re-deriving a rule and silently violating it"), and to write only through `memory_add` (durable facts; supersede by delete and add; "never leave solved problems to rot"). Project notes belong to the user; user-scope notes are global and private.
- The system prompt gets a `<memory>` section from the same store; compaction feeds it (chapter 11.6).

### 4.8 Self-configuration skills
`.fah/skills/` contains `create-goal`, `fa-self-config` and `fa-self-improve`: skills through which the agent writes goal tickets in the house format, edits its own configuration, and proposes improvements to itself. Issue titles use the prefixes `[GOAL]`, `[BUG]`, `[ENH]`, `[PERF]`, `FLAKE:` (the house taxonomy that the agents and workflows parse).

## 5. Why it was built this way (decisions and trade-offs)

| Decision | Alternatives considered | Why this one | Cost / risk |
|---|---|---|---|
| The product builds itself (dogfooding) | Separate tooling for the factory | Every harness bug is felt by the builder; bench and production use coincide | A bug in the harness can break the loop that fixes it (ghost-seized issues, red main) |
| Factory in a separate repo, called by thin stubs | Copy workflows into each repo | One place to fix the loop; `fa` is one client | A mutable ref runs whatever is at head (accepted trade-off, documented) |
| Dispatch-only CI under an SM | CI on every push | Cheaper; controlled validation | Opaque to a casual contributor; depends on the SM being healthy |
| Different models for dev and review | Same model | Independent perspective | More keys and cost; both can still share blind spots |
| Rework cap (`MAX_AUTO_REWORK_ROUNDS`) | Unlimited | Stops endless loops | Stuck work escalates to a human |
| Label-based state and locks | A database | Visible in the GitHub UI; no extra infrastructure | Labels are mutable by anyone with write access; races handled by "first actor wins" |
| Bot App token for release pushes | PAT | Auditable bypass identity (gh-1402) | One more credential to guard |
| Constitution file instead of tribal knowledge | Rely on review | Agents obey a file they can grep | The file is huge, conflicts creep in, and it costs context on every run |
| Committed memory notes | Per-user memory only | Shared, versioned, reviewable | 861 notes accumulate noise; quality depends on pruning |
| Self-filed issues for flakes and red main | Humans triage | Continuous maintenance at machine speed | Issue noise; risk of fixing symptoms |

## 6. Theory behind it (the "lecture" part)

### 6.1 Autonomous software delivery: levels of autonomy
It helps to separate who does what: **assistant** (human drives, model suggests), **agent in the loop** (human approves each step), **agent on the loop** (agent proceeds, human monitors and can intervene), **agent out of the loop** (full autonomy within guardrails). This repo targets "on the loop" for routine changes: guardrails are required checks, caps, review by a second agent, and human-set goals and rules. The central design question is not "can the model code" but "what happens when it is wrong, and who notices".

*In my project:* Verdaca's deliberation loop (Course 2.4) is a smaller version: producer, independent reviewer, synthesizer, with typed outcomes and receipts.

### 6.2 Maker-checker and independent verification
Four-eyes controls require that the person who makes a change is not the one who approves it. With agents, "independent" has degrees: a different session, a different prompt, a different model family, a deterministic test. Strongest are checks that do not depend on a model's judgement (CI, merge bot). The loop uses all three levels: a second model reviews, deterministic gates run, a deterministic bot merges.

*In my project:* Course 2.7 recorded the limit: self-critique by the same model dropped hedges rather than finding errors.

### 6.3 Distributed locks, idempotence and reconciliation
A reconciler periodically compares desired and actual state and acts to close the gap (as in Kubernetes controllers). Because ticks can overlap or be dropped (GitHub drops scheduled runs; the merge bot exists because the cron tick is best-effort), actions must be **idempotent** and claims must be **exclusive** (a lock label, a concurrency group). Event triggers give speed; the periodic tick gives eventual correctness.

*In my project:* the SM tick plus the event-driven merge bot is a textbook split between a slow level-triggered reconciler and a fast edge-triggered path.

### 6.4 Least privilege for automation identities
Automation needs identities with just enough rights. GitHub Apps give fine-grained, short-lived tokens and a distinguishable author; personal tokens do not. Branch protection with required status checks plus a bypass for exactly one bot makes the exception auditable. Reusable workflows centralise logic but make the caller trust the callee's ref: pin by commit for stability, track `main` for speed, and know which one you chose.

*In my project:* the explicit permission blocks with comments explaining each grant are the practice to copy.

### 6.5 Constitution files and context cost
Agent instruction files (`AGENTS.md`, `CLAUDE.md`) turn conventions into something an agent can follow. Their cost is context: every line is paid for on every run and competes with the task. Practical rules from agent-building experience: keep the file short and specific, move detail into skills and docs loaded on demand (progressive disclosure, chapter 11.6), and test rules (a rule nobody tests drifts). A 134 KB file contradicts the first rule; the repo's own "no essays" principle is the correct one.

*In my project:* my `CLAUDE.md` for Foorilla is about 3 KB; the context-engineering template (Course 8) argues for the same split.

### 6.6 Measuring AI-driven delivery
To judge such a process you need outcome metrics, not activity counts: merged changes, cycle time, change failure rate, revert rate, review findings per PR, rework rounds, cost per merged change, and counter-metrics (flake count, red-main minutes). Counting AI-authored commits measures adoption, not value. Course 3 gives the method: unit of delivery = merged change, cost allocation, distributions rather than averages.

*In my project:* this repo is a ready-made case study for the Course 3 framework, with the caveat that I only have the top of the list.

# Course 17 - Chapter 17.5: Explanation validation and deterministic fallback

_Andrey Popov's project notes: how it works, why it was built this way, and the theory behind it._

**In short:** B-v1 checks complete bounded-English explanations against approved assertions, citations, qualifications and exact rule arithmetic. Wrong meaning causes whole-draft deterministic fallback. Demonstrations used constructed bytes and mock transport; callback limits are request-local, not real-provider exactly-once guarantees.

## 2. The problem (business view, plain English)

An explanation can cite the right report while changing a value, reversing an alert or dropping a material qualification. Checking whether a citation exists cannot establish what the sentence means. The prototype therefore allows a controlled English grammar, binds its complete meaning to approved evidence and replaces a rejected draft with a deterministic summary. It sacrifices expressive freedom to make a narrow assurance claim inspectable.

I defined specifications and key decisions and supervised AI-assisted implementation and review; I did not manually write every component. Retained demonstrations used the real framework with synthetic evidence, mock transport and constructed response bytes. Historical Databricks proof belongs to an earlier wheel; Fabric adapters are locally tested but actual integration remains unproven. Live LLM and Teams implementation remain deferred.

## 4. How it works (technical walkthrough)

```text
eligible evidence -> checked host plan -> optional callback
                          |                    |
                          |             original UTF-8 bytes
                          |                    v
                          +-> eight ordered validation passes
                               |                    |
                           all pass             any fails
                               |                    |
                       accepted sentences    complete local fallback
                               +----------+---------+
                                          v
                              checked, escaped final display
```

Paths identify implementation, not study commands.

1. `src/forecast/explanations.py:460` builds a plan with the routed request, evidence, assertion catalogue, required coverage, citations and qualifications. Host invariants are checked before the optional callback; the model cannot decide its own checklist.
2. At `:174`, canonical JSON is hashed into a context identifier. The callback receives approved meanings, grammar and required bindings, not raw source annotation text. The identifier binds the response to the current plan; it is not an authenticity signature.
3. `src/forecast/explanations.py:715` checks original bytes before decoding and parses JSON with duplicate-key rejection. It does not repair JSON, strip fences or silently retain the last duplicate key.
4. `:795` checks context, known assertions, coverage, citations, qualifications, whole-sentence parsing and semantic agreement after schema validation. `src/forecast/explanation_language.py:343` uses full matching to a selected production and creates a typed syntax tree.
5. `src/forecast/explanations.py:925` renders all required eligible facts on any draft rejection. `:881` retains qualifications and quoted unverified annotations in escaped display text. Raw drafts and intermediate framework events are not public answers.
6. `src/forecast/orchestrator.py:207` sets the callback latch before awaiting it. `src/forecast/io.py:828` is a caller-owned mock runtime with separate callback and send counters, a capped deadline and bounded cleanup.

The retained negative example changes fixture WAPE 0.36 to 0.63: semantic rejection leads to fallback. These are July 2026 synthetic fixture values, distinct from historical Databricks values around 0.298 and 0.324. The separate portfolio retrieval chatbot does not gain B-v1 sentence validation by sharing project content.

## 5. Why it was built this way (decisions and trade-offs)

| Decision | Alternatives considered | Why this one | Cost / risk |
| --- | --- | --- | --- |
| Bounded complete grammar | Citation checks; LLM judge | Deterministically inspect sentence meaning | Rejects useful unlisted paraphrases |
| Host-owned required assertions | Model chooses its summary coverage | Stops omission of material facts | Verbose output and rigid completeness |
| Whole-draft fallback | Retain valid-looking sentences; repair | One clear release rule | Loses good wording with bad wording |
| Original bytes, no repair | Parse and re-encode upstream | Preserve the actual validation subject | Integration adapters must preserve text |
| One optional local callback | Retry or alternate provider | Bounded local attempt policy | Lower availability of generated wording |
| Mock runtime first | Assume SDK behavior | Isolate deterministic lifecycle checks | Real HTTP behavior still unproven |

Local acceptance covers trusted bounded synthetic behavior. It does not establish unrestricted English verification, production ingestion safety or real-provider attempt counts. The 65,536-byte response limit is not a token budget or permission to ingest arbitrary external evidence.

## 6. Theory behind it (the lecture part)

### 6.1 Syntax, semantics and evidence binding

Syntax determines whether text belongs to a language. Semantics determines the proposition it expresses. Binding determines whether that proposition agrees with the eligible evidence. A JSON object may be structurally valid while saying the wrong model improved; a grammatical sentence may be internally consistent but cite another period. In this project, all three levels are required; correct structured metadata cannot overwrite contrary authored meaning.

### 6.2 Controlled language and its assurance boundary

A controlled language has explicit productions. A gate sentence includes candidate, threshold, baseline, relation, Boolean result and dates. A valid prefix followed by "so deploy immediately" must fail, even with correct numbers. Its typed parse tree exposes meaning for comparison. In this project, unsupported synonyms, extra clauses and causal business claims fall back; there is no arbitrary-English safety verdict.

### 6.3 Eight ordered checks

The pipeline is: (1) bytes/UTF-8/JSON/schema and size; (2) context; (3) known proposition and allowed realization; (4) topic and required assertion coverage; (5) exact citation sets; (6) exact qualification sets; (7) full sentence parse; (8) semantic and rule agreement. The first failure yields a fixed safe reason. Order prevents an unknown assertion from being treated as an ordinary missing requirement and avoids interpreting unbounded malformed text. In this project, a citation-correct wrong value reaches semantic rejection; an appended recommendation fails language parsing.

### 6.4 Context binding and canonicalization

Canonicalization fixes object-key order, array policies, decimal spellings and escaping; counts remain integers and decimal meanings avoid binary floating-point round trips. The digest covers request, evidence and assertion plan, excluding itself. A response for another plan fails even if its sentences look reasonable. Hash agreement establishes neither truth nor authorship. In this project, the host reconstructs and rechecks its own plan rather than trusting a digest alone.

### 6.5 Proof-carrying explanation, within a small domain

A useful analogy is proof-carrying data: text travels with proposition references, operands, citations and qualifications that a checker can verify. Gate logic uses `candidate <= 0.95 * baseline`, so equality passes. Monitoring uses strict `>` comparisons and OR, so equality alone does not alert. A sentence can contain correct numbers yet reverse "less than" or the Boolean result; both must match. In this project, exact arithmetic and complete meaning checks establish agreement with supplied evidence, not a proof that the upstream world was measured correctly.

### 6.6 Qualifications are part of meaning

"The model passed" differs materially from "this synthetic fixture's candidate passed its validation gate." Required qualifications preserve identity, time, acceptance scope and observed/inferred status. Their IDs are not enough: the host displays the corresponding local values beside accepted text. Untrusted annotations remain quoted and escaped, not promoted into factual narration. In this project, removing the synthetic or inferred qualification rejects the draft even if its core arithmetic is correct.

### 6.7 Atomic fallback and availability

Atomic release means the user receives a complete accepted draft or a complete deterministic replacement, never selected fragments of a rejected draft. Mixing fragments complicates coverage and can retain a misleading causal bridge between individually valid statements. Evidence eligibility is independent of wording availability: a timeout can preserve an answered evidence status while adding a provider limitation. A broken local plan instead produces a gap; fallback must be checked too. In this project, no retry or repair attempts to rescue a rejected explanation.

### 6.8 Local at-most-once versus distributed exactly-once

An asynchronous `await` yields control, so setting an invocation flag afterward creates a duplicate-entry window. Setting it before awaiting closes that window within the request's executor state. A restart loses memory; a duplicate inbound message can create a fresh executor. Durable idempotency needs persistent identity and state at appropriate effect boundaries. Callback entries, mock sends, HTTP requests and provider executions are also different counts. In this project, one local callback does not establish one real request, one charge or deduplication across Teams redelivery.

### 6.9 Deadlines, cancellation and late results

A deadline is a monotonic time boundary, not a guarantee that a remote operation never ran. The mock runtime includes setup and transport in `min(requested_timeout, 30 seconds)`, fixes timeout before cancellation, grants 100 ms cancellation grace and drains owned tasks for one second on shutdown. Cancellation is cooperative; an uncooperative in-process task may survive. Late results are cleanup-only, and caller cancellation propagates. In this project, the retained 10 ms cooperative mock demonstrates local timeout fallback; it does not measure real HTTP cancellation, exact elapsed time or provider billing.

## 8. Glossary

| Term | One-line definition |
| --- | --- |
| Controlled English | Restricted sentence productions with explicit meanings |
| Full parse | Entire sentence consumed by the selected grammar production |
| Syntax tree | Typed representation of what the authored sentence says |
| Intrinsic semantics | Whether a sentence's own arithmetic and relations are consistent |
| Evidence binding | Agreement of parsed meaning with the host's eligible assertion |
| Canonicalization | Deterministic encoding before comparing or hashing objects |
| Atomic fallback | Complete replacement of a rejected generated draft |
| Qualification | Mandatory local context preserving scope, time and evidence strength |
| Deadline | Time boundary after which an outcome cannot become a successful answer |
| Mock send | Dispatch into the injected offline client, not a real HTTP request |

# Course 11 · Chapter 11.7: Quality gates that a machine can enforce

_Andrey Popov's project notes: how it works, why it was built this way, and the theory behind it._

**In short:** How the repo enforces quality by machine: CRAP formula and ratchet with worked numbers, file-size ceiling, duplication, coverage, golden tests, parity guards, deterministic CI with a mock LLM server, flake quarantine, auto-release, and Terminal-Bench benchmarking via Harbor.

## 2. The problem (business view, plain English)

A codebase of 185,000 lines in the core alone, written to a large part by AI agents working in parallel, drifts fast. Nobody reads every diff. The usual human safeguards (review, taste, memory of why a rule exists) do not scale to dozens of agent-authored pull requests a day. The answer here is to turn every rule that can be turned into a script into a script that fails the build: size of files, complexity versus coverage, duplication, formatting, lockfiles, goldens, parity between app and CLI, and the boundary between deterministic and live-model tests.

Finance analogy: pre-trade and end-of-day controls. Hard limits that block the ticket (gates), limits that can only be tightened and never loosened without a documented exception (ratchets), and reconciliations that must tie out before sign-off (parity checks).

## 4. How it works (technical walkthrough)

### 4.1 The gate list
Every commit, locally through `scripts/pre-commit` (a thin wrapper) and in CI through the same `ci_fast_gate.sh` stages, must pass:
| Gate | Rule | Protects against |
|---|---|---|
| format | `dart format` self-heals staged files; a blocking backstop remains | style noise, merge conflicts |
| analyze | `dart analyze` clean (explicit directories) | type and lint errors |
| tests | `dart test`, deterministic only, sharded | regressions |
| coverage | line coverage of `lib/` ≥ 80% (full ratchet on main; PRs ratchet changed lines via `diff_coverage.py`) | untested code |
| CRAP | per-method score ≤ threshold, ratchet pinned at the current maximum (12.0 core, 30.0 app) | complex untested methods |
| size | no `.dart` file over 2,800 lines (crap4dart `loc` gate; target < 2,000) | god files |
| duplication | jscpd < 1% core, < 3.7% app, cross-module "dupx" baseline 0.31% | copy-paste |
| goldens | UI changes need golden tests; `check_goldens.py` fails on missing coverage and on **orphan** snapshots | unreviewed visual change |
| parity | every shared setting exists on CLI and app or has a written exemption (`parity` tests) | "CLI got X, app didn't" |
| lockfiles | seven lockfiles committed and enforced; pod-sync checks; path-pin version sync | irreproducible builds |
| prompts | `prompts.g.dart` must match the Markdown prompts | stale generated code |
| action pins | `check_action_pins.sh` (GitHub Actions pinned to commit SHAs) | supply-chain drift |
| changelog size | pub.dev rejects packages over a size cap; `check_changelog_size.sh` guards the 256 KiB limit | failed release (issue gh-1452) |

CI path classification: docs-only changes run size and analyze; `lib/`, `bin/`, `test/` changes add tests, coverage, CRAP and duplication; `flutter_app/` and `packages/` add the Flutter stages; unknown paths run everything ("safe default"). The same classifier runs in the hook and in CI (`ci_fast_gate.sh --dry-run`), and both print `GATE_STAGE <name> OK|SKIP` markers so their outputs can be diffed for parity.

### 4.2 CRAP, with numbers
The **CRAP** score (Change Risk Anti-Patterns; Savoia and Evans) combines cyclomatic complexity CC and test coverage cov (0 to 1) for one method:

`CRAP = CC² × (1 − cov)³ + CC`

Worked examples (my calculation):
| CC | coverage | CRAP |
|---|---|---|
| 3 | 0% | 3²×1 + 3 = **12.0** |
| 9 | 100% | 9 |
| 12 | 100% | 12 |
| 12 | 50% | 144×0.125 + 12 = **30.0** |
| 20 | 80% | 400×0.008 + 20 = 23.2 |
| 20 | 0% | 400 + 20 = 420 |

This explains the repo's own comment (*CRAP* lines 14-34): the whole-tree measurement found "54 methods at exactly 12.00 (the CC-3 at 0% tier + fully covered CC-12 dispatchers) and 83 at 9.00 (CC-9 at 100%)". Those are exactly the first, third and second table rows. A fully covered method scores CC, so to get the maximum below 12 you must split any method with CC above 11 and cover trivial methods. The comment also records the earlier worst value, 356.34 (`_handleKey` in the TUI), and the app's "ladder" of milestones, from 2450 down to 30.

**Ratchet** means: the threshold equals the current worst score and may only go down; `check_crap_guards.py` rejects a PR that raises it relative to the base ref, except through a documented `# raise-issue: gh-N` comment tied to an open restore issue. It also checks that the README badge equals the config and that the generated-code excludes are identical across the two packages.

### 4.3 Deterministic CI: no live models in the merge path (gh-1199)
"The Quality gate is deterministic-only: mock LLM everywhere, live models never." Real-provider test files carry tags `@Tags(['integration','llm'])` and run only in a tag-only provider-smoke job and in the nightly with secrets. A script `check_llm_tag_boundary.py` fails any integration-tagged file that looks live without the `llm` tag, and a test proves the shard selection stays live-free. No-key integration tests use a local `MockLlmServer`. Real-model verification belongs to the benchmark harnesses run under supervision.

### 4.4 Sharding, durations and flaky tests
- `test-core` runs in several shards balanced by recorded **durations** (`scripts/test_shards.json`, rebalanced weekly by a workflow from junit timing); a runtime packer places new test directories missing from the manifest.
- A **flake** is a test red in at least two distinct-SHA gate runs within 24 hours; it is **quarantined** via a checked-in `scripts/test_quarantine.json` after review. A `flake-watch` workflow files the issue and opens the PR; nightly keeps running the quarantined file to produce "un-quarantine" evidence.
- A `watchdog` job flags legs slower than twice baseline; a timed-out leg gets one **empty-commit retrigger**, never `gh run rerun` (which would reallocate into the same degraded runner pool).
- Runner policy: pure-Dart and terminal (PTY) jobs run on ARM Linux runners; a single self-hosted Mac runner is reserved for macOS-only work (*CI* lines 1-10).

### 4.5 Golden tests and the UI
Any change under `flutter_app/lib/` is incomplete until golden tests are right: coverage first (new widget file, new golden test and a map entry in a guard test), real fonts, full-frame snapshots (1280×800 desktop, 390×844 phone) with realistic content, determinism, and a rule to "open every changed PNG" after regenerating. The store screenshots for App Store and Play are committed goldens too, with size and aspect-ratio rules enforced by tests (Play rejects a 10:16 image, for example).

### 4.6 Parity and capability tests
`lib/src/parity/settings_registry.dart` lists shared settings; `dart test test/parity/` fails if a setting is on one platform only without an exemption and a reason. The capability matrix completeness test does the same for host wiring (chapter 11.6). The wire protocol has golden fixtures per version (chapter 11.6).

### 4.7 Release as part of the gate
Every push to `main` auto-releases a patch version to pub.dev (`scripts/auto_release.sh`, version `1.0.<counter>`), authored by a release-bot GitHub App whose token alone can push past the protected-branch rules (a PAT or the default token cannot pass the required checks, gh-1402). A scheduled catch-up release runs every two hours because pub.dev caps publishes per day. Binaries build per tag, with an installer smoke test. The 256 KiB changelog cap broke a release once (gh-1452) and now has a pre-flight guard.

### 4.8 Benchmarks: how the harness is measured
- `Bench Harbor` runs the **Terminal-Bench** family (2.0, 2.1, 3.0, 4.0) through the Harbor CLI with a custom agent adapter `bench/harbor_fa/fa_agent.py` (uploads the built `fa` bundle into the task container, runs `fa -p "<instruction>"`). The default is 5 attempts per task, as the leaderboard protocol asks. Dataset ids are resolved and validated; `@latest` is mutable, so the resolved content hash is recorded with the run date.
- A **ledger** records `dataset / model / fa commit / date / resolved-of-attempted / cost / run URL`. Cost uses `bench/pricing.json`.
- The **legacy** run on `terminal-bench-core 0.1.1` with `glm-5.3-flash` gave 26 of 80 tasks (32.5%); harness-side failure clusters are tracked in an issue. Dataset rot is repaired by a patch script after each fresh download.
- Supporting tools: `post_mortem_usage.py`, `fa_usage.py`, per-task test-budget override tables with a "planner fairness guard" (gh-1407), the stall sentinel's payload replay (chapter 11.2), and the FinalizeGate near-miss data (chapter 11.3). A second benchmark, MLS-Bench, has its workflow live and no scores yet.

## 5. Why it was built this way (decisions and trade-offs)

| Decision | Alternatives considered | Why this one | Cost / risk |
|---|---|---|---|
| Ratchets (thresholds only fall) | Fixed targets; periodic cleanup sprints | Never gets worse; progress is automatic and reviewable | Reaching a target can take years; the threshold sits at the current worst method |
| CRAP instead of coverage alone | Coverage % only | Targets the dangerous combination: complex and untested | Needs a tool and an lcov per package; gameable by trivial tests |
| God-file ceiling of 2,800 lines | Review taste | Mechanical, agents obey it; split by `part` files, not new public API | Splits can be cosmetic (a `part of` file is the same library) |
| Same script in hook and CI | Separate hook and CI configs | Parity; diffable markers | Slow hook unless path filters are good |
| Deterministic-only merge path | Run live-model tests on PRs | A model's mood must not block a merge | Real regressions found later (nightly, bench) |
| Quarantine with proof | Retry until green | Keeps the gate honest, forces a fix PR | Quarantined tests lose protection meanwhile |
| Dispatch-only CI on PRs | Run on every push | Cheaper, controlled by the SM | Less transparent; depends on an orchestrator workflow |
| Release on every push to main | Manual releases | Continuous delivery; small increments | Many versions (551 at v1.0.551), store/pub caps, consumers need pins |
| Benchmark with a public leaderboard dataset | Own task set | External comparability | Dataset rot, cost, scores not yet published in the doc |

## 6. Theory behind it (the "lecture" part)

### 6.1 Cyclomatic complexity
Cyclomatic complexity (McCabe, 1976) counts linearly independent paths through a method: `CC = E − N + 2P` on the control-flow graph, or in practice 1 + number of decision points (`if`, `case`, loops, `&&`, `||`, `catch`). It is a proxy for the number of tests needed to cover all branches and for how hard the code is to understand. Common guidance is to keep methods under about 10. A large `switch` dispatcher has high CC but low cognitive load, which is a known weakness of the metric.

*In my project:* the repo's CC-12 "dispatchers" were split into sub-dispatchers, which lowers CC at the cost of more functions.

### 6.2 CRAP and risk-based thresholds
CRAP is a heuristic for "how risky is it to change this method": high when it is complex and poorly covered; equal to CC when fully covered. It rewards *covering* a hot spot as much as *simplifying* it. Limitations: coverage measures execution, not assertion strength; a test that calls a method and asserts nothing lowers the score without protecting anything.

*In my project:* the finance parallel is a risk-weighted limit, not a flat one.

### 6.3 Ratchets and Goodhart's law
A ratchet encodes progress as a one-way constraint. It works because it needs no judgement on any given day: the number cannot rise. The risk is **Goodhart's law**: when a measure becomes a target it ceases to be a good measure. Agents optimising a gate will happily add trivial tests or split methods cosmetically. Countermeasures: several different metrics (coverage, CRAP, duplication, size), human review of the gate configuration itself (the reason for `--only-down` and documented raises), and periodic independent evaluation (the benchmark).

*In my project:* Course 2.6 ("false green", what a test does not prove) is the same point.

### 6.4 The test pyramid, determinism and flakiness
Fast deterministic unit tests at the base, fewer integration tests above, few end-to-end tests on top. A flaky test passes and fails on the same code; the cost is lost trust, so teams quarantine and fix. LLM-calling tests are *non-deterministic by nature*, so a sound design isolates them: mock the model for logic tests, and evaluate real models in a separate, statistical pipeline (benchmarks with repeated trials, as here: 5 attempts per task).

*In my project:* in the LangGraph routing eval (Course 7.3) I separated labelled-set evaluation from unit tests for the same reason.

### 6.5 Golden (snapshot) testing
A golden test compares output to a committed reference file (here, PNG images of widgets). It catches unintended visual change cheaply, and its failure mode is "update and move on" without looking. The repo's rules (open every changed PNG, full frames, fixed data, no orphans) are the human-discipline layer on top.

*In my project:* the same weakness applies to any snapshot test.

### 6.6 Benchmarks and trials
A benchmark measures a system on a fixed set of tasks. Agent outcomes vary between runs, so reports use several trials per task and a pass rate (here **resolved / attempted trials**). Comparisons need the same dataset version, model, harness commit, and time budget; a "mutable latest" dataset breaks that, hence recording the content hash. Terminal-Bench scores model plus harness together, which is why harness engineering (chapters 11.2 and 11.3) can move the score.

*In my project:* Course 3.1 explains why "felt faster" is not evidence; a benchmark ledger is the harness-level answer.

### 6.7 Supply-chain hygiene
Pinning GitHub Actions to commit SHAs, committing lockfiles, and using a GitHub App token instead of a personal token reduce the blast radius of a compromised dependency or leaked credential. Required status checks plus a bot with bypass rights is a standard but delicate pattern: auditability depends on the bot identity.

*In my project:* the rule "any automation that pushes release-path changes must use the App token" is spelled out in `AGENTS.md`.

## 8. Glossary

| Term | One-line definition |
|---|---|
| Quality gate | A check that must pass before a commit or merge |
| Ratchet | A threshold allowed only to improve |
| CC | Cyclomatic complexity: number of independent paths in a method |
| CRAP | `CC² × (1 − cov)³ + CC` per method |
| `crap4dart` | The Dart CRAP analyser by the repo owner, also enforces a file-size `loc` gate |
| jscpd | Copy-paste detector; reports duplication % |
| dupx | Cross-module duplication check across package roots |
| Shard | One slice of the test suite run in parallel |
| Quarantine | Listing a proven flaky test so it no longer blocks merges |
| Golden test | Test comparing output to a committed reference |
| Orphan snapshot | Committed golden file no test references |
| Parity guard | Test that shared settings exist on all platforms or are exempted |
| `MockLlmServer` | Local fake model endpoint for deterministic integration tests |
| `llm` tag | Marks tests that call real providers; excluded from merge gates |
| Harbor / Terminal-Bench | Framework and task family for benchmarking terminal agents |
| Ledger | Table of benchmark runs with dataset, model, commit, score, cost |

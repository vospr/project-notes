**In short:** How the workflow was exposed to Claude Desktop through an MCP server: FastMCP, six tools, stdio transport, logs redirected to a file. Called once end to end from Desktop (27 s, about $0.03); this path has no per-user auth.

## 2. The problem (business view, plain English)

A governed answer is only useful if people can ask for it where they already work. Claude Desktop is a chat app that can call external "tools" through a standard protocol. If Verdaca speaks that protocol, a user can ask Claude Desktop a question and Desktop can call Verdaca to produce a receipt.

Finance analogy: a standard payment-message format (a bank connector). Any front end that speaks the format can submit a payment instruction. The format does not itself decide who may pay or how much; that is the job of the bank's own checks. MCP is the message format; authorisation and limits still have to be built.

## 4. How it works (technical walkthrough)

```
Claude Desktop (host)                       MCP client inside Desktop
   |  reads config, spawns subprocess:  uv run ... scripts/live/deliberate_mcp_server.py
   |                          stdin/stdout = JSON-RPC 2.0 messages (one per line)
   v
FastMCP server "verdaca-mcp"   <- create_verdaca_mcp_server(deliberator=...)   server.py:23
   initialize -> tools/list (6 tools) -> prompts/list -> resources/list      (log: 4 requests at each start)
   tools/call verdaca_deliberate(question, evidence[])
        -> deliberator -> IterationController.run_deliberation  (2.4) -> 4 LiteLLM calls (2.3)
        -> writes docs/receipts/receipt-<id>.json, returns {"receipt": {...}, "receipt_path": "..."}
   logs go to docs/receipts/mcp-server.log (stdout is the protocol channel)
```

**FastMCP.** `FastMCP(name, instructions=..., stateless_http=True)` is the decorator-based Python server from the official MCP SDK (`from mcp.server.fastmcp import FastMCP`, pinned `mcp==1.27.0`). A function decorated with `@server.tool(name=..., description=..., structured_output=True)` becomes a tool; the SDK builds the JSON input schema from the Python type hints and validates calls against it (`MCP tools.py:177-186`). Resources and prompts use `@server.resource` and `@server.prompt` (`resources.py:106-162`, `prompts.py:10-24`).

**Tool surface.** Five original tools: `verdaca_start_analysis`, `verdaca_estimate_cost`, `verdaca_get_result`, `verdaca_list_sessions`, `verdaca_get_artifact`; five resources (`verdaca://methodology`, `verdaca://templates`, session summary, transcript, artifact); one prompt. A sixth tool, `verdaca_deliberate`, is registered only when a deliberator is passed in (`tools.py:175-186`); a test checks the default server still lists five (AC11 in the live-wiring suite; README table). The adapter never imports the MAC kernel: the deliberator is injected as a callable (`tools.py:40-42`).

**Why gateway tools use a worker thread.** FastMCP runs sync tools on the event-loop thread, but the kernel's `execute` uses `asyncio.run` and refuses to run inside a loop. The fix: make the tools `async` and call `anyio.to_thread.run_sync(gateway.execute, ...)` (`tools.py:1-16, 220`). This is also why the runtime composition uses an in-memory nonce store (2.

**Transports.** *stdio:* the client launches the server as a child process and exchanges newline-delimited JSON-RPC over stdin and stdout; `stdio.py:13-26` and the script call `run("stdio")`. Because stdout is the protocol channel, nothing else may print there, so logging is redirected to a file (*DMS* docstring and `main`). *Streamable HTTP:* one endpoint `/mcp`, `stateless_http=True` so each request stands alone (`http.py:38-57`; `test_stateless_http_invariant.py`). The port `MCPTransportPort` declares both (`transport.py:8-18`).

**The one recorded Desktop call** (`mcp-server.log`, committed lines): `16:44:38` `CallToolRequest`; `verdaca_deliberate called: question=… evidence_ids=['E1','E2','E3','E4']`; four `LiteLLM completion` lines in order haiku, sonnet, sonnet, haiku; `16:45:06` `done: outcome=answer reason=None calls=4 cost_usd=0.031389`. ## 6. Theory behind it (the "lecture" part)

### 6.1 The Model Context Protocol
MCP (introduced by Anthropic in late 2024, open specification) standardises how an AI application connects to external capabilities. Roles: **host** (the app the user sees, e.g. Claude Desktop), **client** (a connector inside the host, one per server), **server** (a program that exposes capabilities). Messages are JSON-RPC 2.0: requests with an `id`, responses, and one-way notifications. A session starts with `initialize` (client and server exchange protocol version and capabilities), then the client sends an `initialized` notification, then normal calls. Three server primitives: **tools** (functions the model can call, chosen by the model; the host normally asks the user to allow them), **resources** (readable data identified by URI, chosen by the application), **prompts** (templates the user can pick). Tool calls return content plus optionally *structured output* matching a JSON schema.

*In my project:* five tools, five resources and one prompt, plus `verdaca_deliberate`; the log shows `ListTools`, `ListPrompts`, `ListResources` at each start (`mcp-server.log`).

### 6.2 Transports: stdio and Streamable HTTP
**stdio:** the host spawns the server as a subprocess; messages are newline-delimited JSON on stdin and stdout; stderr may carry logs. Pros: no network, no port, simple. Cons: one client, local only; the server inherits the user's permissions and environment, so it is trusted code. **Streamable HTTP:** a single HTTP endpoint accepting POST (and optionally server-sent events for streaming); can be stateless. It needs authentication; the spec's standard is OAuth 2.x-based authorisation (revised in later versions; the review cites the 2025-11-25 revision as adding standard authorisation and elicitation). Rule for stdio: **never write non-protocol bytes to stdout**; one stray `print` corrupts the stream.

*In my project:* Desktop used stdio; HTTP exists but has a different tool set and no wired bearer check.

### 6.3 FastMCP and schema from type hints
FastMCP is a high-level Python layer: decorate a function, and the framework derives the tool's name, description and JSON Schema from its signature and docstring, handles the protocol plumbing, validates inputs, and serialises outputs. The schema quality is the quality of your type hints: `list[dict[str, str]]` accepts any list of string dicts, so required keys are not enforced by the schema; a Pydantic model would make `id`, `source` and `text` required and produce a precise error to the model. FastMCP v1 ships inside the official SDK; a separate, extended `fastmcp` package also exists (I did not check which features differ).

*In my project:* `evidence: list[dict[str, str]]` (`tools.py:183-186`).

### 6.4 Tool design for LLM callers
The caller is a language model that reads your tool description and writes the arguments. Good tool design: precise names and descriptions (the project even tests that descriptions avoid forbidden phrases, `test_mcp_tools_contract.py:104-123`); small required arguments; typed schemas; error messages the model can act on; idempotent or clearly side-effecting behaviour; return data that is compact enough for the context window. Because the model transcribes arguments, **byte-exact fidelity is not guaranteed**, and any record built from arguments records the transcription.

*In my project:* the Desktop run's pasted text changed in whitespace (README).

### 6.5 Trust, consent and the confused deputy on MCP
A tool call is the model acting on the user's behalf with the server's credentials. Controls sit at three places: **host consent** (user approves each call), **server authentication/authorisation** (who may call, limits), **content trust** (tool results and resource text are untrusted input that may carry prompt injection). The server is a "deputy" with a key (here the owner's Anthropic API key): without its own checks, any approved call spends that key.

*In my project:* consent is Desktop's; the server has no caller identity and no spend cap; the receipt does not record who called.

### 6.6 Evidence from a single integration run
One successful run of a tool shows the plumbing works end to end once: config, spawn, handshake, schema, call, result. It does not show reliability (repeatability), safety (auth, limits), or quality (answer correctness). State the claim at exactly that strength: "called once from Claude Desktop; receipt and log in the repo".

*In my project:* README table: "run once from Claude Desktop over stdio".

## 8. Glossary

| Term | One-line definition |
|---|---|
| MCP | Model Context Protocol: open standard for connecting AI apps to tools and data |
| Host / client / server | App the user sees / connector inside it / program exposing capabilities |
| JSON-RPC 2.0 | Request/response message format MCP uses |
| Tool | A callable function the model can invoke |
| Resource | Readable data addressed by a URI |
| Prompt | A reusable message template offered by the server |
| stdio transport | Server runs as a child process; JSON lines over stdin/stdout |
| Streamable HTTP | HTTP transport with a single `/mcp` endpoint, optionally stateless |
| FastMCP | Decorator-based Python framework for MCP servers |
| Structured output | Tool result validated against a JSON schema |
| `initialize` | First request: version and capability negotiation |
| Deliberator | Callable injected into the adapter that runs a deliberation |
| Worker-thread bridge | `anyio.to_thread.run_sync` call that lets sync kernel code run outside the loop |
| Elicitation | MCP feature letting a server ask the user for input or approval |
| O-7 | Finding: MCP path carries no per-user bearer token |

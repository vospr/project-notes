## 2. The problem (business view, plain English)

Regulated users need to know who asked, that the request was not replayed, and that spending is capped, all before any money is spent on a model call. The gateway is the one door every channel (MCP, Teams, Slack) goes through, so the checks live in one place.

Finance analogy: a payment authorisation chain. First the card is verified (identity). Then the one-time authorisation code is checked so a captured message cannot be re-sent (replay). Then the credit limit is checked on the account that actually pays. "Spend-blind" is what happens if the limit is checked on one account while the purchases are charged to another: the limit never moves, and every check passes.

All steps 1-4 happen before any model call (`service.py:69-73`). Failures are wrapped into typed gateway errors (`service.py:175-176`).

**Step 1: identity.** `_extract_kid_from_bearer` reads the unverified header only to get `kid` (`oidc.py:39-61`). `JwksCache.get_key(issuer, kid)` returns the matching public key, refreshing the JWKS once if the `kid` is unknown (`oidc.py:141-151`). `JwtVerifier.decode` verifies signature and `aud` with authlib (`jwt.py:60-74`). Algorithms are an allow-list of RS/ES families; "none" and HMAC are excluded (`jwt.py:20-22`), and construction fails if the IdP advertises none of them (`jwt.py:43-52`). There is no static-key fallback; the earlier fallback was called a "CVE-class" bug and removed (`jwt.py:1-8`). Required claims: `sub, iss, aud, iat, exp` (`claims.py:29`). I found no explicit check that `iss` equals the configured issuer; trust comes from the signature under that issuer's key (my reading).

**Step 2: replay.** `nonce` or `jti` from the claims is inserted into a SQLite table with a primary key and a 600 s TTL; a duplicate raises `NonceReplayError` (`nonce.py:20-68`, `service.py:211-219`). The insert runs in `BEGIN IMMEDIATE` so two concurrent duplicates cannot both pass.

**Step 3-4: budgets and policy.** `enforce_budget` uses the OIDC `sub` as the virtual-key alias and asks LiteLLM whether the key is over budget (`policy.py:60-70`). It fails closed (raises) if no virtual-key adapter is configured. In production `policy_health_check` refuses to start without one (`policy.py:99-134`). The allow-list rejects everyone by default (`policy.py:137-144`). Budget caps are optional.

**Step 6: the call.** `max_tokens=1_024`, `temperature=0.0` (`service.py:132-133`). Compare the deliberation path in 2.3-2.4, which does not use this gateway.

**Why "spend-blind" happened (reconstructed from the sources).** Two decisions made independently: (1) the LLM substrate became the LiteLLM *library* called in-process, after the Docker sidecar was tried and dropped (`adapters/litellm/.../adapter.py:1-12`); (2) per-subject budgets were built as LiteLLM *proxy* "virtual keys" (`virtual_keys.py`). Virtual keys only meter requests that pass through the proxy. The first decision removed the proxy from the model path, and the stubbed demo path hid it because the stub never rejects (``). The test that found it is named for the control it breaks (CC6.7-c). Why nobody caught it earlier: not in the sources.

## 5. Why it was built this way (decision table)

| Decision | Alternatives | Why this one | Cost / risk |
|---|---|---|---|
| Auth before everything, in one gateway | Per-channel auth | One place to audit; channels stay thin | One door means one lock; throughput 1 |
| Resolve keys from JWKS by `kid`, no static key | Pin one public key | Provider rotation without redeploy (`jwt.py:1-8`) | Cache TTL vs revocation |
| Allow-list of asymmetric algorithms | Trust header `alg` | Blocks alg-confusion and `alg: none` (`jwt.py:20-22`) | Rejects IdPs offering only HS256 |
| Nonce store in SQLite (WAL) | Redis | No extra service for a solo project | Single node; in-memory in runtime |
| Per-subject budget via LiteLLM virtual keys | Own ledger only | LiteLLM already offers budgets and TPM/RPM caps | Spend-blind |
| Fail closed on missing config | Warn and continue | Misconfiguration surfaces at startup in production (`policy.py:121-128`) | Dev needs the stub profile |
| Deferrals recorded as tests | A markdown list | Cannot silently disappear; meta-tests fail if a caveat is empty (`test_stage14_deferred_register.py:112-150`) ||

## 6. Theory behind it (the "lecture" part)

### 6.1 Authentication, OAuth 2.0 and OpenID Connect
OAuth 2.0 (RFC 6749) delegates *authorisation*: a client gets an access token for a resource. OpenID Connect adds an identity layer on top: an **ID token**, a signed JWT that says who authenticated (`sub`), who issued it (`iss`), for which client (`aud`), when (`iat`, `exp`). Providers publish a **discovery document** at `/.well-known/openid-configuration` with `issuer`, `jwks_uri` and supported signing algorithms. An **issuer** is the identity provider; a **tenant** is one customer's directory inside it.

*In my project:* `discover` fetches that document (`idp.py:15-44`); the gateway only validates tokens, it never logs users in.

### 6.2 JWT and JWS
A JWT is `base64url(header).base64url(payload).signature`. With JWS the signature covers header and payload. Standard claims (RFC 7519): `iss, sub, aud, exp, nbf, iat, jti`. Checks a verifier must make: signature with the right key and an allowed algorithm; `aud` equals me; `exp` in the future; `iss` is who I trust. Known attacks: `alg: none` (no signature), and algorithm confusion (RS256 public key used as an HMAC secret). Defence: choose the algorithm from your own allow-list, never from the token.

*In my project:* `_ALLOWED_ALGORITHMS` (`jwt.py:20`); `aud` enforced via `claims_options` (`jwt.py:68`).

### 6.3 JWKS and key rotation
A **JWKS** is a JSON list of public keys, each with a `kid` (key id). The token header names its `kid`, so the verifier picks the right key. Providers rotate keys: publish new, sign with new, retire old. A cache must therefore (a) serve from memory, (b) refresh on unknown `kid`, (c) expire on a TTL. The trade-off: a longer TTL is cheaper but keeps retired keys valid longer; refresh-on-miss without rate limits lets attackers force fetches.

### 6.4 Replay attacks and nonces
A replay re-sends a valid captured message. Defences: one-time identifiers (nonce, `jti`) stored until the message expires; short token lifetime; binding to a channel or key. The store must keep each ID at least as long as the token can still be accepted. Formally, if tokens are valid for T seconds and the store keeps IDs for TTL, replay safety needs TTL ≥ T plus clock skew. Replay protection is separate from **idempotency**: a replay is an attacker re-using a message; an idempotent retry is a client deliberately repeating a request and expecting the same answer. They need different identifiers (token ID versus request key).

*In my project:* TTL is 600 s (`nonce.py:26`). I found no check that this is ≥ the real token lifetime. The code uses `idempotency_key` for retries, but the nonce is consumed first.

### 6.5 Budgets, quotas and the metering point
To cap spend you need a **meter** on the path that spends, and a **gate** that reads it. Control theory in one line: you cannot regulate a quantity you do not measure. Typical designs: a proxy in front of the provider that counts tokens and money per key; or the caller records cost after each call into a ledger and checks it before the next. Both have a race: concurrent calls can all pass the gate before any cost is recorded, so a hard cap needs reservation, and a soft cap is "approximately enforced".

*In my project:* the virtual-key meter is not on the model path; the local ledger meter is, but its caps default to none.

### 6.6 Fail-closed and defence in depth
Fail-closed: if a control cannot be evaluated, deny. Defence in depth: several independent layers (identity, replay, budget, allow-list) so one failure is not fatal. It fails if the layers share a blind spot, such as the same missing meter.

*In my project:* missing virtual-key config raises (`policy.py:68-69`); the allow-list denies all by default.

### 6.7 Egress topology and the confused deputy
A control only governs the traffic that passes through it. If a service holds a powerful shared credential (here a static per-provider API key) and different users reach it, the service can be tricked or simply mis-account for who used what: the "confused deputy" pattern. Per-tenant outbound credentials are the remedy.

*In my project:* the outbound model key is one static per-provider key, not per tenant (`RG` ledger, "NOT per-tenant outbound credential", CC6.7-c).

## 8. Glossary

| Term | One-line definition |
|---|---|
| OIDC | OpenID Connect: identity layer on OAuth 2.0 using signed ID tokens |
| IdP / issuer | The identity provider that signs tokens; `iss` names it |
| JWT | Signed JSON token: header, claims, signature |
| JWS | The signing format a JWT usually uses |
| JWKS | JSON list of the issuer's public keys |
| `kid` | Key id in the JWT header; selects the JWKS key |
| `aud` | Audience: who the token is for |
| `jti` / nonce | One-time token identifier used for replay detection |
| Replay attack | Re-sending a captured valid message |
| Idempotency key | Client-chosen ID so a retried request has one effect |
| Virtual key | A LiteLLM proxy credential with its own budget and rate limits |
| Spend-blind | The budget gate reads a meter that does not see the real spend |
| Fail-closed | Deny when a control cannot be evaluated |
| WAL | SQLite write-ahead log mode; also the name of the gateway's idempotency store |
| Composition root | The place that picks real or stub dependencies (see 2.1) |
| O-9, O-11, CC6.7-c | Deferral IDs in the register: nonce thread-affinity, throughput 1, spend-blind |

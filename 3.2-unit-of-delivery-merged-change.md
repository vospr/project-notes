# Course 3 · Chapter 3.2: Unit of delivery = merged change: why "Done" overstates, the PR lifecycle

_Andrey Popov's project notes: how it works, why it was built this way, and the theory behind it._

**In short:** Defines the unit of delivery as a ticket with a merged pull request; on a first sample the Done column overstated delivery by about 20%. Covers the PR lifecycle, vote-proxy review timing and reporting distributions, not per-PR averages.

## 2. The problem (business view, plain English)

The programme wanted cost per delivered unit of work. "Delivered" needed a definition that did not depend on a human setting a status. On the board, a ticket can be closed as not planned, closed after a research spike, or marked complete while its only PR was never merged. Counting closed tickets would count all three as delivery.

On the first sample of tickets that carried recorded AI spend, the board's Done column overstated real delivery by about 20%. So the unit became: a ticket with at least one linked PR **merged to the main branch**. A merge is machine-countable from one API, needs no human judgement, and is the control point the workflow already gates.

Finance analogy: revenue recognition. "Booked" is a status (Done). "Invoiced" is closer (merged). "Cash received" is the real outcome (running in production and used). A CFO who reports booked orders as revenue overstates the year. I picked "invoiced" because it is observable; I did not claim "cash".

## 4. How it works (technical walkthrough)

```
 board status        ticket ──closes── PR(s) ──► merged to main?  ── yes ─► "delivered" bucket
 (Done / closed)                                      │
                                                      └─ no ─► open / closed without delivery bucket
                                                               (spend stays in the numerator)

 PR lifecycle (ADO collector):   created ── votes/threads ── closed(completed)
                                    │            │                 │
                                    └─ lifetime = created→closed  ─┘
                                    └─ first qualifying vote = created→earliest non-author vote
```

**Cost side (GitHub repository).** A ticket row is `delivered` only if at least one linked PR merged to main. A closed-unmerged PR does not qualify. Research and open work stay visible in their own buckets. Spend on open work remains in the numerator: 7 of the 24 sampled tickets were open. In the first result, about two-thirds of the allocated spend (roughly 70%) sat on the 12 delivered ticket rows; the rest was on open work, one ticket closed without August delivery, and a little measurement work (; exact amounts deliberately not copied).

**Delivery context captured.** `mergedAt` (UTC), changed files, additions and deletions. Size is shown as bands and context. It is never cost per line, because line count is gameable and rewards verbose output. August PR size ranged from 1 to 19 changed files, median 7.

**Why the per-PR average was retired.** PR size varied from a one-file, 8-line change to a 19-file and a 16-file change. The lead pointed out the same thing: a one-line fix and a multi-week feature each count as one change, and the blended story-point figure already existed.

**Forward PR-flow side (ADO collector).** Reads *completed* PRs whose `closedDate` falls in a half-open UTC window, pages through them twice and reconciles the two ID sets, then reads every PR's thread history. For each PR it classifies the vote evidence into one of eight classes and computes two durations: creation to close, and creation to the earliest qualifying vote (a non-zero `VoteUpdate` by a non-author, non-container identity). It emits sanitized rows only: no identities, titles, comments or URLs.

**Results (shape, not client numbers to publish).** Each monthly closure cohort held several hundred completed PRs (about 800 in August, a little fewer in September). About 91% of the August cohort and 94% of the September cohort had a qualifying vote. The eight classes sum to the cohort in both months. I checked this myself against the report tables.

**Forward capture on the GitHub side.** A local event store records phase start, pause, resume, finish and an explicit `reviewer_start`. A read-only observer collects the PR's created, ready-for-review, merge and approval times and counts review rounds. An approval counts only if its reviewed commit equals the PR head. A comment that was later edited does not count as a response. Phase-boundary and reviewer-start capture are manual commands; no automatic hook exists in the inspected configuration.

## 5. Why it was built this way (decisions and trade-offs)

| Decision | Alternatives | Why this one | Cost / risk |
|---|---|---|---|
| Unit = ticket with a merged PR | Closed ticket; closed-as-completed; story points | Observable from one API, no human status needed, the workflow already gates the merge | Misses tickets delivered without code; merged is not deployed |
| Keep non-delivering spend in the numerator | Drop it | Dropping flatters the delivered distribution and breaks the tie to the bill | Delivered tickets look cheaper than their share of waste |
| Report the distribution with PR size bands | Average cost per PR | Averages hide heterogeneity; the lead's critique | Size is context, not a denominator, so no single "price" |
| Never cost per line | Per line or per file | Lines are gameable and reward verbosity | Less comparable across tickets |
| State both a cost-incurred period and a delivery cut-off | One month label | Spend in month P may deliver in P+1 | Cohorts shift; no trend from one month |
| Vote proxy kept labelled as a proxy | Call it "review start" | A vote is not pickup; absence of a vote is not absence of review | The "wait" metric the programme wants stays unmeasured |
| Strict collection: every thread history must be reachable | Best effort | A silent gap would bias the proxy; zero unavailable in both months | Collector fails rather than reports partial data |

## 6. Theory behind it (the "lecture" part)

### 6.1 Operational definitions and construct validity
A **construct** is the thing you care about ("delivered work"). An **operational definition** is the measurable rule you use ("a ticket with at least one PR merged to main"). **Construct validity** is how well the rule captures the construct. A rule can be reliable (everyone computes the same number) and still invalid. Typical failures: a status set by a person (reliable only if they follow the rules), a proxy that is easy to game, or a definition that includes cases you would not call delivery.

*In my project:* "Done" is a status with weak validity (3 of 17 closed tickets did not deliver a change); "merged to main" is machine-checkable but still short of "in production and used".

### 6.2 Unit of analysis and denominators
The unit decides what a ratio means. A per-PR average treats a one-line fix and a major feature as the same unit. When units differ a lot, report a **distribution** (median, quartiles, tail) and show the size as context. Percentiles on small samples are unstable: with n = 12, the nearest-rank p90 is the 11th value, almost the maximum.

*In my project:* the August result reports n = 12 with a median, Q1–Q3 and p90 (; amounts deliberately not copied). I recomputed these from the per-ticket table: the median is the mean of the 6th and 7th values, while Q1, Q3 and p90 are nearest-rank (3rd, 9th, 11th). The document says only that Q1, Q3 and p90 use nearest rank. Mixed definitions are harmless here but be ready to say so.

### 6.3 Many-to-many relations and double counting
A PR can close several tickets and a ticket can need several PRs. If you join and then sum, a quantity attached to one side is counted once per match. Safe practice: decide the grain of the output (here: ticket), attribute each measured quantity at the grain where it was measured (spend by working directory, hence by ticket), and use the other relation only as context.

*In my project:* 12 PRs map to 14 closing tickets; spend is attributed per ticket, PRs are context.

### 6.4 The PR lifecycle and the timestamps in it
A pull request goes through: **create** (possibly as draft) → **ready for review** → **review activity** (comments, votes or approvals, change requests, new commits that move the head revision) → **approve** → **merge** or **abandon**. Then, outside the PR: build, release, deploy, observe. Useful durations: lifetime (create → close), time to first response, review rounds, approval to merge. Only some are observable: platforms record when a vote was cast, not when the reviewer opened the diff. An approval applies to a specific head revision; after new commits it may be stale.

*In my project:* ADO gives creation, close and vote-update events; GitHub gives created, ready-for-review, reviews with commit ids, and merge. Reviewer pickup is the missing event, so it is specified (an explicit human-start signal tied to the same revision), not inferred.

### 6.5 Closure cohorts, censoring and survivorship
A **closure cohort** contains items that finished in the window. Items still open are **right-censored**: you know they lasted at least this long, not how long. A closure cohort therefore understates the tail and is shaped by what happened to close in the period. A cohort defined by activity within the window has different problems (it splits items at the edges). Neither is wrong; each must be named, and only like-for-like cohorts compared.

*In my project:* the ADO result is a closure cohort of completed PRs; some had been created before the reporting month, and some qualifying first votes predate it. Abandoned and open PRs are excluded.

### 6.6 Lead time, cycle time and flow efficiency
**Lead time** runs from request to delivery; **cycle time** from work start to delivery. **Flow efficiency** = touch time / lead time. In knowledge work it is often low, because items wait in queues (for review, QA, release). Speeding up the touch part (writing code) raises overall speed only slightly if the wait part dominates (Amdahl's-law-style reasoning).

*In my project:* the dashboard showed lead time about 3.5× cycle time, which is why the programme's real question is the wait after an agent finishes.1).

### 6.7 Proxy versus construct
A proxy correlates with the construct but is not the construct. State it, and state when the proxy fails. A vote timestamp is evidence that someone engaged; it is not evidence of when they began, whether they were human, or whether a review took place at all.

*In my project:* the qualifying-vote class excludes author votes, container identities, zero votes and unresolved actors, and each excluded class is counted, not dropped.

## 8. Glossary

| Term | One-line definition |
|---|---|
| Delivered ticket | A ticket with at least one linked PR merged to the main branch |
| Delivery-state bucket | Delivered, open or non-delivering, closed without delivery: where spend is reported |
| Closure cohort | Items whose close date falls in the window, whenever they started |
| Right-censoring | Items still open: duration known only as "at least this long" |
| PR lifetime | Time from PR creation to close |
| Qualifying vote | Non-zero vote by a non-author, non-container individual identity |
| Vote proxy | Creation-to-first-qualifying-vote duration, used because pickup time is not recorded |
| Closing reference | Keyword like "closes #N" in a PR body that links a PR to a ticket |
| Half-open interval | `[start, end)`: start inclusive, end exclusive |
| Nearest-rank percentile | The k-th smallest value with k = ceil(p × n) |
| Cost-incurred period | The month in which the spend happened |
| Delivery cut-off | The date up to which merges are counted |

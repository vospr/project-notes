**In short:** Plain-English knowledge graph basics: nodes and edges, taxonomy versus ontology versus graph, property graph versus RDF, extracted versus inferred edges, entity resolution, and when plain links are enough.

## 2. The problem (business view, plain English)

Documents hide relationships. "Order service calls payment service" is buried in code; "this decision replaced that one" is buried in meeting notes. Search finds text that mentions a word; it does not answer "what depends on this?" or "what was decided before this?". A knowledge graph stores relationships as data, so a question about links becomes a lookup instead of a reading task.

Analogy: a metro map. The text of the timetable lists stations; the map shows which lines connect, so "how do I get from A to B?" is a path, not a search.

## 4. How it works

### 4.1 The smallest graph
```
(order-service) --calls--> (payment-service)
(payment-service) --reads--> (customer-db)
```
Three nodes, two edges. Question "what breaks if customer-db changes?" = walk the edges backwards: payment-service, then order-service.

In code (a plain list of triples is already a graph):
```python
edges = [("order-service", "calls", "payment-service"),
         ("payment-service", "reads", "customer-db")]
dependents = [a for a, rel, b in edges if b == "customer-db"]   # ['payment-service']
```

### 4.2 The ladder from list to graph
| Level | What it is | Example |
|---|---|---|
| Glossary / list | Terms and definitions | "Tenant: a customer organisation" |
| **Taxonomy** | A tree of categories (is-a, part-of) | Vehicle > Car > Estate |
| **Ontology** | Defined kinds of things and allowed relations, with rules | "A Tenant has many Users; a User belongs to one Tenant" |
| **Knowledge graph** | The actual data using that vocabulary | "Acme is a Tenant; Jo is a User of Acme" |

Most vendor pages describe these as layers of one idea, with the graph as the layer that holds the real instances. A recurring criticism: many products sold as "ontologies" are just governed property graphs or glossaries with typed links.

### 4.3 Two ways to store a graph
| | Property graph | RDF triples |
|---|---|---|
| Shape | Nodes and edges that can carry key-value properties | Every fact is subject-predicate-object |
| Schema | Flexible; you enforce it | Standards (OWL, SHACL) for rules and reasoning |
| Good for | Application graphs, code graphs, quick builds | Shared vocabularies, compliance reasoning |
| Risk | Same concept drifts across teams without rules | Heavier to model and query |

Rule of thumb from the sources: model-built graphs over unstructured documents suit exploration where no schema exists yet; RDF/OWL suits questions that need an authoritative schema, such as regulatory checks.

### 4.4 Where edges come from, and why the label matters
A code parser reads syntax and writes an edge only for what is written in the code: this is **extracted** (deterministic, repeatable). A model or heuristic that guesses "these two modules are related" writes an **inferred** edge, ideally with a confidence score. In my local graphs about 96 to 98% of edges are extracted and 2 to 4% inferred, with inferred ones carrying a confidence around 0.8. Keeping the label lets a reader trust the first kind and verify the second.

### 4.5 Do I need a graph at all?
```
Are the links already written as links (imports, wiki links, foreign keys)?  -> traverse those; no new graph store
Do I need to answer "what depends on X / what connects A and B"?             -> a graph helps
Do I only need "find the page about X"?                                      -> search or an index file
```

## 5. Why it was built this way (decisions and trade-offs)

| Decision | Alternatives | Why this one | Cost / risk |
|---|---|---|---|
| Parser-built graphs for code | Model-built entity graph | Deterministic, free of model cost, rebuildable from source | Only captures what syntax shows; misses intent |
| Keep edge labels (extracted vs inferred) | Treat all edges equal | Reader can verify guesses | A little more output to read |
| Plain typed links for the wiki | A graph database | Pages are already linked; zero extra infrastructure | No graph queries across pages |
| Property graph over RDF for tooling | RDF/OWL | Faster to build; fits code analysis | Weak guarantees about meaning |

## 6. Theory behind it (the "lecture" part)

### 6.1 Graph vocabulary
A graph has *nodes* (things) and *edges* (links); edges can be *directed* (A calls B) and *typed* (calls, reads, replaces). A *path* is a chain of edges; a *neighbourhood* is everything within a few hops; a *community* is a group of nodes more connected to each other than to the rest.
*In this course:* "communities" appear in both code graphs (14.8) and GraphRAG summaries (14.3).

### 6.2 Multi-hop reasoning
A question needing two or more edges ("the owner of the service that reads this table") is multi-hop. Text search handles one hop badly and two hops worse, because the answer is spread across documents.
*In this course:* multi-hop demand is the test for whether a graph is worth building (14.5, 14.10).

### 6.3 Closed vs open vocabulary
A closed vocabulary (an ontology) allows only declared node and edge types; an open one lets a model invent types as it reads. Closed is consistent but costly to design; open is quick but drifts.
*In this course:* GraphRAG extraction is open by default; code graphs are closed by the parser's grammar.

### 6.4 Entity resolution
"Acme", "Acme Ltd" and "ACME" must become one node, or the graph splits one thing into three. It is the quiet hard part of every graph built from text.
*In this course:* one reason model-built graphs need review.

## 8. Glossary

| Term | One-line definition |
|---|---|
| Node | A thing in the graph (file, function, person, decision) |
| Edge | A typed, usually directed link between two nodes |
| Triple | Subject-predicate-object fact, the unit of RDF |
| Taxonomy | A tree of categories |
| Ontology | Defined types of things and allowed relations, with rules |
| Property graph | Nodes and edges that carry key-value properties |
| RDF / OWL | Standards for triples and for ontologies with reasoning |
| Extracted edge | An edge read directly from the source |
| Inferred edge | An edge guessed by a model or heuristic, with a confidence |
| Community | A cluster of nodes densely linked to each other |
| Multi-hop question | A question that needs two or more edges to answer |
| Entity resolution | Merging different names for the same thing into one node |

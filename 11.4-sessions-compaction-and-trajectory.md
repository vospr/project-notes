# Course 11 · Chapter 11.4: Sessions, compaction and the trajectory ledger

_Andrey Popov's project notes: how it works, why it was built this way, and the theory behind it._

**In short:** Append-only JSONL session trees, token-based classic compaction (reserve 16,384, keep about 20,000, failure-safe), structured compaction (hide first, then checkpoint, expand on demand), the obligations ledger and operative pins that protect user intent, and the trajectory read model.

## 2. The problem (business view, plain English)

A coding agent works for hours. Its history grows by every file it reads and every command output. The model has a fixed window, say 200,000 tokens, and every turn re-sends the whole history, so cost grows and quality drops as the history fills with stale noise. Something must shrink it. The naive fix, delete the oldest messages, loses the original task. The next fix, ask the model for a summary, loses details the work depends on (a path, an error message, a decision) and, worse, can silently drop an instruction the user gave an hour ago.

Second problem: the process dies. A laptop sleeps, a job is killed, a crash happens. The user expects to resume, and to branch from an earlier point to try another approach, without losing the record of what was done.

Finance analogy: the session file is the trade blotter, append-only and never edited. Compaction is the daily position summary: a compact view for working with, produced from the blotter, never replacing it.

## 4. How it works (technical walkthrough)

### 4.1 The session file
- One session = one **JSONL** file: first line a header `{"type":"session","version":3,...}` with id, timestamp, `cwd` and optional parent session path; then one JSON record per line. Version 4 is a rotated-segment marker.
- Every record has `id`, `parentId`, `timestamp` and a `type` discriminator. `parentId` makes the records a **tree**.
- Record types (*SR* class list): `MessageRecord`, `ThinkingLevelChangeRecord`, `ModelChangeRecord`, `ActiveToolsChangeRecord`, `CompactionRecord`, `HiddenRangeRecord`, `CompactCheckpointRecord`, `SegmentPinRecord`, `BranchSummaryRecord`, `CheckpointRecord`, `CustomRecord`, `CustomMessageRecord`, `LabelRecord`, `SessionInfoRecord`, `LeafRecord`. The family is `sealed`.
- **Path on disk:** `<sessionsRoot>/<--encoded-cwd-->/<timestamp>_<sessionId>.jsonl` (*RP* header). Sessions are grouped by working directory.
- **The file is the source of truth.** The storage appends one line first and then updates its in-memory index (*SS* header). A crash after the append loses nothing; a crash before it loses only the record that was never written.
- A **`LeafRecord`** moves the "current position". The model context is rebuilt by walking from the active leaf up to the root (*ST* header). Branching is simply appending a record whose parent is an earlier record; the old branch stays in the file. Labels name points; branch summaries describe an abandoned branch when you jump away.
- **`CustomRecord`** carries typed host data in the same file: the shell job registry, subagent registry, the obligations ledger, the task ledger, heartbeat records. Several of these use **latest-snapshot-wins**: each change appends a full new snapshot, the last one counts, older ones stay as the audit trail (*OL* header).

### 4.2 Windowed storage (issue #135; *WS*)
A session can reach 14 MB or more. Opening it by parsing everything costs time proportional to the file. The windowed storage reads a **byte-scanned tail**, so open cost is O(window), not O(file). The window is anchored on the newest records; appends and tail ingests evict the oldest side. Scrolling up (`loadOlder`) slides the window; `jumpToOffset` re-centres it; a sparse offset map remembers record byte offsets. The session leaf is always the **true file leaf**, regardless of what is resident. Small sessions degenerate to "the window is the file".

### 4.3 Classic compaction
Four steps, all token-based:
1. **Measure.** `estimateContextTokens`: 4 characters per token; image = 4,800 characters; trust provider-reported usage for everything up to the last assistant message that has it, and estimate only the trailing messages.
2. **Decide.** `shouldCompact`: tokens above `window − reserveTokens` (reserve 16,384 by default).
3. **Cut.** `findCutPoint` walks the branch **backwards**, accumulating estimated tokens until about `keepRecentTokens` (20,000) are kept; it snaps forward to a valid boundary (never a tool result) and back over non-message records so configuration entries stay with the kept region. If the cut falls in the middle of a turn, it records the turn start and a "split turn" flag, and a separate turn-prefix summary prompt exists for that case.
4. **Summarise.** An injected `SummarizeFn` (usually the cheap `smol` role) gets the serialized old region plus a fixed prompt and returns a checkpoint. `CompactionManager.compactSession` appends a `CompactionRecord`; the **projection** replaces the summarised region with the summary on the next rebuild. **On any failure nothing is appended**, so history is never lost.

The summary prompt is "a lossless handoff, not a digest" with a fixed skeleton: Open User Requests (each with acceptance criterion; closes only with evidence or an explicit cancel), Goal, Constraints & Preferences, Progress (Done / In Progress / Blocked), Key Decisions, Next Steps, Critical Context (data, test verdicts, command outputs, error traces). There is also an **update** prompt that merges a new region into the previous summary, and a branch-summary prompt.

**Small-window scaling** (*CP* lines 438-470): fixed defaults of 16,384 and 20,000 would exceed the whole window of an on-device model (2,048 to 8,192 tokens), so `reserveTokens = min(16384, max(1024, window ÷ 4))` and `keepRecentTokens = min(20000, max(2048, window ÷ 2))`, with extra clamps for tiny windows.

Worked example: a 200,000-token model gets reserve 16,384, so compaction triggers at about 183,600 tokens; it keeps about 20,000 recent tokens verbatim and summarises everything before the cut.

### 4.4 The auto-compactor around it
Shared by the CLI and the Flutter app so there is one policy:
- **smol → main fallback:** if the cheap summariser fails (rate limit, 403) and it is a different model or endpoint from the main chain, retry once with the main stream; if they are the same, skip (it would re-trigger the same error);
- **transient retry:** 5xx, connection closed/reset, socket exception, stream closed: up to 3 attempts with 1 s and 2 s backoff; hard refusals (usage limit, 429, validation, auth) fail fast, "retrying burns the same quota twice";
- **multi-pass:** if the transcript still exceeds the window after one pass (a 1M-token session landing in a 200k model), repeat until it fits or a per-run pass cap is hit;
- hosts inject the summariser, persistence and progress through configuration; no hidden coupling to `AgentCli` or `AgentService`.
The agent loop cooperates: before a request it checks the window and can ask the host for one synchronous "emergency" compaction (chapter 11.2). After the run, the host compacts for the next turn.

### 4.5 Structured compaction (issue #148; *SE*, ledger, markers, expand tool, projection)
Classic compaction is lossy and irreversible in context (the file keeps everything, the model sees only the summary). The structured engine adds a **reversible** step first.

1. **Context ledger** (`ledger.dart`): a numbered list of one line per visible record, e.g. `[3] assistant-TOOLCALL(read) ~40tok`, `[4] toolResult(read) ~4.0k · x.dart contents…`, `[5] ckpt 2-4 ~38k → covers:3,4 · summary…`. Real user turns are tagged `·exempt` and **can never be hidden**. Numeric ids come from the 1-based JSONL line number and are never persisted.
2. **Pass 1: Hide.** A `smol`-role **judge** model reads the ledger and returns a JSON array of ids and ranges to hide, e.g. `["3","5","7-8","12"]`. Rules in the prompt: never hide user requests, answers and decisions, the last ~8 records, or unresolved errors; prime candidates are consumed tool results, superseded re-reads, stale grep output, thinking whose conclusion is stated, large one-off logs. **Pair rule:** a tool call and all its results hide together or not at all. Hidden records become one-line **markers** such as `[3:hidden·tool_result·4.2k·"first line…"]`, kept to about 12 tokens of addressing so the markers do not become the new bloat. The judge runs again while pressure remains (bounded).
3. **Pass 2: Checkpoint.** If pressure remains, the oldest hideable range is summarised into a checkpoint whose marker lists every id it covers (`[2-6:ckpt·38k→40tok·covers:3,5]`). Checkpoints **nest** up to a depth cap; beyond it the deepest level folds into the new checkpoint.
4. **Expand on demand:** the `compact_expand` tool pulls a hidden or covered segment back into the conversation by marker id, paged and capped by a per-turn expand budget (32k tokens). With no target it lists what is hidden; a query ranks it. The session file never changes, expanded content enters as a normal tool result and may be re-hidden later. A zero-tool fallback is `read $FAH_SESSION_FILE:<line>`.
5. **Failure contract:** like the classic engine, a failed pass appends nothing; on hard failure or residual overflow the host falls back to the classic compactor, whose summary then renders under the structured projection as an opaque `legacy-ckpt` marker.

State lives in two record types, `HiddenRangeRecord` and `CompactCheckpointRecord`; the projection derives "what is hidden, what is swallowed by which checkpoint" at render time, keyed by stable record ids.

### 4.6 Invariants that protect the user's intent
- **Obligations ledger** (issue #1380; *OL*): a snapshot record holding the owner's standing rules, open asks, agent commitments and pending waits as **verbatim quotes with a pointer to the source record**. The engine, not the model's goodwill, maintains it. The projection renders it as a compact block at level 0, so "hide/compact/flatten at any depth can never sink an obligation below the visible surface". The text is the exact source span, never a paraphrase; the budget applies only at render time.
- **The #488 lesson** (review-blocking on this slice): the latest snapshot may lie *below* a windowed session's resident tail. A writer that trusts the resident view appends a latest-wins snapshot that silently **erases** every earlier entry. Rehydration therefore goes through a raw file scan (`readCustomRecordsOfType`), never the resident entries.
- **Operative pins** (gh-1409; *OP*): a skill's `operative:` directives become durable context, pinned verbatim across every compaction and re-injected on resume. They are derived state rebuilt at request assembly; every rendered pin is byte-identical to its front-matter string, so the pipeline cannot paraphrase it. Invariants P1-P6 cover: file unchanged, deterministic rebuild, byte-identical text, no dangling pins (a pin whose skill is gone is dropped **with a notice**), no silent rebind, and a per-window budget with a drop notice.

### 4.7 Trajectory ledger (*TJ*, README)
Every session projects into an **immutable snapshot**: turns, timeline modes, full-text search. It is the read model for the `/trajectory` REPL commands (`view`, `cost`, `tail`, `inspect`) and the `fa trajectory` headless command, ported from the "deepseek-harness" UI contract. It is a *view* for humans and tools, built from the session records and loop events; it does not feed the model.

### 4.8 Prompts are files
All LLM prompts, including the compaction ones, are Markdown files with YAML front matter under `prompts/`; `dart run scripts/gen_prompts.dart` generates `prompts.g.dart`, and a test fails on drift (*AGENTS* "Prompts live outside Dart code"). The summary prompt is "forked from pi's SUMMARIZATION_PROMPT; body wording diverges deliberately".

## 5. Why it was built this way (decisions and trade-offs)

| Decision | Alternatives considered | Why this one | Cost / risk |
|---|---|---|---|
| Append-only JSONL tree | SQLite; one JSON blob | Crash-safe, diff-able, branchable, greppable; the file is the truth | Big files; needs windowed reads (#135) |
| Branching by `parentId` and `leaf` records | Copy the session on fork | Cheap branches, full history kept | Context rebuild must walk the path; more complex than a list |
| Token-based triggers | Message-count triggers | Message sizes vary enormously | Heuristic estimate (4 chars/token) |
| Trust provider usage when present | Always estimate | Real numbers beat guesses | Usage may be missing or stale for some providers |
| Failure-safe compaction (append only on success) | Mutate in place | Never lose history | A failed compaction leaves the context big; needs a fallback valve |
| Cheap `smol` model summarises | Main model | Cost and rate limits | Weaker summaries; hence the smol → main fallback |
| Structured: hide first, checkpoint second | Summary only | Hiding is lossless and reversible; summaries are not | Two LLM passes, a judge that can mis-hide; mitigated by exempt user turns and expand tool |
| Verbatim quotes in obligations ledger | Model-written paraphrase | Paraphrase is where instructions die | Takes window space; budgeted at render |
| Pins derived, never summarised | Let the summary carry them | Byte-identical operative rules | Needs a registry and notices |

## 6. Theory behind it (the "lecture" part)

### 6.1 Append-only logs, event sourcing and write-ahead logs
An **append-only log** records changes instead of overwriting state. **Event sourcing** keeps the log as the truth and derives current state by replaying it; a **write-ahead log** appends before applying so a crash can be recovered. Benefits: audit trail, time travel, simple concurrency (only appends), easy replication. Costs: replay time (so snapshots), and schema evolution of old records. Latest-snapshot-wins records are the usual compromise: each snapshot is a full state, replay needs only the last one.

*In my project:* Verdaca's JSON receipts (Course 2.4) are single-run logs; here the log is the live working memory of the agent.

### 6.2 Trees and branching histories
Git models history as a DAG; this session is a simpler tree. The active branch is a root-to-leaf path. Moving the leaf is cheap; "forking" is appending a child of an earlier node. Rebuilding context means walking parents, O(depth). A branch summary compresses an abandoned path so that its lessons survive.

*In my project:* the `/checkpoint` and `/rewind` tools and tree navigation use this structure.

### 6.3 The context window as a budget
The window bounds input plus output. Each turn re-sends the whole history, so the cost of a long session grows roughly with the *sum* of its context sizes, which is quadratic in turns if history only grows. Compaction caps that. Quality also drops as the window fills with irrelevant material ("context rot"), which is why hiding stale tool output helps even before the window is full. Reserve tokens ensure the summary call and the next answer still fit.

*In my project:* Course 3.5 (cost anatomy of one ticket: context × turns) is the same arithmetic on a real ticket.

### 6.4 Summarisation as lossy compression
A summary is lossy compression with a model as the codec. What it loses is not random: details that looked unimportant at summary time and mattered later (an exact error string, a constraint mentioned once). Mitigations used here: a fixed skeleton (so categories are never skipped), a "preserve every path/error/decision" instruction, iterative *update* summaries, **verbatim** quoting for obligations, and keeping the raw record on disk for expansion. A cheaper alternative is **observation masking**: replacing old tool outputs by placeholders while keeping the agent's own reasoning, which, as I remember a 2025 study by JetBrains Research ("The Complexity Trap"; not in the repo sources, re-check before quoting), was competitive with LLM summarisation on coding-agent tasks; the structured engine's hide pass is that idea with a judge.

*In my project:* the finance parallel is a month-end close: keep the ledger, publish a summary, and be able to drill down to the entry.

### 6.5 Token estimation
Byte-pair-encoding tokenisers produce on average about 4 characters per token in English prose, fewer in code and much fewer in some scripts. Exact counting needs the provider's tokenizer; many harnesses estimate and correct with the provider-reported usage. A conservative estimate triggers earlier; an optimistic one risks overflow, which is why an overflow guard sits behind it.

*In my project:* images are priced at a flat 1,200 tokens, an approximation of provider-specific image costs.

### 6.6 Windowed (paged) reads
Reading the end of a large file means seeking from the end and scanning backwards for line breaks. A sparse index from record to byte offset avoids re-scanning. The invariant to preserve is that *logical* state (the true leaf, the latest snapshots) is never derived from the *resident* subset.

*In my project:* issue #488 is exactly that bug class, found and then guarded in the design.

## 8. Glossary

| Term | One-line definition |
|---|---|
| JSONL | One JSON object per line |
| Record | One line of the session file; has `id`, `parentId`, `type` |
| Leaf | The current end of the active branch |
| Branch summary | Summary of an abandoned branch kept when navigating away |
| Compaction | Replacing old history in the context by a shorter representation |
| Reserve tokens | Space kept free for the summary and the next answer (default 16,384) |
| Keep-recent tokens | Recent tail kept verbatim (default about 20,000) |
| Cut point | Record where the kept region starts; never a tool result |
| `smol` | The cheap model role used for summaries and the hide judge |
| Hide pass | Reversible replacement of records by one-line markers |
| Checkpoint | Summary of a range, with a marker listing the ids it covers |
| `compact_expand` | Tool that restores hidden content by marker id, within a budget |
| Obligations ledger | Verbatim record of standing rules, open asks, commitments |
| Operative pin | A skill directive kept byte-identical across compactions |
| Latest-snapshot-wins | Each change writes a full state; the last record counts |
| Trajectory | Immutable read model of a run, for viewing and search |

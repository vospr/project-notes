# Course 14 · Chapter 14.1: The map: five ways to give a model knowledge

_Andrey Popov's project notes: how it works, why it was built this way, and the theory behind it._

**In short:** Five ways to give a model knowledge: put it in the prompt, retrieval, knowledge graph, LLM wiki and agent memory. When each fits, when to skip retrieval (under about 200k tokens), local versus global questions, and why a code graph is not GraphRAG.

## 2. The problem (business view, plain English)

A language model knows only what it was trained on and what you put in front of it right now. Company knowledge (decisions, code, contracts, notes) is neither. Teams reach for "RAG" as if it were the only answer, then discover that some questions need relationships ("who depends on this?"), some need a summary of everything ("what are the main themes?"), and some are just stale because nobody updated the source. Picking the wrong approach wastes money, or worse, gives confident answers from old facts.

Analogy: a library. You can (a) hand the reader the whole shelf, (b) give them a card catalogue, (c) draw a map of how books cite each other, (d) hire a librarian who writes and keeps up summary pages, (e) let the reader keep a notebook of what they learned last time. These are five different tools; real libraries use several.

## 4. How it works

### 4.1 The five ways, side by side
| # | Approach | What it is | Best at | Weak at |
|---|---|---|---|---|
| 1 | **Put it in the prompt** (long context) | Paste the documents into the context window | Small, stable knowledge; whole-document reasoning | Cost per question grows with size; no access control per document |
| 2 | **RAG** (retrieval-augmented generation) | Find the few most relevant text pieces for the question, give only those | Large corpora, lookups of facts | Relationships across pieces; "summarise everything" questions |
| 3 | **Knowledge graph / GraphRAG** | Store things (nodes) and links between them (edges); retrieve by following links or by group summaries | Multi-hop questions ("which services call this one?"), whole-corpus themes | Costly to build; needs upkeep; overkill for simple lookups |
| 4 | **LLM wiki** | An LLM writes and maintains linked markdown pages from raw sources; you read and query the pages | Knowledge that compounds; human-readable; auditable | Depends on the LLM keeping it consistent; needs lint |
| 5 | **Agent memory** | The agent saves facts from its own work and recalls them later | Preferences, past decisions, what changed | Facts go stale or contradict; storage grows |

### 4.2 The first decision: do you need retrieval at all?
Anthropic's guidance: if the knowledge base is under roughly 200,000 tokens (about 500 pages), put it all in the prompt and use prompt caching; use retrieval only above that. My own July research agrees in spirit: measure first, add machinery only when a measured failure demands it.

```
corpus fits in the window and is not secret per user?  -> approach 1
lookups, many documents, wording matches?               -> approach 2 (lexical first, 14.5)
questions follow links (callers, owners, dependencies)? -> approach 3 (14.2, 14.3, 14.8)
knowledge should accumulate and be read by humans?      -> approach 4 (14.4)
the agent must remember its own history?                -> approach 5 (14.6)
```

### 4.3 They combine
Approaches are layers, not rivals. A typical 2026 stack: an index file or keyword search finds the page (2), a wiki page holds the curated answer (4), a graph answers "what depends on X?" (3), and a small memory file holds standing preferences (5).

## 5. Why it was built this way (decisions and trade-offs)

| Decision | Alternatives | Why this one | Cost / risk |
|---|---|---|---|
| Treat the five as a ladder, lightest first | Start with a vector database and a graph | Each step adds build cost, upkeep and a new way to be stale | You may under-build; mitigate with a measured benchmark (14.7) |
| Keep code relationships and document search as separate systems | One universal index | Different authority and freshness rules (14.6); code graphs can be rebuilt from source | Two things to maintain |
| Humans read the wiki pages | Hidden vector store only | Auditable; a reviewer can see and correct what the model "knows" | Writing and linting effort |

## 6. Theory behind it (the "lecture" part)

### 6.1 Parametric vs non-parametric knowledge
*Parametric* knowledge lives in the model weights (fixed at training). *Non-parametric* knowledge lives outside (documents, graphs, memory) and is looked up at question time. All five approaches are ways of supplying non-parametric knowledge.
*In this course:* the whole course is about how to store and refresh the non-parametric part.

### 6.2 Local vs global questions
A *local* question is answered by a few passages ("What port does the service use?"). A *global* question needs the whole corpus ("What are the main risks across all these reports?"). Plain RAG is built for local questions; graph-based summaries (14.3) and LLM wikis (14.4) address global ones.
*In this course:* decide by the question type, not by fashion.

### 6.3 Retrieval, memory and knowledge are different jobs
Retrieval finds relevant text. A knowledge base is curated, maintained truth. Memory is the agent's own history. Mixing them causes the classic bug of an old memory beating a newer document (14.6).
*In this course:* every later chapter asks "where does this fact live, and who updates it?"

### 6.4 Cost shape
Long context: cost per question. RAG: index cost once, small cost per question. GraphRAG: large index cost, varied query cost. Wiki: ongoing LLM cost per ingest. Memory: small cost, growth over time.
*In this course:* cost is a design input, not an afterthought (14.3 has real numbers).

## 8. Glossary

| Term | One-line definition |
|---|---|
| RAG | Retrieve relevant text, then let the model answer from it |
| Long context | Putting the whole knowledge into the prompt |
| Knowledge graph | Things (nodes) and typed links (edges) stored as data |
| GraphRAG | Retrieval that uses a graph built from documents, often with group summaries |
| LLM wiki | Linked markdown pages written and maintained by an LLM from raw sources |
| Agent memory | Facts an agent saves from its own work and recalls later |
| Local question | Answerable from a few passages |
| Global question | Needs a view of the whole corpus |
| Parametric knowledge | Knowledge stored in model weights |
| Prompt caching | Reusing the processed prompt prefix across calls to cut cost |

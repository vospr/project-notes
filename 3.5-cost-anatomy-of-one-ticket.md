# Course 3 · Chapter 3.5: Cost anatomy of one ticket: context × turns, never-reset sessions, subagent cost

_Andrey Popov's project notes: how it works, why it was built this way, and the theory behind it._

**In short:** Cost dissection of one outlier ticket: 89% of token volume came from one never-reset parent conversation; 13 subagents were only about 11%. Late turns cost about 8x early ones; fixes are phase resets, batching and disk artifacts.

## 2. The problem (business view, plain English)

In the first month, one feature ticket consumed a very large share of one licence's measured history. A manager would guess "too many AI reviewers". The data said otherwise: about 90% of the token volume came from one parent conversation that was never reset, and all 13 delegated agents (plan reviews, QA, research, code reviews) together were about 10%. A late turn cost about 8 times an early one for the same kind of work.

This turned a vague worry ("AI is expensive") into an operating checklist: reset at phase boundaries, batch independent tool calls, keep agent output on disk, match model and effort to the phase.

Finance analogy: interest on a growing balance. Each turn "pays interest" on the entire outstanding conversation. A long unbroken session is a loan that keeps compounding in size; a reset is amortising the balance and starting a new, small one.

## 4. How it works (technical walkthrough)

```
turn n:  [ system + instructions + all earlier messages + all earlier tool results + reports ]  ← read again every turn
              context C_n  (only grows within one session)
cost_read  ≈  Σ_n  C_n  =  N × C̄          levers:  fewer turns N   |   smaller carried context C̄
```

**Step 1: split by population.** Parent session: 1 file, ~606 canonical events, 88.75% of cache-read. Subagents: 13 files, 415 events, 11.25%. Mean cache-read per event: ~568K in the parent vs ~105K in a subagent, 5.4×. That ratio is the value of context isolation.

**Step 2: look at turns over time.** Per hour, the parent's mean cache-read per event rose from ~97K to ~841K over eight hours of work (about 8.7× parent-only; the write-up's blended figure is about 8×). The last four hours held 75% of all cache-read across 500 events. I recomputed this from the frozen file and the hourly values match.

**Step 3: look at what the turns were.** Parent tool calls were mostly `Bash` (about half), then `Edit` (about a third), with a handful of delegations. Batching: 91% of tool-issuing turns made exactly one call; mean 1.12 calls per turn. The frozen diagnostic confirms 1.12 for the parent, but the subagents batch far more: density 1.76, with about 60% of tool turns batched.

**Step 4: look at what the workflow made happen.** The prescribed single plan-review pass ran seven times because each pass requested another after "revise and re-review"; four were driven by defects introduced by an earlier fix; all reports entered the parent context in full and stayed there; fold-in edits ran in the same context. Reviews had real yield, so "review less" is the wrong lesson.

**Step 5: model and effort.** About 94% of cache-read ran on the premium model at maximum reasoning effort, after a mid-session switch. This is a rate lever, not a volume lever: cost is Σ tokens × rate(model, bucket). Currency was not computed.

**Step 6: the fixes, mapped to the two levers.** Reset context at phase boundaries (reduces C̄); batch independent calls (reduces N); write agent findings to disk and pass paths not text (reduces C̄); vary model by phase (changes the rate); one waiting mechanism per wait; cap plan-review iterations.

**Step 7: make it repeatable.** A bounded Claude-only diagnostic (`ai-context-economy/v0`) reports events, turns, tool calls, mean cache-read per event, batching density and two non-gating alerts for one ticket over an explicit interval. Its event denominator reconciles with the collector, and its outcome fields are always null.

## 5. Why it was built this way (decisions and trade-offs)

| Decision | Alternatives | Why this one | Cost / risk |
|---|---|---|---|
| Dissect one outlier ticket | Aggregate statistics only | The extreme case exposes a mechanism the average hides | One case; selection by outlier (regression to the mean) |
| Split parent vs subagent by file | Attribute by tool name | Subagent logs are separate files; exact split | Hourly buckets blend both |
| Model cost as N × C̄ | Count tokens only | Two levers, each testable | Ignores bucket prices and cache-write |
| Express fixes as scenario percentages, labelled non-additive | Claim measured savings | No controlled before/after exists | Numbers get quoted as results |
| Diagnostic with alerts that never gate | Pass/fail gate | One calibration case; avoid false authority ||
| Keep the diagnostic Claude-only | Add Codex | No tested parent/subagent contract for Codex | Half the usage is not covered |
| Phase-local contexts with disk artifacts | One long session or `/compact` | The plan, decisions, branch and review audit already survive a reset | Re-bootstrap cost, discipline needed |

## 6. Theory behind it (the "lecture" part)

### 6.1 Why a long conversation gets expensive: context re-reading and prompt caching
A language model API is stateless. Each turn, the client sends the whole conversation so far (instructions, earlier messages, tool outputs) and the model processes it again. **Prompt caching** lets the provider reuse the already-processed prefix: the first time a prefix is stored it is billed as a **cache write** (more than normal input); later turns that hit the cache are billed as **cache reads** (much less than normal input). Output tokens cost most per token. So per turn the bill is roughly `read(C_n)·r_read + new_tokens·r_in + output·r_out + writes·r_write`. Cache reads are cheap per token but enormous in count, so they dominate token volume (98.7% here).

*In my project:* the allocation key in chapter 3.3 is cache-read for exactly this reason: it is the bucket that exists for every session. It is a volume, not a price.

### 6.2 Quadratic growth and what a reset does
If the carried context grows by about `g` tokens per turn from a start `c₀`, the context at turn `n` is `c₀ + g·n`. Summed over `N` turns:

`Σ C_n = N·c₀ + g·N(N+1)/2`

The growth term is quadratic in `N`. Reset after every `N/k` turns (k segments, each restarting at `c₀`):

`Σ = N·c₀ + g·N²/(2k)` (approximately)

so the growth term falls by a factor `k`. Toy example (my numbers, not the case's): N = 600, c₀ = 50K, g = 1K. One session: 30M + 180M = 210M. Four segments of 150 turns: 4 × (7.5M + 11.3M) = 75M, about 64% less. The cost of resetting is the re-loading of `c₀` (already in the formula) plus any extra turns caused by lost continuity (not in it).

### 6.3 Two levers, multiplicative, not independent
`cost ≈ N × C̄`. Reducing N by a fraction a and C̄ by a fraction b gives a factor `(1−a)(1−b)`. With a = 35% and b = 55% that is 0.65 × 0.45 = 0.29, a 71% reduction, which the write-up quotes as about 70%. Savings from different levers are **not additive** (96% would mean almost nothing left). They are also not fully independent: fewer turns means fewer tool results accumulating, so C̄ falls too (the write-up says this). A **scenario estimate** states its assumptions and varies one input; a **measured effect** needs a comparison (before/after, or A/B).

*In my project:* 70% is a scenario estimate on a volume measure, not a measured money saving.

### 6.4 What a subagent really costs
A subagent runs in its own isolated context: it starts small, so each of its turns re-reads little. That is why its mean cache-read per turn was 5× lower. But delegation is not free: (a) the subagent pays for its own bootstrap (a cache write of its prompt and files), and (b) whatever it **returns** enters the parent context and is re-read on every later parent turn. A report of R tokens returned at turn t, with N − t turns remaining, adds about `R·(N − t)` cache-read tokens. The cheap pattern is to return a short summary and write the detail to disk, to be read only when needed.

*In my project:* the reviewers were cheap; their full reports and the fold-in edits that followed were not.

### 6.5 Batching: dependency graphs and turn counts
Independent tool calls can be issued in the same turn, so they share one context read. Dependent calls (call 2 needs call 1's output) must be sequential. Think of the calls as a dependency graph: the minimum number of turns is the length of its longest chain, not the number of calls.

*In my project:* the parent averaged 1.12 calls per turn; subagents about 1.76. The estimated saving assumes half the calls were independent and batched three at a time.

### 6.6 Case studies: selection bias and circular calibration
A case chosen because it is an outlier is subject to **regression to the mean**: the next case will usually look less extreme even with no intervention. A threshold calibrated on the case it will later flag guarantees a hit on that case and says nothing about the population. To validate you need other cases, or a prospective test.

### 6.7 Token share is not cost share
Weights for buckets and models differ (this chapter's illustration shows shares moving from 0.12% to about 5% for output, and from 11% to about 16% for subagents). A volume metric answers "where did the context go?"; it needs rates to answer "where did the money go?".

*In my project:* the write-up itself says currency requires the model-specific rate card.

## 8. Glossary

| Term | One-line definition |
|---|---|
| Carried context (C̄) | The tokens re-read on each turn: instructions, earlier messages, tool results |
| Turn (N) | One billed model response |
| Cache read / write | Billing buckets for reusing / storing a processed prompt prefix |
| Parent / subagent | The main conversation / a delegated agent with its own isolated context |
| Phase boundary | The point between plan, implement, review and evidence where a reset is safe |
| Reset | Clearing or restarting the session so context starts small again |
| Batching density | Tool calls per tool-issuing turn |
| Batched-turn share | Share of tool-issuing turns with more than one call |
| Scenario estimate | A what-if under stated assumptions, not a measured effect |
| Rate lever | Changing model or effort, which changes price per token, not volume |
| Fold-in | Applying review findings by editing in the same context |
| Non-gating alert | A flag that never blocks any step |

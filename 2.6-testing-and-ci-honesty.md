## 2. The problem (business view, plain English)

A green dashboard is a claim: "the checks pass." If the checks that ran are not the checks that matter, the claim is empty. For a project whose pitch is "you can prove afterwards what happened", an unreliable build signal is a credibility problem. The best story available is that the failure was found, fixed and written up.

Finance analogy: a bank reconciliation that shows "reconciled" because one account was left out of the file. The report is correct about the accounts it covered and silent about the missing one. The control that matters is the completeness check: does the population in the test equal the population in the ledger?

## 6. Theory behind it (the "lecture" part)

### 6.1 What a passing test is evidence of
A test is a small experiment with a pass/fail oracle. A green suite supports the claim "for the inputs and checks in these tests, the behaviour matched the oracle". It is silent on everything not exercised. Two errors: a **false green** (the suite passes while a defect exists; a missed detection) and a **false red** (a flaky or stale test fails while the code is fine). Test adequacy is a question of coverage of the *risk*, not of the lines.

*In my project:* "411/0" was green about a set of tests that did not include the ones that would have failed.

### 6.2 Test discovery and the completeness check
Frameworks find tests by rules: root directory, configuration file, naming patterns, import paths. A test not collected cannot fail. Controls: (a) assert that the number of collected tests does not drop (a ratchet); (b) assert that every test directory is listed in CI (the project's AC13 does this for kernel suites); (c) fresh-clone builds; (d) make CI fail on collection errors and on empty suites. In audit terms: **completeness** of the population before testing it.

*In my project:* four discovery failures: gitignored directory; CI scoped to a sub-folder; per-package configs needing separate runs; a merge that deleted the directory.

### 6.3 Test doubles
Gerard Meszaros's taxonomy: **dummy** (placeholder), **stub** (canned answers), **fake** (working simplified implementation, e.g. an in-memory database), **mock** (verifies interactions), **spy** (records calls). A fake or stub makes a test fast and hermetic and also defines the world in which the test is true. If the double drifts from the real service, tests stay green and production fails.

*In my project:* hand-written fakes of Mem0 and Letta clients; a scripted model for the deliberation loop; synthetic HTTP cassettes.

### 6.4 Contract tests versus integration tests, and the test pyramid
The pyramid (Cohn): many fast unit tests, fewer integration tests, few end-to-end tests. **Contract tests** check that two parts agree on an interface (provider contract, consumer expectations). A contract against a fake checks your *model* of the vendor; a smaller set of integration tests against the real thing keeps the model honest.

*In my project:* the pyramid is wide at the bottom and the top is one manual live run (June 2026, no committed log) plus three deliberation runs.

### 6.5 Coverage and mutation testing
**Statement coverage** = executed statements / total statements; **branch coverage** counts both outcomes of each decision. Both measure *execution*, not *checking*: a test that runs a line without asserting anything adds coverage. **Mutation testing** changes the code (flip a comparison, delete a call) and checks that some test fails; **mutation score** = killed mutants / (total mutants - equivalent mutants). A high score means the tests actually constrain behaviour. Property-based testing (Hypothesis) generates many inputs against stated properties and shrinks failures.

*In my project:* no coverage in CI, no mutation testing; Hypothesis in three files.

### 6.6 Tests that check shape, not substance
A test that asserts a field exists, a count is stable, or a function does not import X proves a *structural* property. It can pass while the behaviour that makes the property valuable is absent. Spot the pattern: the assertion would still pass if the feature were a constant or a stub.

*In my project:* T7.6 ("deliberation surface") passes when `dissent_frames` is a tuple and may be empty, and when `cited_tradeoffs` is non-empty, which it is because the gateway fills it with two fixed strings (`test_t7_6_deliberation_surface.py`, tests 1-2; `service.py:342`). The test is honest in its docstring ("emptiness is the no-dissent case") but its name reads like a capability.

### 6.7 CI as a source of truth, and "honest green"
CI should be the arbiter: clean environment, pinned dependencies, no local state. Principles: green must mean the same thing every time; report skips; fail on lint and type errors if you claim them; never claim a number you did not produce in CI; date every count. Related process fix from the review: "done = recorded run producing a receipt; CI fails if `tests/` untracked; no 'LIVE' label without a log from a real external system".

*In my project:* the workflow comment "Required gate" and the AC13 test that parses the YAML are steps in that direction.

## 8. Glossary

| Term | One-line definition |
|---|---|
| False green | Suite passes although a defect exists, often because the relevant tests did not run |
| Test discovery | The rules by which a runner finds tests (root, config, names) |
| Collected / passed / skipped | Found by the runner / ran and succeeded / found but not run |
| Hermetic test | Runs with no network, credentials or external services |
| Fake / stub / mock | Test doubles: working simplification / canned answers / interaction checker |
| Cassette (VCR) | Stored HTTP exchange replayed in tests; here all hand-made ("synthetic") |
| Contract test | Checks that an implementation honours an interface |
| AST gate | Test that parses source code and asserts a structural rule |
| `no_waiver` pin | Marker plus a test fixing the count of non-skippable invariants (14 / 9 / 23) |
| Deferred register | Test file listing known gaps as named skips with caveats |
| Parametrisation | One test function run over many inputs; raises pass counts |
| Coverage | Share of code executed by tests, not of behaviour checked |
| Mutation score | Share of injected defects that tests catch |
| Branch protection | GitHub setting that requires checks before merge |
| Ratchet | A metric that may only improve, enforced by CI |

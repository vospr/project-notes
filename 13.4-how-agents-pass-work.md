# Course 13 · Chapter 13.4: How agents pass work to each other

_Andrey Popov's project notes: how it works, why it was built this way, and the theory behind it._

**In short:** How agents hand work to each other: agent as a tool versus handoff, passing history versus a summary versus a file, typed results, spec files as hand-over, good briefs, and why stopped does not mean done.

## 2. The problem (business view, plain English)

Most failures in agent teams happen **at the hand-over**, not inside an agent. The helper didn't get the reason behind the task; the summary dropped the one detail that mattered; the result came back as a friendly paragraph the next agent misread; nobody could tell afterwards what was passed. It is the same in human teams: a bad shift handover in a hospital causes more errors than a bad doctor.

Analogy: passing a case file between departments. A good file has a fixed cover sheet (who, what, status, deadline), the key documents, and a short note on why. A bad one is "see attached, thanks".

## 4. How it works

### 4.1 Two ways to involve another agent
| | **Agent as a tool** | **Full handoff** |
|---|---|---|
| What happens | Main agent calls a helper like a function, gets a result, **stays in charge** | Main agent **gives the conversation away**; the other agent now leads |
| Analogy | Calling an outside consultant for one answer | Transferring a customer to another department |
| Who keeps the context | The caller | The receiver (gets the conversation or a summary) |
| Good for | Research, checking, calculating, drafting a part | Customer conversations that change topic; specialist takes over |
| Names | Agent Framework: agent as a tool; ADK: `AgentTool`; Claude Code: `Task` subagent | Agent Framework: handoff; ADK: transfer to a sub-agent; OpenAI Agents SDK: handoff |

### 4.2 What to pass along: three options
| Pass | Pros | Cons | Use when |
|---|---|---|---|
| **The whole history** | Nothing is lost; the receiver sees all decisions | Expensive; the receiver's context fills up; leaks irrelevant or sensitive data | Short conversations; tightly connected work |
| **A summary / brief** | Small, focused, cheap | The summary can drop the one key detail | Most agent-as-a-tool calls |
| **A file / artifact** (plan, spec, diff, report) | Durable, reviewable by humans, versioned, survives restarts | Needs a fixed structure and a place to live | Long processes, several sessions, humans in the loop |

The client shared-agents guidance says it in one line: **"Share artifacts, not whole history."** Each agent runs in its own session and reads the files the previous one left.

### 4.3 Hand-over through repo files (the spec-driven pattern)
```
 Jira ticket
     │
 [Plan agent]     reads ticket + code ─► writes  changes/<ticket>/proposal.md  (what and why, acceptance criteria)
                                                 changes/<ticket>/design.md    (how)
                                                 changes/<ticket>/tasks.md     (ordered checklist)
     │  commits to a branch, opens a draft PR ─► HUMANS REVIEW THE SPEC  ◄── approval point
     ▼
 [Implement agent] new session, reads tasks.md, does only those tasks, writes code + tests
     │
 [Verify agent]   new session, builds, tests, reviews against proposal.md, opens the PR
     │                                                                    ◄── approval point (peer review)
     ▼
 merged change: spec files and code reviewed together
```
Why this works: the hand-over is **visible** (anyone can read it), **reversible** (it's in git), **checkable** (verify compares against acceptance criteria), and it **forces a human checkpoint** before code is written.

### 4.4 Typed results, not friendly paragraphs
Between agents, ask for a fixed shape:
```
{ "status": "done" | "blocked" | "failed",
  "summary": "...", "evidence": ["commit abc123", "test report path"],
  "open_questions": [...], "next_step": "..." }
```
The next agent (or code) can check `status` without guessing from prose. If the result doesn't match the shape, reject and ask again (12.5).

### 4.5 A good brief to a helper
Cognition's rule: give the **why**, not only the **what**. A good brief has:
1. the goal and why it matters
2. what is already decided (style, constraints, earlier choices)
3. what to return, in which shape
4. limits: time, tools, budget, what not to touch

## 5. Why it was built this way (decisions and trade-offs)

| Decision | Alternatives | Why this one | Cost / risk |
|---|---|---|---|
| Files in the repo as hand-over | Pass chat history between agents | Reviewable, versioned, survives sessions, humans can edit | Files must follow a template; stale files mislead |
| New session per agent | One long session for all roles | Clean context; each agent focused on one job | Anything not written down is lost |
| Human review of the spec before code | Review only the final PR | Cheaper to fix a plan than code | Slower; needs reviewers to actually read it |
| Typed result shape | Free text | Code can route and check results | Needs validation and retries |

## 6. Theory behind it (the "lecture" part)

### 6.1 Contracts between components
In software, two parts that talk through an agreed shape (an interface or schema) can change independently. Agents are the same: a fixed brief and result format is the contract.
*In this course:* the JSON result in §4.4 is the contract; 12.5 covers enforcing it.

### 6.2 Lossy compression
A summary is lossy compression: smaller, but some information is gone for good. The risk grows with each hand-over (summary of a summary).
*In this course:* keep the original in a file and pass a summary **plus a pointer** to it.

### 6.3 Spec-driven development (SDD)
Write a short specification (what, why, how, tasks) before code, review it, then implement against it. Old idea, new reason: AI makes code cheap, so the spec becomes the main place where humans steer.
*In this course:* the plan agent writes the spec; the implement agent follows it; the verify agent checks it.

### 6.4 Shared state vs message passing
Agents can share one big state object (a blackboard) or send each other messages. Shared state is simple but needs merge rules when two write at once; messages are cleaner but need a format.
*In this course:* 13.8 shows the Python side (reducers); A2A (13.6) is message passing between companies.

## 8. Glossary

| Term | One-line definition |
|---|---|
| Agent as a tool | Calling another agent like a function; the caller stays in charge |
| Handoff | Giving control of the conversation to another agent |
| Brief | The instructions and context passed to a helper |
| Artifact | A file or object produced by an agent (spec, diff, report) used by the next step |
| Typed result | A result in a fixed structure that code can check |
| Spec-driven development | Write and review a specification before writing code |
| OpenSpec | A lightweight SDD format: proposal, design, tasks per change |
| Receipt | A record proving a step finished: who, what, evidence, outcome |
| Blackboard | A shared state that several agents read and write |

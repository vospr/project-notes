## 6. Theory behind it (the lecture part)

### 6.1 Claims, evidence and warrants

An assurance argument has a claim, supporting evidence and a warrant explaining why the evidence bears on the claim. "The suite passed" is evidence; "therefore every managed service integration works" is an invalid warrant when the services were mocked. A good argument lists assumptions and defeaters: conditions that would undermine the conclusion. In this case, local adapter tests support local policy behaviour, while actual service contracts and managed identity remain explicit defeaters of a Fabric-readiness claim.

### 6.2 Internal and external validity

Internal validity asks whether the observation supports a conclusion under the tested conditions. External validity asks whether it generalises to another environment, workload or population. Deterministic mocks improve control over conditions but remove real-service behaviour; live tests add realism but cover only their actual scope. In this case, the local wrong-value demonstration supports rejection of that constructed response under the bounded contract, not general live LLM reliability.

### 6.3 Artifact identity and reproducibility

An experiment is reproducible only when relevant code, dependencies, data, configuration and procedure can be identified. A source hash detects byte differences, but does not prove the bytes were executed, reviewed or correct. Build identity and runtime observation connect source to execution; permissions and resource state add operational context. In this case, the historical wheel's success cannot transfer automatically to an updated wheel or applied Fabric adapter source.

### 6.4 Precommitment and repeated testing

Choosing a rule after seeing outcomes creates an incentive to fit the decision to the result. A validation gate written beforehand constrains that discretion. If baseline error is positive, relative improvement is `(baseline - candidate) / baseline`; requiring at least 5% is equivalent to `candidate <= 0.95 * baseline`. Equality passes this gate. Repeatedly consulting final-test outcomes while adjusting the model turns test data into another validation set. In this case, the historical gate and final-test boundary remain protected even when preparing new teaching material.

### 6.5 Three-valued operational reasoning

Operational observations often need true, false and unknown. A timeout is not a negative existence result; an empty version list does not prove the model container is absent. Conflating unknown with false can trigger destructive creation or adoption. Fail-closed logic requires positive evidence for the permitted transition. In this case, the Fabric contract distinguishes absent, existing-empty, existing-with-versions and unknown/conflict before model operations.

### 6.6 Time of check versus time of use

A resource can change after inspection. A check performed at time t does not freeze state at time t+1. Mitigations include freshness limits, rechecks, conditional writes, transactions and exclusive writers, each with its own limits. Two matching inventories increase evidence of stability but do not create transaction isolation. In this case, bounded repeated inventories and context rechecks are local controls; they cannot prove no external writer changed the live registry.

### 6.7 Resource budgets are part of correctness

A function that eventually finds the answer but never stops under malformed pagination can be operationally incorrect. Bound attempts, elapsed time, pages, bytes and memory according to the operation. Wall-clock freshness and monotonic elapsed deadlines serve different purposes: one interprets observation age, the other limits execution duration. In this case, metadata inspection, later session work and adapter inventories have distinct budgets; ceilings are not instructions to consume the maximum.

### 6.8 Evidence maturity is not a completion percentage

Syntax checks, unit tests, local integration, target-platform execution and business outcomes answer different questions. Passing more unit tests cannot mathematically substitute for a missing live context observation. A maturity ladder is useful only if it shows what is missing rather than implying linear completion. In this case, reporting historical live evidence and later local evidence in separate columns is more informative than claiming the whole project is "90% production ready".

### 6.9 Decision rights and learning evidence

Authority to execute, acceptance of an implementation and assessment of a person's understanding are separate decisions. A reviewer can recommend; an owner can approve a bounded operation; a quiz can reveal understanding. None substitutes for the others. In this case, I retain owner responsibility for AI-assisted work, while the learning checkpoint remains pending until an actual review or assessment takes place.

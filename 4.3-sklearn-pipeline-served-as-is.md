# Course 4 · Chapter 4.3: One sklearn Pipeline, served as-is (scaler → PCA → gradient boosting)

_Andrey Popov's project notes: how it works, why it was built this way, and the theory behind it._

**In short:** Training to serving as one artefact: a scikit-learn pipeline (scaler, PCA 32, gradient boosting) logged to MLflow and loaded unchanged by the API, so served predictions equal trained ones. Uses skops instead of pickle.

## 2. The problem (business view, plain English)

A model is trained in one place and used in another. In v1 the code that built features for training (stage 2) and the code that rebuilt them for serving (stage 6) were two separate implementations. Any small difference gives the model inputs it never saw in training, and it fails quietly: predictions still come out, just wrong.

Finance analogy: a credit-scoring model developed in Python by the quants and re-coded in the bank's production system by IT. A different rounding rule, a different treatment of missing values, a different date convention, and the production score drifts from the validated one. Model-risk teams call this implementation risk. The cure is the same: ship **one artefact** and run that.

## 4. How it works (training to serving)

```
train.py                                                   serve.py
raw patches (n,32,32) --flatten--> (n,1024)                request JSON (k,32,32) --reshape--> (k,1024)
        |                                                          |
  Pipeline.fit(X_train)                                            |   mlflow.sklearn.load_model("models:/seismic-facies@champion")
   scaler.fit_transform  -> mean/std per pixel                     |        (same Pipeline object, deserialised)
   pca.fit_transform     -> 32 components                          v
   clf.fit               -> boosted trees               pipeline.predict / predict_proba  -> {"facies": [...], "proba": [...]}
        |
  mlflow.sklearn.log_model(pipeline)  ==> registered version  ==> alias `champion`
```

**The Pipeline**: `StandardScaler` → `PCA(n_components=32, random_state=0)` → `HistGradientBoostingClassifier(random_state=0)`. Input is 1,024 raw amplitudes per patch (32×32 flattened, *model.py:11-13*). `test_02_pipeline.py:10-16` asserts it is a `Pipeline` with the steps `scaler`, `pca`, `clf`.

**Training**: `pipeline.fit(Xtr, ds.y_train)` fits all three steps on training data only. Each transformer learns from the output of the previous one: the scaler learns 1,024 means and standard deviations, PCA learns 32 directions on the standardised data, the booster learns trees on the 32 scores. Validation and test patches are only ever passed through `predict`.

**Logging**: `mlflow.sklearn.log_model(pipeline, name="model", registered_model_name=model_name, input_example=Xtr[:2], skops_trusted_types=TRUSTED_TYPES)`. One call stores the fitted object (scaler statistics, PCA components, trees), a signature inferred from the example, and the environment: the demo log shows MLflow exported 93 dependencies from `uv.lock`. `TRUSTED_TYPES` lists the one extra type skops must accept for gradient boosting, instead of trusting every type.

**Serving**: at startup `create_app` loads `models:/seismic-facies@champion` (or `MODEL_URI`) with `mlflow.sklearn.load_model`; `/predict` reshapes the JSON to (k, 1024) and returns `model.predict(flat)` and `model.predict_proba(flat)`. There is no PCA, scaler or statistic anywhere in the file.

**What v1 did instead**: hand-written `extract_handcrafted_features` and `extract_embeddings`, loading `feature_scaler.pkl` and a PCA pickle separately. By my reading three things were wrong. (1) Default PCA path `data/silver/pca_model.pkl` (:94), but stage 2 saved the PCA as `data/silver/embedder/pca.pkl`; with the file missing the code prints a warning and returns **32 zeros** for the embedding (:173-178, :229-231). (2) Stage 2 standardised each trace before PCA; stage 6 applies PCA to the raw trace (:246) and never loads that scaler. (3) A trace of the wrong length is silently cut or zero-padded (:236-243).

## 5. Why it was built this way (decisions and trade-offs)

| Decision | Alternatives | Why this one | Cost / risk |
|---|---|---|---|
| One sklearn Pipeline logged to MLflow and loaded as-is | Separate feature code in training and serving; feature store | Removes the second implementation; fit-on-train-only is built in | Everything must be expressible as a Pipeline; flatten still lives outside |
| scikit-learn on flattened pixels | CNN (the review suggests a small 2D CNN) | Laptop, quick, easy to log and test | Weak image model (chapter 4.2) |
| StandardScaler + PCA(32) before the booster | Booster on raw pixels; handcrafted texture features | PCA compresses 1,024 correlated pixels to 32 scores; kept from v1 design | PCA is unsupervised and may drop class-relevant detail; no variance report |
| `HistGradientBoostingClassifier` | Random forest, logistic regression | Best of four on validation (0.824 vs 0.788 vs 0.507, *family log:7-10*) | No hyperparameter search; early-stopping behaviour differs by data size |
| `mlflow.sklearn.load_model` in the API | pyfunc with enforced signature | Direct access to `predict_proba` | No schema enforcement at the model boundary |
| Alias URI `models:/seismic-facies@champion` | Pin a version number | Promotion changes what is served without a code change (chapter 4.5) | Needs a restart to take effect; no automatic rollback |
| skops with an explicit trusted type | Plain pickle | Pickle runs arbitrary code on load; skops refuses unknown types | The trust list is a manual maintenance point |

## 6. Theory behind it (the "lecture" part)

### 6.1 The scikit-learn estimator and Pipeline contract
A **transformer** has `fit(X)` (learn parameters from data) and `transform(X)` (apply them). An **estimator/classifier** has `fit(X, y)` and `predict(X)`. `Pipeline([(n1, t1), ..., (nk, clf)])` chains them: `fit` calls `fit_transform` on each transformer in order, passing the output on, then `fit` on the last step; `predict` calls `transform` on every transformer, then `predict`. The fitted parameters (means, components, trees) are attributes of the one object, so serialising the Pipeline serialises the whole function from raw input to prediction.

The main benefit is **leakage control**: inside cross-validation, a Pipeline refits the scaler on each training fold. If you scale first and cross-validate afterwards, the scaler has seen the validation fold.

*In my project:* the scaler and PCA are refit on the training patches only and travel inside the registered artefact.

### 6.2 Standardisation and PCA
`StandardScaler`: z = (x − μ)/σ per feature, with μ, σ from the training set. PCA on centred data X (n×d) uses the SVD X = UΣVᵀ. The columns of V are the principal directions; the variance along direction j is σ_j²/(n−1); the scores are XV_k for the first k directions. The explained-variance ratio of the first k is Σ_{j≤k} σ_j² / Σ_j σ_j². PCA is **unsupervised**: it keeps directions of high variance, not directions that separate classes. It is sensitive to feature scale, which is why a scaler comes first.

*In my project:* 1,024 pixels → 32 scores. The fraction of variance kept is not reported.

### 6.3 Gradient boosting and the histogram variant
Boosting builds an additive model F_m(x) = F_{m−1}(x) + ν·h_m(x), where each tree h_m is fitted to the negative gradient of the loss at the current predictions (for squared error these are residuals; for multiclass log-loss, K trees per round, one per class, combined by softmax). ν is the learning rate. **Histogram-based** boosting first bins each feature into at most 255 bins, so finding a split costs O(bins) instead of O(samples). **Early stopping** holds out a validation fraction and stops adding trees when the loss has not improved for a set number of rounds. Controls on complexity: number of rounds, learning rate, tree depth/leaves, L2 regularisation.

*In my project:* defaults only, 100 rounds maximum unless early stopping ends it sooner, no tuning.

### 6.4 Train/serve skew
Skew is any difference between the inputs a model saw in training and the inputs it receives in production, caused by the pipeline rather than the world. Typical sources: (1) **code skew**, two implementations of the same feature; (2) **data skew**, different sources, different missing-value handling, different units; (3) **time skew**, features computed with data that is not available at prediction time. Defences, from strongest: one artefact that contains the preprocessing; one shared library called from both sides; a feature store; **parity tests** that feed the same raw rows through both paths and compare; logging the model's inputs in production and comparing them with training (drift, chapter 4.6).

*In my project:* the first defence plus a value-level parity test. The input log-and-compare defence is not built.

### 6.5 Safe model packaging
Python's pickle can execute code during loading, so loading a model file from an untrusted place is arbitrary code execution. Safer formats (skops for scikit-learn, ONNX, safetensors) restrict what can be loaded. A **model signature** describes the input and output schema; a **model URI** with a version or alias identifies what is served; recording the **environment** (pinned dependencies) makes the artefact reproducible.

*In my project:* skops with a one-type trust list, signature from `input_example`, environment exported from `uv.lock`.

## 8. Glossary

| Term | One-line definition |
|---|---|
| Pipeline | A chain of transformers plus a final estimator, fitted and applied as one object |
| Transformer | Object with `fit` and `transform` (scaler, PCA) |
| Fit on train only | Learn every statistic from training rows, never from validation or test rows |
| StandardScaler | Subtract mean, divide by standard deviation, per feature |
| PCA | Projection onto the directions of largest variance |
| Explained variance ratio | Share of total variance kept by the first k components |
| Gradient boosting | Additive trees, each fitted to the loss gradient of the current model |
| Histogram gradient boosting | Boosting on binned features (fast splits) |
| Early stopping | Stop adding trees when a held-out loss stops improving |
| Train/serve skew | Inputs differ between training and production because of pipeline differences |
| Parity test | Same raw input through both paths; outputs must match |
| Model signature | Declared input/output schema of a logged model |
| skops | Safer serialisation format for scikit-learn models than pickle |
| `classes_` | The class labels in the order of `predict_proba` columns |

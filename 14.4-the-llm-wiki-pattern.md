# Course 14 · Chapter 14.4: The LLM wiki pattern

_Andrey Popov's project notes: how it works, why it was built this way, and the theory behind it._

**In short:** The LLM wiki pattern from Karpathy: raw sources, LLM-written wiki and a schema file; ingest, query and lint; index.md and log.md; compile at ingest instead of rediscovering; scale limit; drift and silent errors.

## 2. The problem (business view, plain English)

With ordinary retrieval, the model rediscovers the same knowledge on every question: it fetches pieces, stitches them together, and forgets. Nothing accumulates. A person doing the same job would write notes: a page per topic, linked to other pages, updated as new documents arrive. People do not keep such wikis current because the bookkeeping (updating five linked pages when one document arrives) is tedious. A language model does not mind the bookkeeping.

Analogy: a research assistant who, instead of re-reading all the papers every time you ask a question, keeps a tidy binder with one summary page per topic and updates it whenever a new paper arrives.

## 4. How it works

### 4.1 Three layers
```
raw sources   (articles, papers, handoffs)   LLM reads, NEVER edits
     |
wiki          (summaries, entity pages,      LLM writes and maintains; humans read
     |         concept pages, overview)
schema        (CLAUDE.md / AGENTS.md)        rules: structure, naming, workflows; you refine it
```

### 4.2 Three operations
| Operation | What happens |
|---|---|
| **Ingest** | You add a source. The model reads it, discusses takeaways, writes a summary page, updates the index and related pages, appends to the log. One source may touch 10 to 15 pages. The author prefers one source at a time with supervision. |
| **Query** | The model searches the wiki, reads relevant pages and answers with citations. A good answer can be filed back as a new page so it compounds. |
| **Lint** | Periodic health check: contradictions, stale claims, orphan pages (nothing links to them), missing concept pages, missing cross-references, gaps in the data. |

### 4.3 Two special files
- **`index.md`**: content-oriented catalogue of every page: link, one-line summary, optional metadata. Read first when answering; updated on each ingest.
- **`log.md`**: chronological, append-only record of ingests, queries and lint passes. A consistent entry prefix (for example a dated heading with the word "ingest") makes it searchable with simple tools. Guides disagree on whether newest goes first; check the gist if order matters.

### 4.4 A tiny example of the discipline
```
raw/handoff-2026-10-02.md        <- never edited
wiki/architecture.md             <- gets one new bullet, with "Source: raw/handoff-2026-10-02.md"
wiki/index.md                    <- summary line refreshed
wiki/log.md                      <- "## [2026-10-02] ingest | handoff-2026-10-02"
```

### 4.5 Scale
The author says the index-based approach works well at roughly 100 sources and hundreds of pages without embedding-based search. Beyond that, add a search tool (for example local hybrid search, 14.5) in front of the pages.

## 5. Why it was built this way (decisions and trade-offs)

| Decision | Alternatives | Why this one | Cost / risk |
|---|---|---|---|
| Compile knowledge at ingest time | Retrieve and synthesise at every question | Work is done once; answers compound; humans can read and fix pages | LLM cost on each ingest; mistakes persist until linted |
| Raw sources immutable | Edit sources | Provenance: you can always check the page against the original | More storage |
| Index file instead of a vector store | Embeddings | Auditable, no infrastructure, good to moderate scale | Hits a ceiling |
| A schema file | Ad hoc prompting | Turns the model into a disciplined maintainer; refine over time | Must be kept in step with practice |
| Human reviews risky changes | Fully autonomous updates | Wikis can look clean and still be wrong (dropped facts, merged concepts) | Review time |

## 6. Theory behind it (the "lecture" part)

### 6.1 Compilation vs interpretation
A compiler translates once and runs fast; an interpreter translates on every run. RAG interprets knowledge at each question; a wiki compiles it. Compilation can be wrong in a way that stays wrong, so it needs tests (lint).
*In this course:* the "lint" operation is the test suite of the wiki.

### 6.2 Maintenance is the real cost
The gist's argument: human wikis die because upkeep, not reading or thinking, is the burden. Cheap automated upkeep changes the economics, but only if the upkeep is checkable.
*In this course:* anti-rot (14.6) is that checkability.

### 6.3 Provenance
Every claim should point back to a source file and date, so a reader can verify it and a checker can detect when the source has changed.
*In this course:* "Source:" lines and the compiled-date headers in my wiki pages are provenance, but without hashes they cannot be machine-checked (14.10).

### 6.4 Supersede, do not silently overwrite
When a decision changes, mark the old one as replaced and keep it visible, rather than quietly editing it away. Otherwise two versions of the truth coexist or the history vanishes.
*In this course:* the Verdaca wiki shows both ways: a post-close paragraph added on top of older text that is now historical.

### 6.5 Wiki vs RAG in one table
| | RAG | LLM wiki |
|---|---|---|
| Work happens | At question time | At ingest time |
| Knowledge accumulates | No | Yes |
| Readable by humans | Indirectly | Yes, directly |
| Scale | Large | Moderate, then add search |
| Main failure | Missing or irrelevant chunks | Drift and silent errors |

## 8. Glossary

| Term | One-line definition |
|---|---|
| LLM wiki | Linked markdown pages written and maintained by an LLM from raw sources |
| Raw sources | The original documents; read-only for the model |
| Schema file | Instructions that define the wiki's structure and workflows |
| Ingest | Add a source and update all affected pages |
| Lint | Periodic check for contradictions, staleness, orphans and gaps |
| Orphan page | A page that nothing links to |
| `index.md` | Catalogue of every page with a one-line summary |
| `log.md` | Append-only, dated record of operations |
| Compounding | Answers and pages added back so later questions are easier |
| Supersede | Mark an older statement as replaced, keeping it visible |

_Andrey Popov's project notes: how it works, why it was built this way, and the theory behind it._

**In short:** The promotion gate and registry: a new model becomes champion only if it beats the majority baseline on accuracy and macro-F1 and the incumbent on macro-F1; ties lose. Uses MLflow aliases; rejected versions stay registered for audit.

## 2. The problem (business view, plain English)

In v1 a model was registered but nothing decided whether it was good enough to use: the function that moves a model between lifecycle stages existed and was never called. Every retrain could replace the last without a check. The redo adds a rule: a new model only becomes the one that is served if it beats a dumb baseline and the model currently in service.

Finance analogy: a champion–challenger test in credit decisioning. The incumbent strategy keeps running until a challenger beats it on the same hold-out population. Model-risk policy usually adds a minimum sample, a significance or margin requirement, and a human sign-off. This repo implements the first part only.

## 4. How it works

```
train.run(ds)
   fit Pipeline on train  ──►  score on VALIDATION: metrics
                                majority baseline on validation
                                champion (alias lookup, load, re-score on validation) or None
   gate.decide(metrics, baseline, champion) ──► promote? + reasons
   predict test1 once (reporting only)
   mlflow run: params, metrics (val_*, test_*), tags gate.promote / gate.reasons, per-class report
   log_model(registered_model_name) ──► new model VERSION n   (always, even if rejected)
   if promote: set alias `champion` -> n
serve: models:/seismic-facies@champion  (resolved at API startup)
```

**The gate**:
```python
for k in ("accuracy", "macro_f1"):
    if challenger[k] <= baseline[k]: reasons.append(...)
if champion is not None and challenger["macro_f1"] <= champion["macro_f1"]:
    reasons.append(...)
return GateResult(promote=not reasons, reasons=reasons or ["beats baseline" + ...])
```
`promote` is true only if the `reasons` list is empty. All failed checks are listed together. The baseline is the **training** majority class applied to the evaluation labels; the same helper computes it on validation for the gate and on test1 for reporting.

**Registry mechanics**: `log_model(..., registered_model_name=name)` creates a new numbered version every run. Only `client.set_registered_model_alias(name, "champion", version)` marks it as the served one. Rejected versions stay registered "for audit"; the verdict is stored as run tags `gate.promote` and `gate.reasons` (:76), on the run, not on the model version.

**What the gate tests assert**
- below baseline on either metric is rejected (:16-20, including accuracy 0.60 with macro-F1 0.10 equal to baseline)
- first model promoted if it beats baseline (:23)
- worse than the champion and **tied** both rejected, strictly better promoted (:27-30)
- integration through a real MLflow sqlite store: a good model gets the alias; a weak one (`n_components=1`) is registered but does not move it; a uniform-random `DummyClassifier` gets no alias at all (:33-58)

## 5. Why it was built this way (decisions and trade-offs)

| Decision | Alternatives | Why this one | Cost / risk |
|---|---|---|---|
| Beat the majority baseline on accuracy and macro-F1 | Macro-F1 only; a stronger baseline | Macro-F1 alone passes a no-skill model that spreads its guesses (chapter 4.1) | Majority baseline is the weakest baseline |
| Beat the incumbent champion | Absolute threshold | No silent regression across retrains | Ratchet on a reused validation set |
| Champion re-scored on the same validation set | Compare stored scores | Like-for-like even if the data or code changed | Needs loading and predicting every run |
| Champion compared on macro-F1 only | Accuracy too; per-class floors | Imbalanced data | Accuracy can drop silently |
| Strict inequality, ties lose | `>=` or a margin | Identical retrains must not churn the alias | No tolerance for noise |
| Register every run, alias only on promotion | Register only winners | Audit trail of rejections | Registry fills with rejected versions |
| Aliases (`@champion`) | MLflow stages (deprecated) | Current pattern; the served model changes without code change | Restart needed to pick up a change |
| Gate on validation, not test1 | Test1 (first pass) | Decisions must not use the reporting set (chapter 4.4) | Validation lacks rare classes |
| Automatic promotion | Human approval step | Small demo | Not acceptable in regulated settings |

## 6. Theory behind it (the "lecture" part)

### 6.1 Experiment tracking versus model registry
**Tracking** records what happened: an *experiment* contains *runs*; each run stores parameters, metrics, tags and *artifacts* (files such as the model, plots, a per-class report). **The registry** manages what is used: a *registered model* (a name) has numbered *versions*, each pointing to the artifacts of one run, with tags and aliases. Backends: a *backend store* (here SQLite) for metadata and an *artifact store* (a folder) for files. A registered version is meant to be immutable; what changes is which version a name or alias points to.

*In my project:* one experiment `seismic-facies`, one registered model `seismic-facies`, runs log `val_*`, `test_*` metrics and the gate tags.

### 6.2 Stages versus aliases
Older MLflow used fixed lifecycle **stages** (None, Staging, Production, Archived); one version per stage; deprecated in the 2.9+/3.x line. **Aliases** are named, mutable pointers to exactly one version of a model; a version can carry several aliases; a model URI `models:/name@alias` resolves the alias when loaded. Common names: `champion` (serving), `challenger` (candidate under test). Rolling back is repointing the alias, not retraining.

*In my project:* one alias, `champion`, set by the gate; serving URI default `models:/seismic-facies@champion`.

### 6.3 Release gates
A gate is a rule evaluated automatically before a model reaches users. Typical layers: (1) **absolute**: beats a baseline or a threshold; (2) **relative**: beats the incumbent; (3) **safety/slices**: no class or segment falls below a floor; (4) **operational**: latency, size, schema compatibility; (5) **human approval** where policy requires it; (6) staged rollout (shadow mode, canary, A/B test). A gate must be able to fail, and a gate's own failure mode (error, missing data) should fail **closed**: no promotion.

*In my project:* layers (1) and (2) only; failure of the champion lookup fails open.

### 6.4 Comparing two classifiers fairly
Two models scored on the same n cases are **paired**. Let b = cases model A gets right and B wrong, c = the reverse. **McNemar's test**: under equal accuracy b and c are about equal; the statistic (|b − c| − 1)²/(b + c) follows χ² with 1 degree of freedom, or z = (b − c)/√(b + c). A difference in macro-F1 has no simple closed form; use a **paired bootstrap**, resampling cases (or, with spatial data, whole sections) and recomputing the difference. A **margin** δ turns "better" into "better by at least δ" (non-inferiority and superiority tests use this). Without any of these, small improvements are noise, and picking the best of many noisy challengers drifts upward (chapter 4.4, §6.4).

*In my project:* none used. The gate's rule is a point comparison of two single-seed numbers.

### 6.5 Choosing the gate metric
Pick the metric the business cares about and check it against chance. For K balanced-ish classes, accuracy has chance max π_c, macro-F1 has chance 1/K for a prior-matched guesser and 2p/(1+p)/K for a majority predictor (derivation in chapter 4.1). Two metrics are safer than one because they fail differently: macro-F1 alone is beaten by a spread-out random guesser (0.33 vs 0.23 in v1), accuracy alone by a majority predictor on imbalanced data. Add per-class recall floors when a rare class must not be ignored.

*In my project:* both metrics against the baseline; no per-class floor.

### 6.6 Determinism and flaky gates
With fixed seeds the same data and code give identical numbers (run 2 equals run 1 to every digit). Change a seed and a gate with no margin can flip between promote and reject. Remedies: several seeds per candidate with mean and spread, a margin larger than the seed-to-seed spread, or a statistical test.

*In my project:* seeds fixed at 0, single seed, so the tie test is deterministic and says nothing about stability.

## 8. Glossary

| Term | One-line definition |
|---|---|
| Experiment / run | A group of training attempts / one attempt with its params, metrics, files |
| Registered model | A named model in the registry, with numbered versions |
| Model version | One immutable registered artefact (here: one Pipeline) |
| Alias | A mutable name (`champion`) pointing to one version; URI `models:/name@alias` |
| Stage (deprecated) | Fixed lifecycle label in older MLflow |
| Champion / challenger | The model in service / a candidate to replace it |
| Promotion gate | Automatic rule that decides whether a candidate becomes the champion |
| Majority-class baseline | Always predict the most frequent training class |
| Strict inequality | `<=` rejects ties: a challenger must be strictly better |
| Paired comparison | Two models scored on the same cases; errors compared case by case |
| McNemar's test | Test on the discordant pairs b and c of two classifiers |
| Fail open / fail closed | On error, allow / block the action |
| Backend store / artifact store | Where MLflow keeps metadata / files |
| skops trusted types | Types the loader is allowed to rebuild (security) |

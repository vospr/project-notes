_Andrey Popov's project notes: how it works, why it was built this way, and the theory behind it._

**In short:** Safety, security and governance for LLM applications: guardrail layers and modes, prompt injection and its architectural defences, untrusted tool metadata, PII redaction, data residency, central policy across teams, audit trails and the OWASP LLM Top 10.

## 2. The problem (business view, plain English)

An LLM application takes untrusted text in, produces text that people act on, and increasingly calls tools that change things. That opens three doors: someone makes it say what it must not (toxic content, investment advice, a competitor's name, a leaked system prompt), someone makes it do what it must not (injection through a retrieved document that triggers a tool call), and data goes where it must not (PII to a model provider, EU data to a US region, one client's documents to another). In a bank all three are supervisory issues, not just product bugs.

Finance analogy: controls in a payments process. Input checks (sanctions screening), output checks (four-eyes on large payments), segregation of duties (who can release), data controls (need-to-know), and an audit log a regulator can replay. Guardrails are the same control framework applied to a model.

## 4. How it works (guardrails in layers)

```
 user input ─► INPUT LAYER (in parallel, all before the model)
               ├─ toxicity / content filters ............ block
               ├─ prompt-attack / injection classifier ... block or flag
               ├─ PII detection ......................... redact (mask) before sending
               └─ denied topics (e.g. investment advice) . block with a fixed message
                     │
                     ▼
 model ◄── trusted instructions (system / operator) kept separate from untrusted data
   │         (retrieved docs, web pages, tool outputs, emails = data, never commands)
   ▼
 ACTION LAYER ─ tool gates: least privilege, approval for consequential actions, deny by default
   │
   ▼
 OUTPUT LAYER ─ content filters · PII · word filters (competitor names) · topic check ·
               contextual grounding check (threshold high for regulated content)
   │                ├─ block ─► safe fallback message
   │                └─ detect ─► deliver + notify / queue for human review
   ▼
 AUDIT ─ who, what, when: API audit log, data-access log, prompt/response store with retention
```

## 5. Why it is done this way (decisions and trade-offs)

| Decision | Alternatives | Why this one | Cost / risk |
|---|---|---|---|
| Layered guardrails outside the model | System-prompt rules only | Independent of model behaviour; testable; auditable | Latency; false positives |
| Input filters in parallel, before the model | Sequential stages | Same protection, lower latency | All must finish before the call |
| Redact PII before the model | Detect only; trust provider terms | Data never leaves; simplest compliance story | Redaction can remove needed context |
| Detect-and-notify for some categories | Block everything flagged | Keeps useful answers flowing; humans see edge cases | Needs a review process |
| Trust per server/vendor, not per annotation | Trust annotations | Annotations are self-reported | Manual vendor assessment |
| Central guardrail required by org policy | Each team configures its own | Uniform, enforced, auditable | Less team flexibility |
| Geo-scoped inference + deny other regions | Single region; trust the app | Residency enforced by platform and policy | Possible capacity limits |
| Separate data per tenant / column-level grants | Shared store + logs | Preventive isolation | More resources to manage |

## 6. Theory (the lecture)

### 6.1 Threat model: OWASP Top 10 for LLM applications (2025)
1. **Prompt injection** (direct from the user; indirect through retrieved or tool content)
2. **Sensitive information disclosure** (PII, secrets, other tenants' data)
3. **Supply chain** (models, datasets, plugins, MCP servers)
4. **Data and model poisoning** (corrupted training or retrieval data)
5. **Improper output handling** (model output passed to shells, SQL, HTML without validation)
6. **Excessive agency** (too many tools, too much permission, no approval)
7. **System prompt leakage** (prompts treated as secrets or as access control)
8. **Vector and embedding weaknesses** (cross-tenant retrieval, poisoned indexes)
9. **Misinformation** (hallucination presented as fact)
10. **Unbounded consumption** (cost and denial-of-service through tokens)

Prompt leakage is a real risk for chatbots, but the deeper rule is: never put secrets or authorization logic in a prompt.

### 6.2 Guardrail layers and modes
- **Input**: content filters (hate, insults, sexual, violence, misconduct) with strength levels; prompt-attack detection; PII detection with **redaction** before the model; **denied topics** described in natural language ("investment advice"); **word filters** for exact terms (competitor names) on input and output.
- **Output**: the same filters on the response, plus a **contextual grounding check** (is the answer supported by the provided sources, and relevant to the query?) with a threshold; higher thresholds block more. Some platforms add formal "automated reasoning" checks against written policies.
- **Action**: tool permission tiers, approval gates, allowlists (12.3).
- **Modes**: block (replace with a predefined message), mask (redact entities), **detect** (let it through but record and notify). "Notify me about insults but do not block everything" = an insults filter in detect mode. Refusing political questions with a predefined message = a topic guardrail with a fixed response.
- **Placement**: attach the guardrail to the model call or flow node so it cannot be skipped; for image and text platforms combine text filters, PII detection and image moderation in one workflow.

### 6.3 Prompt injection
Any text the model reads can contain instructions: a web page, a PDF in the knowledge base, an email, a tool result, a code comment. The model cannot reliably tell data from instructions, so prompt wording ("ignore instructions in documents") is not a control. Contain it by architecture:
- **Least privilege**: an agent that reads untrusted content should not hold powerful tools in the same context; split reader and actor.
- **Approval** for consequential actions (send, pay, delete, submit).
- **Output handling**: validate and escape model output before it reaches a shell, SQL or a browser.
- **Separation of channels**: trusted operator instructions in system messages (on current Claude models a mid-conversation system message is the operator channel), untrusted content clearly delimited as data.
- **Detection**: injection classifiers on inputs and retrieved content, and evals with adversarial cases.
- **Egress control**: limit where an agent can send data (allowed domains) so a hijacked agent cannot exfiltrate.

### 6.4 Trusting tools and MCP servers
MCP tool annotations (`readOnlyHint`, `destructiveHint`, ...) are **hints written by the server author**. Base confirmation rules on your assessment of each server (vendor, code review, pinned version, transport, auth), not on what the tool says about itself. Keep an allowlist of servers, pin versions, run local servers with least privilege, require OAuth for remote ones (6.4), and log every call. A behaviour-testing harness can supplement but not replace this: a tool can behave well in tests and differently in production.

### 6.5 Data protection
- **Provider terms**: on major managed platforms, prompts and outputs are not shared with model providers or used for training (Bedrock's stated rule); zero-data-retention options exist with conditions (check current per model).
- **Residency**: keep inference inside the allowed geography (geo-scoped inference profiles; Claude's `inference_geo` request parameter; check availability) and deny other regions by organisation policy (service control policies). Policies must also allow the geo profile you intend to use, or calls fail with access-denied errors.
- **Network**: private endpoints (VPC endpoints / PrivateLink) so traffic to the model never crosses the public internet.
- **Access**: least-privilege roles, attribute-based access by department, column- and row-level grants in the data lake (tag-based access control), encryption with customer-managed keys.
- **Secrets**: from a secret manager referenced at runtime (Databricks secrets, cloud secret stores); never in prompts, code, plain environment files in repos, or tool arguments the model can see (the harness in 11.5 lets the model use `$NAME` and never sees the value).
- **Swiss context**: FADP/nDSG for personal data, FINMA outsourcing and cloud expectations, client confidentiality; see 10.4 and 6.3.

### 6.6 Central policy at organisation scale
For many teams and accounts: deny model invocation unless an approved guardrail identifier is attached, allow only approved models, and deploy the guardrail itself centrally (infrastructure as code to every account). Give business units **standardised, versioned blueprints** (security, observability, deployment patterns for RAG) through a service catalog instead of a design document each team interprets. Manage **prompt templates** as governed assets: versions, approval permissions, parameters (variables) instead of free text, and an audit log of changes.

### 6.7 Audit and lineage
Regulators and auditors ask "who accessed what, when, and what did the model say?" Keep: an API audit log (management and data events, including key usage), data-access logs on storage, model invocation logs with prompts, responses, and images or documents where required, with retention; a registry of data sources with tags so generated content can be traced to its sources; and lineage of training and retrieval data (lifecycle management) for regulated decisions such as loan approvals. Use API audit logs to detect unauthorized model calls.

### 6.8 Oversight and evaluation of safety
Scale with automation, focus humans on risk: an LLM judge for accuracy and appropriateness on samples, guardrails for policy compliance on every call, and human review for flagged and critical interactions (human-in-the-loop services or your own queue). Red-team before launch (injection, jailbreaks, PII extraction, off-topic), and keep those cases in the regression suite (10.1). Grounding plus guardrails plus logged prompt-response pairs is the least-effort governance baseline for a customer-facing assistant.

## 8. Glossary

| Term | One-line definition |
|---|---|
| Guardrail | Policy check on inputs, outputs or actions, outside the model |
| Denied topic | Subject the assistant must refuse, described in natural language |
| Word filter | Exact terms blocked on input or output |
| Contextual grounding check | Test that an answer is supported by its sources and relevant to the query |
| Detect vs block vs mask | Record and notify / replace / redact |
| Prompt injection (direct, indirect) | Instructions smuggled in through user input / through content the model reads |
| Excessive agency | An agent with more tools or permissions than its task needs |
| PII redaction | Removing personal data before it reaches the model or the log |
| Data residency | Requirement that data and processing stay in a geography |
| Geo inference profile | Routing that spreads requests only across regions of one geography |
| Private endpoint | Network path to a service that avoids the public internet |
| Service control policy | Organisation-level rule that caps what accounts may do |
| Audit trail | Durable record of who did what, when |
| Red-teaming | Adversarial testing for jailbreaks, injection and leakage |

# Course 10 · Chapter 10.1: LLM evaluation: golden sets, LLM-as-judge, metrics, sample size, regression suites

_Andrey Popov's project notes: how it works, why it was built this way, and the theory behind it._

**In short:** How to evaluate an LLM application: golden sets, programmatic scorers before LLM judges, judge biases and calibration against humans, confidence intervals and sample size (97 items for plus or minus 10 points), CI regression suites and FINMA-style tests.

## 2. The problem (business view, plain English)

An LLM application fails in ways a unit test cannot see: the answer is fluent and wrong, a prompt tweak fixes one case and breaks three, a model upgrade changes behaviour overnight. Without a measurement, every change is an opinion. At a Swiss bank or insurer the problem is sharper. FINMA Guidance 08/2024 says that supervised institutions should schedule tests for accuracy, robustness, stability and, where needed, bias, define performance indicators in advance, and monitor outputs over time (see 10.4). "It looked good in the demo" is not an answer to a model-validation function or an auditor.

Finance analogy: back-testing and champion-challenger. A trading or credit model is never judged on a story. It is run on held-out history, compared with a benchmark, and re-tested when the market changes. An eval set is the LLM version of the back-test window; the regression suite is the standing champion-challenger run; a judge model is a junior reviewer whose own error rate you must measure before you rely on them.

## 4. How it works (an eval pipeline end to end)

```
 production traces / SMEs ─► candidate cases ─► label (guideline, 2 annotators, kappa) ─► golden set (versioned)
                                                                                           │
 system under test (prompt vN, model, retriever) ─► run (repeat k times) ─► outputs + raw replies saved
                                                                                           │
          scorers: exact / schema / code check ─┬─► metrics per slice ─► CI (bootstrap / Wilson) ─► compare to baseline
          LLM judge (calibrated on human set) ──┘                                            │
                                                                                      gate in CI: block / warn
 online: shadow ► canary ► A/B ► sampled human review ─► new failures flow back into the golden set
```

**Step 1: define the task and the failure modes.** Write what "good" means per task (an annotation guideline). List failure modes from real data: wrong fact, missing citation, wrong format, unsafe content, refusal when it should answer. Error analysis comes before metric design: read 50-100 real outputs, group the failures, and let the categories drive the metrics.

**Step 2: build the golden set.** Sources: production logs (with consent and PII handling), domain-expert written cases, adversarial cases, and out-of-scope cases on purpose. Label with a written guideline; double-label a sample; measure agreement. Version the set like code. Keep a dev split for tuning and a held-out split for the number you report.

**Step 3: score.** Prefer programmatic checks (schema validity, exact match, regex, unit-test style assertions on extracted values). Use an LLM judge only where the criterion needs language understanding. Save per-item predictions and raw replies, otherwise no paired test and no error analysis are possible.

**Step 4: aggregate with uncertainty.** Metric per slice, with an interval, against a named baseline (rules, previous prompt, previous model, simple heuristic).

**Step 5: gate.** A cheap subset on every pull request; the full suite nightly or on release. Block only on effects larger than the noise.

**Step 6: online.** Shadow mode (the new system runs on live traffic, users see the old output), canary, A/B, sampled human review of production outputs. Monitor drift in inputs and in judge scores.

## 5. Why it is done this way (decisions and trade-offs)

| Decision | Alternatives | Why this one | Cost / risk |
|---|---|---|---|
| Golden set from real traffic plus expert cases | Synthetic LLM-written cases only | Real distribution; synthetic cases share the generator's blind spots | PII handling; slow to collect |
| Programmatic scorer first, judge second | Judge for everything | Deterministic, free, auditable | Cannot score open-ended quality |
| Calibrate judge on 100-200 human-labelled items | Trust the judge | Gives TPR/TNR so scores can be corrected | Human labelling cost |
| Pairwise for "which is better", pointwise for pass/fail gates | One mode for all | Humans and judges are more reliable at relative comparisons; gates need absolute thresholds | Pairwise needs position swapping (2x cost) |
| Interval and paired test | Single accuracy number | Shows if a gain is noise | Needs per-item results saved |
| Two-tier CI (smoke on PR, full nightly) | Full suite every commit | Cost and speed (each LLM eval costs money and minutes) | Nightly catches regressions a day late |
| Thresholds written before results | Decide after seeing numbers | Prevents moving the goalposts (`1.5-feature-ablation.md`) | Thresholds may need revision with real variance |
| Shadow mode before launch (banks) | Direct launch | Real inputs, no customer impact; evidence for the validation function | Needs infrastructure; double inference cost |

## 6. Theory (the lecture)

### 6.1 What an eval is, and offline vs online
An **evaluation** is a repeatable procedure that maps a system version to numbers that support a decision. **Offline evals** run on a fixed dataset: cheap, fast, repeatable, safe; their weakness is **construct validity** (does the dataset represent production?) and staleness. **Online evals** use live traffic: A/B tests, canaries, shadow runs, implicit signals (edits, regenerations, abandon rate), explicit feedback (thumbs), and sampled human review. Online tests measure what matters but are slow, noisy and need guardrail metrics (latency, cost, complaint rate, escalation rate). Good practice is a funnel: offline eval filters candidates, shadow mode verifies on real inputs, a canary or A/B test confirms impact.

*In my project:* only offline. The 40-row set is a developer's idea of user queries, not traffic (`7.3-building-a-routing-eval.md`).

### 6.2 Golden sets and labels
A **golden (gold) set** is a collection of inputs with agreed correct outputs or grading criteria. Requirements: **representative** (matches the production mix, including hard and out-of-scope cases), **correct** (labels verified), **sufficient** (n large enough for the decision, 6.5), **independent** (not used to tune the system), **versioned**. Contamination (test items copied into prompts or training data) invalidates results. Inter-annotator agreement: Cohen's κ = (p_o − p_e) / (1 − p_e), where p_o is observed agreement and p_e is chance agreement; κ above about 0.8 is strong. Disagreement bounds the achievable accuracy: if humans agree 90%, a system scoring 95% against one annotator is suspicious.

*In my project:* one AI annotator, no κ, no split (`7.3-building-a-routing-eval.md`).

### 6.3 Metrics by task type
**Classification / routing.** Confusion matrix; accuracy = correct / n; per class precision P = TP/(TP+FP), recall R = TP/(TP+FN), F1 = 2PR/(P+R); macro-F1 averages F1 over classes (small classes count equally); micro-F1 pools counts. Always report a majority-class baseline. If one class is a default or "abstain" bucket, its recall is trivially high; look at its precision.

**Extraction (structured fields from documents).** Parse validity (does it match the schema), then field-level exact match or normalised match (dates, amounts, currency), per-field precision and recall, and document-level "all fields correct" rate. In finance, amount and date fields carry zero tolerance; weight them in the score.

**Retrieval** (10.2): recall@k, MRR, nDCG.

**Generation (free text).** Options, from cheap to expensive: (a) reference-based overlap (BLEU, ROUGE): weak for open answers; (b) embedding similarity (BERTScore and similar): captures meaning better, still a proxy; (c) rule checks (contains citation, no forbidden phrase, length bounds, valid JSON); (d) LLM-as-judge with a rubric (6.4); (e) human review. For **faithfulness** (is every claim supported by the provided context) use claim decomposition: split the answer into atomic claims, check each against the context, faithfulness = supported claims / all claims.

**Code / task completion.** Unit tests as oracle; **pass@k** (Chen et al., 2021): with n samples of which c pass, pass@k = 1 − C(n−c, k) / C(n, k), the chance that at least one of k samples passes. For reliability-critical use, report **pass^k** (all k attempts pass) which falls as p^k: p = 0.9 gives 0.73 at k = 3 and 0.59 at k = 5 (my arithmetic).

*In my project:* accuracy, per-route recall and (my arithmetic) precision and macro-F1 for the router (`7.3-building-a-routing-eval.md`).

### 6.4 LLM-as-judge
Use a model to grade another model's output against a rubric or a reference. Reported agreement with humans can be high (Zheng et al., 2023, "Judging LLM-as-a-Judge with MT-Bench and Chatbot Arena", reported above 80% agreement for a strong judge, similar to human-human agreement on that task). It is cheap and scalable, but it is a **measuring instrument with its own error**, so it must be calibrated.

Known biases:
- **Position bias:** the judge prefers the answer in a given slot (often the first). Mitigation: run both orders and count a win only if it holds in both; otherwise call it a tie.
- **Verbosity (length) bias:** longer answers score higher. Mitigation: rubric that penalises padding, length-controlled comparison, or compare at equal length.
- **Self-preference (self-enhancement) bias:** a judge favours text from its own model family. Mitigation: judge with a different family from the generator, or use several judges.
- Also: sensitivity to rubric wording, to formatting (markdown, lists), and to a "confident" tone; weak at checking facts it does not know; can be prompt-injected by the output it grades.

Good judge design: an explicit rubric with anchored levels, a binary or 3-point scale rather than 1-10, reasoning before the verdict (or a structured output with reasons), a reference answer when one exists, temperature 0, pinned judge model version.

**Calibration against humans.** Label 100-200 items by humans (double-labelled on a sample). Run the judge. Compute agreement (κ) and, for a binary criterion, the judge's true-positive rate (TPR) and true-negative rate (TNR) against the human labels. An observed judge pass rate q relates to the true pass rate π by q = π·TPR + (1 − π)(1 − TNR). Solving gives the corrected estimate (Rogan-Gladen): **π = (q + TNR − 1) / (TPR + TNR − 1)**. Example (my arithmetic): judge says 70% pass, TPR = 0.9, TNR = 0.8, so π = (0.70 + 0.8 − 1) / (0.9 + 0.8 − 1) = 0.5 / 0.7 = 0.714. If TPR + TNR is near 1 the judge is almost uninformative and the correction blows up.

**Pairwise vs pointwise.**
| | Pointwise (score one output) | Pairwise (pick the better of two) |
|---|---|---|
| Good for | Absolute gates (pass/fail), production monitoring | Model/prompt comparison, preference ranking |
| Reliability | Scores drift, scale use varies | More stable; humans and judges are better at relative judgement |
| Cost | n judge calls | 2n calls if you swap positions |
| Aggregation | Mean / pass rate | Win rate with ties; Bradley-Terry or Elo for many systems |
| Risk | Calibration of the scale | Position bias; intransitivity |

Bradley-Terry: P(i beats j) = s_i / (s_i + s_j); fit s from the win matrix by maximum likelihood.

*In my project:* not built. The label contract of the router is the same problem in miniature: who labelled, and was it checked (`7.3-building-a-routing-eval.md`).

### 6.5 Sample size and confidence intervals
For a measured proportion p̂ on n independent items, SE = √(p̂(1 − p̂)/n). Wilson interval (better at small n and near 0 or 1): centre (p̂ + z²/2n) / (1 + z²/n), half-width z·√(p̂(1 − p̂)/n + z²/4n²) / (1 + z²/n), z = 1.96 for 95%.

**Sample size for a target margin E** at 95%: n = z²·p(1 − p) / E². Worst case p = 0.5: E = 10 points needs 97 items, E = 5 points needs 385, E = 3 points needs 1,068 (my arithmetic).

**Comparing two systems on the same items (paired).** b = items only A got right, c = items only B got right. Exact McNemar: under no difference, b ~ Binomial(b + c, ½). SE of the accuracy difference = √(b + c − (b − c)²/n) / n. If the systems differ on a fraction d of items, SE ≈ √(d/n): with d = 10% and n = 400, SE ≈ 1.6 points, so a 95% interval of about ±3 points (my arithmetic). Pairing helps when systems agree on most items.

**Power / minimum detectable effect.** For two independent accuracies near p̄, 80% power, 5% two-sided: n per arm ≈ 2(1.96 + 0.84)² p̄(1 − p̄) / δ². At p̄ = 0.6, detecting δ = 10 points needs about 380 per arm; at n = 40 the smallest reliably detectable unpaired gap is about 31 points.

**Non-determinism.** Add variance from the model: repeat each item k times, average per item, and use **cluster/bootstrap** resampling over items (the repeats of one item are not independent). Bootstrap: resample items with replacement 1,000-10,000 times, recompute the metric, take the 2.5th and 97.5th percentiles. For paired comparison bootstrap the per-item differences.

**Rule of three.** Zero events in n trials: 95% upper bound ≈ 3/n.

**Multiple comparisons / winner's curse.** Comparing many prompts on one set and picking the best inflates its score. Re-confirm the winner on fresh data.

*In my project:* SE of 26/40 is 7.5 points; Wilson interval about 49.5-77.9%; MDE about 31 points (`7.3-building-a-routing-eval.md`).

### 6.6 Regression suites in CI
A **regression suite** is a standing set of cases that must not get worse. Pattern:
- **Tiers.** (1) Deterministic checks (schema, format, forbidden content, tool-call shape) on every commit: seconds, free. (2) A small golden subset (30-100 cases) with an LLM judge on every pull request that touches prompts, retrieval or model config. (3) The full suite nightly and before release.
- **What triggers it:** change in prompt, model id or version, retriever, chunking, tool schema, or dependency.
- **Gating rule:** block if the metric falls by more than the noise margin Δ, estimated from repeat runs; warn on smaller falls. A drop of 2 points on 40 items is noise; on 1,000 items it may be real.
- **Pin everything:** model version (dated snapshot where available; aliases drift), prompt version, retriever index version, temperature, seed where supported.
- **Cost control:** cache judge calls by (input, output, rubric hash); run the cheap tier first.
- **Close the loop:** every production failure becomes a new case with its label.
- **Do not let the suite rot:** review flaky cases, retire stale ones, keep a changelog for the golden set.

*In my project:* the router eval is committed with results and a test pins the README to the JSON; rules-only re-runs are tested; LLM arms cannot be re-verified offline. CI honesty (`2.6-testing-and-ci-honesty.md`): a green suite means little if tests are not collected or only prove shape.

### 6.7 Eval-driven development
Write the eval before (or together with) the feature, like test-driven development. Loop: collect 20-50 real or realistic cases → write a first metric → establish the baseline (simplest prompt or rules) → change one thing → re-measure → keep or revert. Rules: change one variable at a time; look at failures, not only the score; keep a log of experiments; pre-register the decision threshold. Risk: **Goodhart's law**. When a metric becomes a target it stops being a good measure, so refresh the set and keep a hidden holdout.

*In my project:* the redo of the concierge built the eval after the claim ("hybrid routing is accurate and cost-effective") had no evidence; the right order is the reverse (`7.3-building-a-routing-eval.md`).

### 6.8 Safety, bias and robustness evals (what Swiss supervisors ask about)
FINMA lists tests for accuracy, robustness, stability and, if necessary, bias, including sensitivity analyses, stress tests, adversarial tests with incorrect input, comparison with simpler benchmark models, and repeatability checks (Guidance 08/2024, section 2.4 and footnote 8; see 10.4). For an LLM application translate this into: paraphrase and typo robustness (same answer under rewording), adversarial and prompt-injection cases, out-of-scope refusals, demographic parity checks on outputs where a decision touches customers, repeatability (same input, k runs, agreement), and a **simple benchmark** (rules, keyword search or a smaller model) that the LLM must beat.

*In my project:* the rules-only arm and the majority-class baseline play the role of the "simpler benchmark" (`7.3-building-a-routing-eval.md`; `4.5-promotion-gate-and-mlflow.md`).

## 8. Glossary

| Term | One-line definition |
|---|---|
| Golden set | Labelled cases used as the reference for scoring |
| Offline / online eval | On a fixed dataset / on live traffic |
| Shadow mode | New system runs on live inputs, output is logged but not shown |
| Canary | Release to a small share of traffic first |
| LLM-as-judge | A model grades another model's output against a rubric |
| Position bias | Judge favours an answer because of its slot |
| Verbosity bias | Judge favours longer answers |
| Self-preference bias | Judge favours output from its own model family |
| Pointwise / pairwise | Score one output / choose the better of two |
| Cohen's kappa | Agreement between two raters, corrected for chance |
| TPR / TNR | Judge's rate of correct "pass" / correct "fail" against human labels |
| Rogan-Gladen | Correction of an observed rate for known TPR and TNR |
| Wilson interval | Confidence interval for a proportion that behaves well at small n |
| McNemar test | Paired test on items where two systems disagree |
| MDE | Smallest true effect a test can reliably detect |
| pass@k / pass^k | At least one of k passes / all k pass |
| Bootstrap | Resampling items to estimate an interval |
| Regression suite | Standing cases that must not get worse |
| Goodhart's law | A measure that becomes a target stops measuring well |
| Faithfulness | Share of answer claims supported by the provided context |

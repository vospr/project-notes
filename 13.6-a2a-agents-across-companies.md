# Course 13 · Chapter 13.6: A2A, how agents from different teams and companies talk

_Andrey Popov's project notes: how it works, why it was built this way, and the theory behind it._

**In short:** A2A (Agent2Agent) protocol: Agent Cards, Tasks with a life cycle, Messages and Artifacts, opaque agents across companies, how it differs from MCP, v1.0 and security questions.

## 2. The problem (business view, plain English)

Inside one company, agents can share a framework and call each other directly. Across teams, vendors or companies that breaks: each agent runs on a different framework, in a different cloud, owned by different people who don't want to share their prompts, tools or data. Without a standard, every pair of agents needs custom glue.

Example: your procurement agent needs a quote from a supplier's sales agent, and then a shipping estimate from a logistics provider's agent. You can't (and don't want to) see inside them. You just need to **ask, wait, receive the result**.

Analogy: a phone line between offices with a standard way to say who you are, what you need, and to call back later. You don't need to know how the other office works inside.

## 4. How it works

### 4.1 MCP vs A2A
| | **MCP** | **A2A** |
|---|---|---|
| Connects | agent ↔ **tool or data source** | agent ↔ **another agent** |
| The other side is | a function with a clear input and output | an **autonomous agent** that may think, ask questions and take time |
| Typical duration | milliseconds to seconds | seconds to **hours or days** |
| What you see inside | tool description and schema | **nothing** (agents are "opaque"); only what they publish |
| Analogy | using a calculator | asking a colleague in another firm |

They are complementary: an A2A agent uses MCP tools inside; you talk to it with A2A from outside.

### 4.2 The main ideas
```
 Client agent (yours)                                  Remote agent (theirs)
       │  1. fetch the Agent Card  ───────────────────►  /.well-known/agent-card.json
       │     (who are you, what can you do, how to authenticate, which transport)
       │  2. send a Message / create a Task  ─────────►
       │                                         ◄───── status updates (working, needs input ...)
       │  3. (optional) answer a question  ───────────►
       │                                         ◄───── final Artifact(s) + status "completed"
```
| Object | Plain meaning |
|---|---|
| **Agent Card** | A JSON "business card" the remote agent publishes: name, description, skills, endpoint, supported auth, capabilities (streaming, push notifications). v1.0 adds **signed** cards so you can verify who issued them |
| **Task** | A unit of work with an id and a **life cycle**: submitted → working → input-required → completed / failed / canceled |
| **Message** | One turn of conversation between client and remote agent, made of **Parts** (text, file, structured data) |
| **Artifact** | The output of a task (a document, a table, a file) |
| **Streaming / push** | Progress updates while a long task runs, or a callback when it finishes |

Transports (v1.0): JSON-RPC 2.0 over HTTP, gRPC, or REST. Security: standard web auth (OAuth 2.0, OpenID Connect, API keys, mutual TLS), declared in the Agent Card.

### 4.3 What makes it different from "just call an API"
1. **Long-running by design**: tasks have states, progress and the option to ask the caller a question mid-way.
2. **Discovery**: the card tells a client what the agent can do and how to connect.
3. **Opaque**: the remote agent keeps its prompts, memory and tools private.
4. **Vendor-neutral**: it works between Agent Framework, ADK, LangGraph and others.

### 4.4 Who backs it (as of this writing)
Started by Google (April 2025), donated to the **Linux Foundation** (June 2025). The foundation reports **150+ organisations** supporting it after the first year, stable **v1.0** in 2026, and support in **Microsoft Foundry and Copilot Studio**, Google ADK and other frameworks.

### 4.5 In Azure and ADK terms
- **Azure:** Foundry and Agent Framework can expose an agent as an A2A server and call remote A2A agents.
- ** `adk api_server --a2a` exposes an agent; `RemoteA2aAgent` consumes one.

## 5. Why it was built this way (decisions and trade-offs)

| Decision | Alternatives | Why this one | Cost / risk |
|---|---|---|---|
| Agents are opaque | Share prompts and tools across companies | Protects intellectual property and security | You can't debug inside the remote agent; you depend on its card and logs |
| Task life cycle with states | Plain request/response | Agent work is slow and may need input | More complexity for simple calls |
| Built on web standards (HTTP, JSON, OAuth) | New transport and auth | Reuse existing gateways, firewalls, identity | Inherits their weaknesses |
| Agent Card for discovery | Hand-written integration docs | Clients can read capabilities automatically | Cards can lie or be spoofed; hence signing |
| Separate from MCP | One protocol for both | Tools and agents behave differently | Two protocols to secure |

## 6. Theory behind it (the "lecture" part)

### 6.1 Interoperability standards and network effects
A standard becomes valuable when enough parties adopt it (email, HTTP). Early support by large cloud vendors and a neutral foundation are the signals that it will survive.
*In this course:* the Linux Foundation home and the 150+ members.

### 6.2 Opaque vs transparent collaboration
In an **opaque** model each party shows only an interface. In a **transparent** model they share internals (like agents inside one framework sharing state). Opaque is safer between companies; transparent is faster inside one team.
*In this course:* use direct calls and shared files inside a team (13.4); A2A across boundaries.

### 6.3 Asynchronous long-running operations
Work that takes minutes or hours needs an id, a status you can poll or subscribe to, and a way to deliver the result later. Same pattern as a payment processing job or a bank transfer.
*In this course:* A2A Tasks.

### 6.4 Trust boundaries
Anything arriving from another organisation is **untrusted input**: the text, the files, even the Agent Card. This is prompt injection (12.8) at organisation scale.
*In this course:* §7 security list.

## 8. Glossary

| Term | One-line definition |
|---|---|
| A2A | Agent2Agent protocol: standard for one agent to call another across frameworks and organisations |
| Agent Card | JSON description an agent publishes: skills, endpoint, auth, capabilities |
| Signed Agent Card | A card with a cryptographic signature proving who issued it (v1.0) |
| Task | A unit of work with an id and a life cycle of states |
| Message | One conversational turn made of parts |
| Part | A piece of content in a message: text, file or structured data |
| Artifact | A result produced by a task |
| Opaque agent | An agent whose internals are hidden from the caller |
| Client agent / remote agent | The caller and the called party |
| Linux Foundation | Neutral organisation that governs A2A since June 2025 |
| JSON-RPC | A simple request/response format over HTTP used as one A2A binding |

# Course 11 · Chapter 11.6: Subagents, skills, MCP, A2A, DAP and the host wiring matrix

_Andrey Popov's project notes: how it works, why it was built this way, and the theory behind it._

**In short:** Extension and delegation in the harness: the task tool and retained subagents with heartbeats, skills with progressive disclosure, MCP and A2A and the DAP/1 hub, memory tools, wire protocol v1 (NDJSON, additive-only), and the capability by host matrix where an off capability is invisible.

## 2. The problem (business view, plain English)

One agent in one context window does not scale to big tasks. Delegating to **subagents** keeps the main context clean and runs work in parallel, but it creates new problems: how many may run at once, what does the parent see, can it talk to a child later, what does it cost, what happens when a child stalls. Next, the agent needs tools and knowledge that live elsewhere: other tool servers (MCP), other agents (A2A), instructions written for other products (skills in Claude, Copilot, Codex layouts). Finally the same engine must live in a terminal, a phone app, a browser and an Outlook add-in, where half the abilities (processes, files) do not exist.

Finance analogy: subagents are desks with their own books reporting to the head of desk; MCP is the vendor-connectivity layer (market data, execution venues); A2A is inter-bank messaging; the capability matrix is the permission map of which desk may trade which product from which location.

## 4. How it works (technical walkthrough)

### 4.1 Subagents: the `task` tool and the retained runtime
**Batch shape**: `{context, tasks[]}`. The call fans out under a session-wide **semaphore** (`maxConcurrent`; `0` = unbounded) and has two modes:
- **Blocking** (default): the tool result carries every item's output; previews are capped, full outputs stay addressable as `agent://<id>`.
- **Background** (`background: true`): ids are allocated up front, one job per item is registered, the call returns immediately, and completions arrive later as async-result injections into the parent conversation.

**Agent types**: built-in `task` (general worker), `explore` (read-only research on the cheap `smol` role) and `review` (read-only on the `slow` role). Each type has a **restricted tool surface**; host config can override or add types. The header says that discovering markdown agent definitions from project, user and plugin folders (as oh-my-pi does) was a follow-up; `agent_discovery.dart` exists and I did not read it.

**Subagents 2.0** (*SUB*, "implemented, phases 0-5 shipped on main 2026-08-15"):
1. every child runs in its **own JSONL session**, not a bare in-memory agent, so its transcript persists, survives compaction of the parent, and can be inspected and resumed;
2. children are **retained and addressable**: status `queued / running / idle / completed / failed / aborted`; the parent can message, fork or dispose them;
3. spawning is **fire-and-forget** with an admission handle; a semaphore bounds concurrency;
4. observable: `task_status`, `task_observe`, `/tasks`;
5. **bidirectional messaging** (parent to child steering; child to parent replies and terminal notices), sibling to sibling messaging that is rate-limited and **hop-capped** (`hops` field, 0 refuses relaying);
6. per-subagent model and provider pins, so the orchestrator can run on a big model and the children on cheaper ones;
7. long-term memory and A2A interop (below).
Registry state is persisted in the parent session as a `subagent_registry` record and rehydrated on restart.

**Heartbeat** (*HB*, issue #383): while background children run, the parent gets one compact digest per `subagents.heartbeatMinutes` through the steering channel: per child, age, provider requests and tokens, last activity, and a classification `healthy | stalled | no-progress-since-spawn`. A child that never issued a provider request, or went quiet for `stallMinutes`, gets `[WARN] STALLED` (doubling to `[WARN][WARN]`) with the suggested action `task_status → task_cancel → respawn`. **Delivery SLO** instrumentation logs stage timestamps (send → enqueue → wake → consumed) and shows a diagnostic when a stage exceeds its SLO: "no silent queues".

### 4.2 Agent messaging fabric
Every agent owns a **file inbox** under the session root; two `fa` instances can chat live; subagents are first-class addressable mailboxes. A hub-backed layer can sit over the file layer; if storage falls back to another root, only the file layer swaps. `agent_directory` lists siblings and `agent_message` sends (the repo's own `AGENTS.md` tells agents to talk to peers through the inbox fabric, never by reading each other's working files). Messages can be scheduled (`schedule_message_tool.dart`) and have inbox-wake policies.

### 4.3 DAP/1: the hub (*DAP*, README)
A signed WebSocket hub: agents exchange **end-to-end encrypted** channel messages and DMs (the hub sees only ciphertext) and see presence. Inbound hub mail is drained into the loop as steering messages. The client is the hosted package `fah_hub_client` plus `bin/fah_hub_plugin.dart`. The protocol doc is "reconstructed from the code that speaks the protocol", with a `FakeHub` in tests as the executable reference.

### 4.4 MCP
One connection per configured server, **established lazily in the background** at agent start (boot never blocks). Reconnect with **capped exponential backoff** (the policy reused from the LSP manager). Status per server: `connecting / connected / failed`, fed into the system prompt and into a "not connected" note on the tool wrapper. When a server's tool list changes, `onChanged` fires so the host re-registers tools in the `ToolRegistry`. Stdio servers need a process-capable host; on the web they land in `failed` with a clean "not supported" note, while remote HTTP servers still connect (both HTTP transports are pure Dart).

### 4.5 A2A
Agent2Agent is Google's protocol for agents talking to remote agents (Agent Card discovery, JSON-RPC tasks). Here a `A2aManager` mirrors the MCP manager's lazy connect; a remote agent task maps onto the **same `SubagentHandle` registry** as local children, so `task_status`, `task_observe` and `task_send` work the same way for local and remote workers. `fa serve --a2a` mounts the agent itself as a remote endpoint; the request handler is pure Dart and transport-agnostic.

### 4.6 Skills
- A skill is `<root>/<name>/SKILL.md` (canonical, the open Agent Skills standard shared by Claude Code, GitHub Copilot and OpenAI Codex) or a flat `<name>.md`; Claude's command files are also discovered as invocable skills.
- Roots have a **source**: first-party `.fah/skills` and `.agents/skills` are always read; third-party `.claude/`, `.github/`, `.codex/` and their `~/` mirrors are read subject to a consent state (`ask`, `granted` default, `denied`).
- Front matter is a typed manifest: the standard fields plus Claude extensions (`when_to_use`, `arguments`, `allowed-tools`, `disallowed-tools`, `model`, `effort`, `context: fork`, `hooks`, `paths`, ...), Copilot instruction fields (`applyTo`, `excludeAgent`) and this repo's `operative` pins. **Unknown keys never break loading**; they are collected as notes.
- **Progressive disclosure:** the model never receives skill bodies up front. The prompt lists name, description and location only; the agent loads the file with `read` when the task matches. Explicit invocation: `/skill:<name>` or `/name`, with `$ARGUMENTS` rendering. A skill's `allowed-tools` becomes a one-turn approval grant (chapter 11.5).

### 4.7 Memory
`memory_add` (write tier), `memory_search`, `memory_list` (read tier), `memory_delete`, backed by the `flutter_agent_memory` package through a `MemoryController` with two scopes: **project** (committed under `memory/note/`, treated as the user's) and **user** (global, private). It renders a `<memory>` section into the system prompt, is fed by compaction (`compaction_memory_hook.dart`), and `AGENTS.md` instructs agents to `memory_search` before non-trivial work. Chapter 11.8 returns to this.

### 4.8 Plugins
A `FahPlugin` API "shaped after pi packages": third-party packages add tools, hooks, slash commands and configuration without forking. Built-in plugins ship in the core (`inspect_image`, `transcribe_audio`) and load from `.fah/packages.yaml` or `--plugin`.

### 4.9 Wire protocol v1
The boundary between engine and host is a frozen, versioned JSON protocol: **events out, commands in**.
- **Framing:** NDJSON, one object per line, UTF-8, never batched on a line.
- **Frames:** `{"v":1,"kind":"...", ...}`. **Additive-only within a major**: new kinds and optional fields are allowed; changing or removing anything bumps `v`. Unknown fields are ignored; unknown event kinds become `unknown_event` passthrough (render nothing, keep the run alive).
- **Handshake:** client `hello {versions, caps}`, server `welcome {version, caps}` with the highest common version; **no overlap is a loud handshake error**, never a guessed version.
- **Events:** the `AgentEvent` kinds from chapter 11.3, `message_update` carrying the partial message and the nested provider delta; plus interaction requests `approval_request`, `ask_request`, `secret_request` that the host answers with matching response commands (echoing `id`).
- **Commands:** `prompt`, `steer`, `abort`, the three responses, and `session_control {op, params}`.
- **Secrets:** fields like `secret_response.value`, `model_request.rawWireDump` and `rawBody` are registered as secret; hosts must pass frames through `redactForLog` before logging.
- **Golden fixtures** under `test/wire/fixtures/v1/` pin every frame; a schema change without fixtures fails CI, and reference clients parse old-version fixtures both ways. Transport is free; the default is the in-process Dart adapter; a TypeScript client lives in `sdk/web`.

### 4.10 Host wiring and the capability matrix
There are seven hosts: `cli`, `macos`, `ios`, `android`, `web`, `extension`, `outlook`. A **capability** (config sections, compaction, load modes, MCP, messaging fabric, approval gate, skills, sandbox env, background shell jobs, sqlite/LSP/DAP families, on-device providers, JS apps, checkpoint/rewind, ...) has, for each host, one declared state:
- `on` (default transports),
- `off(reason)`: not wired; the reason must reach the UI and prompts,
- `transport(choice, reason)`: wired but narrowed to specific transports.
Rules: the **narrowing invariant** (a profile may only narrow what the platform floor allows; force-enabling a missing ability throws `HostProfileViolation` at construction); **declared at birth** (every new capability states its cell for all seven hosts, and a matrix-completeness test rejects undeclared ones); **off means invisible** (hidden from menus, settings, slash commands, tool palettes **and** from everything model-facing: tool schemas, prompt sections, skill lists, help); hosts build their stack through `wireAgentCore` (typed services in, wired core out), never by hand-registering tools behind a bare `if`; host extensions declare states for all built-in profiles and the builder rejects tool-id collisions at build time; extensions are additive only (memory, compaction, JSONL session, trajectory are SDK invariants with no override point). A **parity registry** (`lib/src/parity/settings_registry.dart`) lists shared settings, and a guard test fails if a setting exists on the CLI but not the app without a written exemption.

## 5. Why it was built this way (decisions and trade-offs)

| Decision | Alternatives considered | Why this one | Cost / risk |
|---|---|---|---|
| Children get their own JSONL sessions | In-memory child agents | Inspectable, resumable, survive parent compaction (*SUB* goal 1) | More files, rehydration logic |
| Fire-and-forget spawn + semaphore | Blocking spawn only | Parent never blocked; bounded cost | Async result handling, heartbeats needed |
| Hop cap on sibling messages | None | Prevents message storms between agents | Legitimate long relays refused |
| Heartbeat digests through the steering channel | Separate monitoring UI | The orchestrator itself can react | Adds steering turns (capped) |
| Remote A2A tasks map to the local handle registry | Separate remote API | One set of tools for local and remote | Hides latency and trust differences |
| Skills disclosed progressively | Inline all skills in the prompt | Saves context; model loads on demand | Needs the model to notice a match |
| Read third-party skill folders by default | Opt-in | Zero-setup migration | Instruction and script injection surface |
| Wire protocol additive-only + goldens | Free evolution | Hosts in other languages can trust it | Slower change; fixture upkeep |
| Capability matrix declared at birth | Ad-hoc `if (isWeb)` | "CLI got X, app didn't" cannot happen silently | Heavy ceremony per feature |
| Off capability invisible to the model | Show and refuse at call time | The model never plans with unavailable tools | More wiring to hide in every surface |

## 6. Theory behind it (the "lecture" part)

### 6.1 Orchestrator-worker multi-agent patterns
Multi-agent systems split work across agents with separate contexts. The common shape is **orchestrator-worker**: a lead agent plans and delegates, workers execute in parallel and return condensed results. Benefits: parallelism and context isolation (the lead's window is not flooded by a worker's file reads). Costs: token use rises, coordination errors appear, and the lead must verify returned work. Reported industry experience is that multi-agent setups pay off for breadth-first research and large independent tasks, and are wasteful for tightly coupled edits. Controls: concurrency bounds, per-worker model tiers, hard timeouts, heartbeats.

*In my project:* Course 8.2 (dispatcher, least-privilege agents, sizing pipeline depth) is the same decision at design level.

### 6.2 The actor model
Actors own private state and communicate only by asynchronous messages to mailboxes; they are created dynamically and supervised. A retained subagent with an inbox, a status, and message envelopes is an actor. Back-pressure, rate limits and **hop counts** (a time-to-live for relayed messages, like IP TTL) prevent runaway messaging.

*In my project:* the per-agent inbox is a folder of files, so it is a durable mailbox (restart behaviour not read).

### 6.3 MCP and A2A: two different seams
**MCP (Model Context Protocol)** standardises how a model-hosting application connects to **tools, resources and prompts** (JSON-RPC over stdio or HTTP). **A2A** standardises how **one agent delegates to another agent** (Agent Cards for discovery, task lifecycle, messages). Rule of thumb: MCP is how an agent uses a capability; A2A is how an agent hands work to a peer that may itself plan and use tools. Both inherit trust problems: tool descriptions and remote outputs are untrusted input, and remote endpoints need authentication.

*In my project:* Course 6 (stateless versus stateful servers, auth for MCP) covers the server side; here we have the client side with lazy connect and reconnect.

### 6.4 Progressive disclosure for context economy
Putting all instructions in the prompt wastes the window and dilutes attention. A common pattern is a small index (name and one-line description) always present, with full content loaded on demand. It trades a possible miss (the model fails to load a relevant skill) for a large saving, and moves discovery quality into the description text.

*In my project:* description wording is the interface; it is why my own `/job-*` skill descriptions are written as trigger conditions.

### 6.5 API versioning and compatibility
Rules that keep a protocol stable: **additive changes only** within a version, **tolerant readers** (ignore unknown fields), **explicit negotiation** (hello and welcome), **degrade, don't fail** on unknown kinds, **fixtures for every version** (consumer-driven contract tests). Postel's law ("be liberal in what you accept") has a known downside of accumulating ambiguity, so strict handshakes (no overlap is an error) balance it.

*In my project:* the fixture discipline is the same as my contract tests per port in Course 2.1.

### 6.6 Feature matrices and capability negotiation
When one core targets many platforms, an explicit capability × platform matrix replaces scattered conditionals. Properties worth having: **completeness** (every cell declared, tested), **monotonic narrowing** (a profile cannot enable what the platform lacks), and **consistency of surface** (a disabled feature disappears everywhere the user or the model can see it). It is the product-line engineering idea of a feature model.

*In my project:* "off means invisible to the model" is the agent-specific twist: the model plans from the tool list it is given.

### 6.7 End-to-end encryption through a relay
A hub that only forwards ciphertext cannot read messages even if compromised; sender identity is proven by **signatures** on frames; confidentiality comes from **per-channel keys**. Trade-offs: key distribution and rotation, no server-side search or moderation.

*In my project:* I did not read the cipher choices; the DAP doc cites the client package's `payload_crypto.dart` and `canonical.dart` for signing and encryption.

## 8. Glossary

| Term | One-line definition |
|---|---|
| `task` tool | Spawns subagents in batch, blocking or background |
| Retained subagent | A child kept alive after finishing, addressable for follow-up |
| Admission handle | Id returned at spawn so results can be matched later |
| Hop cap | Remaining relay budget on an inter-agent message |
| Heartbeat digest | Periodic status summary of running children sent to the parent |
| Delivery SLO | Per-stage time budget for message delivery, logged when exceeded |
| Agent fabric | Per-agent file inboxes, optionally backed by a hub |
| DAP/1 | This project's signed, encrypted agent-messaging hub protocol (not the Debug Adapter Protocol) |
| MCP | Model Context Protocol: connects an app to tools, resources, prompts |
| A2A | Agent2Agent protocol: delegate tasks to remote agents |
| Skill | A `SKILL.md` instruction package disclosed on demand |
| Progressive disclosure | Show an index first, load content when needed |
| Wire protocol v1 | NDJSON events out, commands in, additive-only versioning |
| `unknown_event` | Passthrough frame for event kinds the host does not know |
| Capability profile | Per-host table of on / off(reason) / transport(choice) states |
| `wireAgentCore` | Builder through which a host assembles the core |

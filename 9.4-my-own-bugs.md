## 2. The problem (business view, plain English)

A forecast is only useful if it uses what you will know when you must act. A model that quietly sees tomorrow's information looks excellent in the back-test and fails in production. The thesis was graded 5/6, so the examiners judged the write-up, but nobody ran the code against the text until the portfolio review on 2026-09-30.

Finance analogy: a back-tested trading strategy that uses the day's closing price to decide the morning trade. The Sharpe ratio is wonderful and meaningless. The professional response to finding it is to say so first, size it, and show the fix.

## 4. How it works (the bug register)

**The timeline that defines "leak".** For day D, hour h:
```
D−2 12:00  auction sets all 24 prices of D−1          ← known by D−1
D−1 12:00  auction sets all 24 prices of D            ← FORECAST MADE BEFORE THIS
  legal inputs : price(D−1, h), price(D−2, h), price(D−7, h), max price of D−1, calendar
  illegal      : max price of D (contains price(D,h) itself), actual production of D at h
```

**Bug 1 [R]: same-day maximum and same-hour production (target leakage).**
- *Code:* `Price_MAX = groupby(date)['Price'].transform('max')`; exog list uses `ln_Price_MAX` and `ln_Volume`; the previous-day column `Price_24_MAX = Price_MAX.shift(24)` is computed but not used. `Volume` is never lagged. The 2024 run repeats the pattern. Unused `Price_Week` and `Price_Month` are also same-period means that include the future.
- *Text:* the thesis equation uses "the maximum of the previous day's 24 hourly ln-prices" and "lagged electricity infeed".
- *Why it is a leak:* the row for hour h of day D contains the maximum over all 24 hours of D, including price(D, h). On the daily peak hour the feature equals the target; on every other hour it still tells the model how high the peak will be.
- *Size:* +14% MSE when fixed (OLS, same-day max 40.0 → previous-day max 45.5, review re-run); naive rules score 65–83, so the corrected regression still beats the best naive rule by about 30%. Max vs min makes almost no difference; same-day vs previous-day is the whole gap. Volume's coefficient is −0.012: negligible.
- *Touches:* every model (same X), every table, the 2024 test, and the max-vs-min choice.
- *Fix (one line):* put `ln_Price_24_MAX` in `exog_vars`, lag the volume.

**Bug 2 [R]: combination weights fitted on the evaluation period.** CLS fitted on and scored against the test targets; 2024 CLS refitted on 2024 actuals and returned the starting point 0.2 × 5. Details in 9.3. *Touches:* the headline "CLS is best" (55.4 vs 57.4 equal weights). *Fix:* weights from a block before the one scored, or apply the 2020 weights to 2024.

**Bug 3 [R]: dummy-variable trap.** Design = constant + 7 weekday + 12 month dummies + 5 numerics = 25 columns, rank 23. Evidence in the output: `Df Model 22`, `Df Residuals 18271` (18,294 − 23 = 18,271), warning "number of constraints is 24, but rank is 23", condition number 3.29e16, smallest eigenvalue 5.2e-29. The thesis says "the reference month … is omitted to avoid the dummy variable trap", yet Table 3 lists all 12 months and 7 weekdays plus a constant. *Touches:* the interpretation of Table 3 and Table 5 (individual coefficients, p-values). *Not touched:* predictions. *Fix:* drop one weekday and one month (or the constant).

**Bug 4 [R]: metric choice.** Headline metrics are MSE, MAPE and R²; MAE is dropped on purpose although the introduction claims lower "MAE and MAPE". MAPE explodes on 2024 because negative prices were clamped to 0.01 and sit in the denominator. "Surpasses even the best individual model on every metric" is contradicted by the thesis's own MAPE (110.8% vs 64.3%). No naive baseline, no rMAE, no Diebold-Mariano. Fix: MAE, RMSE, sMAPE, rMAE, DM test.

## 6. Theory behind it (the "lecture" part)

### 6.1 Data leakage: a taxonomy
Leakage means the evaluation uses information that would not exist at prediction time (Kaufman, Rosset, Perlich & Stitelman 2012). Main forms:
- **Target leakage:** a feature contains the target or a function of it (my same-day maximum).
- **Temporal leakage:** a feature uses the future (same-day production, same-week mean).
- **Train-test contamination:** preprocessing fitted on all data (z-scores and median computed on the whole sample; the scaler, by contrast, was fitted on train only).
- **Selection on the test set:** choosing models, hyperparameters or ensemble members after seeing test scores (dropping the plain NN from the 2024 blend; fitting CLS on test).
- **Target cleaning:** altering test targets so hard cases disappear.
Detection: for every feature ask "when is this known?"; look for results that are too good; ablate by replacing a suspect feature with its lagged version and see how much accuracy drops; compare with naive baselines. Remedy: write the information set down before building features.

*In my project:* bugs 1, 2, 5, 11 are leakage in four different forms.

### 6.2 Perfect collinearity and the dummy-variable trap
Categorical variable with k levels → k dummies D₁…D_k with ΣD_j = 1. With a constant column, the columns are linearly dependent, so X'X is singular and the coefficients are not unique. *Example:* three levels, y = a + b₁D₁ + b₂D₂ + b₃D₃. The parameter vectors (a, b) = (0, 10, 12, 15) and (5, 5, 7, 10) give identical fitted values. Software returns one of them (statsmodels uses the pseudo-inverse, the minimum-norm solution). What *is* identified: fitted values, and **differences** between levels (b₂ − b₁). What is *not*: each level on its own, its standard error, and its p-value. With two categorical groups plus a constant the rank deficit is 2 (the weekday dummies sum to the constant, and so do the month dummies). Fix: drop one level per group (the reference level) or drop the constant. Ridge and Lasso still return a unique answer because the penalty picks one, but the values depend on the penalty.

*Numbers from the project:* OLS Monday = 0.517, Ridge 0.097, Lasso 0.086, the levels disagree by a factor of 6; the contrast Monday − Sunday is 0.239 (OLS), 0.228 (Ridge), 0.219 (Lasso), nearly the same. So statements like "January is higher than March" are fine as contrasts; "relative to the omitted reference month" and "all coefficients significant" are not.

### 6.3 Choosing and reading an error metric
Each loss implies a different point forecast: squared error → the conditional **mean**; absolute error → the **median**; percentage error |y − f|/y → a forecast biased **low**, because over-forecasts are punished more than under-forecasts and the denominator explodes as y → 0. *Example:* actual 0.01, forecast 30: error = 2,999 = 299,900%. Actual 100, forecast 130: 30%. One clamped hour outweighs thousands of normal ones, which is why the 2024 MAPE is 64 (6,400%).
Better choices for prices that cross zero: MAE and RMSE (scale-dependent, in EUR/MWh), sMAPE (bounded but still unstable near 0), **rMAE** or MASE (error relative to a naive forecast; Hyndman & Koehler 2006), and a significance test (Diebold-Mariano, 9.3). Rules: (i) report at least two *different* metrics, not MSE and R², which rank identically; (ii) evaluate on raw targets, including spikes; (iii) match the training loss to the evaluation metric or say why not; (iv) always show a naive benchmark.

*In my project:* fit loss is MSE in log space, evaluation is MSE in price levels, headline is MAPE; the thesis argued against MSE for NN training and for it as an evaluation metric within a few pages.

### 6.4 In-sample versus out-of-sample, and a guaranteed win
Fitting a parameter on the scored data can only lower in-sample loss. If equal weights are a feasible point of the CLS problem (same member set), in-sample CLS MSE ≤ equal-weight MSE **by construction**, so seeing it win proves nothing. The honest test applies weights fitted on earlier data to later data. The same holds for hyperparameters and member selection.

*In my project:* CLS (55.2) vs equal (57.3) is not even a clean nested comparison because the member sets differ (9.3).

### 6.5 Reproducibility basics
A result is reproducible if a stranger can regenerate the table: data fetch script, pinned versions, fixed seeds, a run log, a single entry point. Stochastic models need several seeds and a mean ± spread. A "frozen" artefact is honest if it says what it is. The cost of not doing this is exactly what happened: thesis tables for the NN cannot be regenerated from the committed notebook.

*In my project:* no data in the repo, Colab and Drive paths, no seeds.

## 8. Glossary

| Term | One-line definition |
|---|---|
| Target leakage | A feature contains the target or a function of it |
| Look-ahead / temporal leakage | A feature uses information from after the forecast time |
| Train-test contamination | Preprocessing or selection that uses test data |
| Information set | Everything known at forecast time |
| Dummy-variable trap | k dummies plus a constant are perfectly collinear |
| Reference level | The omitted category the other dummies are measured against |
| Rank-deficient design | X has fewer independent columns than columns |
| Pseudo-inverse | Minimum-norm solution of a singular least-squares problem |
| Estimable contrast | A combination of coefficients that is identified despite collinearity (e.g., level differences) |
| MAPE | Mean absolute percentage error; unstable near zero actuals |
| sMAPE | Symmetric MAPE; bounded but unstable near zero |
| rMAE / MASE | Error relative to a naive forecast |
| Diebold-Mariano | Test of equal predictive accuracy of two forecasts |
| Frozen repo | Repository kept exactly as submitted, defects included |
| Selection on the test set | Making choices after seeing test scores |

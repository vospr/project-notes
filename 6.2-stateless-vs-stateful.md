# Course 6 · Chapter 6.2: Stateless vs stateful (sessions, serverless, handles, the July 2026 spec)

_Andrey Popov's project notes: how it works, why it was built this way, and the theory behind it._

**In short:** Why the MCP server keeps no state: a new server per request so any serverless instance can answer, versus sessions that need affinity (1/N chance of reaching the owner). Covers the July 2026 spec dropping sessions and the handle pattern.

## 2. The problem (business view, plain English)

A coaching conversation has a shape: it moves through phases, and the system must remember where the user is. Exposing that conversation through MCP raises a design choice: who holds the memory? If the AI platform holds it, a third party processes all coaching content. If the coaching server holds it, the server needs a verified user identity and somewhere durable to keep state, which is awkward on serverless hosting.

The memo's answer for Phase 1: keep no coaching state at all. One question in, one answer out. Multi-turn coaching waits until identity and a data-protection assessment exist.

Finance analogy: a payment API where every instruction is self-contained and carries its own reference, versus a FIX trading session with logon, sequence numbers and resend rules. The self-contained API scales by adding servers; the session needs the same counterparty connection to survive. MCP before July 2026 allowed both; after it, only the first shape exists at the protocol level.

## 4. How it works (technical walkthrough)

```
Request 1 ─► [instance A] new McpServer + transport ─► answer ─► discarded
Request 2 ─► [instance B] new McpServer + transport ─► answer ─► discarded     no shared memory
Request 3 ─► [instance C] ...                                                  needed anywhere

With a session:  initialize ─► A mints Mcp-Session-Id=abc, keeps state in A's RAM
                 request 2 ─► lands on B ─► "unknown session abc" ─► client must re-initialize
```

**What the code does.** For every request to `/mcp`, `http.ts` calls `createCoachingMcpServer`, creates a `StreamableHTTPServerTransport({ sessionIdGenerator: undefined })`, connects them and hands the request to the transport (`http.ts:27-35`). Building the server only registers handlers (`server.ts:33-291`), so it is cheap. Nothing survives the request: no session ID is minted, no map of sessions exists. Any instance can serve any request. That is what serverless scale-out needs.

**What stdio does.** One long-lived process per client, spawned by the host (`stdio.ts:12-17`). State could live in memory there without harm, but the tools do not use any. The stub keeps nothing between calls (`coaching-data.ts:40-100`).

**What is given up in this mode (1.x era, per the review):** server-initiated notifications, sampling and elicitation, and stream resumability.

**What the memo's three state options mean:**
| Option | Where state lives | Memo's verdict |
|---|---|---|
| Client-side state | In the platform's context window | GDPR risk: a third party processes all coaching content |
| Server-side sessions (`Mcp-Session-Id`) | In one server process | Needs persistent compute, affinity, adds latency |
| Hybrid session token | In an encrypted token the client sends back | Stateless server, but the token grows; complex |

**What the 2026-07-28 spec did (all from *SPEC-CL26*):**
- No protocol sessions, no `Mcp-Session-Id` (major 1). List endpoints no longer vary per connection.
- No `initialize` handshake; each request carries `protocolVersion` and `clientCapabilities` in `_meta` (major 2). New `server/discover` to learn versions and capabilities (major 3).
- Server-initiated requests replaced by multi round-trip requests: the server returns `input_required`, the client retries with the answers (major 7; *SPEC-MRTR*).
- No SSE resumability: a broken stream loses the in-flight request and the client re-issues it (major 9).
- Required `Mcp-Method` / `Mcp-Name` headers, and `ttlMs` / `cacheScope` on list results (minor 4-5).
- State across calls: "explicit, server-minted handles passed as ordinary tool arguments" (major 1). Guidance: a handle is "a name, not a capability", so check authorization on every call; use opaque, high-entropy, expiring IDs; document the lifetime; return a clear error on expiry.

**The multi-turn arc, as proposed (not built).** A tool `start_arc` returns an `arcId`; later calls pass it back. The server stores the arc, encrypted per user, so any instance can load it. It needs verified identity and a completed impact assessment first, which is the memo's deferral reason.

## 5. Why it was built this way (decisions and trade-offs)

| Decision | Alternatives | Why this one | Cost / risk |
|---|---|---|---|
| Stateless HTTP, new server per request | Sessions with affinity or a store | Serverless needs any-instance-serves-any-request | No server push in the 1.x era; no per-request cleanup |
| Single-turn advice only in Phase 1 | Expose the full coaching loop | No identity yet, no impact assessment; third parties should not see coaching state | No coaching arc; quality may drop |
| Reject client-side state | Let Copilot/ChatGPT carry the arc | Third-party AI would process everything | Follow-ups rely on the platform's own context |
| Defer server-side sessions | Build them now | Need verified identity and persistent state | Overstated as "needs persistent compute" |
| Keep a hybrid token as a later option | Ignore | Stateless server with state in the request | Token grows; encryption overhead; not the spec's handle |
| Write it up as a memo, not code | Build the loop | One-day timebox; the decision was the product | The multi-turn design is unbuilt |

## 6. Theory behind it (the "lecture" part)

### 6.1 What "state" is, and the REST stateless constraint
**State** is information that a later operation depends on. A system is **stateless** at a given layer when each request carries everything needed to process it, so the server keeps no memory of earlier requests. Fielding's REST style makes this a constraint: session state is kept entirely on the client (Fielding, 2000, §5.1.3; general knowledge, check the source). Gains: **scalability** (any server can answer), **reliability** (recovery from partial failure is easy, retry elsewhere), **visibility** (an intermediary can understand a request alone). Costs: repeated data in every request, less server control, and the client must carry or re-send context.

*In my project:* the HTTP endpoint is stateless per request (`http.ts:27-35`); the coaching application above it is also stateless by design. These are two layers; both can be stateless independently.

### 6.2 Sessions, sticky routing, and the 1/N problem
A **session** binds several requests to server-side memory. If that memory lives in one process and a load balancer spreads requests over N instances without affinity, the chance that the next request reaches the owner is 1/N, and that the next k all do is (1/N)^k. With N = 4 and k = 5 follow-up calls that is 1/1024, about 0.1%. Instance recycling makes it worse: the owner may be gone. Three fixes: **sticky routing** (affinity; one instance becomes a single point of failure for its sessions), a **shared session store** (extra hop, extra dependency), or **no server-side session** (stateless).

*In my project:* this is the review's drill Q2: an `Mcp-Session-Id` minted at `initialize` lives in one process's memory, so a later request on another instance gets "unknown session" and the client must re-initialize (*Review §6 drill 2* "session affinity needed").

### 6.3 Serverless constraints
**Serverless** (function-as-a-service) runs code on short-lived instances that the platform starts, scales out and stops. Properties relevant here: instances are ephemeral (memory may vanish between calls), scale-out is automatic (so N is unknown and changes), **scale-to-zero** causes cold starts, and execution has time limits that cut long-lived streams (general knowledge; the review notes Functions time limits, *Review §6 drill 2*). Consequence: in-memory session state is not "inefficient", it is a correctness bug.

*In my project:* the memo targets a serverless HTTP backend; the review says the actual code is a plain Node `http` server, not a Functions handler, so serverless fit is by pattern, not by deployment.

### 6.4 Where state can live, and what protects it
| Placement | Mechanism | Main risks | Controls |
|---|---|---|---|
| **Client-carried** | Signed or encrypted token sent back each call (cookie, JWT analogue; MCP `requestState`) | Tampering, replay, size growth, hard to revoke, data sits in a third party's context | Integrity protection (HMAC or AEAD), bind to the authenticated principal, short TTL, request-specific binding; treat as attacker-controlled input |
| **Server-held, keyed by handle** | Store maps ID → state; client passes the ID (MCP "handles") | Guessing, stolen ID, state growth, cross-user access | Opaque high-entropy ID, authorize on every call, expiry, clear expiry error |
| **Server-held, keyed by connection** | Protocol session | Affinity, scale-out failure | Removed from MCP in 2026-07-28 |

An important data-protection point: an **encrypted** token that only the server can decrypt still routes ciphertext of personal data through a third party; whether that counts as disclosure is a legal question I do not settle here (chapter 6.3 flags it). A **handle** keeps the content on the server and sends only an ID, but moves the risk to the server store, which then needs identity, per-user encryption and erasure.

*In my project:* the memo's hybrid row is the client-carried type; the review's `arcId` plan is the handle type.

### 6.5 Retries and idempotency in a stateless world
Stateless request/response over a network is at-least-once in practice: a timed-out call may or may not have executed. Safe retries need idempotent operations or an **idempotency key**. Without sessions, there is no connection-level "I already sent that", so the key must be in the request. Multi round-trip requests make this explicit: the retry is a new request with a new JSON-RPC `id`, carrying `requestState`, and a one-time redemption "MUST" be enforced server-side (*SPEC-MRTR* warning).

*In my project:* `book-session` is not idempotent (`coaching-data.ts:91`); the stateless design makes this more, not less, important (chapter 6.1, section 6.5).

### 6.6 Stateful applications on stateless protocols
A stateless protocol does not forbid stateful applications. It moves state from an implicit connection to explicit data: a handle in a tool argument, a stored record keyed by it. Benefits: visible, testable, any instance can serve. Costs: the **model** must carry the handle forward (it is text in the conversation), so the design relies on the model behaving, and the handle appears in the model's context. A handle is also a business object: it needs lifetime and deletion rules (GDPR erasure, chapter 6.3).

*In my project:* the proposed `arcId` arc is this pattern; Phase 1 avoids it by not having an arc at all.

### 6.7 Cost of the stateless choice for server push
Without a session there is no standing channel for server-initiated messages. The 2026-07-28 spec answers with two patterns: the server asks for input by *returning* `input_required` (multi round-trip), and clients opt into change notifications by opening a `subscriptions/listen` stream. So "stateless" does not mean "no interactivity"; it means interactivity is carried by explicit requests and replies.

*In my project:* nothing here uses push; all four tool and resource interactions are plain request/response.

## 8. Glossary

| Term | One-line definition |
|---|---|
| Stateless | Each request carries all it needs; the server keeps no memory between requests |
| Session | Server-side memory tying several requests together |
| `Mcp-Session-Id` | Header in 2025-era Streamable HTTP identifying a session; removed in 2026-07-28 |
| `sessionIdGenerator: undefined` | SDK 1.x setting that turns sessions off (`http.ts:30`) |
| Sticky routing / affinity | Load balancer sends a client to the same instance every time |
| Serverless | Platform runs short-lived, auto-scaled instances; no memory guarantee |
| Scale-to-zero / cold start | Instances stop when idle; the next call waits for a new one |
| Handle | Server-minted ID passed as a normal tool argument to refer to server-side state |
| `requestState` | Opaque server blob the client echoes on retry; must be integrity-protected |
| MRTR | Multi round-trip requests: server returns `input_required`, client retries with answers |
| `server/discover` | 2026-07-28 RPC that advertises versions, capabilities, identity |
| `subscriptions/listen` | Long-lived POST stream for opted-in change notifications |
| Idempotency key | Caller-chosen unique key making a repeated request safe |
| Bearer token (handle as) | An ID that grants access to whoever holds it |
| Hybrid session token | The memo's encrypted state carried by the client |

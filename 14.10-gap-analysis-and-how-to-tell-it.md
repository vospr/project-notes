# Course 14 · Chapter 14.10: Gap analysis and how to tell it

_Andrey Popov's project notes: how it works, why it was built this way, and the theory behind it._

**In short:** Gap analysis of Andrey's knowledge systems: benchmark designed but not run, stale checks, wikis without lint or log, priority order, what he would not build and when he would change his mind, and a two-minute honest story.

## 2. The problem (business view, plain English)

A knowledge system earns trust only if it is right when someone relies on it, and if its owner can say how right. Mine have a good design and uneven upkeep. A reader who finds the weak spots by themselves, in a review or a hiring conversation, will trust the rest less. A reader who hears about them first, with a plan, trusts more. This chapter lists the weak spots so that I find them first.

## 4. How it works

### 4.1 Priority order and why
```
1. a routine that runs the freshness checks, then clear the red lights (stale graph, stale catalogue, wrong README numbers)   about 1.5 days
2. run the benchmark baseline on the current approach                                                                         1 to 2 days
3. lint and a log for the wikis; cleaner wiki page headers                                                                    about 1.5 days
4. hygiene: registry of studies, digest pull job, session index refresh, leftover instructions from the old machine           about 1 day
5. graph depth (semantic refresh, backend coverage, second tool): only if the benchmark or active work needs it
6. documentary GraphRAG: stay deferred
```
Reasoning: trust first (red lights that the system itself raises), then evidence (the baseline), then the cheap structural checks, then extension. Extending (backend graphs, dense retrieval, GraphRAG) comes last because every extension adds something more to keep fresh.

### 4.2 What I would not build, and the condition to change my mind
| Not building | Change my mind when |
|---|---|
| Vector index over everything | Holdout paraphrase Recall@5 improves at least 10 points over the best lexical result with exact queries within 2 points |
| Documentary GraphRAG | The multi-hop holdout set repeatedly fails and lighter chaining cannot recover the evidence |
| A reranker by default | Right sources are in the candidates but rank low (MRR gate) |
| Autonomous wiki updates | Lint plus a measured error rate show approval is rarely changing anything |

## 5. Why it was built this way (decisions and trade-offs)

| Decision | Alternatives | Why this one | Cost / risk |
|---|---|---|---|
| Fix trust and measurement before adding capability | Add hybrid retrieval now | New capability on top of red lights adds noise | Looks like less progress |
| Run the cheapest baseline first | Compare all six variants at once | A0 may already be good enough; stop early if gates pass | One more step before building |
| Keep the gates as numbers | "Looks better" | Prevents infrastructure creep | Numbers are judgement |
| Say the weak spots out loud | Present the design only | A reviewer who finds the gaps alone trusts less | Less polished first impression |

## 6. Theory behind it (the "lecture" part)

### 6.1 Technical debt for knowledge systems
Debt is what you must pay later to keep a system correct. For knowledge systems it is stale indexes, uncleared warnings, copied numbers and unlinted pages.
*In this course:* the stale graph, stale catalogue, wrong README numbers and unlinted wikis are interest on one missing routine: nothing runs the checks.

### 6.2 Observability for knowledge
A system you cannot see is a system that rots. A single line per store (fresh / stale / invalid, with a date) is the cheapest form of observability.
*In this course:* a one-line-per-store status at session start is the fix.

### 6.3 Measure before you build
Add a component only if a measured failure and a stated threshold justify it.
*In this course:* the baseline run comes before any retrieval upgrade.

### 6.4 Honest reporting
State what was run, what was read, and what was not. Do not turn a design into a result.
*In this course:* the source caveat at the top of every note in this course.

### 6.5 Expected value of extension
Each added capability adds a thing to keep fresh. Extension pays only if the questions it serves are frequent and currently failing.
*In this course:* the "not building" table above.

## 8. Glossary

| Term | One-line definition |
|---|---|
| Gap register | A list of known weaknesses with evidence, severity and fix |
| Baseline | The current approach measured first |
| Red light | A check result that says stale or invalid |
| Routine | A recurring action that keeps a system healthy |
| Interest (debt) | The growing cost of leaving a known problem |
| Retention gate | A threshold a new component must pass to be kept |
| Observability | Being able to see the state of a system from outside |
| Overclaiming | Describing a design as if it were a measured result |

**In short:** Fundamentals behind AI certification questions: task types, overfitting versus leakage, metrics under class imbalance, why LLM outputs vary and what stabilises them in 2026, the customization ladder from prompting to pre-training, and responsible-AI dimensions.

## 2. The problem (business view, plain English)

Every AI certification opens with the same layer: what kind of learning problem is this, how do you know the model generalises, which number proves it works, and when do you change the model rather than the prompt. Getting the fundamentals right is cheap credibility; getting them wrong colours every later answer.

Finance analogy: a credit analyst who confuses a default-probability model (classification) with a loss-given-default model (regression), or who judges a scorecard on the development sample, would not pass a model-validation review. The same mistakes in AI vocabulary sound just as bad to a hiring panel.

## 4. How it works (the decision path)

```
 business question
   │
   ├─ predict a label? ──────────── yes ─► classification (binary / multi-class)
   ├─ predict a number? ─────────── yes ─► regression (or forecasting if ordered in time)
   ├─ find groups, no labels? ───── yes ─► clustering (unsupervised)
   ├─ choose actions by reward? ─── yes ─► reinforcement learning
   └─ produce text / image / code? ─ yes ─► generative model (transformer for text, diffusion for images)
                                              │
            customization ladder (stop at the first step that passes the eval):
            1 prompt (instructions, few-shot)      cheapest, minutes
            2 RAG / tools (fresh, private, cited)  days
            3 fine-tune (SFT, LoRA)                behaviour, format, narrow skill
            4 continued pre-training              unfamiliar domain language, large corpus
            5 pre-training from scratch           almost never
```

Each step up costs more, takes longer, and moves more responsibility (and security ownership) onto you.

## 5. Why it is done this way (decisions and trade-offs)

| Decision | Alternatives | Why this one | Cost / risk |
|---|---|---|---|
| Start with prompt + RAG | Fine-tune first | Knowledge changes daily; RAG updates without retraining and can cite | Retrieval quality becomes the bottleneck (12.6) |
| Fine-tune for style/format only | Fine-tune for facts | Facts learnt in weights are stale, uncitable, and can leak | Needs labelled examples, re-runs on model upgrades |
| Interpretable model for regulated decisions | Deep model + post-hoc explanation | Logistic regression / scorecards are explainable by construction | May lose accuracy; must still be validated |
| Macro-F1 or PR-AUC under imbalance | Accuracy | Accuracy rewards the majority class | Harder to explain to business |
| Business KPI (conversion, handle time) beside model metrics | Model metric only | Shows the effect the business pays for | Needs an experiment design to attribute |
| Smaller domain model when cost matters | Largest model | Cost per call drops; quality often holds on narrow tasks | Must be proven on your eval |

## 6. Theory (the lecture)

### 6.1 Learning types and task types
**Supervised** learning maps inputs to known labels: **classification** (discrete label: fraud / not fraud = binary; species of animal = multi-class) and **regression** (a number: price, demand). **Unsupervised** learning finds structure without labels: **clustering** (customer segments), dimensionality reduction, anomaly detection. **Reinforcement learning** learns a policy from rewards (robotics, game play, RLHF for LLMs). **Time-series forecasting** is regression with an order in time, which changes how you split data (no random shuffles) and which baselines you beat (naive last value, seasonal naive).

Data types: **structured** data has a fixed schema (a CSV of measurements, a table); **unstructured** data has none (forum text, call transcripts, video). Matching technology to data: text reviews → NLP; labelled animal images → computer vision; daily sales → forecasting. Generative architectures: **transformers** for text and code; **diffusion models** for images; **object detection** models for locating things in images (checking a logo is placed correctly).

*In my projects:* classification (4.2, 7.3), ranking (1.1), forecasting (9.x).

### 6.2 Bias, variance, overfitting
Expected error = bias² + variance + irreducible noise. **High bias** (underfitting): the model is too simple, bad on train and test. **High variance** (overfitting): it memorises the training set, great on train, poor on unseen data. Symptom pattern: training accuracy high, validation accuracy low and diverging as training continues. Fixes for variance: more data, data augmentation, regularisation (L1/L2, dropout), simpler model, early stopping, cross-validation for model selection. Fixes for bias: richer features, bigger model, less regularisation. **Leakage** looks like the opposite of overfitting (great test score) but is a broken split: information from the future or from the label slips into the features.

*In my projects:* spatial blocks against leakage in seismic (4.4); same-day leakage in the thesis (9.4).

### 6.3 Metrics
| Task | Metric | When it misleads |
|---|---|---|
| Classification | Accuracy = correct / all | Imbalanced classes |
| | Precision = TP/(TP+FP), recall = TP/(TP+FN), F1 | Choose by the cost of each error type (fraud: recall; spam folder: precision) |
| | ROC-AUC, PR-AUC | ROC looks good under heavy imbalance; prefer PR-AUC |
| Regression | MAE, RMSE (MSE), MAPE | RMSE punishes outliers; MAPE explodes near zero |
| Translation | BLEU (n-gram overlap), chrF, COMET | Overlap misses meaning |
| Summarisation | ROUGE, faithfulness (claims supported / all claims) | ROUGE rewards copying |
| Language model | Perplexity | Training metric, not a production quality metric |
| Retrieval | Recall@k, MRR, nDCG | See 10.2 |
| Business | Conversion rate, handle time, deflection, CSAT | Needs attribution (A/B or holdout) |

Monitoring in production: throughput (requests per unit time), latency, error rate, cost, plus quality signals. Not perplexity, not leaderboard scores.

### 6.4 How an LLM behaves
**Pre-training**: next-token prediction on a huge corpus (web, code, books) gives a base model. **Instruction tuning** (supervised fine-tuning on prompt/response pairs) and **preference tuning** (RLHF, RLAIF, constitutional methods) turn it into an assistant. **Tokens** are sub-word units; the **context window** is the maximum tokens per request (input + output) and is a model-selection criterion. Current Claude models offer 1M tokens of context (check current).

**Sampling.** The model outputs a probability distribution over the next token. Temperature rescales it (lower = sharper), top-p keeps the smallest set of tokens whose probability sums to p, top-k keeps the k most likely. **Nondeterminism**: the same prompt gives different outputs because sampling is random, and even "greedy" decoding varies with batching and hardware. In 2026 the newest Claude models fix sampling internally (non-default `temperature`/`top_p`/`top_k` return 400) and expose **effort** and adaptive thinking instead. So "make it consistent" means: pin the model version, constrain the output shape (structured outputs, 12.5), cache identical answers (12.7), and measure repeatability in the eval (10.1).

**Hallucination**: fluent output not supported by the input or by fact. Causes: missing knowledge, retrieval that fetched the wrong passage, pressure to answer, long noisy context. Mitigations: grounding with citations (12.6), permission to abstain, verification steps, grounding checks (12.8).

**Prompt engineering** is designing the input (instructions, role, examples, output format) to get the desired output; it is the cheapest lever.

### 6.5 The customization ladder
| Step | Changes | Good for | Not for |
|---|---|---|---|
| Prompt, few-shot | Input only | Format, tone, task framing | Facts the model has never seen |
| RAG | Input, fetched per query | Fresh, private, citable knowledge; access control per user | Teaching a new skill |
| Tools / agents | Live actions and data | Prices, orders, SQL over Delta tables, web | Static reference text |
| Fine-tune (SFT, LoRA/PEFT) | Weights, small | Consistent style, a narrow classification/extraction skill, smaller cheaper model | Facts that change; "hoping it learns what is appropriate" |
| Distillation | Train a small model on a big model's outputs | Cost and latency | Without an eval to prove parity |
| Continued pre-training | Weights, large, unlabelled domain text | Truly foreign vocabulary (some legal, medical, code bases) | Most enterprise needs |
| Pre-training | Everything | Foundation-model labs | Everyone else |

Security ownership grows with each step (AWS's GenAI Security Scoping Matrix: using a SaaS app with embedded AI = least ownership; training your own model = most).

### 6.6 Model selection
Criteria in order: does it pass **your eval** on your data; context window and modality (text, image, audio); latency and throughput; cost per completed task (not per token); data residency and terms (where inference runs, whether inputs are used for training: on AWS Bedrock prompts and outputs are not shared with model providers); licence for open-weight models; support for tools and structured output. Leaderboards (Chatbot Arena, MTEB for embeddings, code leaderboards) are for shortlisting only. A smaller domain model is often the cost-conscious choice if it passes the eval.

### 6.7 Responsible AI
Dimensions (AWS lists eight; others use similar lists): **fairness** (no unjustified difference between groups), **explainability**, **transparency** (people know they deal with AI and how it is used), **privacy and security**, **safety**, **controllability** (humans can intervene), **veracity and robustness**, **governance** (accountability, audit). For hiring, fairness and transparency are the two that come first.

Practices: balanced and representative data (augment under-represented classes to reduce bias in generated images of people), bias metrics before and after training (SageMaker Clarify on AWS), interpretable models where decisions affect people (logistic regression for risk), human review for low-confidence predictions (Amazon A2I on AWS), and documentation: **model cards** (your model's purpose, data, metrics, limits, risks) and vendor **service cards** (the provider's model's intended use and limits). For regulated decisions (loans): data lineage and lifecycle management of training data, audit trails, and no quiet manual overrides. Legal hygiene for training data: use data you own or that is clearly licensed, and ask curators **before** use, never after. Swiss angle: FINMA expects documentation, independent review and testing for material AI uses (see `10.4-finma-ai-guidance-and-model-risk.md`).

## 8. Glossary

| Term | One-line definition |
|---|---|
| Supervised / unsupervised | Learning with labels / finding structure without labels |
| Classification / regression | Predict a category / predict a number |
| Clustering | Group similar items without labels |
| Overfitting (high variance) | Fits training data, fails on new data |
| Underfitting (high bias) | Too simple; fails on training and new data |
| Leakage | Information unavailable at prediction time slips into training or features |
| Precision / recall | Share of flagged that are right / share of true cases found |
| BLEU / ROUGE | N-gram overlap metrics for translation / summaries |
| Perplexity | How surprised a language model is by text; a training metric |
| Context window | Max tokens a model can process in one request |
| Temperature / top-p | Sampling controls for randomness; removed on the newest Claude models |
| Hallucination | Fluent output not supported by facts or inputs |
| Fine-tuning (SFT, LoRA) | Further training on labelled examples; LoRA updates small adapter weights |
| Continued pre-training | More unsupervised training on a domain corpus |
| Distillation | Train a smaller model to imitate a larger one |
| Model card / service card | Documentation of a model's purpose, data, metrics, limits |
| Responsible AI | Fairness, explainability, transparency, privacy, safety, robustness, governance |

# Course 6 · Chapter 6.4: Auth for MCP today (OAuth resource server, PRM, client registration)

_Andrey Popov's project notes: how it works, why it was built this way, and the theory behind it._

## 2. The problem (business view, plain English)

Once the MCP server returns real, user-specific coaching, it must know **who is calling** and **what that person may do**. The AI platform calls the server on the employee's behalf. The server must not trust the platform blindly, and the platform must not hand out the employee's passwords. OAuth is the standard answer: the employee signs in with the company identity provider, which gives the platform a token for exactly this server.

Finance analogy: a limited power of attorney. The client (employee) authorises an agent (the AI app) to act at one specific bank (this server) with specific permissions (scopes) for a limited time. The bank checks the document is real, was issued for this bank, and covers the action. If the agent presents a power of attorney drawn for a *different* bank, this bank must refuse it.

## 4. How it works (technical walkthrough)

**What is in the repo.** Nothing for auth. `http.ts` answers `/health` and `/mcp` for anyone who can reach port 3000 on loopback (`http.ts:18-35`). `` says: "no authentication, rate limiting or input hardening".

**What the memo said to do.** Add authorization "following the MCP authorization spec. Start with API-key validation and move to full OAuth 2.1"; harden per an external security guide: input sanitization, per-tool rate limits, OAuth 2.1, TLS.

**What the spec requires today (2026-07-28):**
```
Client                      MCP server (resource server)          Authorization server
  │ POST /mcp, no token ───────►│
  │◄── 401, WWW-Authenticate: Bearer resource_metadata="…", scope="…"
  │ GET Protected Resource Metadata ─►│  (lists authorization_servers)
  │ GET AS metadata (RFC 8414 / OpenID) ───────────────────────────►│
  │ register: pre-registered | Client ID Metadata Document | DCR (deprecated)
  │ authorization request: PKCE S256 + resource=<MCP server URI> ──►│  user signs in
  │◄──────────────── code + iss ───────────────────────────────────│
  │ token request: code_verifier + resource ───────────────────────►│
  │◄──────────────── access token ─────────────────────────────────│
  │ POST /mcp, Authorization: Bearer <token> ─►│ validate signature, issuer, audience, expiry, scope
```
Key rules, all from *SPEC-AUTH*, *SPEC-DISC*, *SPEC-SEC*:
- The MCP server **acts as an OAuth 2.1 resource server**; the authorization server may be separate. Servers MUST implement Protected Resource Metadata (RFC 9728) and include `authorization_servers` (at least one). Discovery: `resource_metadata` in the 401's `WWW-Authenticate`, or a well-known URI.
- Clients MUST send the `resource` parameter (canonical URI of the MCP server) in authorization and token requests, and MUST use PKCE with S256 after checking the server advertises it.
- The server MUST validate that each token was **issued for it** (audience) and reject others; invalid or expired tokens get **401**; insufficient scope gets **403** with `error="insufficient_scope"` and the needed `scope`.
- Tokens go in the `Authorization: Bearer` header on **every** request, never in the query string.
- Authorization servers SHOULD return `iss`; clients MUST compare it with the recorded issuer.
- Client credentials are bound to the authorization server that issued them.
- `tools/list` MAY vary by the authorization presented, e.g. only tools the granted scopes permit.

**Client registration priority:** (1) pre-registered credentials if the client has them; (2) Client ID Metadata Documents if the authorization server sets `client_id_metadata_document_supported`; (3) Dynamic Client Registration as a fallback; (4) ask the user.

**The review's design for the memo's case:** resource server only; Entra as authorization server with the platform serving the metadata; per-tool scopes `coaching.advice` and `sessions.book`; manual OAuth registration for Copilot Studio; real user identity in the token. Unverified by me.

## 6. Theory behind it (the "lecture" part)

OAuth/OIDC details not in the MCP pages are general knowledge (check the RFCs).

### 6.1 Authentication, authorization, and OAuth roles
**Authentication** answers "who is this?". **Authorization** answers "what may they do?". OAuth 2.x is an **authorization** framework: it lets a client obtain a limited access token from an authorization server with the resource owner's consent, then present it to a resource server. OpenID Connect adds an identity layer (ID token) on top. Roles: **resource owner** (the employee), **client** (the AI app), **authorization server (AS)** (issues tokens), **resource server (RS)** (holds the protected API; here the MCP server). A **public client** cannot keep a secret (desktop apps); a **confidential client** can.

*In my project:* the design in the spec makes the MCP server only an RS. The 2025-03-26 model had the MCP server doubling as the AS; that was the older, heavier model.

### 6.2 Authorization code flow with PKCE
The client sends the user to the AS with a `code_challenge`; after sign-in the AS returns a short-lived `code`; the client exchanges it with the original `code_verifier`. For S256: `code_challenge = BASE64URL(SHA256(code_verifier))`. An attacker who steals the code cannot redeem it without the verifier. OAuth 2.1 makes PKCE mandatory for all clients and removes the implicit and password grants.

*In my project:* the spec requires PKCE S256 and tells clients to refuse an AS that does not advertise `code_challenge_methods_supported`.

### 6.3 Validating a token at the resource server
A JWT access token is validated locally: signature against the AS's published keys (JWKS), `iss` equals the expected issuer, `aud` contains this resource, `exp`/`nbf` valid, required `scope` present. Written as one condition: *accept ⇔ signature_ok ∧ iss = expected ∧ resource ∈ aud ∧ now < exp ∧ scope ⊇ required*. Opaque tokens are validated by calling the AS's introspection endpoint (RFC 7662). The **audience** check is the one most often skipped, and the spec makes it a MUST.

*In my project:* none of it exists. A future handler would implement this check before any tool code runs.

### 6.4 Resource indicators, audience, and the confused deputy
RFC 8707 lets a client name the target resource in the token request, so the AS issues a token whose audience is that resource. This stops a malicious server from replaying a token against a different one. A **confused deputy** is a service tricked into using its authority for someone else; **token passthrough** (forwarding the client's token upstream) is the classic form. The spec forbids it: the server must obtain a separate upstream token. The standard enterprise pattern is token exchange / on-behalf-of (RFC 8693; general knowledge).

*In my project:* open question 1 asks about "pass-through of the user's identity"; the correct design is exchange, not passthrough.

### 6.5 Discovery: Protected Resource Metadata and AS metadata
RFC 9728 defines a JSON document, served by the resource, that names the resource and its `authorization_servers` (and optionally `scopes_supported`). A client learns where to find it from the `resource_metadata` parameter of the 401 `WWW-Authenticate` header, or by probing the well-known path `/.well-known/oauth-protected-resource` (root or path-specific). RFC 8414 and OpenID Connect Discovery define the AS's own metadata (endpoints, `code_challenge_methods_supported`, `issuer`). The client MUST check that `issuer` matches the URL it used. The purpose: a client that has never heard of your server can find out how to authenticate with no hard-coded configuration.

*In my project:* the memo lists none of this; the 2025-03-26 page it cites used a different, server-centred discovery.

### 6.6 Client registration: three ways, three trade-offs
| Mechanism | How | Strength | Weakness |
|---|---|---|---|
| **Pre-registration** | A human registers the client at the AS and configures the ID/secret | Strong control, simple to audit | Does not scale to many clients/servers |
| **Dynamic Client Registration (RFC 7591)** | Client POSTs its metadata to `/register`, gets credentials | No human step | Unbounded registrations, abuse, state to manage; now deprecated in MCP |
| **Client ID Metadata Documents** | `client_id` is an HTTPS URL; the AS fetches a JSON document from it | No registration state; portable across ASes | AS must fetch URLs (SSRF risk), cannot stop localhost redirect impersonation alone |

Finance analogy: bilateral onboarding (pre-registration) versus open account opening with no checks (DCR) versus a verifiable public identifier like an LEI that the bank looks up (CIMD).

*In my project:* the memo has no registration thinking; the review's plan uses pre-registration for Copilot Studio (*Review §8 point 4*, unverified).

### 6.7 Scopes, least privilege, step-up
A **scope** is a named permission. Least privilege: request and grant only what an operation needs. The server's 401 can carry a `scope` hint; a later 403 `insufficient_scope` triggers **step-up**: the client re-authorises with the union of old and new scopes and retries a limited number of times. Servers must honour scope hierarchies (broader implies narrower). Scope design can mirror the tool list: `coaching.advice` for advice, `sessions.book` for booking.

*In my project:* the scope-line from chapter 6.3 becomes the scope list: read-only advice needs less than booking.

### 6.8 What an API key is good for
An API key identifies an **application** with a shared secret. It is acceptable for server-to-server calls to non-personal capabilities, with rotation, per-key limits and no per-user claims. It cannot express "this employee, these permissions, revocable by the employee's company". Treat it as a stepping stone, not as the user-identity answer.

*In my project:* "API key first" is fine for reference data and nothing personal.

### 6.9 Threat list for MCP authorization (from *SPEC-SEC*)
Token theft (short-lived tokens, secure storage); code interception (PKCE); mix-up attacks (compare `iss`); open redirect (exact redirect-URI match, `state`); SSRF through CIMD fetches; confused deputy in proxy servers; DNS rebinding on local servers (Origin check, loopback bind).

## 8. Glossary

| Term | One-line definition |
|---|---|
| OAuth 2.1 | Consolidated OAuth: authorization code + PKCE, no implicit/password grants |
| Resource server (RS) | The API that accepts access tokens; here the MCP server |
| Authorization server (AS) | Issues tokens after authenticating the user |
| PKCE (S256) | Code challenge/verifier pair binding the code to the client that asked |
| PRM | Protected Resource Metadata (RFC 9728): document naming a resource's authorization servers |
| `resource_metadata` | Parameter in `WWW-Authenticate` pointing to the PRM URL |
| Resource indicator (RFC 8707) | Parameter naming the target server so the token's audience is bound to it |
| Audience (`aud`) | Who the token is meant for; the RS must check it |
| Scope | Named permission carried in the token |
| Step-up | Re-authorising with more scopes after a 403 `insufficient_scope` |
| DCR (RFC 7591) | Dynamic Client Registration; deprecated in MCP in favour of CIMD |
| CIMD | Client ID Metadata Document: `client_id` is an HTTPS URL to the client's JSON metadata |
| Token passthrough | Forwarding a received token upstream; forbidden by the spec |
| Token exchange / OBO | Trading one token for another to call a downstream API as the user |
| `iss` (RFC 9207) | Issuer in the authorization response; guards against mix-up attacks |
| Bearer token | A token that works for whoever presents it |
| JWKS | Published signing keys used to verify JWTs |

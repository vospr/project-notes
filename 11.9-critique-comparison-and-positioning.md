## 2. The problem (business view, plain English)

A hiring manager for an AI engineering role wants to know whether you understand how production agent systems fail, not only how to call a model. The cheapest way to show that, apart from building one, is to read a serious one critically and be precise about what you learned and what you do not know. The risk is overclaiming: presenting someone else's repository as your experience, or praising it without having run it. This chapter is the guard against both.

Finance analogy: it is a due-diligence memo on a counterparty's operations. You read the control framework, test a sample, and write down what is strong, what is weak, and what you could not verify.

### 4.2 Strengths, each with the evidence behind it
1. **Failure classes are separated and named.** Transport errors retry in place, rate limits rotate and fall back, overflow goes to compaction, stalls dump a replayable payload, and anything already shown to the user is never silently replayed (chapter 11.2). Each rule cites an incident number. This is the part of the repo most worth copying.
2. **Guards exist because of recorded incidents.** The pairing repair (#85), the misuse breaker (the 15-identical-calls incident), the stuck-call supervisor (gh-1054), the obligations ledger (#488 lesson) are all post-mortems turned into code and tests (chapters 11.3, 11.4). Contrast with generic "best practices" lists.
3. **Compaction protects intent.** Hide before summarise, exempt user turns, verbatim obligations, byte-identical pins, notices on every drop (chapter 11.4). Most harnesses summarise and hope.
4. **Hashline edits are compare-and-swap** on file content: drift is rejected before any write (chapter 11.5).
5. **Rules are machine-checked.** CRAP ratchet with an only-down guard, file ceiling, duplication, goldens, parity matrix, deterministic CI with the `llm` tag boundary (chapter 11.7). The repo's own comments admit what is not yet earned (the 8.0 repin).
6. **Honest documentation of divergences.** File headers list what differs from pi-mono and oh-my-pi and why. That is rare and makes the code teachable.
7. **A frozen, versioned host protocol** with fixtures for every version (chapter 11.6).

### 4.3 Risks and weak points, each with the evidence behind it
1. **Scope and size.** A harness, a terminal UI (62k lines), a Flutter app, a browser extension, an Outlook add-in, a messaging hub, a sandbox, a JS app runtime, store pipelines. 185k lines of `lib/` for one owner plus agents is a large surface; the file-size gate and CRAP ratchet are symptoms of that pressure (chapter 11.7).
2. **Regex-based classification** of provider errors and overflow (chapter 11.2) is pragmatic and brittle. Wording changes silently reclassify errors. Recorded-body contract tests would reduce the risk; I did not see them.
3. **Autonomous mode removes the interceptor** and relies on external isolation (chapter 11.5), while the factory itself runs agents with write permissions against a mutable factory ref (chapter 11.8).
4. **Guards leak across modes.** The FinalizeGate fired in interactive autopilot sessions (#1516) because the prompt had no scope clause and the gate is tied to a permission mode. Coupling a prompt contract to an unrelated mode switch is a design smell.
5. **No outcome data for the AI loop.** The repo reports activity (labels, counts), not defect rate, revert rate or cost per merged change (chapter 11.8).
6. **A 134 KB `AGENTS.md`** costs context on every agent run and will contain contradictions over time (chapter 11.8).
7. **Flaky and red-main tickets are constant** in the newest issues (timing assertions on loaded runners, port clashes). That is normal for a fast-moving repo with agent-written tests, and also a sign that the deterministic claim is aspirational at the margin.
8. **Self-grading.** The FinalizeGate ledger is written by the same agent that did the work (chapter 11.3). Useful evidence; not independent verification.
9. **Reduced ports.** Many features are "ported (reduced)" from oh-my-pi: no tree-sitter hashline blocks, no AST rules in TTSR, fewer agent roles. Fine, but it means the repo is a subset of its parents in places.

## 5. Why it was built this way (decisions and trade-offs)

Summarised from chapters 11.1 to 11.8; the cross-cutting trade-offs are:
| Decision | Alternatives considered | Why this one | Cost / risk |
|---|---|---|---|
| Port a TypeScript design, keep it "mechanically close" | New design | Inherit field-tested behaviour; fixes port | Inherits shape and gaps; Dart idiom suffers in places |
| One core for seven hosts | Per-platform apps | One engine, one behaviour | Capability ceremony and a very large core |
| Guards per incident | Generic framework | Each guard has a reason and a test | Many special cases to understand |
| Metrics-as-gates | Review-based quality | Scales with agent-written code | Goodhart; needs outcome measurement |
| Build the product with itself | Separate tools | Fast feedback on the harness | Self-referential failures |
| Heavy documentation in code headers | Separate docs | Divergences stay next to code | Headers drift; hard to see the whole |

## 6. Theory behind it (the "lecture" part)

### 6.1 Reading a codebase critically (due diligence)
A structured read has four passes: **contract** (what does it promise: README, goal, protocol docs), **structure** (layers and dependencies: directory census, imports), **failure handling** (what happens when things go wrong: retries, guards, tests), and **evidence** (what proves it works: tests, benchmarks, production history). Separate *what the code says* from *what I ran* and from *what I assume*. Write down what could not be verified.

*In my project:* every chapter in this course carries a source caveat for that reason.

### 6.2 Risk-based assessment of agent systems
Agent risk comes from four factors: **autonomy** (how many steps without a human), **authority** (what tools and permissions), **exposure** (what data and networks), and **observability** (can you reconstruct what happened). Controls map to them: caps and approvals (autonomy), tiers and sandboxes (authority), redaction and scoping (exposure), ledgers and trajectories (observability). A fair assessment scores each factor and notes which controls are preventive, detective or corrective.

*In my project:* the FINMA-oriented chapter in Course 10 uses the same split for model risk.

### 6.3 Build, buy or study
For a team the options are: use a vendor agent product, build on a framework, or build a harness. Study of an open-source harness informs all three: it tells you which concerns a product hides and which you would have to own. The decision criteria are control (data, models, policies), portability (hosts, languages), cost of ownership (surface area, maintenance), and time to value.

*In my project:* in Swiss banking contexts, data residency and auditability push toward more control and therefore toward understanding exactly this layer.

### 6.4 The honest-claims ladder
Claims about a system come in rungs: **I read it**, **I ran it**, **I measured it**, **I operated it**, **I built it**. State the rung. This course is at "I read it" for most parts, with a few first-hand counts.

*In my project:* the same discipline as the evidence ladder for hooks (Course 8.3).

# Course 1 · Chapter 1.4: Rule 3 and the exclusion rules: business rules as guarded SQL

_Andrey Popov's project notes: how it works, why it was built this way, and the theory behind it._

## 2. The problem (business view, plain English)

Some open positions are tied to a client deal ("deal-aligned"). For those, the staffing desk later rejects candidates who have the wrong skill, are far off in seniority, or sit in a location that is too expensive for the deal's rate zone. The model did not know these rules, so managers were shown candidates the desk would refuse anyway.

The fix the product owner asked for: remove those candidates from the model's scope before results are shown. No retraining. Just cut the wrong pairs earlier.

Finance analogy: a credit committee that always rejects deals outside the risk appetite. Pre-screening those deals before the committee meets saves everyone's time, but the pre-screen must apply exactly the committee's rules, or it will throw away deals the committee would have approved.

## 4. How it works (technical walkthrough)

**Activation.** All three rules act only when the position's deal-alignment field is the aligned value or the not-aligned value. Everything else (blank, the not-included value, the deal-pending value) must keep legacy behaviour.

**Where the rules sit (v2).** In the existing dbt filter chain, which cuts the pair space step by step:

```
the candidates intermediate model ─┐
the positions intermediate model ──┴─► the location filter step        ◄── Rule 3 (location)        77.7M rows
                    └► the similarity filter step ◄── Rule 1 (skill) + Rule 2 (seniority)   2.2M rows
                       └► the start-date filter step ─► the skill-ratio filter step ─► the joined-features model ─► features ─► scoring
```
Excluded pairs never reach the eligible-pairs file, so they are never scored. The rules sit beside earlier team filters in the same files: billing type in the location filter, NB-seniority in the similarity filter.

**Rule 1: skill.** Exclude if the candidate's primary skill differs from the position's AND the position's skill is not in the candidate's key skills. COALESCE over the key-skills array turns a NULL array into an empty array.

**Rule 2: seniority.** Map A1…B5 to 1…10 with the team's seniority-mapping UDF (unknown = 0). Exclude when the employee is 2+ levels below the position's minimum or above its maximum. One level below is tolerated on purpose. If either side maps to 0, the rule is skipped (fail-open). For deal-aligned positions it replaces the legacy exact-match seniority predicate.

**Rule 3: location, step by step.** Exclude only when **all three** routes to the position fail:
1. **Assigned location:** the candidate's rate zone is one of the position's, and the candidate's tier number ≥ the position's minimum tier. A position with no rate zones passes everyone.
2. **Organizational location:** the same test on the org location. If the candidate has none (zone 0 and tier 0), the branch **fails** instead of passing. That is the zone-0 guard: without it, "0 = 0" could match a position whose zone is also 0.
3. **IM / relocation:** fails at once if the position does not allow relocation (staffing channel 4) or the IM status is NULL or not the open-for-opportunities status / the on-hold status. Otherwise it passes if **any** IM target location passes the zone/tier test.

Written as `AND NOT (guard AND NOT b1 AND NOT b2 AND NOT b3)`. By De Morgan this means "keep if not deal-aligned, or b1, or b2, or b3".

**Data for Branch 2 and 3** comes from four new CTEs in the employees intermediate model: the latest IM request per employee (`QUALIFY ROW_NUMBER … = 1`); its target locations flattened from JSON and resolved to zone/tier; re-aggregated into an array of (rate zone, country tier) structs; and an org-location lookup. The original relocation CTEs were left untouched; the new ones are deliberately wider (status 4+5, location types 1+2+3, missing active flag = TRUE).

## 5. Why it was built this way (decisions and trade-offs)

| Decision | Alternatives | Why this one | Cost / risk |
|---|---|---|---|
| Filter at inference, no retraining | Filter training data too (pre-filter) | Pre-filter alone still serves the bad pairs; retraining is manual, hours per model × 3 | The model still learns from pairs it will never be shown |
| v1: enforce on every surface (online API, batch, ingestion, telemetry) | Batch only | Acceptance criteria say "applied in models: Top Pos, Top Cand, Opp"; consistency between online and batch | 4 PRs; redirected later |
| v2: dbt-only, forecast-only, inside the existing filter files | Python prediction-step post-score filter (v1) | Tech lead: "almost all filtering is done within dbt in SQL"; matches codebase conventions | Online API not filtered; no telemetry flags |
| Predicates in existing filter models, not a new stage | A new deal-alignment filter model | Fewer models; the rule sits where a reader expects it | Filter files get longer and mix several tickets |
| Separate deal-alignment CTEs | Widen the original relocation CTEs | No side effects on the existing relocation logic | Two similar CTE sets to maintain |
| Fail-open on unknown seniority | Fail-closed (drop unknowns) | Better to show one wrong candidate than hide a right one; non-A/B grades exist | Some wrong candidates survive |
| Zone-0 guard on Branch 2 | Treat 0 as a normal zone | Missing org location is coded 0/0; "0 = 0" would pass falsely | None found |
| Size by simulation before release | Ship and watch | No deal-aligned rows in data ||

## 6. Theory behind it (the "lecture" part)

### 6.1 Hard constraints versus soft scores in ranking
A ranker learns a soft score s(p, c) for a position p and candidate c. Business rules are hard constraints g(p, c) ∈ {keep, drop}. The final list is the top N by s over {c : g(p, c) = keep}. Two places to apply g:
- **Before scoring (candidate generation).** Cheaper (fewer pairs scored) and the model never sees the excluded pairs. This is v2.
- **After scoring (post-filter).** Scores computed for all pairs, then dropped. Easier to log what was filtered and why. This was v1 batch.

Either way, filter **before** the top-N cut. If you cut first and filter afterwards, a list of 10 can shrink to 3. The v1 online design put the filter "before `ORDER BY … LIMIT`" for exactly this reason.

*In my project:* v2 is before scoring, in the dbt filter chain that already cuts 78M pairs to about 2M.

### 6.2 Three-valued logic (the NULL lecture)
SQL has TRUE, FALSE and UNKNOWN (NULL). Rules:
- `NULL = x`, `NULL != x`, `NULL IN (…)` → NULL
- `TRUE AND NULL` → NULL; `FALSE AND NULL` → FALSE
- `TRUE OR NULL` → TRUE; `FALSE OR NULL` → NULL
- `NOT NULL` → NULL
- `WHERE` keeps a row only when the predicate is TRUE. NULL behaves like FALSE.

So a filter written as `WHERE NOT (bad_condition)` has a trap: if `bad_condition` is NULL, `NOT NULL` is NULL and the row is **dropped**. You meant "keep unless clearly bad". You got "drop unless clearly good". Exclusion filters fail closed on NULL unless you force a boolean.

Tools to force a boolean: `COALESCE(x, default)`, `IFNULL(pred, FALSE)`, `x IS NULL OR …`, `IS DISTINCT FROM`, and `CASE WHEN … THEN TRUE ELSE FALSE END` (a CASE never returns NULL if every branch is a literal).

*In my project:* Branches 1–3 are wrapped in CASE with literal TRUE/FALSE, so each branch is a clean boolean. `COALESCE` handles NULL arrays. The explicit internal-mobility-status null check is there.

Finance analogy: a missing rating in a credit filter. "Exclude if rating below BBB" must decide what a missing rating means. If the system silently treats missing as "excluded", you lose half your universe and nobody notices.

### 6.3 Fail-open versus fail-closed
When the rule cannot be evaluated (missing data), you must choose:
- **Fail-open:** keep the item. Cost: a false positive (a wrong candidate is shown).
- **Fail-closed:** drop it. Cost: a false negative (a right candidate is hidden, and nobody sees it was hidden).

Choose by the cost of each error. In staffing, a human reviews the list, so a shown wrong candidate is cheap and a hidden right one is expensive. That argues for fail-open. In security or compliance the opposite holds.

*In my project:* Rule 2 fails open on unknown seniority. Branch 2 fails "closed for that branch only" when there is no org location, which is safe because Rule 3 still keeps the candidate if Branch 1 or 3 passes.

### 6.4 Boolean structure: De Morgan and "all routes must fail"
Rule 3 is a disjunction of routes: keep ⇔ b1 ∨ b2 ∨ b3. Exclusion is the negation: ¬b1 ∧ ¬b2 ∧ ¬b3 (De Morgan). Writing it as `NOT (guard AND NOT b1 AND NOT b2 AND NOT b3)` mirrors the ticket's wording ("AND … AND …") and makes each branch testable on its own.

Testing rule of thumb for an n-branch disjunction: you need at least n + 1 cases: one where each branch alone passes (n cases) and one where all fail. Add the edge cases (NULL, zone 0, empty array) and you have the fixture set the review recommends.

### 6.5 Marginal effect of a rule (why "0%" is a finding)
A new filter's value is its **marginal** exclusion rate: the share of pairs it removes that the earlier filters did not already remove. If filter F₁ already removes set E₁, and the new filter removes E₃, the marginal effect is |E₃ \ E₁| / N. When filters are chained, the measured effect of a later filter on the survivors *is* its marginal effect.

*In my project:* Rule 3 runs inside the location filter step, on pairs that already passed the general cost-tier limitation. A 0% marginal effect is therefore plausible even with deal-aligned rows. The honest framing: "it is a business guarantee at near-zero cost, and I would have measured its marginal effect before building it".

### 6.6 Simulation versus witness testing versus unit tests
- **Simulation:** apply the predicate to a sample and count. Tells you size, not correctness.
- **Witness (live) test:** find real rows where the rule should fire and check it does. Impossible here: 0 deal-aligned rows.
- **Unit test with fixtures:** construct rows by hand (an aligned position + one candidate that fails each branch). Proves every branch without waiting for live data. dbt has had native unit tests since v1.8. This is the review's first "do it again" point.

## 8. Glossary

| Term | One-line definition |
|---|---|
| Deal-aligned position | A position with the deal-alignment field = the aligned value or the not-aligned value; the only ones the rules act on |
| Rate zone | A group of locations with the same billing rate band |
| Cost tier | Cost level of a location within a zone; lower number = more expensive ("2 is higher than 3") |
| Assigned / organizational location | Where the employee works now / where they are employed on paper |
| IM request | Internal-mobility request: the employee's wish to relocate, with status and target locations |
| Staffing channel 4 | The code for "relocation supported" on a position |
| Filter chain | dbt models that cut pairs step by step: location → similarity → start date → ratios |
| Fail-open / fail-closed | Keep / drop the item when the rule cannot be evaluated |
| Three-valued logic | SQL's TRUE / FALSE / NULL; `WHERE` keeps only TRUE |
| Zone-0 guard | Branch 2 fails when the org location is missing (coded 0/0) instead of matching zone 0 |
| Marginal effect | What a new filter removes that earlier filters did not |
| Witness test | Checking a rule on real rows where it should fire |
| `QUALIFY` | BigQuery clause that filters on a window function, e.g. keep `ROW_NUMBER = 1` |

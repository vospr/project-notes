**In short:** The retrieval ladder: index files and grep, BM25 and FTS5, dense, hybrid with reciprocal rank fusion, contextual retrieval (35, 49, 67 percent fewer failures), reranking, agentic search; how to diagnose slow search before adding RAG.

## 2. The problem (business view, plain English)

"Our knowledge search is slow or misses things, should we do RAG?" is the question I was asked by a colleague in July. The honest answer is that "slow" has at least five different causes and RAG fixes only one of them. Teams that jump to a vector database add infrastructure, a re-embedding pipeline and a new way for answers to go stale, without ever measuring what was wrong.

Analogy: a doctor does not prescribe surgery for "feeling unwell". First a thermometer, then blood tests, then the lightest treatment that works.

## 4. How it works

### 4.1 The ladder, lightest to heaviest
| Rung | What it is | Fixes | Costs |
|---|---|---|---|
| 0. Put it all in the prompt | Skip retrieval below about 200,000 tokens (about 500 pages) with prompt caching | Everything, for small corpora | Cost per question; no per-document access rules |
| 1. Curated index + exact search + point reads | Small map files, `grep`, read only the needed section | Exact names, IDs, symbols; always fresh | More agent turns; fails on paraphrase |
| 2. Keyword ranking (BM25), e.g. SQLite FTS5 | Ranked word matching with headings and metadata kept | Slow scans; ranking | No meaning-matching |
| 3. Dense embeddings | Turn text into vectors; find nearest | Paraphrase, other languages | Index must be rebuilt as text changes; fuzzy on exact terms |
| 4. **Hybrid** | Run 2 and 3, merge ranked lists with **reciprocal rank fusion** | Both exact and fuzzy | Two indexes |
| 5. **Contextual retrieval** | A model prepends a short "where this chunk sits" note to each chunk before indexing | Chunks that make no sense alone | One-time model pass per chunk (about $1.02 per million document tokens with caching, per Anthropic) |
| 6. Reranker | A second model reorders the top candidates | Right answer found but ranked too low | Extra model and latency |
| 7. Agentic search | The agent chooses the tool and iterates: search, read, refine | Variable, multi-step questions | Tokens, latency |

### 4.2 Anthropic's numbers (top-20 chunks, failure rate; baseline 5.7%)
```
contextual embeddings alone            5.7% -> 3.7%   (35% fewer failures)
+ contextual BM25                      5.7% -> 2.9%   (49% fewer)
+ reranking                            5.7% -> 1.9%   (67% fewer)
```
An independent re-run (different embeddings and reranker, Recall@20) reproduced the pattern for keyword search (contextualising lifted BM25 from 70.5 to 89.3) but found the reranker alone slightly ahead of the full stack on contextual data (96.1 vs 95.7). Read: the order of benefit is real; the exact stack needs your own test.

### 4.3 Reciprocal rank fusion in four lines
```python
def rrf(rankings, k=60):                 # rankings: lists of doc ids, best first
    score = {}
    for r in rankings:
        for pos, doc in enumerate(r, 1):
            score[doc] = score.get(doc, 0) + 1 / (k + pos)
    return sorted(score, key=score.get, reverse=True)
```
A document ranked high by both lists wins; no score calibration needed between keyword and vector scores.

### 4.4 Diagnose "slow" before adding a rung
| Observed | Likely cause | First move |
|---|---|---|
| The search command itself is slow | Repeated full scans | Filter the corpus; add a full-text index |
| Search is fast, the answer is slow | Too many agent turns or too much text passed to the model | Routing, smaller heading-aware chunks, a context budget |
| The right source is never found | Paraphrase or language gap | Add a dense side and fuse (rung 4) |
| Found but buried | Ranking | Add a reranker, after checking candidate recall |
| Old or wrong documents used | Missing freshness or authority metadata | Fix metadata and checks first (14.6) |

### 4.5 Keyword search plus an agent
The Amazon-science paper (abstract) reports that an agent with only keyword-search tools reached over 90% of the performance metrics of RAG without a vector database, and calls it simple, cheap, and suited to frequently updated knowledge bases. Treat it as a reason to benchmark lexical-first, not as a guarantee.

## 5. Why it was built this way (decisions and trade-offs)

| Decision | Alternatives | Why this one | Cost / risk |
|---|---|---|---|
| Lexical-first with curated indexes | Vector database from day one | Fast-changing, exact-symbol corpus; nothing to re-embed; easiest to approve on a locked-down machine | Weak on paraphrase and cross-language; more agent turns |
| Keep vector retrieval conditional on a measured gain | Adopt because it is standard | Retention gates: at least 10 points better recall on paraphrase questions, no more than 2 points worse on exact ones | Needs a benchmark first |
| Hybrid before a reranker | Reranker first | A reranker cannot rescue what was never retrieved | One more index |
| Keep every index disposable | Treat the index as data | The source files stay the only truth; rebuild on demand | Rebuild time |

## 6. Theory behind it (the "lecture" part)

### 6.1 Sparse vs dense retrieval
Sparse (BM25) scores shared words, weighting rare words more; it is exact and explainable. Dense scores closeness of meaning in a vector space; it finds paraphrases but can blur exact identifiers.
*In this course:* identifiers, ticket numbers and symbols favour sparse; prose with varied wording favours dense.

### 6.2 BM25 in one idea
A document scores higher when it contains the query's rare words, more times, but with diminishing returns for repeats, and without unfairly favouring long documents.
*In this course:* my portfolio router uses a similar saturating term score (`f / (f + 1.2)`) weighted by how rare a word is.

### 6.3 Recall vs precision
Recall asks "did the right item appear at all?"; precision asks "how much of what appeared is right?". A reranker improves precision at the top; it cannot improve recall.
*In this course:* measure candidate recall before deciding on a reranker (14.7).

### 6.4 Context windows change the economics
Large windows and prompt caching made "just include it" viable for small corpora, and agents with search tools made index-free retrieval viable for changing ones. Both lower the case for default vector infrastructure.
*In this course:* start at rung 0 or 1 and justify each step up.

### 6.5 Chunking and metadata
Splitting text at headings and keeping the file path, heading chain, date and source hash with each chunk is what makes citations and freshness checks possible later.
*In this course:* see 12.6 for chunking strategies; here metadata is the point.

## 8. Glossary

| Term | One-line definition |
|---|---|
| BM25 | Ranked keyword scoring that favours rare words with diminishing returns |
| Dense retrieval | Finding text by closeness of embedding vectors |
| Hybrid search | Combining keyword and vector results |
| Reciprocal rank fusion (RRF) | Merging ranked lists by summing 1/(k + rank) per document |
| Contextual retrieval | Adding a model-written location note to each chunk before indexing |
| Reranker | A model that reorders the top candidates for relevance |
| Agentic search | An agent choosing tools and iterating until it has enough |
| Point read | Reading one section of one file directly |
| SQLite FTS5 | The full-text search module built into SQLite |
| Recall@k | Share of questions where the right item is in the top k |
| Retention gate | A threshold a new component must beat to be kept |

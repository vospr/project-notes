# Course 6 · Chapter 6.3: What to expose before identity and GDPR (DPIA, data exposure to third-party AI, scope lines)

_Andrey Popov's project notes: how it works, why it was built this way, and the theory behind it._

## 2. The problem (business view, plain English)

The coaching product's content is sensitive: employees talk about their manager, their stress, their career. Exposing the coach inside Copilot, ChatGPT Enterprise or Claude means a third-party AI platform sits between the employee and the coaching service. The business question: what can go out through that channel now, before the product has a verified user identity and before a data-protection impact assessment (DPIA) has been done?

The memo's answer is a staged rollout. Expose things that carry no user-specific data (reference data, a single question and answer, booking). Hold back anything that remembers a person (memory, progress, a full multi-turn conversation).

Finance analogy: a new-product approval process. A bank may publish its rate card before know-your-customer checks exist; it may not open accounts. The DPIA is the risk sign-off for the new product; identity is KYC. The scope line is "publish the rate card now, open accounts after sign-off".

## 4. How it works (technical walkthrough)

**The scope line as a table:**
```

```

**Who sees what when a user calls the tool:**
```
Employee ─► AI platform (Copilot/ChatGPT/Claude) ─► MCP server ─► (Phase 2) coaching API / LLM / DB
  question text ─────────────►  platform sees it, may log/retain it
                              tool arguments ──────►  server sees question + theme
                              tool result ◄─────────  response, detectedCue, phase (server.ts:73-78)
  platform's model reads the result and may quote it back, store it in the chat history
```
The platform sees the prompt, the tool arguments and the tool result. Whether it retains or trains on them is open question 3, not answered.

**The memo's reasoning chain:** (1) client-side state sends coaching content to third-party models; (2) server-side sessions need verified identity; (3) no impact assessment exists; (4) single-turn advice is still useful. So defer the multi-turn loop, ship the single-turn subset.

**Options:** A build Phase 1 (recommended), B defer entirely (misses the market window), C full coaching now (premature), D custom API per platform (N integrations).

**What the spike itself exposes.** Placeholder data and canned strings only, no user records (`coaching-data.ts:10-80`). So the spike has nothing sensitive to leak; the privacy reasoning is about the future real backend.

**Next steps as written:** Week 1 connect API, add auth, deploy; Week 2 register in Copilot Studio, add an auth-gated user-specific read-only resource, **start** the impact assessment; Week 3+ hardening, per-user protection, entitlement, monitoring. Note the order.

## 5. Why it was built this way (decisions and trade-offs)

| Decision | Alternatives | Why this one | Cost / risk |
|---|---|---|---|
| Expose single-turn advice, booking, reference data | Expose nothing (option B); expose everything (C) | Gets a distribution channel without user-specific state | Quality may fall without the arc; booking needs identity |
| Defer multi-turn, memory, history | Build with sessions now | Needs identity and an impact assessment first | Smaller product, slower reach |
| Make the DPIA a gate, not a parallel track | Start the DPIA while building | Processing must be assessed before it starts (Art. 35, general knowledge, check the regulation) | The memo's Week 1 does not follow its own gate |
| Reference data as resources | Keep the model private | Cheap context for clients | IP exposure; product owner must approve |
| Document eight open questions instead of answering | Guess | Honest about unknowns; usable by the client's legal team | Many are blockers (auth model, platform terms) |
| Stub backend in the spike | Real backend | No credentials, no real data | "Mostly a backend swap" understates auth, errors, latency |

## 6. Theory behind it (the "lecture" part)

All GDPR content here is from general knowledge; check the regulation and ask counsel.

### 6.1 Personal data, controller, processor
**Personal data** is any information relating to an identified or identifiable person (Art. 4(1)). **Processing** is almost any operation on it, including storing and transmitting. The **controller** decides the purposes and means; the **processor** acts on the controller's instructions under a contract (Art. 28). A platform that stores prompts for its own purposes may be a controller for that part. Roles decide who owes what, so they are the first thing to fix.

*In my project:* the memo asks about processing agreements per platform but does not assign roles.

### 6.2 Lawful basis, purpose limitation, minimisation
Processing needs one of six lawful bases (Art. 6): consent, contract, legal obligation, vital interests, public task, legitimate interests. Principles (Art. 5): purpose limitation, **data minimisation** (only what is needed), storage limitation, security, and **accountability** (be able to show compliance). Special categories (health, beliefs, and others; Art. 9) need an extra condition. In employment, consent is rarely "freely given" because of the power imbalance.

*In my project:* the scope line is minimisation in practice: expose only calls that need no stored personal data. The memo documents its decision, which serves accountability. It does not name a lawful basis.

### 6.3 DPIA (Data Protection Impact Assessment)
Art. 35 requires a DPIA **before** processing that is likely to result in a high risk to people, in particular with new technologies. It must be done for systematic and extensive profiling with significant effects, large-scale special-category data, and large-scale systematic monitoring of public areas. Regulators' guidelines add criteria (new technology, sensitive data, vulnerable subjects such as employees, large scale, matching datasets); meeting two or more usually means a DPIA. Contents (Art. 35(7)): a description of the processing and purposes; an assessment of necessity and proportionality; an assessment of risks to individuals; the measures to address them. Where residual risk stays high, the controller must consult the regulator first (Art. 36). The DPO's advice is sought where there is one.

Risk is judged on likelihood and severity of harm **to the person**, not to the company. A DPIA is not a lawful basis; it is a documented risk analysis.

*In my project:* the memo treats the DPIA as the gate for any coaching content through third-party clients. Employees are vulnerable data subjects and AI platforms are a new technology, so the instinct is sound. The sequencing is the weak part.

### 6.4 Third-party exposure: what the platform sees
An MCP tool call sends the model's arguments to the server and puts the result into the model's context. Everything in that context is visible to the platform operating the model, subject to its enterprise terms (retention, training, location, sub-processors). Chapter V of GDPR (Arts. 44-49) governs transfers outside the EEA. So the question is never only "what does our server store?" but "what flows through the platform, and under whose terms?".

*In my project:* open questions 2, 3 and 7 (residency, training opt-out, erasure) are exactly these; none is answered.

### 6.5 Pseudonymisation versus anonymisation, and encryption
**Anonymous** data cannot reasonably be linked back to a person and falls outside GDPR (Recital 26). **Pseudonymised** data can be linked using extra information and stays personal data (Art. 4(5)). Encrypted data is personal data for anyone who holds the key. Encryption protects against unauthorised access (Art. 32); it does not by itself change the data's legal status.

*In my project:* relevant to the hybrid-token option and to any "aggregate reporting" claim: aggregates are anonymous only if re-identification is not reasonably possible, which the memo does not test.

### 6.6 A scope-line test (my framing, not a standard)
For each capability, ask five questions; expose it before identity only if all pass:
1. **No identifiable person:** does the call neither take nor return data about a specific individual?
2. **No memory:** does the server keep nothing linked to the caller?
3. **Reversible or low impact:** can a wrong or repeated call be undone cheaply?
4. **Not secret:** is the content safe to show any connected platform (IP, contracts)?
5. **Bounded input:** is the free-text field capped and treated as untrusted?

Applied to the memo: reference data passes 1-3, fails 4 until the owner agrees; single-turn advice passes 2 and mostly 3 but only weakly 1 and 5 (free text, inferred cue); booking fails 1 and 3 unless anonymous and idempotent.

Finance analogy: an information barrier. Public research can cross the wall; client-specific positions cannot.

### 6.7 Prompt injection and the exfiltration pattern
Anything in the model's context can steer it, including tool output and user text. A system is most exposed when one model has (a) access to private data, (b) exposure to untrusted content, and (c) a way to send data out (a widely used framing, sometimes called the "lethal trifecta"; general knowledge). Removing any one leg removes the exfiltration path. Mitigations: input caps, content filtering, least privilege, human confirmation, and clients that treat tool annotations as untrusted.

*In my project:* open question 6 flags the free-text `question` as the injection surface once a real LLM sits behind it. Phase 1 with a stub removes leg (a); the real backend brings it back.

## 8. Glossary

| Term | One-line definition |
|---|---|
| GDPR | EU General Data Protection Regulation |
| Personal data | Information relating to an identified or identifiable person (Art. 4(1)) |
| Special category data | Sensitive data such as health; extra conditions (Art. 9) |
| Controller / processor | Decides purposes and means / acts on the controller's instructions |
| Lawful basis | One of six legal grounds for processing (Art. 6) |
| DPIA | Documented risk assessment required before high-risk processing (Art. 35) |
| DPO | Data Protection Officer, advises on compliance where required |
| Data minimisation | Process only what is needed for the purpose |
| Chapter V transfers | Rules for sending personal data outside the EEA (Arts. 44-49) |
| Right to erasure | Person's right to have data deleted (Art. 17) |
| Pseudonymisation | Data linkable to a person only with extra information; still personal data |
| Scope line | The boundary between what is exposed now and what is deferred |
| Third-party AI platform | The vendor running the model the user talks to (Copilot, ChatGPT, Claude) |
| Prompt injection | Text that hijacks a model's behaviour through its context |
| Tool annotations | Server hints about a tool's behaviour; untrusted unless the server is trusted |
| Information barrier | Control that stops sensitive information crossing a boundary (finance analogy) |

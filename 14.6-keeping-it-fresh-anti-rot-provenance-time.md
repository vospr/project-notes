# Course 14 · Chapter 14.6: Keeping it fresh: anti-rot, provenance and time

_Andrey Popov's project notes: how it works, why it was built this way, and the theory behind it._

**In short:** Keeping knowledge fresh: five kinds of rot, authority tiers, hashes and commits, fresh stale invalid checks, provenance, supersede instead of overwrite, temporal facts in memory, lint, fail-open versus fail-closed.

## 2. The problem (business view, plain English)

A knowledge system that is wrong with confidence is worse than none. Rot is quiet: the code changes and the graph still describes the old structure; a decision is reversed and an old wiki page still states it; a copied number in an agent's persona file stops being true. Nobody notices until someone acts on it. In a regulated setting, "the assistant cited a superseded policy" is an incident.

Analogy: food in a fridge. Without dates and a routine check, you find out what has gone off by eating it.

## 4. How it works

### 4.1 Five ways knowledge rots
| Rot | Example | Check that catches it |
|---|---|---|
| **Source drift** | Code changed after the graph was built | Compare commit and file hashes to the graph's manifest |
| **Semantic drift** | Docs changed but only the code layer was refreshed | Separate "code layer fresh" from "doc layer fresh" |
| **Copy drift** | Node counts copied into a persona file | Generate numbers from a state file; never paste them |
| **Authority confusion** | A wiki summary overrides the meeting note it summarises | Tier rules per question type |
| **Silent overwrite** | A decision edited away, history lost | Supersede notes; dated entries; version control |

### 4.2 Authority tiers
```
Tier A  current code and live workspace docs
Tier B  immutable raw evidence (meeting notes, handoffs)
Tier C  curated synthesis (wiki)
Tier D  imported, dated snapshots
Tier E  untrusted comparative material   (excluded unless explicitly requested; always last)
```
Precedence depends on the question, not one global ranking:
| Question type | Order |
|---|---|
| What does the system do now? | A, B, C, D |
| Why was it decided? | B, A, C, D |
| Where do I look? (orientation) | C, A, B, D |
| What did the organisation state? | D, A, B, C |

Wiki pages help you *find* evidence; they do not override primary sources.

### 4.3 Turning "still true?" into a check
Record, for every item: path, content hash, modified time, tier and, for repositories, the commit. Then a checker recomputes and compares.
```
fresh    exit 0   recorded state matches what is on disk
stale    exit 2   covered files changed or were deleted since the build
invalid  exit 3   state missing or unreadable   (never treated as fresh)
```
Two design rules worth copying: missing or invalid state is never "fresh", and the tool warns and continues from source instead of blocking the work (fail-open for convenience, fail-loud for truth).

### 4.4 Provenance and supersede
Each claim carries a source line and a date. When a decision changes, keep the old entry, mark it replaced and point to the new one. A reader (or a checker) can then tell "was true" from "is true".

## 5. Why it was built this way (decisions and trade-offs)

| Decision | Alternatives | Why this one | Cost / risk |
|---|---|---|---|
| Authority tiers with per-question precedence | One global ranking | A meeting note beats a summary for "why", current code beats both for "what now" | Policy to maintain |
| Catalogue is a disposable, deterministic inventory | Hand-maintained index | Rebuilt from sources; identical input gives identical output | Stale until rebuilt |
| Generated state file as the only source of numbers | Counts in prose | One place to be wrong, and it is checkable | Every reader must read the state |
| Fail-open with a warning | Block work when stale | Agents keep working; the user is told | Warnings can be ignored |
| Wiki writes gated by explicit approval | Auto-apply | Human catches silent errors | Slower updates |

## 6. Theory behind it (the "lecture" part)

### 6.1 Single source of truth
Every fact should have one canonical home; everything else is a derived copy that can be regenerated. Derived copies rot; canonical sources are edited.
*In this course:* source files canonical, catalogue and graphs derived, wiki as curated synthesis with source lines.

### 6.2 Content addressing
A hash of a file's bytes identifies its exact content. If the hash changes, the content changed, whatever the timestamp says.
*In this course:* the catalogue stores a SHA-256 per file; a stale hash is a visible failure.

### 6.3 Bi-temporal data
Two time axes: valid time (true in the world from-to) and transaction time (recorded in the system from-to). Corrections add a new record with a later transaction time instead of editing the old one.
*In this course:* "supersede, do not overwrite" is the human-sized version of this idea; temporal graph memories automate it. (From my memory of the bi-temporal literature; not confirmed on the paper's abstract page.)

### 6.4 Fail-open vs fail-closed
Fail-open lets work continue when a check cannot run; fail-closed stops it. Use fail-closed where a wrong answer is costly (gates, publishing), fail-open for advisory context.
*In this course:* the graph hook is fail-open; the portfolio publish script is fail-closed on errors.

### 6.5 Citations are not proof
A link next to an answer shows where the model looked, not that the source supports the claim. Verify the anchor or hash exists and that the quoted passage entails the statement.
*In this course:* my plan includes validating the cited anchor before an answer is produced.

## 8. Glossary

| Term | One-line definition |
|---|---|
| Knowledge rot | A knowledge store becoming wrong as sources change |
| Authority tier | A rank for how much to trust a kind of source |
| Provenance | Where a claim came from, with date |
| Content hash | A fingerprint of a file's exact bytes |
| Drift check | Comparing recorded state with what is now on disk |
| Fail-open | If the check cannot run, continue and warn |
| Supersede | Mark an older statement as replaced, keep it visible |
| Valid time | When a fact was true in the world |
| Record time | When the system learned the fact |
| Lint | Routine checks for structural and content problems |
| Disposable index | Derived data that can always be rebuilt from the sources |

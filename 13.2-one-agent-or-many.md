# Course 13 · Chapter 13.2: One agent or many? When a team of agents pays off

_Andrey Popov's project notes: how it works, why it was built this way, and the theory behind it._

**In short:** When a team of agents beats one agent: parallel work, clean contexts, specialists, against 4x to 15x token cost, lost context and conflicts. Anthropic research system numbers, the counter-argument, and a decision rule.

## 2. The problem (business view, plain English)

"Multi-agent" sounds impressive, so teams build a planner agent, a researcher agent, a writer agent and a critic agent for jobs one agent could do. The result is often slower, several times more expensive, and harder to debug, because now you have to find which agent made the bad decision and what the others were told. The opposite mistake also happens: one agent drowning in a huge task that splits naturally into ten independent pieces.

Analogy: a project with one consultant vs a team of five. The team is faster **if** the work splits cleanly (each person researches one country). It is slower and messier **if** the work is one tightly connected thing (five people co-writing one paragraph).

## 4. How it works

### 4.1 What a team buys you
| Benefit | Plain meaning | Example |
|---|---|---|
| **Parallel work** | Several helpers work at the same time | 5 helpers each research one competitor |
| **Clean memory per job** | Each helper's context holds only its own job | The coder isn't distracted by 40 research pages |
| **Specialists** | Different instructions, tools and even models per role | A cheap fast model for search, a strong model for the final synthesis |
| **More total "thinking"** | More tokens spent on the problem overall | Each helper explores deeper than one agent could |
| **Separation of duties** | The checker is not the author | A verifier that cannot edit code (13.7, 13.10) |

### 4.2 What a team costs
| Cost | Plain meaning |
|---|---|
| **Tokens** | Anthropic reports agents use about **4×** the tokens of a chat, and multi-agent systems about **15×** |
| **Lost context** | Each helper sees only what it was told. Missing details → wrong assumptions |
| **Conflicting decisions** | Two helpers make different style or design choices that don't fit together |
| **Harder debugging** | A bad result can come from any agent, or from the hand-over between them |
| **Coordination overhead** | Someone (an agent or code) must split, assign, wait, merge and check |

### 4.3 The Anthropic research system: the reference case
```
             Lead agent (strong model)
             - reads the question, writes a plan, saves it to memory
             - decides how many helpers and what each one searches
        ┌──────────┼──────────┐
   helper 1    helper 2    helper 3      (cheaper model, each its own clean context,
   searches    searches    searches       searching in parallel; helpers never talk to each other)
        └──────────┼──────────┘
             Lead agent merges the findings → citation step → answer
```
Reported results:
- Lead on Claude Opus 4 + helpers on Sonnet 4 beat a single Opus 4 agent by **90.2%** on their internal research evaluation.
- On the BrowseComp benchmark, **token usage alone explained about 80%** of the difference in quality (three factors together explained about 95%). Put simply: the team won mainly because it **spent more tokens** on the problem, spread across clean contexts.
- It suits **breadth-first** tasks (many independent searches). Anthropic says it fits less well for tightly connected work such as most coding.

### 4.4 The counter-argument: "don't build multi-agents"
The Cognition (Devin) post argues:
1. **Share full context**, not just the message: helpers need the reasoning behind the task, not one line.
2. **Actions carry hidden decisions**: if two helpers each build half a game, one draws a cartoon bird and the other a realistic background. Neither was wrong; they just couldn't see each other's choices.

Their conclusion: for tightly connected work, one agent with good context management beats a team. Both posts agree once you read them together: **a team works when the parts are independent; one agent works when the parts depend on each other.**

### 4.5 The decision rule
```
 Does the work split into parts that don't need to see each other's choices?
     no  ──► one agent (maybe with a plan and files, 13.1)
     yes ──► Is the task worth ~4–15× the tokens? (value, deadline, quality bar)
               no  ──► one agent, or a fixed workflow
               yes ──► a team: lead + helpers, clear hand-over format (13.4), caps (13.10)
```
Extra reasons for a team even when the work is connected: **separation of duties** (author vs checker) and **least privilege** (the agent with deploy rights is not the one reading untrusted web pages).

## 5. Why it was built this way (decisions and trade-offs)

| Decision | Alternatives | Why this one | Cost / risk |
|---|---|---|---|
| Lead + parallel helpers for research | One agent searching serially | Faster; clean context per search thread; more total exploration | ~15× tokens vs chat; lead can misjudge how many helpers |
| Helpers don't talk to each other | Helpers chat freely | Simpler; no loops; the lead keeps one view | Duplicate work if instructions overlap |
| Cheaper model for helpers, strong model for lead | Same model everywhere | Cost; the hard thinking is the plan and the merge | Weak helpers can miss things |
| One agent for coding tasks | A team of coding agents | Code parts depend on each other; hidden decisions conflict | Long single context; needs good context management |

## 6. Theory behind it (the "lecture" part)

### 6.1 Divide and conquer, and its limit
Splitting a problem helps when the pieces are **independent** and merging is cheap. When pieces depend on each other, the cost of communicating between them grows fast and can exceed the benefit. This is the same idea as Amdahl's law in computing: the parts that can't run in parallel limit the speed-up.
*In this course:* research splits well; writing one coherent program usually doesn't.

### 6.2 Test-time compute
Spending more computation at answer time (more tokens of reasoning, more searches, more attempts) improves results on hard tasks. Multi-agent systems are one way to spend more, because each helper adds its own context window.
*In this course:* the 80% "token usage" finding is test-time compute in action.

### 6.3 Communication cost in teams
With *n* agents that can all talk to each other there are *n(n−1)/2* possible channels. Five agents = 10 channels. That is why most production designs use a **hub** (one lead) rather than everyone-talks-to-everyone.
*In this course:* 13.3's patterns are mostly hub shapes.

### 6.4 Separation of duties
An old control principle from finance and audit: the person who makes a payment is not the one who approves it. In agents: the agent that writes the code is not the one that passes it.
*In this course:* the Verify agent in 13.7 cannot edit code.

## 8. Glossary

| Term | One-line definition |
|---|---|
| Multi-agent system | Several agents, each with its own instructions and context, working on one goal |
| Orchestrator / lead agent | The agent that splits work, assigns it and merges results |
| Worker / helper agent | An agent that does one assigned part and reports back |
| Breadth-first task | Many independent sub-searches or sub-jobs (good for teams) |
| Tightly coupled task | Parts depend on each other's choices (usually better for one agent) |
| Test-time compute | Extra computation spent while answering, to improve quality |
| Separation of duties | The doer and the checker are different parties |
| Token multiplier | How many times more tokens a design uses than a single chat |

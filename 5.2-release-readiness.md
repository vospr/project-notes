# Course 5 · Chapter 5.2: Release readiness: go/no-go, kill switch, tenant isolation tests, encryption gate, smoke tests

_Andrey Popov's project notes: how it works, why it was built this way, and the theory behind it._

## 2. The problem (business view, plain English)

The rebuilt assistant stores personal coaching conversations for employees of several client organisations, and it sends messages on timers (weekly nudges by e-mail and Slack). Before the first internal milestone, the team needed answers to four questions. Can we switch the AI or the messages off in minutes if something goes wrong? Can one organisation ever see another's data? Is every column that holds personal text protected, and will it stay so as the team adds columns? After each deploy, do we know the app, the database key and the timers really work?

Finance analogy: month-end close. Before the books are released you need a sign-off checklist (go/no-go), a circuit breaker on payments (kill switch), proof that client money is held in segregated accounts (tenant isolation), a register in which every asset is either capitalised or expensed with a written reason (encryption census), and a post-close tie-out that the sub-ledgers still reconcile (smoke tests).

## 4. How it works (technical walkthrough)

```
 PR opened ──► unit + integration tests (required) ─┬─ isolation suite (ISO)
               + silent-revert guard (5.3)          └─ encryption-coverage gate (COVT)
 merge to main ─► build images ─► [warn: kill-switch flag set?] ─► deploy QA (new revision)
                                                                     │
                                  smoke job "Smoke Tests" (required) ◄┘
                                   1 wait for 200 on /       2 /api/health: the database-connection flag, the encryption-canary flag, the org-decryption flag
                                   3 Slack container /health 4 timer liveness (insert due dispatch, wait ≤90 s)
 break-glass:  az containerapp update --set-env-vars KILL_SWITCH=true  → new revision
```

**Kill switch.** Two flags. Generation: guard at the top of the model-client factory, the single chokepoint for every Claude call (chat, background Haiku, memory synthesis, report narrative). Notifications: early return in the exported dispatcher and sweep functions (not only in the timer wrapper, so tests and manual calls obey it too). Semantics: unset or empty = runs (fail-open); `true` = off; `false` = explicit on; anything else throws. The flag is read on each call, never cached, and the guard runs **before** the cached client is returned, so flipping it works for an already-warm worker. The test override client bypasses it by design (recorded in the commit's test list: "override bypasses kill"). A typo such as `True` therefore fails closed for that call (error), while an absent flag fails open.

**Visibility check.** Before each QA/UAT deploy, a step queries the live app's `api` container (selected by name, not by index; index 0 is the frontend with no env block, *B1494*) and writes a summary warning if either flag is `true`. Reason: the new revision will drop it.

**Isolation suite.** One user holds participants in two orgs. Block 1 drives the create-session handler with a memory, journey-step, assessment or artifact id owned by the other org and expects 404 `NOT_FOUND` and no orphan session row. Blocks 2–4 run the weekly-nudge sweep and dispatcher against both orgs with a random sentinel per org, then decrypt the stored snapshots and assert the foreign sentinel is absent **and the own sentinel is present**. The "present" assertion is the false-negative guard: without it an empty result would pass. The LLM is mocked to throw so the nudge uses its deterministic fallback copy. Block 6 is a thin always-on subset.

**Encryption gate.** Census = every column of every Drizzle table whose SQL type is not a known non-string type (integers, booleans, uuid, timestamps, ...). Test 1: every census column is classified. Further tests: no orphan entries, no column both ways, no blank reasons, a census-closure test that proves the detector can fail, and anchor columns so a broken type matcher cannot make the census empty and pass.

**Smoke tests.** Health must report the database-connection flag, the encryption-canary flag (an encrypted canary row decrypts with the live key, so key drift is caught) and the org-decryption flag (a real org name decrypts). Timer liveness inserts a due notification instance (already cancelled) and a due dispatch for a real participant via `psql`, then waits up to 90 s for the real notification dispatcher timer to mark it suppressed with reason the cancelled-instance code; a cleanup trap deletes the rows. This was written because all four timers had been silently dead until 2026-06-12 (5.1, *B1427*).

## 5. Why it was built this way (decisions and trade-offs)

| Decision | Alternatives considered | Why this one | Cost / risk |
|---|---|---|---|
| Kill switch as environment flags at one chokepoint | Remove the timer and redeploy (the old plan, *the architecture document:712*); a database flag; a feature-flag service | No new infrastructure; works with the existing error handling and needs no frontend change (commit body) | Needs platform access; new revision; volatile across deploys |
| Two independent flags | One global flag | Kill sends without killing chat, or the reverse | Two things to remember |
| Fail-open default, strict parse | Fail-closed default | A missing variable must not take the product down; a typo must not silently mis-route | A typo breaks the call it guards |
| Isolation tests at real seams with sentinels | Mock the repository; test every endpoint | A real DB graph with two orgs finds real leaks; sentinels make a leak visible in decrypted blobs | Seams only |
| Gate on classification, not on write path | Runtime assertion in the repository layer | Pure reflection, no DB, runs in the required PR check, forces a human decision per column | Cannot prove encryption happened |
| Plaintext allowed with a written reason | Encrypt everything | Hashes, enums and ids must stay queryable in SQL; audit tables must be readable | 179 reasons to keep honest |
| Post-deploy smoke as a required check on QA/UAT | Pre-deploy gate with traffic shifting | No production pipeline yet; shipped as detectors first | Detects only, no rollback |
| Timer liveness through the real timer | Call the dispatcher function directly | Direct calls already existed in tests; the gap was "does the timer host start" | Writes fixture rows to the shared QA DB |

## 6. Theory behind it (the "lecture" part)

### 6.1 Release readiness and go/no-go
A *go/no-go* decision compares evidence against pre-agreed exit criteria. A useful checklist has four parts: scope (what is being released and to whom), controls (what limits damage: kill switch, rollback, monitoring), evidence (tests, smoke results, open defects with owners) and a named decider. Risk is usually ranked as probability × impact; high-impact, low-probability items (cross-tenant leak) get preventive controls, high-probability items get detection. A *pilot* limits impact by limiting audience, which is a control in itself.
*In my project:* the milestone was an internal pilot; my controls target the high-impact failures (data leak, runaway AI cost or messages, unnoticed key drift, dead timers).

### 6.2 Feature flags and kill switches
Fowler distinguishes release toggles (short-lived), experiment toggles, permission toggles and **ops toggles** (long-lived, flipped by operators). A kill switch is an ops toggle. Design questions: who flips it, how fast it takes effect, what the default is when unset (fail-open or fail-closed), whether it survives redeploys (is it in version-controlled config or only in the running system, "configuration drift"), and whether it has been exercised (an untested switch is a hypothesis).
*In my project:* env-var ops toggle, fail-open, volatile across deploys, with a visibility warning to reduce drift.

### 6.3 Multi-tenancy and isolation testing
Three classic data models: *silo* (database per tenant), *bridge* (schema per tenant) and *pool* (shared tables with a tenant key). Pool is cheapest and needs enforcement in code (every query filtered) or in the database (row-level security). The typical bug is *broken object-level authorisation* (BOLA / IDOR): the caller supplies an id that belongs to someone else and the server forgets to check ownership. Testing it needs two tenants with realistic data, **canary values** unique per tenant, a negative assertion (foreign canary absent) and a positive control (own canary present), otherwise a test that finds nothing proves nothing.
*In my project:* pool model with app-level checks; the suite attacks the context-reference guard (a BOLA seam) and the nudge pipeline with per-org sentinels.

### 6.4 Encryption at rest, blind indexes and coverage gates
Application-level encryption protects values even from someone with database access, but ciphertext cannot be searched. The standard answer is a *blind index*: store a keyed or plain hash next to the ciphertext and query by hash. Operationally you need key management and a way to detect *key drift* (an environment running with the wrong key). A *coverage gate* is a different thing from encryption: it enforces that every item in a population has been consciously classified. Soundness (the property really holds) and completeness (nothing is unclassified) are separate claims; a census proves completeness of classification only.
*In my project:* hash columns for lookups, an encrypted canary row in the health check for key drift, and a CI census that fails on any unclassified text column.

### 6.5 Health checks, smoke tests and synthetic probes
*Liveness* says the process is up; *readiness* says it can serve; a *deep health check* exercises dependencies (database, key). A *smoke test* is a small set of end-to-end checks after a deploy; a *synthetic transaction* is a scripted user-like action. Background jobs need a *heartbeat* check (dead-man's switch): prove that a timer fires, not just that the web endpoint answers. After a deploy, poll for the expected **version** before judging, or you may test the outgoing revision (the staging and prod gates do this). Without automated rollback, a smoke test is a detector.
*In my project:* deep health with canary and org decrypt, plus a heartbeat probe for the dispatcher timer.

### 6.6 Fail-open versus fail-closed (recap of 1.4)
When a control cannot evaluate, fail-open keeps the service up and fail-closed blocks. For a *kill switch* the default (unset) is open, because the normal state is "running". For a *security check* the default is closed.
*In my project:* unset kill-switch flag runs; an invalid value throws; the encryption census treats unknown column types as string-bearing.

## 8. Glossary

| Term | One-line definition |
|---|---|
| Go/no-go | Release decision against agreed criteria, with a named decider |
| Kill switch | Operator-flipped flag that disables a risky feature without a code change |
| Ops toggle | Long-lived flag controlled by operations, not by developers |
| Fail-open / fail-closed | Behaviour when the control cannot be evaluated: allow / block |
| Break-glass | Emergency procedure outside the normal pipeline |
| Revision | Immutable snapshot of a Container App's template; env change creates a new one |
| Tenant / org | A client organisation whose data must be isolated from others |
| BOLA / IDOR | Using someone else's object id because the server does not check ownership |
| Sentinel (canary value) | Unique marker planted in one tenant's data to detect leaks |
| False-negative guard | Positive control proving a "nothing found" test could have found something |
| Census | Complete enumeration of a population (here: all text columns) |
| Blind index | Hash stored beside ciphertext to allow equality lookup |
| Key drift | An environment using a different encryption key than the data was written with |
| Canary row | Known encrypted value that must decrypt, used to detect key drift |
| Smoke test | Small post-deploy check that the system basically works |
| Heartbeat / dead-man's switch | Check that a periodic job actually ran |

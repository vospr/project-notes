# Course 11 · Chapter 11.1: The design contract and the map of the repo

_Andrey Popov's project notes: how it works, why it was built this way, and the theory behind it._

**In short:** What an agent harness is and how flutter_agent_harness (an open-source Dart harness, studied not built by Andrey) is laid out: pure-Dart core, ExecutionEnv portability boundary, errors-as-events, six design rules, ports from pi-mono and oh-my-pi, seven hosts.

## 2. The problem (business view, plain English)

A language model on its own only turns text into text. To work as a coding assistant it needs a surrounding program that sends the conversation to a provider, streams the answer, runs the tools the model asks for (read a file, run a shell command), feeds the results back, remembers the session, trims the history when it gets too long, and asks the human before anything dangerous. That surrounding program is the **harness**. Without one, every product re-writes the same fragile glue, and each rewrite finds the same bugs again: a dropped connection kills the run, a corrupted history causes permanent API errors, a runaway tool call burns money.

`flutter_agent_harness` (short name `fa`) is a harness written in Dart. Its stated goal is one core that runs on the Dart VM, in Flutter apps on desktop and phone, and in the web browser, plus a terminal coding agent built on top (*README* intro; *GOAL* "Objective"). It is the successor of an older assistant stack built on another Dart agent library (*GOAL* "Downstream consumer").

Finance analogy: the model is the trader, the harness is the whole middle and back office: order routing, limits, confirmations, books and records, and the kill switch. Nobody praises the back office when it works; everybody notices when it does not.

### 4.2 The six rules of the core (*README* "Design contract"; *GOAL* "Architecture contract")
1. **Pure Dart core.** No `dart:io` and no Flutter imports in `lib/`. Platform abilities sit behind abstractions; the IO implementation is a separate entry point `lib/io.dart`, so the core compiles for the web (*AGENTS* "Hard architecture rules").
2. **Errors-as-events.** A provider never throws. Network failures, 429, malformed SSE all arrive as an `error` event with a stop reason. The loop never dies on a dropped connection.
3. **Streaming-first, partial-first.** `Stream<AgentEvent>` everywhere; each delta event carries the live partial message.
4. **Native tool calling** per provider (OpenAI `tools`, Anthropic `tool_use`, Google `functionCalling`). Prompt-based tool calling exists only as an opt-in adapter for chat-only runtimes such as an on-device model.
5. **Token accounting inline**, overflow detection per provider, and context management by **tokens**, never by message count.
6. **Cancellation everywhere** through one `CancelToken`: providers, loop and tools.

### 4.3 The three small building blocks that show the style
- **`EventStream<T, R>`**: a `Stream<T>` that also has a `result` future. Producers `push` events; the stream completes when a "done" or "error" event is pushed, and `result` resolves with the final message. One deliberate divergence from the original: if the stream ends without a completion event, `result` completes with a `StateError`, because a future that never completes is worse than an error (*ES* lines 20-25, 56-63).
- **`CancelToken` / `CancelTokenSource`**: the source cancels, the token is handed around. Listeners run in microtasks. Same split as .NET and Dart's own cancellation proposals: only the owner can cancel, everyone can observe.
- **`ExecutionEnv`**: `FileSystem` and `Shell` as abstract interfaces plus a `Result` type, so file operations return failures as values. The default IO version lives in `lib/io.dart`; a browser version can sit on browser storage.

### 4.4 Sealed types for the wire
`StopReason` is an enum with five values: `stop`, `length`, `toolUse`, `error`, `aborted` (*TY* line 19). Content blocks (`TextContent`, `ThinkingContent`, `ToolCall`, `ImageContent`) and stream events (`StartEvent`, `TextDeltaEvent`, `ToolCallEndEvent`, `DoneEvent`, `ErrorEvent`, and so on, *TY* lines 296-861) are `sealed` classes. In Dart, a `switch` over a sealed type must be exhaustive, so adding a new event type breaks every consumer at compile time instead of at 3 a.m. (*ES* lines 120-126 uses exactly this switch).

### 4.6 Seven hosts, one core
The same core is wired into seven hosts: `cli`, `macos`, `ios`, `android`, `web`, `extension` (browser), `outlook` (add-in). A **capability profile** per host says for each capability whether it is `on`, `off(reason)` or `transport(choice, reason)`; a profile can only narrow what the platform allows, and violations throw at build time (*HCP* lines 1-28; *AGENTS* "Cross-platform parity"). Chapter 11.6 covers it.

## 5. Why it was built this way (decisions and trade-offs)

| Decision | Alternatives considered | Why this one | Cost / risk |
|---|---|---|---|
| Port pi-mono's architecture "mechanically close" | Design from scratch; copy a Python framework | Future upstream fixes port easily (*ES* lines 1-9, *TY* lines 1-14) | The Dart code inherits upstream's shape, including its warts; upstream bug-for-bug parity is a moving target |
| Pure-Dart core, IO behind `ExecutionEnv` | Use `dart:io` freely; separate web fork | One core for VM, Flutter and web | Every file or process feature needs an interface and a fake; more code |
| Errors as events, never thrown | Exceptions from providers | The loop stays simple and survives network trouble (*GOAL* "Invariant to preserve") | Every adapter must catch everything; a bug that throws breaks the contract |
| `sealed` event and block hierarchies | Free-form maps; open class trees | Exhaustive `switch` at compile time | Adding a new event kind touches many files |
| Token-based context management | Count messages | Messages differ in size by orders of magnitude | Needs an estimator (4 chars per token) and trusts provider usage numbers when present (chapter 11.4) |
| One OpenAI-compatible adapter, reused via `baseUrl` | One adapter per vendor | Covers OpenRouter, DeepSeek, Kimi, Grok and others (*README* "Providers"; *GOAL* agenix section) | Vendor quirks pile up inside one adapter |

## 6. Theory behind it (the "lecture" part)

### 6.1 What an agent harness is
An **agent** in the LLM sense is a loop: call the model; if it asks for tools, run them and append the results; call again; stop when the model answers without tool calls. This is the ReAct pattern (reason and act, Yao et al., 2022). A **harness** is everything around that loop that makes it dependable: provider adapters, retries, context management, persistence, permissions, observability. A **framework** (LangGraph, for example) usually gives you a way to compose steps; a harness gives you one opinionated runtime. Benchmarks such as Terminal-Bench measure the model and the harness together, which is why harness engineering matters (chapter 11.7).

*In my project:* Course 7 (LangGraph concierge) is the framework view of the same idea; Course 11 is the runtime view.

### 6.2 Ports and adapters, again
Hexagonal architecture (Cockburn) puts the domain in the middle and talks to the world through **ports** (interfaces) implemented by **adapters**. The dependency rule says the core never imports an adapter. Here the core is the agent logic, the port is `ExecutionEnv` (and `StreamFunction` for providers), and the adapters are `lib/io.dart`, the browser storage, and each provider. The compile-time proof is the web build: if the core touched `dart:io`, the web compiler would refuse it.

*In my project:* Course 2.1 (Verdaca) uses the same pattern with import-linter as the enforcement; here the Dart compiler is part of the enforcement.

### 6.3 Errors as values
There are two ways to report failure: throw, or return a value that carries the failure. Throwing is invisible in the signature and travels up the stack unpredictably. Returning a result type (`Result`, `Either`) makes the caller handle it. This repo uses both on purpose: values for expected failures (a provider error becomes an event; a file operation returns `Result`), exceptions for programmer or configuration errors (a sealed exception hierarchy with `cause`, taken from agenix, *GOAL*).

*In my project:* the "providers never throw" rule is why the agent loop has no `try`/`catch` around the stream; the cost of a violation is a dead run.

### 6.4 Sealed types and exhaustiveness
A sealed type is a closed set of subtypes known at compile time. A `switch` over it must cover every subtype or it will not compile. This is the algebraic data type of functional languages. It turns "I forgot a case" from a runtime bug into a build error. The price is that extending the set is a breaking change for consumers, which is why the repo's wire protocol has an explicit "unknown event degrades to passthrough" rule (chapter 11.6).

*In my project:* the event families `AssistantMessageEvent` and `AgentEvent` are sealed and live in core libraries that outer layers cannot extend, which is why some notices travel through listener callbacks instead (*fallback_stream.dart* header, chapter 11.2).

### 6.5 Cancellation as a first-class concept
Long-running async work needs a way to stop. Without it you leak connections, processes and money. A cancellation token passes the "stop" signal down into every layer that can stop: the HTTP request, the stream reader, the tool process. The key design choice is that cancellation is **cooperative**: the callee must check or listen. That is why the contract says "everywhere".

*In my project:* the loop also checks the token before each provider call and produces a synthetic aborted message instead of trusting the provider to report it (*agent_loop.dart* header).

## 8. Glossary

| Term | One-line definition |
|---|---|
| Harness | The runtime around an LLM that handles providers, loop, tools, sessions, safety |
| `fa` / `fah` | The terminal coding agent built on the library (`bin/fah.dart`) |

| Port / adapter | Interface the core needs / concrete implementation of it |
| `ExecutionEnv` | Abstract file system and shell; the portability boundary |
| `CancelToken` | Cooperative cancel signal passed through providers, loop and tools |
| `EventStream` | A `Stream` with an awaitable final result |
| Sealed class | A closed class hierarchy; `switch` over it must be exhaustive |
| Host | A program that embeds the core: CLI, macOS app, web page, add-in |

| Pub.dev | Dart's package registry; the package is published there automatically |

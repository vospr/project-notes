## 2. The problem (business view, plain English)

Without measurement, retrieval changes are opinions. Someone adds embeddings and the demo feels better; two weeks later an exact ticket number no longer matches. A benchmark is a set of real questions with known right sources that you rerun after every change, so you can see what got better and what broke, and so you can decide whether a new component earns its upkeep.

Analogy: a driving test with the same route every time. You change the car's tyres and run the route again.

## 4. How it works

### 4.1 Retrieval metrics (need a labelled question set)
| Metric | Question it answers | Tiny example |
|---|---|---|
| **Recall@k** | Is the right source anywhere in the top k? | Right page at rank 3, k=5 -> 1; at rank 8 -> 0 |
| **Precision@k** | How much of the top k is relevant? | 2 of 5 relevant -> 0.4 |
| **MRR** | How high is the first right result? | Rank 1 -> 1.0; rank 4 -> 0.25; average over questions |
| **nDCG** | Ranking quality when some sources are more relevant than others (graded 0 to 3) | Penalises putting the best source low |

```python
def recall_at_k(ranked, gold, k=5):  return int(any(d in gold for d in ranked[:k]))
def mrr(ranked, gold):
    for i, d in enumerate(ranked, 1):
        if d in gold: return 1 / i
    return 0.0
```

### 4.2 Answer metrics (usually judged by a model)
RAGAS-style frameworks split context metrics (context precision, context recall) from response metrics (faithfulness: is the answer supported by the retrieved context?). Most response metrics use a language model as judge, which needs less labelling and adds noise. One source suggests labelling 200 to 300 question-passage pairs to validate the judge.

### 4.3 Read the pattern
| Symptom | Points to |
|---|---|
| Recall@k low | Retrieval misses (wording, chunking, index) |
| Recall fine, MRR / nDCG low | Ranking (reranker candidate) |
| Retrieval fine, faithfulness low | Generation / grounding problem |
| Good scores, wrong or old answers | Freshness and authority (14.6), which these metrics ignore |

### 4.4 My benchmark design (not yet run)
**Decision it supports:** is the curated-lexical approach enough, or do we need a full-text index, dense retrieval, a reranker, or documentary GraphRAG?

Hypotheses (each with a falsifying result): exact lexical retrieval stays best for identifiers; source routing saves more than embeddings; dense helps mainly paraphrase-heavy prose; code graphs stay separate from document retrieval; multi-hop demand is too small to justify GraphRAG.

**44 questions**, built from real tickets, meeting corrections and past wrong-source cases:
| Category | Count |
|---|---:|
| Exact identifiers and symbols | 8 |
| Paraphrase and terminology variation | 8 |
| Temporal and authority conflicts | 8 |
| Cross-source and multi-hop | 8 |
| Code structure and graph navigation | 6 |
| Negative, unanswerable, adversarial | 6 |

**Split:** 24 development, 20 holdout, sealed before any tuning of weights, chunking, synonyms or prompts.

**Three tracks:**
```
A  retrieval only      A0 index+grep -> A1 routed grep -> A2 full-text -> A3 dense -> A4 fused -> A5 +reranker
B  code navigation     B0 graph reports injected -> B1 routed one graph + traversal -> B2 source-only (baseline)
C  end-to-end agent    C0 current -> C1 router -> C2 router + best retrieval; 3 runs per question, median
```
**Gold record:** one JSON line per question with id, split, category, query, expected route, and gold sources (path, anchor, relevance 0 to 3, authority, as-of date).

### 4.5 Retention gates (a component stays only if)
- paraphrase and cross-language Recall@5 improves at least 10 percentage points over the best lexical baseline
- exact-query Recall@5 drops by no more than 2 points
- stale or unauthorised source hits stay at zero
- p95 retrieval latency stays within the interactive budget
- a reranker: MRR@10 improves at least 10% relative when the right source is already a candidate
These thresholds are my proposed defaults.

## 5. Why it was built this way (decisions and trade-offs)

| Decision | Alternatives | Why this one | Cost / risk |
|---|---|---|---|
| Real questions from my own work | Synthetic questions | They reflect actual failures (wrong source chosen before) | Only 44; labelling takes time |
| Sealed holdout | Tune on all | Prevents fitting synonyms and weights to the test | Fewer questions to tune with |
| Score authority and staleness, not just relevance | Relevance only | A relevant but old page is a wrong answer | More labelling fields |
| Separate retrieval-only from end-to-end tracks | Only end-to-end | Isolates search quality from agent behaviour | More runs |
| Mark missing graph coverage as `coverage_missing` | Count as failures | Do not blame the graph for code it never indexed | Reports have a special bucket |
| Explicit gates for keeping components | Keep what feels good | Stops infrastructure creeping in | Gate values are judgement |

## 6. Theory behind it (the "lecture" part)

### 6.1 Offline evaluation
Evaluate on a frozen question set and frozen corpus snapshot (manifest with hashes) so results are comparable across changes.
*In this course:* every run is tied to a catalogue manifest.

### 6.2 Ground truth (gold) and relevance grades
A person marks which sources answer each question, optionally with grades (3 = authoritative, 1 = marginally useful). Disagreement between labellers is normal; review the gold set.
*In this course:* gold sources are human-reviewed before the holdout is sealed.

### 6.3 Overfitting to the test set
If you tune on the same questions you report, the score is optimistic. A holdout used once is the guard.
*In this course:* same rule as "test once" in the seismic project (4.4).

### 6.4 LLM-as-judge limits
Judges prefer fluent, longer and own-family answers, and vary run to run. Validate against human labels on a sample; use them for relative comparison, not absolute truth.
*In this course:* see 10.1.

### 6.5 Negative questions
Include unanswerable questions: the right behaviour is to say "not found", and retrieval should not return a plausible but wrong page.
*In this course:* six of my 44.

## 8. Glossary

| Term | One-line definition |
|---|---|
| Recall@k | Share of questions whose right source appears in the top k |
| Precision@k | Share of the top k that is relevant |
| MRR | Mean of 1 / rank of the first relevant result |
| nDCG | Ranking score that rewards putting highly relevant items first |
| Gold set | Questions with human-labelled right sources |
| Holdout | Questions kept sealed until final comparison |
| Faithfulness | Whether an answer is supported by the retrieved context |
| LLM judge | A model used to score answers |
| Baseline | The simplest current method everything is compared with |
| Retention gate | A threshold a component must beat to be kept |
| p95 latency | The time under which 95% of requests finish |

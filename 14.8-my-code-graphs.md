# Course 14 · Chapter 14.8: My code graphs

_Andrey Popov's project notes: how it works, why it was built this way, and the theory behind it._

**In short:** Andrey's code graphs: parser-built graphs with extracted versus inferred edges, graphify and Understand-Anything, a fail-open hook that gives the agent one relevant graph report per session, a state file for coverage and freshness, and honest stale findings.

## 2. The problem (business view, plain English)

An AI coding agent on a large codebase wastes time and tokens grepping around. "Who calls this? What are the central modules? What connects the web app to the API?" are structure questions. A graph built by a parser answers them in one query, and a short report of the most connected nodes ("god nodes") tells the agent where to start. The risk: a graph is a snapshot. If it is old, covers only part of the repo, or its numbers are copied into prose, the agent gets a confident, wrong map.

Analogy: a street map printed in June. Excellent for finding the main roads, dangerous if a bridge closed in September and nobody told you.

## 4. How it works

### 4.1 What a code graph is
A parser reads source code and emits nodes (files, classes, functions) and edges (imports, calls, contains). No language model is needed for this part, so it is repeatable and free of model cost. A clustering step groups nodes into communities, and a report lists the most connected nodes (god nodes) and surprising cross-community links.

```
source files --(tree-sitter parser)--> nodes + edges --(clustering)--> communities
                                              |
                                  graph.json  +  GRAPH_REPORT.md  (+ graph.html viewer)
```

### 4.2 graphify
- Parses code locally with tree-sitter across about 40 languages; no embeddings or vector store.
- Documents, PDFs and images go through a model-based semantic pass; code-only runs need no model key.
- Every edge is tagged `EXTRACTED` (explicit in source) or `INFERRED` (resolved by the tool, with a confidence). In my three graphs about 96 to 98% of edges are extracted.
- Query by command: `graphify query`, `graphify path A B`, `graphify explain X`.

### 4.3 Understand-Anything
A plugin that runs a team of analysis steps over a repository and writes one JSON graph plus a dashboard. It adds model-written summaries per node, grouped "layers" and a guided tour. Output goes to a cache directory; my notes say the cache is kept outside the clone and linked in with a directory junction so the clone stays clean. It produces a different graph of the same code (narrower scope, different clustering, enriched with summaries), so the two are not interchangeable.

### 4.4 The hook: give the agent a map, once
```
before Read / Grep / Glob
   -> pick the ONE repository the target path belongs to
   -> read the generated state; if stale, add a warning
   -> inject about 4,000 characters: Summary, God Nodes, Surprising Connections
   -> remember (session + repo) so it is not injected again; markers expire after 7 days; cache capped at 2,048
   -> any error: do nothing and let the tool run (fail-open)
```
Why it was changed: the earlier version injected excerpts of all three reports before every matching call (about 5,000 characters each time), which wasted context. The current policy: one relevant graph, once per session, plus a warning to confirm material claims in current source.

### 4.5 The state file: numbers come from here
`graph-sources.json` declares, per repository: aliases, coverage root and label, report and graph paths, extraction mode (AST-only or AST-and-semantic), semantic policy, and paths to ignore when checking drift. `kb-graph-state.py build` writes `graph-state.json` with commit, counts, coverage and freshness; `check` compares again and exits 0 (fresh), 2 (stale) or 3 (invalid). The build refuses if the graph and report counts disagree, or the manifest and report corpus sizes disagree.

## 5. Why it was built this way (decisions and trade-offs)

| Decision | Alternatives | Why this one | Cost / risk |
|---|---|---|---|
| Parser (AST) graphs for code | Model-built entity graph over code | Deterministic, free, rebuildable | Syntax only; no intent |
| Keep code graphs separate from document retrieval | One combined index | Different authority and freshness; avoids mixing code with prose of lower authority | Two systems |
| Inject one graph, once per session | Inject all graphs every call | Saves context; relevant only | Selection logic to maintain |
| Fail-open hook | Block when state is bad | Work continues; user is warned | A warning can be ignored |
| Generated state as the numeric source of truth | Counts in persona files | Persona counts were already stale | Every consumer must read the state |
| Explicit coverage labels | Implicit "the graph" | Missing backend code cannot be mistaken for a complete graph | Another field to keep correct |
| Two graph tools side by side | Pick one | Compare scope, clustering and summaries | Double upkeep; a risk that neither is current |

## 6. Theory behind it (the "lecture" part)

### 6.1 Abstract syntax tree (AST)
A tree form of source code produced by a parser: it shows structure (this function contains these calls) without running the code.
*In this course:* AST edges are the extracted ones.

### 6.2 God nodes and communities
A *god node* is a node with unusually many links; in code it is often a central module or a risky dependency. A *community* is a cluster of nodes more linked to each other than to the rest.
*In this course:* the report excerpt the hook injects lists them first because they orient a newcomer fastest.

### 6.3 Snapshot vs live
A graph describes the code at one commit. It is derived data: rebuild on change, and show its commit.
*In this course:* freshness is a comparison between the graph's commit and the repository's.

### 6.4 Coverage
What the graph does and does not include. A graph is only evidence about the part it covers.
*In this course:* "WebApp-only" is a coverage statement, not a defect.

### 6.5 Structural vs semantic layer
The structural layer comes from syntax. The semantic layer adds model-read meaning for docs and images. They go stale separately: code can be fresh while docs are not re-read.
*In this course:* the JS/TS graph is AST-fresh and semantically stale at the same time.

## 8. Glossary

| Term | One-line definition |
|---|---|
| Code graph | Nodes and edges built by parsing source code |
| AST | The tree structure a parser builds from source |
| tree-sitter | A parser library used to read many languages |
| God node | A node with unusually many connections |
| Community | A cluster of nodes more linked to each other than to others |
| EXTRACTED / INFERRED | Edge labels: read directly vs guessed with a confidence |
| `GRAPH_REPORT.md` | A readable summary of the graph's key nodes and links |
| Hook | A script the agent tool runs automatically before or after an action |
| Fail-open | If the script fails, carry on without it |
| Coverage | The part of a repository the graph includes |
| Extraction mode | Whether the graph came from the parser only or parser plus model |
| Drift | Difference between the graph's snapshot and the current code |

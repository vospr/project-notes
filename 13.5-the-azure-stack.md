# Course 13 · Chapter 13.5: The Azure stack for agents, top to bottom (with Google ADK for comparison)

_Andrey Popov's project notes: how it works, why it was built this way, and the theory behind it._

**In short:** The Azure agent stack in layers: Agent Framework (Semantic Kernel and AutoGen merged), Foundry Agent Service and hosted agents, MCP for tools, A2A for agents, Entra identity, with a mapping to Google ADK.

## 2. The problem (business view, plain English)

Building a multi-agent system needs more than agents. Someone must **host** them, give them **identities and permissions**, connect their **tools**, **save their state**, **watch** them, and **control cost**. Doing this by hand for each project is slow and inconsistent. Azure offers a stack where each need has a home. For a company already on Azure and Entra (single sign-on), this is the natural base, which is why this course uses it as the main frame.

Analogy: agents are employees. The framework is the job description language, Foundry is the office building with badges and security, MCP is the toolbox, A2A is the phone line to other companies.

## 4. How it works

### 4.1 The stack in layers
```
 ┌────────────────────────────────────────────────────────────────────┐
 │ People & apps    Copilot Studio, Teams, your web app, VS Code        │
 ├────────────────────────────────────────────────────────────────────┤
 │ Agent-to-agent   A2A (13.6)        lets agents of other teams/companies be called     │
 ├────────────────────────────────────────────────────────────────────┤
 │ Orchestration    Microsoft Agent Framework: agents, workflows, the five patterns (13.3)│
 ├────────────────────────────────────────────────────────────────────┤
 │ Tools            MCP servers (Jira, Azure DevOps, Terraform, search ...), functions   │
 ├────────────────────────────────────────────────────────────────────┤
 │ Hosting & ops    Foundry Agent Service: hosted agents (containers), scaling,          │
 │                  state storage, tracing, evaluations, content safety                  │
 ├────────────────────────────────────────────────────────────────────┤
 │ Models           Foundry model catalog (OpenAI, Anthropic, Mistral, open models ...)  │
 ├────────────────────────────────────────────────────────────────────┤
 │ Identity & policy  Microsoft Entra (who the agent is), RBAC, network, governance      │
 └────────────────────────────────────────────────────────────────────┘
```

### 4.2 Microsoft Agent Framework
- An **open-source SDK and runtime** for building agents and multi-agent workflows in **Python and .NET**.
- It is the **merger of two earlier Microsoft projects**: **Semantic Kernel** (enterprise agent and plugin toolkit) and **AutoGen** (research framework for multi-agent conversations). One framework now, with the five orchestration patterns, checkpoints, human approval, middleware and memory (stable at 1.0 in 2026, per Build 2026 coverage).
- You write the agents and the workflow; the framework runs the loop, calls the model, calls tools and records the steps.

### 4.3 Foundry Agent Service
- The **hosting and operations layer**. You can:
  - run **prompt agents** (configured, no code),
  - run **workflow agents** (multi-agent flows built in a visual designer or YAML, versionable in CI/CD),
  - run **hosted agents**: your own code in a **container**, built with the framework you like. The April 2026 blog lists Agent Framework, LangGraph, Claude Agent SDK, OpenAI Agents SDK and the GitHub Copilot SDK.
- Foundry supplies scaling, state storage, identity for each agent, tracing and evaluation.
- **2026 change to remember:** the older **connected agents** feature and portal-only workflows are being retired (reported by a third-party deep dive; verify with Microsoft's migration guide). The direction is: **orchestration logic lives in Agent Framework code or YAML; Foundry hosts and operates it.**

### 4.4 Where MCP and A2A sit
| Protocol | Connects | Analogy |
|---|---|---|
| **MCP** | an agent ↔ **tools and data** | a standard power socket for appliances |
| **A2A** | an agent ↔ **another agent**, possibly in another company | a standard phone line between offices |

Foundry and Agent Framework support both (13.6 covers A2A).

### 4.5 Identity and control
Each agent gets its own identity in **Entra**, so you can give it exactly the rights it needs (least privilege, 13.10) and see in logs which agent did what. Policies, network limits, content safety filters and approval requirements are set at the platform level instead of in each prompt.

### 4.6 Azure ↔ Google ADK ↔ others
| Idea | Microsoft Agent Framework / Foundry | Google ADK | Others |
|---|---|---|---|
| A single agent with tools | `ChatAgent` / agent with tools | `LlmAgent` | OpenAI Agents SDK `Agent`; Claude Agent SDK |
| Fixed order | Sequential orchestration | `SequentialAgent` | LangGraph linear edges |
| Parallel | Concurrent orchestration | `ParallelAgent` | LangGraph fan-out |
| Loop until condition | Group chat with termination, workflow loop | `LoopAgent` | LangGraph cycles |
| Agent decides who's next | Handoff | `sub_agents` + LLM transfer | OpenAI handoffs |
| Agent used like a tool | Agent as a tool | `AgentTool` | Claude Code `Task` subagent |
| Manager that re-plans | Magentic | (build with LLM agent + tools) | Deep Research lead agent |
| Saved state | Workflow checkpoints, Foundry state | Session state + `MemoryService` | LangGraph checkpointer |
| Agent-to-agent protocol | A2A | `RemoteA2aAgent`, A2A server | A2A everywhere |
| Hosting | Foundry hosted agents | Vertex AI Agent Engine / Cloud Run | any container host |

The point: **the ideas are the same everywhere; only the names change.**

## 5. Why it was built this way (decisions and trade-offs)

| Decision | Alternatives | Why this one | Cost / risk |
|---|---|---|---|
| Azure as the base for this course | Google ADK, LangGraph + any cloud | Already used by the companies I target; Entra identity, DevOps, Terraform and the shared-agents example are Azure-shaped | Vendor tie-in; names and status change often |
| Framework and hosting separated (Agent Framework vs Foundry) | One closed product | Portable code; you can run the same code elsewhere | Two things to learn |
| Hosted agents as containers with your choice of framework | Only Microsoft's framework | Teams keep LangGraph or other code | Less "magic"; you manage the container build |
| One identity per agent | Shared service account | Auditable, least privilege | More setup |

## 6. Theory behind it (the "lecture" part)

### 6.1 Framework vs platform
A **framework** is a library you write code with (Agent Framework, ADK, LangGraph). A **platform** runs, scales and watches that code (Foundry, Vertex AI Agent Engine). Keeping them apart lets you change one without rewriting the other.
*In this course:* §4.2 vs §4.3.

### 6.2 Protocol layers
Standard protocols (MCP for tools, A2A for agents) let parts from different vendors work together, like HTTP did for the web. Without them every pair of systems needs custom glue (n×m connections instead of n+m).
*In this course:* §4.4.

### 6.3 Identity for non-human actors
Agents act on behalf of people or systems, so they need their own identities, scoped rights and logs. This is "workload identity" applied to agents.
*In this course:* §4.5; 13.10 for the controls.

### 6.4 Checkpointing and durable state
Saving the state of a run after each step lets it pause, resume, be approved by a human later and recover from crashes. It only works if state is plain, saveable data (13.8).
*In this course:* workflow checkpoints in Agent Framework; session state in ADK.

## 8. Glossary

| Term | One-line definition |
|---|---|
| Microsoft Agent Framework | Open-source SDK/runtime for agents and multi-agent workflows (Python, .NET); successor of Semantic Kernel and AutoGen |
| Semantic Kernel | Microsoft's earlier enterprise toolkit for AI plugins and agents |
| AutoGen | Microsoft Research's earlier multi-agent conversation framework |
| Foundry Agent Service | Azure service that hosts, scales and operates agents |
| Hosted agent | Your own agent code run as a container on Foundry |
| Prompt agent | An agent defined by configuration (instructions, tools, model) without custom code |
| Workflow agent | A multi-agent flow defined visually or in YAML |
| MCP | Model Context Protocol: standard way for agents to use tools and data |
| A2A | Agent2Agent protocol: standard way for agents to call other agents |
| Entra | Microsoft's identity service, used here to give agents identities |
| Google ADK | Google's Agent Development Kit, the comparison framework |
| Vertex AI Agent Engine | Google's managed hosting for agents |

## 2. The problem (business view, plain English)

A concierge chat is a series of turns. Each turn the system decides what kind of question it is, calls a specialist, checks the answer, and replies. Between turns it must remember *who the user is* and *what was said*, but it must forget *what it decided last turn*. If the "route" from turn 1 is still in the shared state at turn 2, the system answers a booking request with a destination lookup.

That is exactly what the first version did. The app also never printed the answer. So the "working multi-node concierge" on the first version of the site page was contradicted.

Finance analogy: month-end close. Balance-sheet items carry forward (a customer's profile, the conversation so far). Period items (this month's accruals, this turn's route and results) must be reversed at the start of the next period. If you forget the reversal, last month's accrual lands in this month's P&L and nobody sees it until the numbers look odd.

## 4. How it works (technical walkthrough)

```
                    ┌────────────── conditional edge on state["route"] ───────────────┐
START ─► dispatcher ┤  "rag"          ─► rag      ─┐                                  │
                    │  "research"     ─► research ─┤                                  │
                    │  "booking_stub" ─► booking  ─┼─► guardrail ─► synthesis ─┬─ route=="research" ─► followup ─► END
                    └  "fallback"/None─────────────┘                           └─ otherwise ─────────────────────► END
```

**State.** `ConciergeState` is a plain `TypedDict` with 20 required keys (`CC:state.py:8-34`). It uses no LangChain message objects and no reducer: `conversation_history` is a plain list that the dispatcher rebuilds each turn. The deviation from the spec's `add_messages` is written in a comment (`CC:state.py:12-14` vs). `StateUpdate` (`:37-65`) is the type a node returns: any subset of the keys. `TurnResetUpdate` (`:68-81`) lists exactly the turn-scoped fields.

**Nodes.** Seven functions in `NODE_FUNCTIONS` (`CC:graph/__init__.py:16-24`). Each node file is a thin wrapper around an agent class with the same `try/except` pattern (`CC:nodes/dispatcher_node.py`). A wrapper (`_track_node_execution`, `:106-119`) records the execution order in `_executed_nodes` for tests.

**Edges.** Built in `_build_langgraph_compiled` (`CC:graph/__init__.py:122-145`):
- `START → dispatcher` (static)
- `dispatcher →` one of `rag | research | booking_stub | guardrail`, chosen by `lambda s: s.get("route") or "fallback"` (conditional edge 1, `:130-134`)
- `rag / research / booking → guardrail → synthesis` (static)
- `synthesis →` `followup` if `route == "research"`, else `END` (conditional edge 2, `:139-143`)
- `followup → END`

**One turn in the CLI.** `main.py` keeps one `state` dict for the whole session (`:158-163`). Each turn it increments `turn_id`, sets `current_input`, calls `compiled_graph.invoke(state)`, replaces the dict with the result, and prints `current_response` (`CC:main.py:128-137`). The adapter deep-copies the state on the way in (`CC:graph/__init__.py:103`), so a node can't mutate the caller's dict.

**Where the per-turn reset lives.** At the start of `DispatcherAgent.run` (`CC:dispatcher.py:297-304`):

```python
update = cast(StateUpdate,
    {**reset_turn_state(state), "conversation_history": history, "current_response": None})
```

`reset_turn_state` returns 13 fields: `intent, confidence, route, rag_results, research_results, source_attribution, degradation_label, guardrail_passed, proactive_suggestion, clarification_needed, clarification_question, human_handoff, error` (`CC:dispatcher.py:20-36`). Session-scoped fields are left alone: `user_id`, `session_id`, `memory_profile`, `conversation_history` (appended, not cleared).

**The bug and the fix.** Before the fix, `run` began with: "if `state['route']` is already a non-empty string, return `{}`" (4 lines, `git show cc5d3f5`). On turn 2 the CLI passed in the turn-1 route, so the dispatcher did nothing and the reset never ran. Fix: delete those 4 lines, and print the response in `_run_loop`. Tests that had pre-set `state["route"]` to steer the graph were rewritten to use a `force_route` fixture that patches Stage 1 (`CC:tests/conftest.py:61-76`).

**How the fix is tested.**
- `tests/e2e/test_cli_three_turns.py:45-67`: drives `main.main` with three scripted lines (property question, "book me a room", "latest travel trends in thailand") and asserts on stdout that turn 2 shows the booking message and turn 3 shows the research result, in order. All three inputs are Stage-1 rule hits, so no LLM is called (`:39`). Search is faked, session write is stubbed.
- `tests/unit/test_story_3_7_*.py:25-51`: calls the real `run` with stale fields set and asserts they come back reset.
- `tests/e2e/test_e2e_scenario_3_...::TestRouteIsResetEveryTurn`: a stale `route="rag"` is overwritten by `booking_stub`.

## 5. Why it was built this way (decisions and trade-offs)

| Decision | Alternatives | Why this one | Cost / risk |
|---|---|---|---|
| LangGraph `StateGraph` | Plain Python router; Claude tool use | Job description named it | Under-used: no checkpointer, no `interrupt`, no streaming |
| `TypedDict` state, no reducers | Pydantic model; `add_messages` | Simple dicts, dispatcher owns the history list | Deviates from spec; every key is overwrite-only, so a missed reset is silent |
| Reset inside the dispatcher | Reset in `main.py` per turn; reset node before dispatcher | Spec puts it in the dispatcher ||
| Fallback executor when LangGraph is missing | Make LangGraph a hard dependency | Graph still runs without the package | Second copy of the topology to keep in sync |
| Deep-copy state on invoke | Mutate in place | Tests assert the caller's state is not mutated (the no-mutation test in `test_story_2_1_graph_init_contract.py`) | A copy per turn; trivial at this size |
| Re-route every turn (fix) | Cache the route per session | A user changes topic between turns | One more Stage-1 evaluation per turn (microseconds) |

## 6. Theory behind it (the "lecture" part)

### 6.1 State machines and dataflow graphs
A workflow can be modelled as a directed graph G = (V, E). Nodes V are steps; edges E say what runs next. **Static edges** always fire. **Conditional edges** call a routing function r(state) → label and follow the matching edge. If the graph has no cycles it is a DAG: every run terminates. With cycles (loops, retries) you need a stop rule.

An **agent** differs from a **workflow** in who picks the next step. In a workflow the developer fixes the paths (as here). In an agent the model picks the next action at run time. The first is predictable and testable; the second is flexible and harder to bound.

*In my project:* it is a workflow with two conditional edges and no cycle. Calling it "multi-agent" overstates it: only the dispatcher may call an LLM.

### 6.2 How LangGraph executes a graph
`StateGraph(State)` declares a shared state schema. `add_node(name, fn)` registers a function `fn(state) → partial update`. `compile` returns a runnable. LangGraph runs in **super-steps** (it follows the Pregel / bulk-synchronous model): in each step the active nodes read the current state and return updates, then the framework **merges** the updates into the state, then selects the next nodes from the edges.

Merging is per key. By default a new value **overwrites** the old one. A key can carry a **reducer** `(old, new) → merged`, for example `add_messages` appends to a message list. The two other production features are a **checkpointer** (saves state after each step, keyed by a thread id, so a conversation can resume) and **`interrupt`** (pauses at a node to wait for a human).

*In my project:* default overwrite on every key, no checkpointer, no interrupt. Memory, history and human hand-off are hand-rolled in `main.py` and the memory service.

### 6.3 Scopes of state: session, turn, node
A conversational system has three lifetimes:
- **Session-scoped:** identity, profile, history. Written rarely, read every turn.
- **Turn-scoped:** the decision and intermediate results of this turn. Must start from a known blank each turn.
- **Node-local:** never stored in shared state.

With overwrite-only merging, a turn-scoped key that a node does not write keeps its **old** value. The reset is the only thing that protects you. Formal property (an invariant you can test): *for any state S after turn k, the turn-scoped fields of the result of turn k+1 must not depend on S's turn-scoped fields.* In code: run turn k+1 from a polluted state and from a fresh state with the same session fields and input, and compare the turn-scoped outputs.

*In my project:* 13 reset fields, the rest session-scoped. The CLI test checks this indirectly for `route`.

### 6.4 Blackboard architecture and its failure mode
In a **blackboard** design, many components read and write one shared structure. LangGraph state is a blackboard. Benefits: loose coupling, easy to add a node. Failure modes: hidden coupling through keys, stale reads, and write conflicts. Mitigations: narrow the writes (each key has one owner), make turn-scoped keys explicit, and test the contract.

*In my project:* the dispatcher owns routing keys and history; the spec lists which keys are reset. The bug was a node (the dispatcher) not honouring its own contract.

### 6.5 Why unit tests missed a multi-turn bug
Per-turn tests that start from a fresh state can never see state that leaks *between* turns. The bug needs a test with at least two turns through the real entry point. General rule: a stateful system needs at least one test that runs the **session**, not the step. Mocks must stay below that level (fake search and model, never the loop).

*In my project:* 296 e2e tests all called `compiled_graph.invoke` on a fresh state; none ran `main.py` or a second turn. One test asserting the bug existed for the same reason.

### 6.6 Idempotence and determinism for routing nodes
A routing function should be **deterministic** (same input, same route) and, when stateless, **idempotent** (re-running it changes nothing). Stage 1 is both. Stage 2 is not deterministic: no `temperature` is set (`CC:dispatcher.py:261-266`), so the API default applies and repeat runs can differ.

*In my project:* the early-return "optimisation" made routing depend on history, which is the opposite of what a router should do.

## 8. Glossary

| Term | One-line definition |
|---|---|
| StateGraph | LangGraph builder: nodes, edges and a shared state schema, compiled into a runnable |
| Node | A function `state → partial update` |
| Edge (static / conditional) | Fixed next step / next step chosen by a function of the state |
| Reducer | Rule for merging a node's update into a key; default is overwrite |
| Super-step | One round: read state, run active nodes, merge updates, pick next nodes |
| Checkpointer | LangGraph component that saves state per step and thread so a run can resume |
| `interrupt` | LangGraph call that pauses a run to wait for a human |
| Turn-scoped / session-scoped | Field that must be blank each turn / field that lives for the whole conversation |
| Sticky route | The bug: a route from a previous turn is reused |
| `force_route` | Test fixture that patches Stage 1 to pick a given route |
| Fallback executor | Hand-written runner of the same flow when LangGraph is not installed |
| Blackboard | Architecture where components share one mutable structure |

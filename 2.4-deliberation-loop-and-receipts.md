# Course 2 · Chapter 2.4: The deliberation loop and receipts (producer / isolated reviewer / synthesizer, typed outcomes, content hash vs signature)

_Andrey Popov's project notes: how it works, why it was built this way, and the theory behind it._

## 2. The problem (business view, plain English)

A single AI answer comes with no record of what was challenged. Regulated teams want a four-eyes control: one party drafts, an independent party challenges, a third decides, and the file shows all three steps, the evidence, the cost, and who or what was involved. The product idea is that this record, the receipt, is the durable value.

Finance analogy: maker-checker. The maker prepares a journal entry, the checker reviews it without having seen the maker's reasoning, a controller posts it, and the posting carries a document number and a control total. A control total detects accidental change; it does not prove who prepared the entry. That is the hash-versus-signature distinction in 6.5.

## 4. How it works (technical walkthrough)

```
INTERPRET -> DECOMPOSE -> CYCLE_1_PRODUCE -> CYCLE_2_REVIEW -> CYCLE_3_VERIFY -> PUBLISH -> COMPLETE
                              ^                                     |
                              |<------ BACKTRACK_SET <--- blocking--+   (at most once)
        any call / parse / citation failure  ->  FAILED  (terminal, receipt outcome = escalate)

 call 1  producer           question + evidence (+ rejected draft and issues on retry)   Haiku
 call 2  reviewer_counter   question + evidence ONLY ("you have NOT seen any draft")      Sonnet
 call 3  reviewer_critique  question + evidence + draft + its own counterargument -> JSON Sonnet
 call 4  synthesizer        question + evidence + draft + critique -> JSON                 Haiku
```
Source: ``, state set ``, prompts ``. Model choice per role is set by environment variables; the default is Haiku for every role, and the recorded runs put the reviewer on Sonnet 5.5 (`scripts/live/deliberate_live.py`; *Review, Redo*).

**Step by step.**
1. `call` wraps every model call: times it, prices it, appends a `CallRecord`, checks the token and wall-clock budget (400,000 tokens, 900 s, `budget.py`), and converts any exception into `_RunHalt("model_call_failed", first 300 characters)` (``).
2. Producer drafts with "ONLY the numbered evidence" and `[E1]`-style citations (``).
3. Blind pass, then critique. The critique must be a JSON object `{blocking, issues, summary}`; anything else raises `ReplyInvalid` and the run fails as `reviewer_output_invalid` (``, ``).
4. If `blocking`: first time, go to `BACKTRACK_SET`, store the round in `superseded_rounds`, loop to the producer with the rejected draft and issue list; second time, fail as `second_consecutive_blocking_critique` (``).
5. Synthesizer returns `{outcome, answer, cited_evidence_ids, rationale}`. Fail-closed checks: JSON valid and `extra="forbid"` (``), `outcome` one of four, every cited ID exists, `answer` has at least one citation (``).
6. `_receipt` assembles everything, computes the diff, totals tokens and cost, lists truncated calls, and sets `content_sha256` (``).

**Typed outcomes.** `answer | clarify | abstain | escalate` (``). Failure reasons seen in code: `model_call_failed`, `budget_exceeded`, `reviewer_output_invalid`, `second_consecutive_blocking_critique`, `synthesizer_output_invalid`, `unknown_evidence_cited`, `answer_without_citation`. Each returns a partial receipt with outcome `escalate` (*AC* AC5-AC8, AC11).

**The receipt** (``): schema version (`verdaca.receipt/2`), id, time, question, evidence, draft, critique with counterargument, superseded rounds, final, diff, outcome, terminal reason and detail, backtrack count, state log, per-call records (role, model, response id, tokens, cost, status, latency, prompt hash, stop reason), truncated calls, totals, hash. Recorded run `ab32840a`: 4 calls, 4,686 / 2,789 tokens, $0.031389, state log of seven states, no backtrack.

**Hash.** `content_sha256` = SHA-256 of the receipt's JSON with sorted keys and no spaces, excluding the hash field itself (``). `verify_receipt_json(text)` re-hashes the file as written, so schema /1 files still verify. There is no key anywhere in this code. The docstring says it directly: "it is NOT a signature and proves nothing about who produced the receipt" (``). The site says "hashed with SHA-256 (not signed)".

**The older controller.** `MetaAgentController.deliberate` is a scripted scenario with hard-coded gate scores (12 gates at 4, no output); docstring: "smoke-level" (`controller.py:1-20`; *Review §3*). Only `run_deliberation` is model-backed. The quality-gate engine and 12 gates are not part of the live path.

## 5. Why it was built this way (decision table)

| Decision | Alternatives | Why this one | Cost / risk |
|---|---|---|---|
| Reuse the existing 9-state machine | New simple loop | Transitions are checked in one place (``); existing property tests | State names ("verify") promise more than the code does |
| Reviewer writes a counterargument before seeing the draft | Reviewer sees the draft first | Avoids anchoring on the draft (independent first opinion) | Same model critiques against its own text |
| One backtrack, then fail | Loop until clean | Bounded cost and time (arch §5.5) | A second blocking critique ends in escalate, not a better answer |
| Fail closed to `escalate` on every error | Return best effort | In governance an unreviewed answer is worse than none | Conflates error with decision |
| JSON validated by Pydantic, `extra="forbid"` | Provider structured-output feature | Provider-independent | A model can emit valid JSON that is wrong; truncation breaks parsing |
| Hash only, no signature | Sign with a key | No key management; solo project, no consumer | Not tamper-proof (6.5); stated honestly in docs |
| Receipt as JSON file per run | Database | Simple, diffable, committable | No query, no append-only log |
| Cheaper model for producer and synthesizer | One strong model | Cost: reviewer is about 80% of spend (2.3) | The weakest model writes the final record |

## 6. Theory behind it (the "lecture" part)

### 6.1 Maker-checker, independent review and anchoring
The four-eyes principle: the person who does a task must not be the only person who approves it. Independence has levels: different person (level 1), different information (the checker forms a view before seeing the maker's work, as in the Delphi method and the "premortem"), different method or vendor (level 3). Anchoring bias: once you see a proposal, your estimate drifts toward it. Forming an opinion first reduces it.

*In my project:* level 2 on a single vendor: the reviewer's first call is blind; there is no level 3.

### 6.2 LLM-as-judge: strengths and known biases
Using one model to grade or critique another is cheap and scales, but studies of LLM judges report: **self-preference** (a model prefers its own or similar-style outputs), **verbosity bias** (longer answers score higher), **position bias** in pairwise comparison, and **sycophancy** (agreeing with the user's framing). Mitigations: a different model family as judge, blind comparisons, position swapping, calibration against human labels (rank correlation such as Spearman's ρ), and reporting agreement rates.

*In my project:* the earlier "+47%" came from the same session generating and scoring; the new loop does not fix judge bias, it records it.

### 6.3 Multi-agent debate and the evidence on it
Debate or critique-and-revise setups (several model calls that argue, then a decision) can improve factual accuracy and reasoning on some tasks, but gains depend on diversity of the agents; calls with the same model and similar prompts tend to agree and add cost. A fair test needs baselines with the same compute (best-of-n, self-consistency, one longer prompt), several tasks, and a stated metric.

*In my project:* no single-call or equal-compute baseline exists for the recorded question; the claim is "process is recorded", not "answer is better".

### 6.4 State machines, typed outcomes and fail-closed design
A finite state machine is a set of states, an allowed transition relation, and an initial and terminal set; making illegal transitions unrepresentable (an explicit allowed-edge set) turns control flow into data you can test. A **typed outcome** replaces free text with a closed set the caller can switch on. **Fail-closed** means every error maps to the safe state (here `escalate`). Weakness: a catch-all safe state hides which kind of failure occurred unless a reason code travels with it.

*In my project:* nine states, eleven allowed edges (``), four outcomes, seven failure reasons.

### 6.5 Content hash, MAC, digital signature
- **Hash** (SHA-256): a fixed-size fingerprint of data. Collision-resistant: finding two inputs with the same hash is infeasible. Anyone can compute it. It detects *accidental* or *naive* changes.
- **MAC** (HMAC): a hash that mixes in a shared secret key. Only holders of the key can create or verify. Detects tampering by outsiders; both parties can forge.
- **Digital signature** (RSA, ECDSA, Ed25519): the signer's private key signs the hash; anyone with the public key verifies. Gives integrity, authenticity (who signed) and non-repudiation (the signer cannot deny).

The attack that separates them: an editor changes the receipt and recomputes the SHA-256. A bare hash still "verifies". A signature fails unless the editor has the private key. A bare hash is useful if the hash is stored somewhere the editor cannot reach (a ledger, a signed commit, a timestamp service); it is then an anchor. Related: **canonical serialization** (sorted keys, fixed separators; RFC 8785 JSON Canonicalization Scheme is the standard) is needed so the same data always hashes the same; a **hash chain** or Merkle tree links records so deleting one is detectable.

*In my project:* `content_sha256` is a bare hash stored in the same file (``). The committed git history is a weak anchor. The docs say "hashed, not signed", and "signed receipts" are listed as work in progress.

### 6.6 Schema validation as a contract with a stochastic component
A model's output is untrusted input. Validate it against a schema, reject on mismatch, and design the prompt so the schema is easy to meet. Constrained decoding (provider "structured outputs") guarantees syntax; schema validation after the fact only detects violations. Neither checks semantic truth.

*In my project:* prompt-constrained JSON plus Pydantic validation (``); provider structured output is listed as not done.

### 6.7 What a citation check can and cannot prove
Checking that a cited ID exists proves *referential integrity*, not *entailment* (that the span supports the claim). Entailment needs a second reader (a model or a human) or span-level attribution from the provider. Treat the first as a lint, the second as verification.

*In my project:* `unknown_evidence_cited` and `answer_without_citation` are lints (``).

## 8. Glossary

| Term | One-line definition |
|---|---|
| Producer | Role that drafts the answer from the evidence |
| Reviewer | Role that challenges the draft; here two calls: counterargument, then critique |
| Blind pass | The reviewer's first call, which has not seen the draft |
| Synthesizer | Role that writes the final typed record from draft and critique |
| Typed outcome | One of `answer`, `clarify`, `abstain`, `escalate` |
| Fail closed | Map any error to the safe outcome (`escalate`) |
| Backtrack | One allowed return to the producer after a blocking critique |
| Receipt | JSON record of a run: inputs, steps, calls, cost, outcome, hash |
| `content_sha256` | SHA-256 over the canonical receipt JSON without the hash field |
| Hash vs signature | Anyone can recompute a hash; only the key holder can sign |
| Anchor | Storing a hash somewhere the editor cannot change |
| Canonical JSON | Fixed key order and separators so equal data hashes equally |
| Hedge-dropping | The final answer states as fact what the reviewer qualified |
| Self-evaluation loop | The critic checks the draft against its own earlier argument |
| `terminal_reason` | Why a run failed; `None` when the model chose its outcome |
| Maker-checker | Control where a second party reviews the first party's work |
| Entailment | The cited text actually supports the claim |

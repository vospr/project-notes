# Course 1 · Chapter 1.3: Parity safety net — prove a refactor changed nothing

_Andrey Popov's project notes: how it works, why it was built this way, and the theory behind it._

## 2. The problem (business view, plain English)

Think of migrating a bank's valuation engine. The new engine must produce the same NAV as the old one before anyone signs it off. You run both side by side and reconcile. Any break must be explained: a real bug, or a difference in market data between the two runs.

My case was the same. The forecast SQL was refactored: about 900 duplicated lines became shared macros, and big models were split. Nobody could afford a change in who gets recommended to which position. The old code had no data tests at all.

There was one extra difficulty. The source tables are live. They kept changing while I ran the "before" and "after" builds, so even an unchanged pipeline gave different rows. The safety net had to survive that.

## 4. How it works (technical walkthrough)

The net has five layers. Each is chosen for the type of change it protects.

**Layer 0: what is compared.** Three final tables ("terminal marts"): the final candidates-per-position table, the final positions-per-employee table (RDR variant) and the final opportunity table (OPP variant). All derive from the same intermediate chain.

**Layer 1: compile-diff (code, no data).** Run `dbt compile` before and after, diff the generated SQL text. 7 of 8 macro collapses were byte-identical; 1 differed in whitespace only.

**Layer 2: exhaustive input check for the 3 UDFs.** For every distinct input value in the real data, compare `udf(x)` with the old inline `CASE`. 0 divergences.

**Layer 3: set equality for the 3 seeds** versus the old inline lists.

**Layer 4: row-level parity on the terminal marts.** Build a "before" and an "after" dataset, then compare with `audit_helper.compare_queries` through a row-comparison macro macro that:
- wraps 34 FLOAT64 columns in `ROUND(col, 9)`
- drops columns that depend on `CURRENT_DATE` (5 on the candidates-per-position table, 5 on the positions-per-employee table, 1 on the opportunity table)
- adds a row-count sentinel, because set comparison hides duplicate rows

Six tests: one baseline and one row-count test per terminal. Self-compare passed 12/12.

**Layer 5: outcome check.** Compare final recommendations of two branches: bucket stability 99.82%, shared candidates with identical scores.

```
 refactor ──► Layer 1 compile-diff   (same SQL text?)
          ──► Layer 2/3 UDFs, seeds  (same function / same list?)
          ──► Layer 4 row parity     (same rows in 3 final tables?)
          ──► Layer 5 outcome        (same recommendations?)
 each diff ──► drift or refactor?  (categorize)
```

**Step through the hard part: drift.** I first used one locked baseline built in the morning. The comparison showed hundreds of thousands of different rows. Cause: source tables change about 4 rows per minute. So the pattern changed: build "pre" and "post" datasets minutes apart, and categorize each diff. Result over about 390,000 common rows: the skill-coverage model differed in about 250,000 rows, the average-delivery-score column in 58,149, and zero rows were attributable to the fix.

## 5. Why it was built this way (decisions and trade-offs)

| Decision | Alternatives | Why this one | Cost / risk |
|---|---|---|---|
| Compile-diff first | Run the pipeline and compare | Same SQL text means same result for any data | Proves text only, not data or UDF definitions |
| Exhaustive distinct-input check for UDFs | Compare pipeline outputs | Covers every value that exists, not only today's output | Only inputs that exist today |
| Per-risk gates ("calibrated to risk") | One uniform heavy test | Cheap strong proof where possible, data runs only where needed | More moving parts |
| Compare the 3 terminals, not intermediates | Compare every model | Terminals are the output contract; drift grows with depth; intermediates are renamed or split | A wrong intermediate could hide in a terminal rounding |
| Row-hash + row-count sentinel | Triple primary key | the final candidates-per-position table has 351 to 601 duplicates | Set compare ignores duplicate count, so the sentinel is needed |
| `ROUND(col, 9)` tolerance | `dbt_expectations` per-column test | One place for tolerance | Rounding boundary can flip values |
| Exclude `CURRENT_DATE` columns, same-month runs | Freeze the date | Avoids false diffs; horizon filter stays constant within a month | Must re-baseline at month change |
| Per-variant datasets the first variant's suffix and the second variant's suffix | One baseline | Shared the shared intermediate data table table is overwritten by the second variant | Twice the build |
| Pre+post built minutes apart, categorize diffs | Locked baseline | The locked one drifted 16 min | Weaker gate: 71% of rows differ somewhere |

## 6. Theory behind it (the "lecture" part)

### 6.1 Equivalence checking and regression oracles
Two programs P and P′ are *equivalent* if P(x) = P′(x) for every input x. In general that is undecidable, so we use partial proofs of three kinds.

- **Syntactic equality.** If the text is identical (after a fixed compile step), equivalence follows if the engine is deterministic. This is the compile-diff.
- **Exhaustive testing over a finite domain.** If inputs come from a finite set D, check P(x) = P′(x) for all x in D. This is the UDF check, with D = the distinct values in the data.
- **Differential (golden-master) testing.** Run the old system as the oracle and compare outputs on real data. This is layer 4 and 5.

Strength ranking: syntactic > exhaustive on D > sampled on one day's data. *In my project:* exactly this order.

Limit of syntactic equality: the text can be the same while the meaning changes, if something outside the text changes (a UDF body, a seed file, a table). Compile-diff therefore needs layers 2 and 3 beside it.

Finance analogy: a parallel run of an old and new risk engine. A byte-identical config is strong evidence. A reconciliation on one day's positions is weaker, because tomorrow may contain a case you have not seen.

### 6.2 Set versus bag semantics
A SQL table is a bag (duplicates count). `EXCEPT DISTINCT` and `INTERSECT` work on sets. Let A and B be the two tables. Set comparison tests A \ B = ∅ and B \ A = ∅, so two tables can differ in duplicate counts and still pass. Adding |A| = |B| (row-count sentinel) restores part of the check. It is still not a bag-equality proof. *In my project:* the final candidates-per-position table has near-key duplicates, so I added the sentinel.

### 6.3 Confounded comparisons, and how to control them
We compare outputs O_old and O_new. Observed difference D = refactor effect R + source drift S + numeric noise N. A naive diff measures R + S + N. To isolate R, either remove S and N (pin the inputs), or measure them with a *control*: two runs of the *same* code at the same time gap.

- **Pinning.** Use as-of reads on bitemporal data (Chapter 1.2: bitemporal columns). Train sources are pinned, forecast sources are not.
- **Control build.** Same code twice at gap g gives S(g). The pilot model showed 5.28% differing rows at 15 min and 8.8% at 26 min.
- **Categorization.** Classify each differing column as "drift" or "fix-related" by tracing it to its source.

Drift also amplifies with depth: the role-categorization model 5.28%, the employees intermediate model 30.6%, a deep intermediate data table about 99.99%. Each join mixes drifting inputs, so the fraction of changed rows grows as 1 − ∏(1 − pᵢ) for independent sources. Deep tables almost always differ. That is a good argument for judging the *categorical* output, not raw cells.

Finance analogy: a break between two NAV runs with different price snapshots. You do not read it as a system bug until you re-run with the same prices.

### 6.4 Floating point, tolerance and the rounding-boundary problem
A double has 53 bits of mantissa. Machine epsilon is ε = 2⁻⁵² ≈ 2.2·10⁻¹⁶. Floating-point addition is not associative: (a + b) + c ≠ a + (b + c) in general. A parallel SUM or AVG may add in a different order on each run, so the same query on the same data can differ by a few ULPs.

Two tolerance styles:
- **Absolute:** |x − y| ≤ τ. Fine when the scale is known.
- **Relative:** |x − y| ≤ τ·max(|x|, |y|).

Rounding to h = 10⁻⁹ and then comparing is a different thing: it converts a *continuous* error into a *discrete* one. If two values differ by δ ≪ h and are located at random relative to the grid, the chance they land in different cells is about δ/h. With δ ~ 10⁻¹⁵ and h = 10⁻⁹ that is about 10⁻⁶ per cell. So rounding mostly hides noise, but it never removes the failure; at 11.2M rows × 30 columns the expected number of flips is still non-zero.

My note on the train result: *TRN §4* reports 79.9% of shared keys with different content on the candidates-per-position table. A per-cell flip rate near 10⁻⁶ cannot produce that, unless the noise is much bigger than 10⁻¹⁵ or many values sit exactly on a tie.

Better designs: a relative tolerance, a coarser grid, comparing with a tolerance instead of after rounding, or excluding known-noisy columns.

### 6.5 Metrics for comparing two ranked lists
For one position, let A and B be the top-N sets from the old and new runs.
- **Jaccard** J = |A ∩ B| / |A ∪ B|. 1 means identical sets.
- **Top-1 match:** the best candidate is the same.
- **Score exact-match** on shared pairs.
- **Bucket stability:** the share of pairs that stay in the same score bucket.

Reported: top-1 match 76.8% RDR and 81.4% OPP; median Jaccard 0.67 and 0.82; exact score match 88.8% and 93.0%; bucket stability 99.82%. The set metrics are strict (one candidate moves and J drops). Bucket stability is loose (a score can change and keep its bucket). Use both, and say which is which.

Where the real evidence is: for every (position, candidate) pair present in both branches, the score was identical. So the differences are *membership* changes caused by drift, for example a bucket field changing in a source table so the candidate fell out of a join.

### 6.6 What a parity gate can and cannot say
- A gate has false alarms (noise, drift) and misses (masked columns, rounding, "categorized as drift" that was in fact a refactor bug).
- Excluded columns and tolerances are blind spots by design. Each one needs a written reason.
- Parity proves *unchanged*, not *good*. Quality needs a separate evaluation (offline ranking metrics, Chapter 1.1 §6; and the ablation in Chapter 1.5).

## 8. Glossary

| Term | One-line definition |
|---|---|
| Parity | The new output equals the old output under an agreed definition of equal |
| Terminal mart | A final table that nothing else in the project reads: the final candidates-per-position table, the final positions-per-employee table, the final opportunity table |
| Compile-diff | Diff of the SQL that `dbt compile` generates before and after a change |
| `audit_helper.compare_queries` | dbt package macro that compares two queries as sets of rows |
| row-comparison macro | My macro that rounds FLOAT64 columns and drops excluded columns before comparing |
| Row-count sentinel | A test that the two tables have the same number of rows |
| Source drift | Changes in live source tables between two builds |
| Control build | Same code run twice, to measure drift and noise |
| Categorization | Labelling each diff as drift or fix-related |
| Jaccard | Size of intersection divided by size of union |
| Bucket stability | Share of pairs that stay in the same score bucket |
| ULP | Unit in the last place of a floating-point number |
| Source-pinning | Reading sources as of a fixed time so two builds see the same data |
| Baseline | A dataset from the unchanged code, kept as the reference |

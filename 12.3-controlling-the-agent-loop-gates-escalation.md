# Course 12 · Chapter 12.3: Controlling the agent: the loop, deterministic gates, escalation, handoffs, human approval, multi-agent routing

_Andrey Popov's project notes: how it works, why it was built this way, and the theory behind it._

**In short:** Controlling an AI agent: workflows versus agents, enforcing policy in code rather than prompts, escalation triggers, structured handoffs to humans, honest partial failure, human approval workflows, circuit breakers and supervisor routing.

## 2. The problem (business view, plain English)

An agent is a loop in which a model chooses the next action. That flexibility is the value and the risk. Instructions in a prompt are followed most of the time, and "most of the time" is not good enough when the rule is a compliance limit, a refund ceiling or "never submit an application without my tap". Customers also need a clean path to a person when the agent cannot help, and the person needs a usable summary, not a 40-turn transcript.

Finance analogy: four-eyes and authority limits. A clerk can approve refunds up to a limit; above it the system routes to a manager, whatever the clerk believes. The limit is in the system, not in the clerk's memory, and the hand-over note says who, what, how much, why, and what the clerk recommends.

## 4. How it works (the loop with its controls)

```
 user turn ─► [input checks] ─► model (system prompt, tools, history)
                                   │ stop_reason = tool_use
                                   ▼
                     PRE-TOOL GATE (code, not prompt)
                     ├─ policy: amount > limit? → block, start escalation
                     ├─ permission tier / approval needed? → pause for human
                     └─ allowed → execute tool ─► result (or is_error) appended
                                   │
                     loop guards: max turns, token/time budget,
                     repetition breaker, review-cycle cap (3)
                                   │
                     stop_reason = end_turn ─► [output checks] ─► reply
                                   │
               escalation: explicit request | policy exception | no progress
                     └─► structured handoff {customer_id, issue, root_cause,
                          evidence, amount, actions_taken, recommended_action}
```

## 5. Why it is done this way (decisions and trade-offs)

| Decision | Alternatives | Why this one | Cost / risk |
|---|---|---|---|
| Fixed workflow where the steps are known | Agent for everything | Predictable, testable, cheaper | Less flexible on odd inputs |
| Agent where steps depend on findings | Hard-coded decision tree | Handles open-ended cases | Needs gates, caps and evals |
| Policy limits in a pre-tool gate (hook) | Prompt rules, tool-side error only | Guaranteed; independent of model behaviour | Gate code must be tested (8.3 found three bugs) |
| Escalation by explicit request, policy exception, no progress | Sentiment score, fixed failure count, rules engine | Matches when a human actually adds value | Model judgement on "no progress" must be evaluated |
| Structured handoff summary | Full transcript, verbatim complaint | Human acts in a minute | Summary can omit; include evidence excerpts |
| Human approval as a paused workflow with an audit record | Approval by chat message | Durable, resumable, auditable | Latency; humans become the bottleneck |
| Circuit breaker after N review cycles | Unbounded revise loops | Stops token burn and ping-pong | Some solvable cases go to a human |

## 6. Theory (the lecture)

### 6.1 Workflows and agents
A **workflow** is a fixed path through model calls and tools that your code controls; an **agent** is a loop where the model decides which tool to call next until it is done. Common workflow patterns: **prompt chaining** (split a complex task into steps, each simpler; improves quality, not latency or cost), **routing** (classify the input, send it to a specialised path: events vs payments), **parallelisation** (independent sub-tasks at once, or the same task several times and vote), **orchestrator-workers** (a planner splits work for workers), **evaluator-optimizer** (generate, critique, revise). Choose the simplest structure that passes the eval; reach for an agent when the next step genuinely depends on what was found.

Routing in practice is hybrid: deterministic rules in code for cheap, certain cases (file extension, keyword with high confidence), a model or workflow for ambiguous ones, and a fallback. That is the design of my concierge (rules, then one LLM call above a 0.75 floor, then fallback; 7.2).

### 6.2 How the loop decides
The API is stateless. Each turn your code sends the whole conversation plus tool results; the model reads them and either calls tools (`stop_reason: tool_use`) or answers (`end_turn`). There is no hidden plan executor and no orchestration layer reading status fields: when `lookup_order` shows a 45-day-old purchase, the next action (refund or escalate) comes from the model reasoning over that result in context, guided by the system prompt. Frameworks such as LangGraph add an explicit graph around this: you define tools, bind them and the model into an agent node, and build the graph so the model chooses tools inside your control flow.

### 6.3 Deterministic gates
Any rule whose violation is unacceptable belongs in code:
- **Pre-tool hooks** intercept a proposed call before it runs, inspect arguments (amount > 500), and block it, returning a reason and starting the escalation path. In Claude Code a `PreToolUse` hook that exits with code 2 blocks the call and returns stderr to the model (8.3).
- **Tool-side validation** rejects invalid or out-of-policy calls with a structured error. Good defence in depth; on its own it still leaves escalation to the model.
- **Permission tiers** (read / write / execute), allowlists, and approval-required tools. Capability isolation: an agent cannot call a tool it was not given.
- **Output checks** before a reply leaves (PII, policy, grounding; 12.8).

Prompts state intent and improve the odds; code guarantees. Write the policy once in code and also explain it in the prompt so the model plans around it.

### 6.4 Escalation design
Good triggers:
1. **The customer asks for a human.** Do it now, with the context you have. Do not first call investigation tools or ask another question.
2. **Policy exception or authority limit** (manager approval for promotional pricing errors; refunds above the limit).
3. **No meaningful progress** (repeated failures, missing capability, contradictory data).
4. **High-risk or irreversible action** where policy requires a person.

Weak triggers: sentiment scores (punctuation is not need), fixed failure counts, a rules engine that removes judgement from cases rules cannot foresee.

Nuance: a customer who is frustrated but whose issue is resolvable right now ("I just want someone who can help"): acknowledge, say it can be completed now, and offer to do it or escalate. Doing it silently ignores the request; escalating immediately wastes a solvable case.

### 6.5 Handoffs
The receiving human usually cannot see the transcript. Pass a structured summary: customer ID, issue in one line, root cause (duplicate charge after a gateway timeout retried the payment), evidence (transaction IDs, amounts, timestamps), amount, actions already taken, what the agent could not do and why, recommended action. Compile it **before** calling `escalate_to_human`, including mid-process escalations. A reference ID to a stored transcript is a supplement, not a substitute.

### 6.6 Partial failure
When a backend call fails after the agent has done useful work (eligibility verified, charges explained, refund call times out): give the customer what is known, say plainly what could not be completed, and offer retry later or escalation. Never claim an action succeeded when it did not; do not keep the conversation open with endless retries; do not throw away the progress by escalating with nothing.

### 6.7 Human in the loop
- **Confirm destructive actions on ambiguous targets** by showing the candidates with distinguishing fields (name, ID, created date, last activity) and asking for one click. Requiring raw record IDs from users adds friction; soft delete is a recovery net, not a prevention.
- **Approval workflows** for regulated or customer-facing outputs: pause the workflow, notify a reviewer, resume on the decision, and store every decision with who, when, what and why. Step Functions' `waitForTaskToken` is the AWS form; any durable workflow engine works.
- **Caps** on autonomous actions per day and per value, with a kill switch.
- **Risk-tiered autonomy**: read freely, draft freely, act only with approval above a threshold (drafts unlimited; external submissions need a one-tap approval and are capped per day).

### 6.8 Loop safeguards
Max turns or a task budget; wall-clock limits; a **circuit breaker** on revise-review cycles (3, then a human); repetition detection (same tool, same arguments); stuck-tool supervision (a tool that hangs); system-level checks such as "more than 3 tasks blocked at once → pause" or "plan with more than 15 tasks → review before execution" (the article's safeguards, implemented as instructions in my template, 8.2). A completion gate that checks the claimed result before the loop may finish (FinalizeGate in 11.3).

### 6.9 Multi-agent structure
A **supervisor** (or orchestrator) classifies intent and routes to specialist agents, each with its own instructions, tools and data (separate knowledge bases per domain: clinical, insurance, scheduling, claims). The orchestrator decides **what** and **who**; the specialist decides **how** (delegated mechanism selection). New specialists plug in without changing the supervisor if they keep the input/output contract. Costs: more calls and tokens, harder debugging, so trace IDs on every dispatch. Several independent supervisors with manual hand-offs, or one general agent with permission groups, lose either routing quality or isolation.

### 6.10 Planning open-ended work
For "add comprehensive tests to a 200-file legacy codebase": map structure with cheap search (Glob, Grep), find high-impact and heavily coupled modules, write a prioritised plan, check dependencies, then implement in slices. Not alphabetical, not "read all 200 files first", not equal effort per directory.

## 8. Glossary

| Term | One-line definition |
|---|---|
| Workflow | Fixed sequence of model calls and tools controlled by code |
| Agent | Loop in which the model chooses the next tool until done |
| Prompt chaining | Splitting a task into sequential model calls |
| Router | Classifier that sends an input to a specialised path |
| Orchestrator / supervisor | Agent that splits and routes work to specialists |
| Delegated mechanism selection | Orchestrator decides what and who; specialist decides how |
| Pre-tool hook / gate | Code that inspects and may block a tool call before it runs |
| Escalation | Transfer of a case to a human |
| Structured handoff | Typed summary the human can act on without the transcript |
| Circuit breaker | Stop after N failed cycles and hand to a human |
| Task token (callback) | Handle a paused workflow waits on until a human decision arrives |
| Kill switch | Operator control that stops autonomous actions at once |

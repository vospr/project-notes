# Course 5 · Chapter 5.5: My AI delivery method: routing, separate contexts, code graphs, and the cost of the setup

_Andrey Popov's project notes: how it works, why it was built this way, and the theory behind it._

## 2. The problem (business view, plain English)

The team ships about five merged pull requests per working day written mostly with AI agents. For one engineer inside that flow, four things go wrong without discipline. Every ticket gets the same heavy process, even a one-line fix. One long AI conversation carries the plan, the code, the review and the evidence, so it gets slower, costlier and less reliable as it grows (chapter 3.5). The assistant answers from a stale or invented picture of a about 2,500-file codebase. And knowledge from yesterday's session is lost today.

Finance analogy: running an audit. You scope by risk and materiality (routing), keep the preparer and the reviewer apart (separation of duties), keep a ledger index that is re-checked against the books before you rely on it (code graph and freshness check), and file working papers in an organised audit file (wiki compiled from session notes). The overhead of all that is itself a cost that must be justified by the errors it prevents.

## 4. How it works (technical walkthrough)

```
 ticket ─► [design window]  router: read-only route card ─► I confirm
              │  decision context (not a second plan), code graph + wiki lookups, "confirm in source"
              ▼
          [execution window = the client's pipeline, in a fresh per-ticket clone]
              plan ─► (fresh context) implement ─► (fresh context) review + PR ─► (fresh context) evidence/demo ─► merge
              │                                                    ▲ I do not merge from the design window (rule)
 session notes ─► raw handoffs (immutable) ─► gated wiki update ─► curated pages ─► project-knowledge agent
 spend logs ─► per-ticket allocation + context-economy diagnostic ─► checklist (chapter 3.5)
```

**Routing.** Read the whole ticket, comments, linked work and current code first; do not claim, clone, comment or edit before I confirm. Judge by questions, not a score: is the outcome and authority clear; has work already started; is the root cause proven; how many modules, contracts or systems change; does it touch security, privacy, identity, concurrency or destructive state; are decisions and evidence consistent; can one execution session finish and verify it. Pick exactly one of seven routes: resume the current stage; hold and clarify; tiny fix; diagnostic bug (first get a command that goes red); bounded implementation; high-rigor implementation; research or decision spike. Output is a route card with readiness (green, amber, red), why, estimate, blast radius, owner of the plan, gates, escalation triggers, and unresolved facts. Escalation is reversible: start light, move up when the blast radius grows. Rule: for client work the checked-in pipeline owns the plan; I supply verified decision context only.

**Separate contexts.** Planning, implementation, review and evidence/audit run in different conversations; a context is resumed only for the same ticket and phase, re-entering with the ticket, exact artifact path, branch and current task, not a transcript. Why: cost (context re-read every turn, chapter 3.5) and independence (a reviewer who did not write the code does not share its blind spots). Delegated agents return short summaries and put detail in files.

**Disposable clones.** One fresh clone per ticket outside the workspace, with shared folders (docs, knowledge, graph, skills) linked in; closing a ticket deletes the clone but keeps `docs/<ticket>/`. The clone sits beside the workspace, not inside, because the close script force-deletes recursively (*WCLAUDE* "Why sibling").

**Code graph and freshness.** A generator builds, per repository, a graph of files, symbols and relations plus communities. For the client repo: about 41,000 nodes, about 51,000 edges, about 1,900 communities, about 2,500 source files, AST and semantic extraction. `kb-graph-state.py check` returns exit 0 fresh, 2 stale, 3 invalid. A read-only hook injects a compact report once per session and repository, only for covered repositories. Rule: the graph is a navigation aid; a claim that matters is confirmed in the current source. If the state file is missing or invalid, say so and work from source only.

**Knowledge.** Raw session handoffs are immutable. A gated skill compiles them into curated wiki pages and never writes without my approval. A catalogue with hashes and commit metadata detects drift (`build-kb-catalog.py --check`) instead of trusting file dates. A project-knowledge agent answers questions from the clones, graphs and wiki.

**Measurement (*SCRIPTS*, chapters 3.5 and 3.6).** A per-ticket spend collector and a context-economy diagnostic observe parent-versus-subagent consumption and two alerts (mean cache-read per event above about 250,000; low tool-call batching). They never gate anything. The about 250,000 threshold is "single-case reference; calibration pending".

## 5. Why it was built this way (decisions and trade-offs)

| Decision | Alternatives considered | Why this one | Cost / risk |
|---|---|---|---|
| Route before work, read-only, I confirm | Same process for every ticket; let the agent start | Proportionality: a tiny fix should not buy high-rigor process; nothing changes state before a human decision | The router itself costs a session; route quality is unmeasured |
| Design window separate from the execution window | One session does everything | Keeps the client's pipeline authoritative; keeps decisions and evidence outside throwaway clones | Needs discipline; breached once; licence question |
| Separate contexts per phase | One long session | Cost grows with context × turns (3.5) and reviewers should not share the author's context | Re-entry costs; hand-off files must be good |
| Defer to the checked-in pipeline on conflict | Fork or replace it | It is the client's process; one plan owner (*ROUTER* "one plan owner") | I cannot optimise it |
| Code graph + confirm-in-source | Plain search; no map | A about 2,500-file repo does not fit in context; the map saves reads | Stale graphs mislead; the rule adds reads |
| Fail-open hook for graph injection | Block on stale graph | Never block work for a navigation aid | Staleness goes unnoticed |
| Raw notes immutable, wiki compiled behind a gate | Edit one big notes file | Raw is evidence, wiki is a view; approval stops silent drift | Maintenance overhead (53 pages) |
| Small model for reads, large for hard decisions | One model | Premium effort only where reasoning difficulty justifies it | Weak routing can under-power a hard task |
| Measure cost per delivered change, not tokens | Count tokens or prompts | Output matters, tokens don't (chapters 3.1–3.3) | Small n, one operator |

## 6. Theory behind it (the "lecture" part)

### 6.1 Risk-based triage and proportionality
Triage assigns effort in proportion to risk. A simple rule: spend extra process on a ticket when the expected loss it prevents exceeds its cost, `p(error) × impact > cost of the control`. Impact rises with blast radius (modules, contracts, data, users) and with irreversibility (migrations, security, destructive state). Classification should be by observable questions, not by a numeric score that invites false precision, and it must be reversible: escalate when new evidence shows a wider radius. Misclassification has two errors: over-processing (waste) and under-processing (defects); the router should be audited by sampling closed tickets for both.
*In my project:* seven routes decided by questions; escalation triggers on the route card; I have not audited routing accuracy.

### 6.2 Context windows, attention and cost (recap of chapter 3.5)
A model reads the whole context each turn; for a session of N turns with mean context C̄ the read volume is about N × C̄, and since context grows with turns the total grows roughly like N². Prompt caching makes re-reads cheaper per token but not free, and long contexts also dilute attention. Two levers: fewer turns, or a smaller carried context (reset at phase boundaries, return summaries, keep detail on disk). A reset has its own cost (reloading instructions and plan).
*In my project:* the cost case showed a never-reset parent conversation at about 89% of token volume in the first hours; the phase-reset rule is my response, effect not yet measured.

### 6.3 Separation of duties and correlated errors
In control design the preparer and the reviewer must be different, because a reviewer who shares the preparer's information and assumptions repeats the same mistakes. For LLM agents, the same model with the same context is a strongly correlated reviewer: it inherits the plan's framing. A fresh context, a different instruction set, or a different model lowers the correlation but does not remove it (same training data). A human gate remains the independent control.
*In my project:* review and evidence run in fresh contexts; merging stays a human decision.

### 6.4 Code knowledge graphs and retrieval
A code graph represents files, symbols and relations (imports, calls, defines) as nodes and edges; *community detection* clusters densely connected nodes into modules. It answers structural questions (what depends on this) cheaply and can seed retrieval. Limits: a graph is a snapshot; semantic edges extracted by a model can be wrong; staleness silently degrades answers. Treat it as an index, like a database index that must be rebuilt after the table changes, and verify any decisive fact against the source. Freshness is cache invalidation: compare the graph's recorded commit and content hashes to the working tree.
*In my project:* about 41,000 nodes and about 51,000 edges for the client repo, a three-state freshness check, and a "confirm in source" rule; the graph is currently stale.

### 6.5 Knowledge management: immutable log, compiled view
Keep raw events append-only (session handoffs) and derive views from them (wiki pages). The pattern is event sourcing for knowledge: the log is the source of truth, the view can be rebuilt, and any edit to a view must be traceable to events. Approval gates and hash-based catalogues prevent silent drift. The cost is curation; a wiki that nobody reads is pure overhead.
*In my project:* 62 raw files and 53 curated pages; read frequency unknown.

### 6.6 Evaluating a productivity intervention
To claim "the method helped", you need a comparison: before/after on comparable work, or matched tickets with and without. Beware confounders (ticket size, my own learning, model upgrades), measure outcomes (merged, delivered, rework) not activity (prompts, tokens), report distributions not means, and pre-register thresholds to avoid tuning to the case (Goodhart's law: a measure used as a target stops being a good measure). A single instructive case supports a mechanism, not an effect size.
*In my project:* one cost case (mechanism), no controlled comparison, alerts calibrated on the case they flag.

### 6.7 Controls that are only text
A control is real when it is automatic and fails safe. A written rule is a policy, not a control. Hooks are controls only if they receive the right input and use the blocking exit code; otherwise they are decoration. Test a control by trying to break the rule on purpose and observing the block.
*In my project:* the "never merge from this window" rule is policy; my commit/push hooks need a live test.

## 8. Glossary

| Term | One-line definition |
|---|---|
| Route / route card | The chosen process level for a ticket and the one-page record of why |
| Two-window model | Design window (decisions, evidence) vs execution window (the client's pipeline) |
| Context | Everything the model reads each turn: instructions, history, tool results |
| Context reset | Starting a fresh conversation from a short hand-off instead of the long history |
| Subagent | A delegated agent with its own context that returns a short report |
| Cache-read tokens | Tokens re-read from the prompt cache each turn; dominates long sessions |
| Code graph | Nodes and edges for files, symbols and relations, with communities |
| Freshness check | Comparison of the graph's recorded commit and hashes with the working tree |
| Confirm in source | Rule that any decisive claim from the graph or wiki is verified in current code |
| Handoff (raw) | Immutable end-of-session note |
| Wiki (curated) | Pages compiled from handoffs behind an approval gate |
| Carrier / clone | The fresh per-ticket repository copy used for execution |
| Hook | A script run by the coding agent before or after a tool call |
| Exit code 2 | The code that makes a pre-tool hook block the call |
| Goodhart's law | A measure that becomes a target stops being a good measure |
| Proportionality | Process effort scaled to risk |

# Course 12 · Chapter 12.6: Retrieval and grounding beyond the basics: chunking strategies, fixing retrieval by symptom, index types, citations, tenant isolation, evaluating RAG

_Andrey Popov's project notes: how it works, why it was built this way, and the theory behind it._

**In short:** Fixing retrieval problems by symptom: chunking strategies chosen by measurement, hybrid search, metadata filters, rerankers, index types, citations and abstention, tenant isolation, and evaluating retrieval and generation separately.

## 2. The problem (business view, plain English)

Most RAG failures are retrieval failures that look like model failures: the answer cites the wrong paragraph because the right one was split across two chunks; an acronym search returns "semantically similar" documents but not the one with the exact term; a question about last year's report retrieves this year's. The certification questions are mostly symptom-to-fix puzzles, and the fixes are the same on any platform.

Finance analogy: a research desk's document archive. Good indexing is by deal, date and document type (metadata), full-text and concept search together (hybrid), the most relevant memo first (reranking), and only the folders the analyst is cleared for (permissions). Without that, the best analyst still quotes the wrong memo.

## 4. How it works (symptom → fix map)

```
 symptom observed in traces                               first fix to try
 ─────────────────────────────────────────────────────    ─────────────────────────────────────
 misses exact terms, acronyms, IDs, citations         ─►  hybrid: BM25 + dense, fuse with RRF
 too many off-topic hits across types / periods       ─►  metadata filter before similarity
 right document retrieved but ranked 4th or 5th       ─►  reranker (cross-encoder) on top-k
 answer lacks context that sits in the next paragraph ─►  structure-aware / hierarchical chunks
 fixed-size chunks cut arguments or clauses           ─►  chunk on semantic or legal boundaries
 domain words mean something special                  ─►  tuned embedding model or query expansion
 user sees content of another tenant                  ─►  permission filter in retrieval / per-tenant index
 answer cites nothing or invents                      ─►  citations on, abstain rule, grounding check
```

Every fix is validated on a labelled retrieval set (queries with known relevant chunks) before and after.

## 5. Why it is done this way (decisions and trade-offs)

| Decision | Alternatives | Why this one | Cost / risk |
|---|---|---|---|
| One chunk per row with a unique ID and metadata | Arrays of chunks per document; one file per chunk | Indexes sync row by row; filters and citations need per-chunk metadata | More rows |
| Structure-aware or hierarchical chunks for long technical/legal text | Fixed 300-500 tokens | Keeps arguments and clauses whole; parent gives context, child gives precision | Parsing work; re-embedding on change |
| Hybrid retrieval | Dense only | Exact terms and meaning both matter in finance, legal, medical text | Two indexes, fusion tuning |
| Metadata pre-filter | Bigger k; new embedding model | Cheap, explainable, minimal change | Metadata must be extracted and kept clean |
| Reranker on top-k | Increase the number of chunks in the prompt | Puts the best first without bloating context | Extra latency per query |
| Keep vectors in the existing database (pgvector) when scale allows | Migrate to a dedicated vector store | Least development effort; one source of truth | Scale and tuning limits; measure p95 |
| Separate index per tenant where isolation is a requirement | Shared index + filters | Hard isolation, simpler audits | More indexes to run |

## 6. Theory (the lecture)

### 6.1 Storage layout
Store chunks as **one row per chunk**: `chunk_id` (unique), `doc_id`, text, metadata (source, section, page, date, document type, language, access group), and the embedding or a pointer to it. A table with an array of chunks per document cannot be indexed or filtered per chunk. Managed vector indexes either **sync from a source table** (you write rows, the index follows) or take **direct writes** through an API; with managed embeddings the platform computes vectors with its default model.

### 6.2 Chunking strategies
| Strategy | How | Good for | Weak at |
|---|---|---|---|
| Fixed size + overlap | N tokens with 10-20% overlap | Uniform, unstructured text; quick baseline | Splits arguments, tables, clauses |
| Structure-aware | Split on headings, sections, paragraphs, clauses | Contracts, policies, manuals, court opinions | Needs a parser per format |
| Semantic | Break where adjacent-sentence embedding similarity drops below a percentile | Prose with topic shifts | Uneven sizes; cost at ingest |
| Hierarchical (parent-child) | Small child chunks for matching, larger parent returned for context | Long papers where related paragraphs must stay together | Two levels to maintain |
| Contextual chunks | Prepend a short document-level context to each chunk before embedding | Chunks that are ambiguous alone ("the company's revenue grew...") | Ingest cost (check current pricing) |
| Tree summaries (RAPTOR-style) | Cluster and summarise chunks recursively | Questions needing synthesis across a corpus | Complex; summaries can drift |

Choose by measurement: pick a retrieval metric (recall@k, nDCG), build questions with known answers, and sweep chunk sizes and strategies; an LLM judge can score retrieved-chunk relevance at scale. Picking chunk size from intuition, or asking an LLM to pick it from token statistics, is not evidence. The purpose of chunking is **relevance** of what is retrieved, not storage limits or cost.

### 6.3 Fixing retrieval by symptom
- **Hybrid search** combines keyword (BM25) and dense vectors and fuses the ranked lists (RRF); it fixes missed acronyms, codes, names and citations while keeping semantic matches.
- **Metadata filtering** narrows the candidate set by date, type, source, tenant, language before similarity ranking; it is the minimal-change fix for "too many documents evaluated".
- **Rerankers** (cross-encoders, or an LLM) re-score the top 20-100 candidates against the query; better than adding more chunks to the prompt or asking the generator to reorder.
- **Embedding model choice**: a domain-tuned or multilingual embedding model when vocabulary is special (automotive parts, medical acronyms) or when queries and documents are in different languages. Changing the model means re-embedding everything.
- **Query rewriting / expansion** for short or ambiguous queries; with care, because it can drift.

### 6.4 Index types
| Index | Idea | When |
|---|---|---|
| Flat (exact) | Compare the query with every vector | Small collections (thousands to low hundreds of thousands); exact recall; often fastest at small scale |
| HNSW | Navigable small-world graph; approximate | Large collections, low latency, more memory |
| IVF (inverted file) | Cluster vectors; search the nearest clusters | Large collections, less memory, recall depends on probes |
| PQ / quantisation | Compress vectors | Very large collections; some recall loss |

Platform choice follows effort and scale: if the data already sits in PostgreSQL and the scale is modest, `pgvector` next to the data is the least-effort route; serverless vector search with metadata filtering suits managed RAG at tens of millions of vectors; in-memory stores give the lowest latency for small indexes. Always check p95 latency on your own queries.

### 6.5 Grounding, citations and abstention
Ask for answers **only from the retrieved context**, return **citations** to the chunk or page, and allow "I don't know" when the context does not answer. Managed knowledge-base APIs can return citations with the generated answer; the Claude API returns cited spans when `citations` is enabled on document blocks (not combinable with structured outputs). A **grounding check** (is each claim supported by the sources?) can run as a guardrail before the answer is shown (12.8). For long technical generation, grounding in retrieved chunks plus an explicit verify-each-claim step reduces fabrication; raising temperature or one-pass summarisation of the whole document increases it.

### 6.6 Permissions and tenant isolation
Retrieval must only see what the user may see: filter by access group at query time, from the identity of the caller, not from the prompt. When isolation is a hard requirement (per hotel, per client, per business unit) use a separate index per tenant, possibly per account; a shared index with logs is detective only. Limiting what each user can retrieve is also a leakage control (12.8). Offensive or wrong content in answers usually starts in the corpus: curate upstream, including review before indexing.

### 6.7 Freshness
New documents published daily: incremental sync of the index (or direct ingestion for near-real-time data), never retraining. Keep a document version and validity date in metadata so "which version applied on that date" is a filter, not a guess.

### 6.8 Evaluating RAG
Curate a dataset that tests **both** components: for retrieval, queries with the known relevant chunks (recall@k, nDCG); for generation, reference answers or rubrics for faithfulness and answer relevance (10.1, 10.2). Then attribute failures: a wrong answer with the right chunk retrieved is a generation problem; a wrong answer with the right chunk missing is a retrieval problem. Benchmarking several LLMs on the same pipeline tells you nothing about retrieval.

### 6.9 Matching with hard constraints
For "suggest an available team member whose profile fits the project", combine a **tool** for hard constraints (availability for the dates), **embeddings** for fit between profile and scope, and **metadata filters** (only available people). Keyword matching or looping over every profile with a score does not scale and misses meaning.

## 8. Glossary

| Term | One-line definition |
|---|---|
| Chunk | Unit of text that is embedded and retrieved |
| Structure-aware chunking | Splitting on headings, sections or clauses |
| Semantic chunking | Splitting where meaning shifts, detected by embedding similarity |
| Hierarchical (parent-child) chunking | Match on small chunks, return their larger parent |
| Hybrid search | Keyword (BM25) plus vector search, fused |
| Metadata filtering | Restricting candidates by attributes before ranking |
| Reranker | Model that re-scores top candidates against the query |
| Flat / HNSW / IVF | Exact search / graph-based approximate / cluster-based approximate index |
| pgvector | Vector search extension for PostgreSQL |
| Citation | Pointer from an answer claim to its source span |
| Grounding check | Test that each claim is supported by the provided sources |
| Tenant isolation | Guarantee that one customer's data never reaches another's queries |

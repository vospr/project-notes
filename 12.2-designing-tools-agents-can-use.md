# Course 12 · Chapter 12.2: Designing tools an agent can use: descriptions, parameters, granularity, outputs, errors, many tools

_Andrey Popov's project notes: how it works, why it was built this way, and the theory behind it._

**In short:** How to design tools an AI agent can use well: descriptions as the main lever, parameters and enums, merging tools to remove races, outputs with IDs and pagination, structured error results with a retryable flag, and tool search for large toolsets.

## 2. The problem (business view, plain English)

An agent is only as good as the tools it is handed. The model never sees your code; it sees a name, a description and a JSON schema, and it decides from those alone which tool to call and with what. Vague descriptions make it pick `delete_file` when the user said "archive"; a tool that throws an exception makes it say "I'm having trouble" instead of "that tracking number looks malformed, can you check it?"; a tool that returns 40 fields per order fills the context window in ten calls. Most agent failures that look like "the model is dumb" are interface design failures.

Finance analogy: a tool is a form handed to a junior clerk. A form with clear field labels, a drop-down for the department, a confirmation slip showing the amount and the account, and an error message that says "IBAN checksum fails, re-type it" gets processed correctly. A blank sheet that says "Process" does not.

## 4. How it works (what the model sees, and the loop)

```
 request: system + messages + tools[ {name, description, input_schema, strict?} ... ]
                │
                ▼
 model reads ALL tool names + descriptions + schemas ─► chooses tool + arguments (tool_use block)
                │                                         (several tool_use blocks = parallel calls)
                ▼
 your code runs the tool ──► success: compact structured result with IDs (+ cursor, + totals)
                        └──► failure: result with is_error=true and
                                {category: transient|validation|permission|business,
                                 retryable: bool, cause, user_message, suggested_next}
                │
                ▼
 all tool_result blocks go back in ONE user message ─► model decides the next step
```

Inside the tool, before returning: bounded retry with backoff and jitter for errors that recover on immediate retry (timeouts, 503); validation of arguments with a precise message; trimming the payload to the fields the task needs.

## 5. Why it is done this way (decisions and trade-offs)

| Decision | Alternatives | Why this one | Cost / risk |
|---|---|---|---|
| Invest in descriptions first | System-prompt routing, few-shot, removing tools | Read at decision time; scales with the tool set | Longer tool definitions cost input tokens (cache them) |
| Enum for a closed set of values | Free string + validation, semantic matching | The model maps "research database" to `research_papers` well; invalid values impossible | Enum must be updated when values change |
| One atomic `find_and_book` | Check then book; a hold tool | Removes the race between check and act | Larger tool; harder to reuse |
| Accept the ID and resolve internally | Chain `get_details` → `get_neighborhood` | Removes latency and failure coupling | Tool hides a lookup; log it |
| First page + total + cursor | Fetch all pages; hard top-50 | Fast; the model asks for more only when needed | Model must handle cursors |
| Structured errors as results | Exceptions, empty results, generic errors | Model can choose retry, rephrase, ask, or escalate | Error taxonomy must be maintained |
| Retry transient inside the tool | Let the model retry everything | Saves turns; the model never sees noise | Must be bounded (latency) and idempotent |
| Tool search / deferred loading for 50+ tools | All tools always loaded | Selection accuracy and context size | One extra step; search quality matters |

## 6. Theory (the lecture)

### 6.1 What the model knows about a tool
Only three things: the **name**, the **description**, and the **input schema**. It also sees prior tool results. It does not see your implementation, your logs, or your intentions. Therefore the description is the single strongest lever for both **selection** (which tool) and **arguments** (what values). A good description reads like documentation for a new colleague:

- what it does and what it returns, in one or two sentences
- when to use it, and **when not to** ("Do not use for backup files; use `archive_file`")
- each parameter's meaning and format ("`user_id`: UUID of the user to update, required")
- side effects (sends email, charges money, irreversible)
- how it differs from the nearest neighbour tool

When an agent keeps choosing a general built-in tool (Grep, `sed` through Bash) over a specialised one ("Analyzes dependency graph"), the cause is almost always that the built-in tool's description is richer. Fix by describing capabilities and outputs ("builds the dependency graph: direct imports, transitive dependencies, cycles") and when the tool beats text search.

### 6.2 Parameters
- Mark required fields as required, and give every field a description with its format. Types alone (`"type": "string"`) tell the model too little.
- Use an **enum** when the set is closed and small (three databases). Natural language ("check the technical documents") maps well to well-named enum values.
- Use `strict: true` (Claude API) with `additionalProperties: false` and `required` so the arguments are guaranteed to validate against the schema. This removes malformed calls; it does not remove wrong values.
- Do not encode format hints in parameter names (`user_id_string_uuid_format`); put them in the description.
- Validation errors from the tool should name the parameter and the expected form.

### 6.3 Granularity: merge, split, or reshape
Design tools around **tasks the agent performs**, not around your REST endpoints.
- **Merge** when two calls are always made together, or when the gap between them creates a race. `get_available_slots` then `book_appointment` fails 15% of the time because the slot is taken in between; an atomic `find_and_book_appointment` that returns the confirmation or alternatives removes the race. (A 60-second hold tool reduces but does not remove it and adds a step.)
- **Accept the identifier the user has** and resolve internally. If `get_neighborhood_info(address)` always needs `get_property_details` first, let it take `property_id`. A new helper tool keeps the coupling.
- **Do not over-merge** unrelated data into one call ("property with neighbourhood") when callers often need only one part.
- **Split** only when purposes genuinely differ; splitting does not fix a weak description.

### 6.4 Outputs
- Return **structured data with stable IDs** for anything the agent may act on next (`document_id` for `share_document` and `move_document`). Titles and URLs are for humans.
- Return the **decision-relevant fields** for confirmations: a provisioning tool that returns only "OK" leads users to confirm without knowing the cost or the project. Return cost estimate, target project, resource spec and impact.
- **Paginate**: first page, total match count, opaque cursor. The agent fetches more only when the task needs it; auto-fetching all pages costs 15-20 seconds per query.
- **Trim**: 40 fields per order fill the context. Return the fields the workflow needs, or offer a `fields`/`detail` parameter. Prefer meaningful values over internal codes.
- In MCP, `structuredContent` with an `outputSchema` gives clients a typed result; include a text block too for clients that only read text (6.1).

### 6.5 Errors
Two channels, never mixed (MCP): a **protocol error** (JSON-RPC error: unknown tool, malformed request) versus a **tool execution error** (a normal result with `isError: true` that the model reads). In the Claude API the same idea is a `tool_result` block with `is_error: true`.

A useful error result carries:
| Field | Example | Why |
|---|---|---|
| category | `transient` / `validation` / `permission` / `business` / `not_found` | Chooses the recovery path |
| retryable | `false` for "outside 30-day return window" | Stops wasted retries |
| cause | "Order exceeds 30-day return window (purchased 45 days ago)" | Lets the model explain |
| user_message | Customer-friendly wording | Better replies, no internals leaked |
| suggested_next | "Verify the tracking ID format or search by order number" | Turns a dead end into an alternative |

**Where retries live.** Errors that succeed on immediate retry (network timeout, 503, throttling) are retried **inside the tool**, bounded (2-3 attempts, exponential backoff with jitter, a total time cap), and only for idempotent operations or with an idempotency key. If retries are exhausted, return a transient error saying so. Errors that can never succeed by retrying (syntax error in a user filter, business rule violation) return **immediately** with details so the model can fix the input, explain, or escalate. Never convert a failure into an empty success; never swallow it and return nothing.

### 6.6 Many tools
Selection accuracy falls as the tool list grows, and every definition costs context. Options, in order of preference in 2026:
1. **Tool search with deferred loading**: tools are marked `defer_loading: true`; the model calls a search tool and only matching definitions are loaded into context. Loaded definitions are appended, so the prompt cache survives. This solves both "the agent skipped the search" (it cannot call what is not loaded) and "it picked the wrong one from 50" (it chooses among a few).
2. **Namespacing and consolidation**: prefix by system (`jira_search`, `git_create_branch`) and remove near-duplicates.
3. **Subagents with narrow toolsets** (12.3, 12.4).

A composite `find_and_execute(description, params)` hides the choice from you and from the model: wrong matches execute silently. Validation errors after the fact catch only some mistakes.

### 6.7 MCP specifics for tool designers
- An agent connected to several MCP servers sees **all** of their tools at once, discovered at connection time (`tools/list`); it is not limited to one server per turn.
- For standard systems (Jira, GitHub, Slack) prefer an existing, maintained MCP server over a custom wrapper or `curl` through Bash; build custom only for workflows the standard server cannot express.
- Expose **catalogs as resources** (schemas, document hierarchy, issue summaries) so the agent can orient itself without 8-10 exploratory tool calls (12.4).
- Remote servers need authorization: HTTP transport behind an OAuth 2.1 authorization server, not "credentials as environment variables" in a shared layer (see `6.4-auth-for-mcp-today.md`).
- Annotations (`readOnlyHint`, `destructiveHint`, `idempotentHint`, `openWorldHint`) are hints from the server; treat them as untrusted unless the server is trusted.

### 6.8 2026 API notes (Claude)
- **Strict tool use**: `strict: true` on the tool definition guarantees schema-valid `input`.
- **Parallel tool use** is on by default: return all `tool_result` blocks in one user message; for a failed call return a result with `is_error: true`, never drop it.
- **Forced tool choice** (`any` / named tool) returns 400 on Opus 5.5, Sonnet 5.5 and Fable 5.1; `auto` and `none` remain. Order mandatory steps in code (call 1, then call 2) or instruct in the prompt.
- **Programmatic tool calling** lets the model call your tools from inside code execution, so bulky intermediate results stay out of context.
- Parse tool inputs with a JSON parser, never by string matching (escaping varies by model).

## 8. Glossary

| Term | One-line definition |
|---|---|
| Tool definition | Name, description and input JSON schema the model reads |
| `tool_use` / `tool_result` | The model's call block / your reply block with the output |
| `is_error` / `isError` | Flag on a tool result marking a failed execution the model should read |
| Strict tool use | `strict: true`: arguments guaranteed to match the schema |
| Enum parameter | Parameter limited to a fixed list of values |
| Atomic tool | One call that checks and acts, so nothing changes in between |
| Failure coupling | One call's failure breaks a dependent call |
| Cursor pagination | Opaque token for fetching the next page |
| Retryable error | Error that may succeed if repeated (timeout, 503) |
| Idempotency key | Client-chosen ID so a retried action runs only once |
| Tool search / deferred loading | Tools loaded into context only after a search matches them |
| Tool annotations | MCP hints such as `readOnlyHint`; not guarantees |
| Resource (MCP) | Read-only content the client can attach, e.g. a schema or catalog |

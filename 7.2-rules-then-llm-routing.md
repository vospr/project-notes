# Course 7 · Chapter 7.2: Rules-then-LLM routing: confidence floor, fallback, cost per decision

_Andrey Popov's project notes: how it works, why it was built this way, and the theory behind it._

**In short:** Rules-then-LLM routing: regex rules decide clear cases free (threshold 0.72); otherwise one Haiku call must return a route with confidence of at least 0.75, else fall back to a clarifying question or human hand-off. A model call cost $0.00041 on Haiku versus $0.00134 on Opus.

## 2. The problem (business view, plain English)

A travel assistant gets three kinds of request: questions about a destination or property, requests for current information, and requests to book. Sending every message to a large model to decide "which kind is this?" costs money and time on every turn, including turns like "book me a room" that a keyword catches for free. Sending nothing to a model fails on the many requests that contain no keyword.

The design: let cheap rules decide the clear cases, and ask a model only when the rules are not sure. If the model is also not sure, do not guess: ask the user or hand over to a human.

Finance analogy: tiered credit approval. A scorecard auto-approves or auto-declines the clear cases at almost no cost. Borderline cases go to a human underwriter, who is slow and expensive. If the underwriter is also unsure, the file goes back to the customer for more information. The scorecard cut-offs are the rule thresholds; the underwriter's minimum conviction is the confidence floor; "back to the customer" is the fallback.

## 4. How it works (technical walkthrough)

```
user text ─► Stage 1: regexes (config/routing_rules.yaml)
              │  best matching rule = highest score
              ├─ score ≥ 0.72 ──────────────────────────────► route (no LLM, ~0 cost)
              └─ no match, or best score < 0.72
                     │
                     ▼
              Stage 2: one Claude call (policy.yaml: model, max_tokens=128)
                     │  expects {"intent": ..., "confidence": ...}
                     ├─ intent in map AND confidence ≥ 0.75 ─► mapped route
                     ├─ intent unknown OR confidence < 0.75 ─► "fallback"
                     └─ no key / no SDK / unparsable reply ──► Stage-1 result (None) ─► "fallback"
                                                                (API error: exception ─► human hand-off)
fallback ─► guardrail ─► clarifying question / out-of-domain reply / human hand-off ─► synthesis
```

**Stage 1** (`CC:dispatcher.py:196-212`). Every regex rule that matches is collected; the one with the highest `score` wins (`:209`). If that score is below the threshold, the intent is returned but the route is `None`, which means "escalate". The four rules (`CC:config/routing_rules.yaml:4-22`):

| Pattern (words) | Route | Score |
|---|---|---|
| alpine vista, property, resort | rag | 0.91 |
| book, booking, reserve, reservation | booking_stub | 0.95 |
| trend, latest, right now, news | research | 0.82 |
| weather, stock, crypto, politics | fallback | 0.30 |

The last rule can never decide a route: 0.30 is below 0.72, so it only forces escalation. The score works as a **priority**, not a probability: if a text matches both "property" and "book", booking (0.95) wins. By my count of the 40 labelled rows (a standalone re-computation, not the project's code), the rules decide 12, and 11 of those 12 are correct (92% precision, 30% coverage). The one wrong rule hit is "I want to secure a room at the Alpine Vista": "alpine vista" matches the 0.91 property rule, and there is no booking word.

**Stage 2** (`CC:dispatcher.py:249-278`). Skipped when there is no `ANTHROPIC_API_KEY` or no SDK. Otherwise one `messages.create` with the prompt built from `v1.yaml` (role, context, constraints, output format, examples) as the system text, and **only the current user text** as the message (`:261-266`). The reply text is searched with the regex `\{.*\}` (greedy, whole reply) and parsed as JSON (`:230-236`); it must have a non-empty `intent` and a numeric `confidence` in [0, 1] or the parse returns `None` (`:238-246`). The intent goes through a dictionary of six names to four routes (`:40-47`). Confidence below the policy floor (0.75, `policy.yaml:5`) forces `fallback` (`:272-277`).

**How a turn ends in `fallback`.** Seven ways, with three of them indistinguishable in the eval:
1. Out-of-domain text (the wanted case): weather, jokes, "hello".
2. Stage 1 matches only the 0.30 rule and Stage 2 agrees.
3. Stage 2 confidence < 0.75 (`:275`).
4. Stage 2 intent not in the six-name map (`:272`).
5. Stage 2 reply cannot be parsed (`:225-247`).
6. No API key or no SDK (`:252-258`).
7. Stage 2 returns nothing usable and the graph falls back on `route or "fallback"` (`CC:graph/__init__.py:132`).

**What `fallback` does for the user.** The guardrail deflects when the intent is `out_of_domain` (or confidence is under 0.4 and the text looks like a weather question), otherwise asks one fixed clarifying question when confidence is under 0.75, or hands over to a human after `max_clarifications` (3) (`CC:guardrail.py:23, 59-118, 145-154`; `policy.yaml:6`). With no confidence at all (no key), it passes the turn through (`:48-56`). So fallback is a **soft failure**: the user gets a question, not a wrong answer. By reading, the hand-off after 3 clarifications probably cannot fire in a real session (7.

## 5. Why it was built this way (decisions and trade-offs)

| Decision | Alternatives | Why this one | Cost / risk |
|---|---|---|---|
| Rules first, LLM second | LLM for every turn; rules only | Clear cases cost nothing; unclear ones still get handled | Rules are brittle; here they decide only 30% of the test set |
| Highest-score-wins among matching rules | First match; combine scores | Simple, deterministic | Score is a priority, not a probability; one wrong rule hit on the eval set |
| Threshold 0.72 on rules | Calibrated on labelled data | Hand-set | Not tuned; no data behind the number |
| Self-reported LLM confidence with floor 0.75 | Log-probabilities; ensemble; no floor | Cheap and easy in one call ||
| Low confidence goes to `fallback`, not to a guess | Take the best guess | Wrong specialist is worse than a clarifying question | Over-abstains: 13 of the 18 non-fallback-labelled escalated rows ended in `fallback` in the Haiku arm, 14 in the Opus arm (my arithmetic from the confusion blocks) |
| Routes and thresholds in YAML | Hard-coded | New route without dispatcher changes (`tests/test_new_agent_extension.py`, *Review §5*) | Intent-to-route map is still in Python (`:40-47`) |
| Opus first (spec), Haiku after the eval | Keep Opus | "No measurable gain from the bigger model on this set" (README) | One run, 40 rows; Haiku default rests on a null result (see 7.3) |
| Only the current text goes to Stage 2 | Send history | Smaller prompt, lower cost | Follow-ups like "and in Phuket?" have no context; docs say the opposite |

## 6. Theory behind it (the "lecture" part)

### 6.1 Cascades and the reject option
A **cascade** chains classifiers of increasing cost: a cheap model decides when it is confident, and passes the rest to a stronger one. Let h be the share decided by the cheap stage, c₁ its cost, c₂ the cost of the strong stage. Expected cost per item is E[C] = c₁ + (1 − h)·c₂. The saving versus "strong stage always" is h·c₂ − c₁, positive whenever h > c₁/c₂. With c₁ ≈ 0, the saving is simply h·c₂.

A classifier with a **reject option** may answer "I don't know" instead of a class. Chow's rule: reject when the largest posterior is below a threshold τ, where τ is set from the cost of an error versus the cost of a rejection. If an error costs e and a rejection costs r (r < e), reject when max-posterior < 1 − r/e.

*In my project:* h = 12/40 = 30% on the test set, so the rules save 30% of the calls (my arithmetic: 28 calls instead of 40, **if** a hypothetical LLM-only arm used the same tokens per call). Rejection = `fallback`, which asks the user a question; a booking sent down the lookup path would be an error.

### 6.2 Selective classification: coverage versus accuracy
Plot **coverage** (share of items answered) against **accuracy on those answered**. Raising τ lowers coverage and raises accuracy on the answered part. A single accuracy number hides this trade. The honest report is a risk-coverage curve, or at least accuracy at a stated coverage.

*In my project:* the eval reports one overall accuracy where `fallback` counts as a correct answer for fallback-labelled rows, which is 100% in every arm (README says so). Abstention on a research or rag row counts as plain wrong. No risk-coverage view exists.

### 6.3 Calibration and verbalised confidence
A probability forecast p is **calibrated** if, among all cases where it says p, the event happens in a fraction p of them. Measure it with a reliability table (bins of p against observed accuracy) and the **expected calibration error** ECE = Σ_b (n_b/N)·|acc_b − conf_b|. Models that state a number ("confidence: 0.9") in text are **verbalised**-confidence systems: the number is generated like any other token, often clusters at a few values (0.85, 0.9, 0.95) and is not guaranteed to track accuracy. Alternatives: token log-probabilities where available, agreement across samples, or a trained calibrator on labelled data.

*In my project:* the floor 0.75 treats the model's number as a probability. With 28 calls and no stored confidences there is nothing to calibrate against.

### 6.4 Structured output versus regex extraction
Asking for JSON in free text and pulling it out with a regex is fragile: extra braces, code fences, two objects, or text after the JSON can break the greedy pattern; a wrong label name passes parsing and fails later. Better: a response schema with an **enum** of allowed values (structured output or a tool call with a strict schema), so the label vocabulary is enforced at the source and invalid labels cannot occur.

### 6.5 Rule systems: precision, coverage, priority
For a rule set, **coverage** = share of inputs where some rule fires; **precision** = share of firings that are right. Rules are usually high precision, low coverage. When several rules fire you need a conflict-resolution policy (priority, specificity, voting). A rule's "score" is a priority unless someone has measured its precision.

*In my project:* 4 rules, coverage 30%, precision 11/12 on 12 rows (very small sample; a 95% Wilson interval for 11/12 is about 65–99%).

### 6.6 Cost per decision and unit economics
Token price = tokens_in × p_in + tokens_out × p_out. For classification, input is mostly the fixed system prompt, so cost is almost fixed per call; **prompt caching** can cut the repeated prefix, but only above a model-specific minimum prompt length, which a ~157-token prompt is unlikely to reach (check the current documentation before relying on it). Model choice changes cost in two ways: price per token, and how many tokens it writes (verbosity). Report cost **per decision** and per **correct** decision, not only totals.

*In my project:* cost per escalated call is $0.00134 (Opus) vs $0.00041 (Haiku); per *correct* routing it is higher for both, since most escalations ended in `fallback`.

### 6.7 Fail-safe and failure-mode design
List every way a stage can fail and decide, for each, the safe default: missing key, SDK missing, API error, timeout, malformed output, unknown label, low confidence. The safe default for routing is usually "ask or hand over", never "guess". Make each failure **observable** (log the reason), or you cannot improve it.

## 8. Glossary

| Term | One-line definition |
|---|---|
| Stage 1 / Stage 2 | Regex rules (free) / one LLM classification call |
| Escalation threshold (0.72) | Minimum rule score needed to skip the LLM |
| Confidence floor (0.75) | Minimum model-reported confidence needed to use its route |
| Fallback | The "none of the above" route: clarify, deflect or hand over |
| Intent | The label the model returns; mapped to a route by a dictionary |
| Reject option | A classifier's right to abstain |
| Coverage / precision | Share of inputs answered / share of answers right |
| Calibration / ECE | Stated confidence matches observed accuracy / the average gap |
| Verbalised confidence | A number the model writes in its reply, not a measured probability |
| Cascade | Cheap stage first, expensive stage for the rest |
| Cost per decision | Tokens times price for one routing call; zero for a rule hit |
| Priority score | Rule score used only to break ties between matching rules |

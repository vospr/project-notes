# Course 10 · Chapter 10.3: LLM system design: latency, cost, caching, fallbacks, structured outputs, guardrails, observability

_Andrey Popov's project notes: how it works, why it was built this way, and the theory behind it._

## 2. The problem (business view, plain English)

A prototype that works on a laptop becomes a service with users, a budget, a response-time expectation, a security review and an auditor. The questions change from "does the model answer well?" to: how long does the user wait, what does one answer cost, what happens when the provider is down or slow, how do we stop a bad answer reaching a client, and how can we show later what the system did and why.

At a Swiss bank these are not optional extras. FINMA expects governance, an inventory with risk classification, tests and ongoing monitoring, documentation, and fallback solutions for material applications; for outsourced AI components it expects extra tests, controls and contract clauses (Guidance 08/2024; see 10.4). A design that cannot show cost per request, a kill switch, a trace per answer and a tested fallback will not pass the validation function.

Finance analogy: running a payments or trading system. Latency is settlement time; cost per request is cost per transaction; rate limits are exchange throttles; idempotency keys are the reason a retried payment instruction does not pay twice; a circuit breaker is a trading halt; the trace is the audit trail; the kill switch is the stop-trading button.

## 4. How it works (a whiteboard design for one banking use case)

**Use case.** An internal assistant for client advisors: answers questions about the bank's products, internal policies and compliance rules in German, French, Italian or English, with citations to the source paragraph. It does not access client accounts and does not give investment advice to clients; the advisor stays responsible. This is a plausible first use case because the risk is moderate (internal users, human in the loop, no automated customer decision), which matters for FINMA's materiality classification (10.4).

**Step 1: clarify requirements (say these out loud).**
| Question | Assumed answer (illustrative) |
|---|---|
| Users, volume | 2,000 advisors, 10 questions a day: 20,000 requests/day |
| Latency target | TTFT p95 under 2.5 s; full answer p95 under 10 s |
| Availability | 99.5% in business hours; degraded mode allowed |
| Data | Internal documents, classified internal/confidential; no client-identifying data in the prompt |
| Languages | DE, FR, IT, EN, questions and sources may differ in language |
| Hosting | Bank's approved cloud tenancy in Switzerland or the EU; provider under no-training terms; outsourcing assessment done (10.4) |
| Risk | Wrong answer could cause a compliance error; human reviews before action; materiality: moderate |
| Success | Answer accepted with citation by the advisor; measured by sampled review (10.1) |

**Step 2: estimates (Little's law and tokens).** Peak load: 20,000/day over a 9-hour day is 0.62 requests/s on average; assume a peak factor of 5, so about 3.1 requests/s. Concurrency L = lambda x W = 3.1 x 8 s, about 25 concurrent streaming responses. Tokens per request (assumed): 1,500 static instructions, 4,500 retrieved context plus question, 400 output. Peak token rate: 3.1 x 6,400 is about 20,000 tokens/s, about 1.2M tokens/minute, which must fit the provider's rate-limit tier (check current).

**Step 3: architecture.**
```
 Advisor UI (SSO) ─► API gateway: authN/Z, per-user + per-tenant rate limit, request id, kill switch
        │
        ▼
 Orchestrator (stateless service)
   1 input guard: language detect, PII/CID detector (block or mask), injection heuristics, scope check
   2 router: simple FAQ ─► small model;  complex/ambiguous ─► larger model;  out of scope ─► refusal template
   3 query rewrite ─► hybrid retrieval (ACL + validity-date filters) ─► rerank ─► context assembly   (10.2)
   4 LLM call: static prefix cached; structured output {answer, citations[], confidence, abstain}
   5 output guard: schema validate, citations exist and support claims, numbers appear in sources, no PII leak
   6 stream to UI (or buffer until validated)
        │
        ├─ fallback path: retry w/ backoff ─► secondary model/region (evaluated, approved) ─► retrieval-only results ─► "ask compliance"
        └─ trace + metrics + audit store (pseudonymised user id, retention limit)
 Offline: ingestion pipeline, eval suite in CI (10.1), shadow-mode comparison, monitoring dashboard, model inventory entry
```

**Step 4: deep dives (pick three, show numbers).**
- **Cost.** List prices (check current): Sonnet-class $2/$10 and Haiku-class $1/$5 per million input/output tokens. One request at 6,000 in and 400 out: Sonnet $0.012 + $0.004 = $0.016; Haiku $0.006 + $0.002 = $0.008. With the 1,500-token static prefix cached (read at about 0.1x): Sonnet $0.0003 + $0.009 + $0.004 = $0.0133, only 17% cheaper, because the dynamic retrieved context dominates (my arithmetic). Tiering: if 70% of requests are simple and routed to Haiku before the call, blended cost is 0.7 x 0.008 + 0.3 x 0.016 = $0.0104; with a cascade (try Haiku, escalate 30% on low confidence) it is 0.008 + 0.3 x 0.016 = $0.0128 because escalated requests pay twice. At 5M requests a year: about $80k at $0.016, about $52k at $0.0104, about $64k at $0.0128 (my arithmetic). Perspective: $0.016 is roughly half a second of an employee earning CHF 100 an hour, so token cost is small against engineering, review, evaluation and governance cost. Say that, then say why you still track it (scale, abuse, runaway loops).
- **Latency.** Total = queue + TTFT + output tokens / decode speed. Illustration: TTFT 0.9 s, 60 tokens/s, 400 output tokens gives 0.9 + 6.7 = 7.6 s. Levers: shorter answers, smaller model for simple questions, parallel retrieval and guardrails, caching the static prefix (lowers TTFT on long prefixes), streaming, avoiding extra LLM steps (each query rewrite or judge adds seconds). Hedge only on idempotent reads.
- **Security and permissions.** ACL filter inside the search; sentinel-document tests; retrieved text treated as untrusted (indirect injection); no tools with side effects; per-user rate limits; kill switch at the single call chokepoint (same pattern as `5.2-release-readiness.md`).
- **Failure modes.** Provider 429/5xx/timeout: backoff and retry within a budget, then fallback; both models down: show retrieved passages with a notice; guardrail unavailable: fail closed for confidential queries, fail open (with banner) only if the risk owner has agreed; poisoned or stale document: version and validity filters, deletion on supersede.

**Step 5: evaluation and rollout.** Offline golden set and regression suite (10.1); shadow mode on real questions with advisors not seeing outputs; pilot with 50 advisors and mandatory feedback; staged ramp; sampled human review of production answers; drift monitors on question mix, retrieval scores, abstention rate, thumbs-down rate.

**Step 6: governance.** Entry in the AI inventory with a materiality class; documented purpose, data, model choice, limitations, tests and fallback; independent review by a function separate from the builders; monitoring thresholds with named owners; change control for prompt and model changes (a prompt is code); exit plan for the provider (10.4).

## 5. Why it is built this way (decisions and trade-offs)

| Decision | Alternatives | Why this one | Cost / risk |
|---|---|---|---|
| Stateless orchestrator, state in stores | Sticky sessions in memory | Any instance can serve; scales horizontally; same reasoning as stateless MCP (`6.2-stateless-vs-stateful.md`) | History must be passed or loaded each call |
| Tiered models with a router | One strong model for all | Cost and latency down for simple questions | Router errors; two models to evaluate |
| Cache the static prefix, not the answers | Semantic answer cache | Safe: no wrong-answer reuse | Smaller saving when dynamic context dominates |
| Structured output with citations | Free text | Machine-verifiable; supports abstention | Schema design; more output tokens |
| Validate in code, fail closed | Trust the model | A model's output is untrusted input (`2.4-deliberation-loop-and-receipts.md`) | Some valid answers rejected |
| Bounded retries with jitter, then fallback | Infinite retry; no retry | Survives transient faults without a retry storm | Added latency in bad cases |
| Explicit, evaluated fallback (no silent switch) | Automatic provider swap | Behaviour change must be visible and approved (`5.1-architecture-i-joined.md`) | Needs a tested second path |
| Kill switch at one chokepoint | Per-feature flags | One place to stop all LLM calls (`5.2-release-readiness.md`) | Coarse; define fail-open vs fail-closed |
| Per-request trace with ids, not full prompts by default | Log everything | Audit without hoarding personal data | Debugging needs a gated "debug capture" mode |

## 6. Theory (the lecture)

### 6.1 Latency
A request's wall time = network + queueing + **prefill** (processing the input; grows with input length) + **decode** (generating output tokens one after another). **TTFT** (time to first token) is dominated by queueing and prefill; **decode speed** is tokens per second per stream. So T_total ≈ TTFT + N_out / v, where v is decode speed. Output length matters most, because decode is sequential: halving the answer length nearly halves the decode time.

**Streaming** sends tokens as they are generated: the user sees the first words after TTFT. It does not reduce T_total. **Chains**: sequential steps add; independent steps can run in parallel (retrieval and guardrails). **Tails**: with k parallel calls each with a 5% chance of being slow, the chance that at least one is slow is 1 − 0.95^k (k = 4 gives 18.5%, my arithmetic). Report p50, p95, p99, not the mean. **Capacity**: Little's law, L = lambda x W (concurrent requests = arrival rate x time in system). **Levers**: smaller model, shorter output, fewer sequential LLM calls, cached prefix, regional proximity, speculative decoding (provider side), batching for offline work.

*In my project:* the deliberation run is four sequential calls, about 22-27 s per run (N = 3; `2.3-llm-access-and-cost.md`); no latency was measured in the routing eval (`7.3-building-a-routing-eval.md`).

### 6.2 Cost
Per request: C = (t_in − t_c)·p_in + t_c·p_cr + t_out·p_out (+ t_cw·p_cw for tokens written to the cache), with t_c cached-read tokens, p_cr about 0.1 p_in and p_cw about 1.25 p_in for a short-lived cache on the public price structure (check current). Output usually costs several times input per token (5x for the rows above), and "reasoning" or "thinking" tokens are billed as output. Agents and chats re-send the context every turn, so cost grows with turns: if context starts at c0 and grows by d per turn, input over T turns is T·c0 + d·T(T + 1)/2, quadratic in T (`8.1-context-engineering.md`).

**Tiering / cascade.** Pre-routing: C = s·C_big + (1 − s)·C_small + C_router, where s is the share sent to the big model. Cascade: C = C_small + p_esc·C_big (+ judge cost): the escalated share pays twice. Cascade needs a reliable confidence signal; a model's self-reported confidence is not a calibrated probability (`7.2-rules-then-llm-routing.md`). Break-even: the router is worth it if the saved big-model cost exceeds router cost plus the value of extra errors. Other levers: **batch APIs** for non-urgent work (often a discount of about half; check current), shorter prompts, structured short outputs, smaller embeddings, and budgets/quotas.

**Total cost of ownership.** Add evals and judge calls, embeddings, reranking, vector store, logging, engineering time, review and governance effort. Report cost per request, per successful task, and per user.

*In my project:* the formula, `Decimal`, "computed not billed", and the finding that a 5x price gap became a 3.3x measured gap because of output verbosity (`2.3-llm-access-and-cost.md`, `7.3-building-a-routing-eval.md`).

### 6.3 Prompt caching
The provider stores the processed state of a prompt **prefix**; a later request with an identical prefix reuses it: cheaper (cache reads at a fraction of normal input price) and faster to first token. Rules: the prefix must match exactly, token for token, and in order; so put **static content first** (system prompt, policies, tool definitions, few-shot examples), then semi-static, then dynamic (retrieved chunks, user question). There is a minimum prefix length and a time-to-live (for example minutes, with longer options at a different price; check current). A cache **write** costs more than a normal input; a **read** costs much less. Break-even per unit of prefix: one write plus n reads costs 1.25 + 0.1n against 1 + n without caching, so with one reuse (n = 1) it is 1.35 vs 2.0 (my arithmetic): it pays after the first reuse. It does not help when the prompt is mostly dynamic.

*In my project:* cache-read is 98.7% of token volume in the measured ticket, and it is the allocation key in chapter 3.3 because it exists for every session (`3.5-cost-anatomy-of-one-ticket.md`).

### 6.4 Semantic caching and its risks
A semantic cache embeds the incoming question and returns a stored answer if a previous question is within a similarity threshold. It can cut cost and latency for repeated, public, low-stakes questions. Risks, each with a bank example:
- **False hits.** "What is the mortgage rate for 80% loan-to-value?" vs "...for 66%". Embeddings treat numbers, negations and entities as small differences.
- **Staleness.** Rates, fees and policies change; the cache holds yesterday's rule.
- **Cross-user leakage.** An answer built from user A's permitted documents is served to user B. Cache keys must include tenant, role and document-permission scope.
- **Personal data in the cache** (retention, deletion rights).
- **Poisoning.** An attacker plants a bad answer under a popular question.
- **Silent drift.** After a prompt or model change, cached answers keep the old behaviour.
Mitigations: use exact-match caches for deterministic keys; restrict semantic caching to public FAQ content; short TTL; include a version and permission scope in the key; verify entities and numbers match; monitor hit-quality by sampling. In a regulated setting the default answer is "do not cache generated answers about rules or client-specific content".

### 6.5 Retries, timeouts, fallbacks and idempotency
**Classify errors.** Retry: timeouts, connection resets, 429 (rate limit), 500/502/503/529 (overloaded). Do not retry: 400/401/403/404, validation errors, content-policy blocks. **Backoff with jitter.** Delay_k = random(0, min(cap, base·2^k)) ("full jitter"); honour `Retry-After`; cap attempts (for example 3) and total time; use a **retry budget** (a retry may only be, say, 10% of traffic) so retries cannot amplify an outage. **Timeouts** at every hop, with the sum below the user-facing SLO. **Circuit breaker:** after repeated failures stop calling for a cool-down, then probe.

**Idempotency.** A retry may repeat a request that actually succeeded. For pure reads (an LLM call is one) that only wastes money; for side effects (send e-mail, create ticket, book) attach an **idempotency key** chosen by the caller, stored by the server; a repeat with the same key returns the stored result. Distinguish this from **replay protection**, which rejects a repeated one-time token (`2.2-auth-first-gateway.md`). Order matters: if the replay check runs before the idempotency check, a legitimate retry is rejected as a replay (a gap I found in my own gateway, same note).

**Fallbacks.** Ladder: same model, retry, a second region or provider, a smaller model, a degraded feature (retrieval results only, canned answer), a human. Conditions: each rung evaluated and approved (behaviour, residency, contract), the switch logged and visible in the response metadata, and an alert. **Hedged requests** (send a second copy after a delay) cut tail latency but double cost; use for idempotent reads only. **Graceful degradation** beats an error page.

*In my project:* explicit provider switch with no silent fallback (`5.1-architecture-i-joined.md`); fallback as a routing outcome with hand-off after three tries (`7.2-rules-then-llm-routing.md`); booking idempotency key (`6.2-stateless-vs-stateful.md`); retry and truncation handling are weak points I recorded (`2.3-llm-access-and-cost.md`).

### 6.6 Rate limits and capacity
Providers limit requests per minute (RPM), input tokens per minute (ITPM) and output tokens per minute (OTPM) per organisation or key, by tier (check current). Exceeding gives 429. Client side: a **token-bucket** limiter (capacity b, refill rate r: allows bursts up to b, long-run rate r), a queue with priorities (interactive before batch), per-user and per-tenant quotas, and spend caps that stop a runaway loop. Capacity planning: peak requests/s x tokens per request vs limit; keep 30-50% headroom; move batch work to off-peak or a batch API.

*In my project:* per-key budgets existed in the gateway but were spend-blind; the deliberation path had a token and time budget but no dollar cap (`2.2-auth-first-gateway.md`, `2.3-llm-access-and-cost.md`).

### 6.7 Structured outputs and validation
Free text is hard to check. Ask for JSON that matches a schema. Levels of guarantee: (1) prompt only ("reply as JSON"): often works, can fail; (2) **JSON mode**: syntactically valid JSON; (3) **constrained decoding / structured outputs**: decoding is limited to tokens that keep the output valid against a schema, so shape is guaranteed (provider-specific; check current); (4) **tool/function calling**: the model returns arguments for a declared function. In all cases validate in code (Pydantic, JSON Schema) and also validate **semantics**: ranges, enumerations, cross-field rules (currency with amount), citations that exist, numbers that appear in the sources. On failure: one bounded repair attempt (feed back the error), then fail closed with a typed reason. Watch **truncation** (`stop_reason` = length yields broken JSON) and **refusals**. Streaming structured output needs a partial-JSON parser or buffering.

*In my project:* prompt-constrained JSON validated by Pydantic with `extra="forbid"`; all errors fail closed to `escalate`; truncation flagged but not acted on; provider structured output not used (`2.4-deliberation-loop-and-receipts.md`, `2.3-llm-access-and-cost.md`).

### 6.8 Guardrails
Guardrails are controls around the model, in layers (defence in depth):
- **Input:** authentication; scope check; PII or client-identifying data detection (block, mask or route to a safer path); prompt-injection heuristics or classifier; size limits.
- **Retrieval/data:** permission filters; source allow-lists; treat content as untrusted.
- **Model:** system prompt as guidance only; least-privilege tools; no secrets in the prompt.
- **Output:** schema validation; grounding and citation checks; PII leak scan; policy and tone checks; required disclaimers; numeric checks.
- **Action:** human approval for side effects; per-action limits; audit.
- **Operational:** rate limits, budgets, kill switch, monitoring.
Each guardrail has a **false-positive/false-negative** trade-off and adds latency and cost, so it needs its own evaluation (a labelled set of attacks and benign cases). Reference lists: OWASP's Top 10 for LLM applications (prompt injection, sensitive information disclosure, excessive agency, and so on; check current edition), and the NIST AI Risk Management Framework as a governance vocabulary (check current). Text in a prompt is not a control (`5.5-my-ai-delivery-method.md`).

*In my project:* the kill switch, fail-closed validation and the deflection of out-of-domain intents are my examples (`5.2-release-readiness.md`, `2.4-deliberation-loop-and-receipts.md`, `7.2-rules-then-llm-routing.md`).

### 6.9 Observability
Monitoring a normal service uses logs, metrics and traces. An LLM application adds content quality and cost. A **trace** is a tree of **spans** for one request: gateway, guard, rewrite, retrieval, rerank, each LLM call, tool call, validation. Record per span: request id, parent span, model id and version, prompt version, tokens in/out/cached, TTFT and total latency, finish reason, cost, retry count, cache hit, retrieved chunk ids and scores, guardrail verdicts, error type. OpenTelemetry has emerging semantic conventions for generative AI spans (check current). **Metrics:** request rate, error and retry rate, p50/p95/p99 latency, cost per request and per user, cache hit rate, abstention rate, guardrail block rate, user feedback, judge-score sample over time. **Alerts:** cost spike, latency SLO breach, fallback usage, drift in input mix. **Privacy:** log ids and hashes by default; store full prompts only in a gated, short-retention store; pseudonymise users; remember that logs are personal data under the FADP (10.4). **Replayability:** with versions and inputs recorded, you can replay a failing request against a new prompt (and add it to the regression suite).

*In my project:* the receipt is a per-run audit record with calls, tokens, cost and stop reasons and a SHA-256 content hash; the notes are explicit that a hash is not a signature (`2.4-deliberation-loop-and-receipts.md`); the measurement toolkit counts tokens by bucket and reconciles them (`3.5-cost-anatomy-of-one-ticket.md`).

## 8. Glossary

| Term | One-line definition |
|---|---|
| TTFT | Time to first token: delay before the first output token appears |
| Prefill / decode | Processing the input / generating output tokens one by one |
| Streaming | Sending tokens to the client as they are produced |
| Little's law | Concurrent requests = arrival rate x time in system |
| Prompt caching | Reusing the processed state of an identical prompt prefix |
| Semantic cache | Reusing a stored answer for a similar question, by embedding similarity |
| Cascade / routing | Sending requests to cheaper or stronger models by difficulty |
| Backoff with jitter | Waiting a randomised, growing time between retries |
| Retry budget | Cap on retries as a share of traffic |
| Circuit breaker | Stops calling a failing dependency for a cool-down period |
| Idempotency key | Caller-chosen ID so a repeated request has one effect |
| Replay protection | Rejecting a repeated one-time token |
| Token bucket | Rate limiter allowing bursts up to a capacity at a fixed refill rate |
| Constrained decoding | Limiting generation to outputs valid under a schema |
| Guardrail | A control outside the model that limits inputs, outputs or actions |
| Trace / span | One request's tree of timed steps / one step in it |
| Kill switch | Operator control that stops a capability quickly |
| Hedged request | A duplicate request sent after a delay to cut tail latency |

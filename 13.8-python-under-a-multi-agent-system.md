_Andrey Popov's project notes: how it works, why it was built this way, and the theory behind it._

**In short:** Python memory and data types in agent teams: names as pointers, why steps return updates, state as plain data, merge rules for parallel branches, async and the GIL, and the three memory systems (bytes, tokens, rows).

## 2. The problem (business view, plain English)

When people say "the agent team is using too much memory" or "the team behaves strangely", they mix up different things. Python decides how data is stored, shared, copied and saved. In a multi-agent system, **many agents touch the same data at the same time**, and the state must be **saved to a database** so a run can pause for human approval and resume tomorrow. Python habits that are harmless in a small script (sharing a list between functions, keeping a database connection in a variable) turn into real bugs there: a helper silently changes the lead's data, a run can't be saved, two branches overwrite each other, or the bill triples without anyone noticing.

Analogy: a shared whiteboard in a team room. If everyone can erase and rewrite the same line, you get chaos. The fix is rules: write only your own line, add new lines at the bottom, and take a photo (checkpoint) after each round.

## 4. How it works

### 4.1 Names are pointers, not boxes
In Python a variable is a **label pointing to an object**. `b = a` does not copy the data, it adds a second label to the same object.
```python
a = [1, 2, 3]
b = a
b.append(4)
print(a)      # [1, 2, 3, 4]  -> both labels point to the same list
```
**Why agents care:** if two agents (or two parallel branches) receive the same list or dictionary and one edits it, **everyone sees the change**. That is why frameworks make each step **return an update** (a small piece of new data) and let the framework apply it: LangGraph nodes return partial updates; Google ADK records changes as events/deltas. The rule: **don't edit shared data in place; return what changed.**

Related trap, the shared default:
```python
def add(item, bucket=[]):      # one list created once and reused by every call
    bucket.append(item)
    return bucket
```
Every call without a bucket shares the same list. In an agent system that means one run's data leaking into another run's.

### 4.2 Which data types, and what they cost
| Type | What it is in memory | Good for | Watch out |
|---|---|---|---|
| `str`, `int`, `float`, `bool`, `None` | single immutable objects | simple fields | Immutable: "changing" makes a new one |
| `list` | an array of **pointers** to objects (not the objects themselves) | messages, findings in order | Appending at the end is cheap, inserting at the front is slow; grows without limit if you let it |
| `dict` | hash table (key → pointer) | state, JSON-like records | Keys must be immutable; lookups are fast |
| `set` | hash table of unique items | "already seen" checks | Unordered |
| `tuple` | fixed array of pointers, immutable | fixed records, dictionary keys | Can't be changed |
| `deque` | double-ended queue | "keep only the last N messages" | Not a list; slicing differs |
| `dataclass`, Pydantic model | named fields with types (Pydantic also validates) | agent state, tool inputs and outputs | Pydantic validation costs a little time |
| `TypedDict` | a dict with a declared shape | LangGraph-style state | Types are only checked by a type checker |
Because a list holds pointers, `sys.getsizeof(list)` measures only the array of pointers, not the messages inside. Memory in agent systems grows because we **keep adding**, not because of Python's overhead.

### 4.3 "State is data, not objects"
To pause a run (for approval, or after a crash) the framework **saves the state** to a database after each step and can load it later, even in another process. Only plain data survives that trip.
| Can be saved | Cannot be saved |
|---|---|
| text, numbers, true/false, nothing | database connections, HTTP clients, sockets |
| lists and dictionaries of those | functions, lambdas, generators, threads |
| dates, enums, dataclasses (with a serializer) | open files, **model clients**, anything holding a live resource |

So: put **plain data in state**; put **clients, connections and credentials in config/context** (rebuilt at startup). Three vendors do the same thing for the same reason: LangGraph's checkpointer, Agent Framework's checkpoint storage, ADK's session state plus a separate memory service.

Consequence: human-in-the-loop is not a special feature. It is what you get **for free** once every step is a saved row.

### 4.4 Two agents write to the same key: merge rules
When two parallel branches write to the same piece of state, the system needs a rule, otherwise one silently wins.
| Meaning of the key | Merge rule | Example |
|---|---|---|
| Collect everything | append | findings from each researcher |
| "Have we seen it?" | union of sets | visited sources |
| Best so far | max | highest confidence |
| One owner | last write wins | current topic |
In LangGraph these are declared per key. In team design, ask for **every field**: who owns it, and how are parallel writes merged? This is a data-structure decision wearing a concurrency costume. (Order inside an appended list from parallel branches is **not guaranteed**: don't depend on it.)

### 4.5 Why `async`, and what the GIL changes
- Agent work is mostly **waiting** (model calls, tools, network). `asyncio` lets one thread juggle many waiting tasks, which is why Agent Framework, ADK and LangGraph are async-friendly.
- The **GIL** lets only one thread run Python code at a time, so threads don't speed up CPU-heavy work. That rarely matters for agents.
- **Python 3.14** officially supports an optional no-GIL build (PEP 779); the standard build stays the default and some libraries lag. For agents that wait, little changes.
- Never put a **blocking** call inside an async step: it freezes every other agent sharing that loop.

### 4.6 The three memory systems (the key diagram)
| System | Unit | Where | Grows with | Fails as | Control by |
|---|---|---|---|---|---|
| **Process memory** | bytes | RAM | objects kept alive | out-of-memory, slow garbage collection | trimming, `__slots__`, generators |
| **Context window** | tokens | every model call | history + tool results **re-sent each call** | cut-off, cost, slow, worse answers | summarise, trim, retrieve, files |
| **Saved state** | rows / bytes | checkpoint database | steps × state size | disk growth, slow resume | keep state small, prune history |
They don't grow together: tiny RAM with a huge context is normal. **Say the unit** before saying "too much memory".

**The multiplier:** one message appended to state costs you **three times**: it sits in RAM, it is **re-sent in every later model call**, and it is **re-saved on every step**. Tool outputs are the usual culprit.

**Teams multiply it again:** if the lead passes the whole history to N helpers, you pay the context cost N times (13.2, 13.4). Passing a brief and a file pointer is a memory decision as much as a design one.

### 4.7 Why "append only" is also a price decision
Prompt caching matches a **prefix**: if the start of the conversation stays byte-identical, the provider reads it from cache at a fraction of the price (about 0.1× in my notes) and you pay to write only the new tail. If you **edit** earlier messages (summarise the front, inject a timestamp at the top), everything after the edit is billed at full price again. So the same rule as 4.1, "don't edit, append", is a **correctness** rule in Python and a **cost** rule in billing. Check the provider's usage fields (cache read vs cache creation tokens) to verify.

### 4.8 The orchestrator is a graph
Agent systems are **graphs**: steps are nodes, hand-overs are edges. Frameworks store them as sparse maps (adjacency lists). Frameworks like LangGraph run in **supersteps**: all ready steps run, then state merges, then the next step. Cycles need a limit (recursion limit, maximum rounds) or the run never ends. Agent Framework's "sequential / concurrent / handoff / group chat" (13.3) are graph shapes with names.

## 5. Why it was built this way (decisions and trade-offs)

| Decision | Alternatives | Why this one | Cost / risk |
|---|---|---|---|
| Steps return updates, framework merges | Steps edit shared state directly | Safe with parallel branches; easy to record and replay | Slightly more code |
| Plain-data state, clients in config | Keep everything in one object | State can be saved, resumed, inspected | Must rebuild clients on resume |
| Per-key merge rules | Last write wins everywhere | Parallel branches don't silently overwrite | Must think about each key |
| Async steps | Threads per agent | Cheap waiting for many agents | Blocking calls are dangerous |
| Bounded history (trim/summarise) | Keep everything | Controls tokens, cost and save time | Can lose detail; may break caching |

## 6. Theory behind it (the "lecture" part)

### 6.1 Mutable vs immutable
An immutable object cannot change after creation (`str`, `int`, `tuple`); a mutable one can (`list`, `dict`, `set`). Sharing mutable objects between parts of a program is the root of most "who changed this?" bugs.
*In this chapter:* return updates, copy when you must change.

### 6.2 Reference counting and garbage collection
Python frees an object when nothing points to it (reference count zero); a separate collector cleans up cycles (parent ↔ child). Real agent memory problems are almost never the collector; they are **unbounded accumulation** that nothing trims.
*In this chapter:* §4.6 first row.

### 6.3 Serialization and the trust boundary
Turning objects into bytes (JSON, MessagePack, pickle) loses anything that isn't pure data. Formats that can rebuild arbitrary objects (pickle) are also a security risk when loading untrusted data; newer frameworks restrict deserialization to an allowed list of types.
*In this chapter:* §4.3; that is a security posture, not a speed one.

### 6.4 Concurrency models
Threads share memory and need locks; processes don't share memory and talk by messages; `async` runs many tasks on one thread by switching at waits. Agent teams fit "no shared memory, send messages" best.
*In this chapter:* §4.5, and why handing over files and briefs beats sharing live objects (13.4).

### 6.5 Big-O where it actually bites
An orchestrator that **re-saves the whole state on every step** has cost growing with (steps × state size). Let the message list grow without limit and a linear design becomes quadratic.
*In this chapter:* the third cost of the multiplier in §4.6.

## 8. Glossary

| Term | One-line definition |
|---|---|
| Reference / alias | A second name pointing to the same object |
| Mutable / immutable | Can / cannot be changed after creation |
| Shallow copy | A copy of the outer container that still shares the inner objects |
| Checkpoint | A saved snapshot of the run's state |
| Serialization | Turning objects into bytes or text for storing or sending |
| State | The shared data of a run, saved at each step |
| Config / context | Things the run needs but that are not saved: clients, credentials |
| Reducer | A per-key rule for merging parallel updates |
| Superstep | One round: all ready steps run, then state merges |
| GIL | Lock letting one thread run Python code at a time |
| `asyncio` | Python's event loop for many waiting tasks |
| Context window | Everything the model sees in one call, measured in tokens |
| Prompt cache | Provider-side reuse of an unchanged prompt prefix at lower price |
| `deque` | Double-ended queue; good for "keep last N" |
| `__slots__` | Declaration that makes small objects use less memory |

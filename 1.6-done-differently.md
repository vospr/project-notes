## 2. The problem (business view, plain English)

"What would you do differently?" is a seniority test. A junior says "nothing" or lists tools. A senior names the **specific cost** of each choice and the cheaper way to get the same assurance.

Finance analogy: a post-implementation review after a model migration. You ask five questions. Did we back-test the logic on constructed cases (unit tests)? Did we fix the interface spec between teams (contracts)? Did we reconcile old against new on pinned inputs (data diff)? Did we set a stop-loss before trading (cost caps)? Did we release in small clips or one block trade (merge small)? My project passed the reconciliation question well (Ch 1.3) and was weaker on the other four. This chapter is that review, with evidence.

## 6. Theory behind it (the "lecture" part)

### 6.1 The testing pyramid for data, and the dbt unit test
Software testing has a pyramid: many fast **unit** tests, fewer **integration** tests, few slow **end-to-end** tests. Data work has the same shape, but three different things get called "tests":

| Kind | Input | Asks | Catches | Example here |
|---|---|---|---|---|
| Unit test | Constructed rows | Is the **logic** right? | Wrong branch, NULL handling, type bugs | Not found in the sources |
| Data test | The real table | Is the **data** healthy? | Duplicates, NULL keys, bad values | 148 tests (A), 52-60 (B) |
| Parity / diff | Old vs new output | Did the output **change**? | Regressions | Ch 1.3 gate |

A unit test needs an **oracle**: the expected output you wrote by hand. Coverage for logic is by branch. For a predicate with *n* conditions, MC/DC coverage needs at least *n* + 1 cases, which is the rule I used for Rule 3 in Ch 1.4 §6.4. In dbt (1.8+, *check*) a unit test is YAML: the model, `given` rows for each `ref`/`source`, and `expect` rows. It runs with `dbt test` on small inline data, so it costs almost nothing in BigQuery. Practical limits: you must supply the inputs' columns or have empty upstream tables; arrays and structs need care in fixtures; it proves logic, not real-data behaviour; run it in dev and CI, not production.

The key property: **unit tests do not need live data**. That is exactly the gap *VAL* describes ("current snapshot has no aligned rows").
*In my project:* 0 unit tests found; A.

### 6.2 Contracts: interface specs between producer and consumer
An interface contract is a promise about the **shape** of a producer's output: column names, types, nullability. A change is **breaking** if a consumer built on the old schema S can fail on the new schema S′. Removing or renaming a column, changing a type incompatibly, or loosening nullability are breaking; adding a column is not. Two styles: **producer-enforced** (the producer cannot build a table that violates the declared schema) and **consumer-driven** (each consumer states what it needs; tools like Pact test that). A dbt model contract is producer-enforced: `contract: {enforced: true}` plus column names and `data_type` (dbt 1.5+, *check*); the build fails if the SELECT does not match. It checks shape only, not values. In BigQuery most constraints are not enforced by the engine, so uniqueness stays a test. A **schema contract** is not a **data contract**: the latter adds semantics, freshness and ownership.

*In my project:* the three terminal marts are the interface to the batch loader (*VAL*: the loader reads the final candidates-per-position table). The hand-reconciled INFORMATION_SCHEMA table was a contract written after the fact.

### 6.3 Data-diff methods
Let A be the old output and B the new one. Methods, cheapest first:
1. **Profile diff:** row counts, NULL rates, distinct counts, quantiles, schema. Cheap, catches gross change. My row-count sentinel is this.
2. **Set diff:** (A \ B) ∪ (B \ A) with `EXCEPT`. Needs a sort or shuffle of whole rows; memory grows with N. This is the `audit_helper` OOM. Set semantics also hide duplicate counts (Ch 1.3 §6.2).
3. **Keyed diff:** FULL OUTER JOIN on a primary key, then label each key *added*, *removed* or *changed* and count changed columns. One join, interpretable. Needs a real key (the near-key problem, *A-*).
4. **Checksum bisection** (the idea behind open-source `data-diff`): hash key ranges, compare hashes, recurse only into ranges that differ. Cost is about O(d log N) transferred for d differences. It wins across databases; inside one warehouse a keyed join is usually simpler.
5. **Tolerance and distribution tests** for floats: absolute or relative tolerance; PSI or KS for distributions (Ch 1.3 §6.4).

The comparison is only meaningful if inputs are identical. Observed difference = refactor effect + source drift + numeric noise (Ch 1.3 §6.3). Three controls: **pin inputs** (BigQuery table snapshots, or `FOR SYSTEM_TIME AS OF` within the time-travel window, 7 days by default, *check*), a **control build** (same code twice), or **parallel builds** to shrink the gap. Pinning is the only one that can give a true zero.

A **PR-level data diff** automates this: CI detects changed models (`state:modified+`), builds them into a per-PR schema from pinned inputs, diffs against the baseline built from the same pin, and posts row-count and column-change summaries on the PR. Also separate **test** from **report**: a test has a binary expected result and can gate CI; a diff under drift is a report. Mine ran as tests that were expected to fail.
*In my project:* *PROP* wanted this; I built a hand-made macro and baseline datasets instead.

### 6.4 Cost control in BigQuery on-demand pricing
**On-demand** cost = bytes read by the query × a price per TiB (about $6.2 per TiB at the time I last knew; first 1 TiB per month free; *check the current list*). Bytes depend on the **columns referenced** and on partition or cluster pruning, not on `LIMIT` or rows returned. Capacity pricing charges slot-hours with a configurable maximum, so a ceiling exists on compute but bytes no longer set the bill. Basic arithmetic: 1 TiB = 1024 GiB, so about 19,000 GiB = 18.14 TiB.

Controls, in order of when they act:
- **Estimate.** A **dry run** returns an upper bound of bytes, no charge. A pipeline estimate is simply Σ over runs of Σ over models of measured bytes: *precedent × multiplicity*. Step 2 was two full builds, so "2 × 18.2 TiB".
- **Per-query cap.** `maximum_bytes_billed` makes a query fail, with no charge, if its estimate exceeds the limit. dbt-bigquery exposes it as a profile setting. It bounds **one query**, not the number of queries.
- **Aggregate cap.** Custom quotas on "query usage per day" per project or per user, and a reservation with a maximum slot count. **Budgets and alerts only notify**, and they lag.
- **Attribution.** Job labels (dbt query comments) and the `INFORMATION_SCHEMA.JOBS*` views. They need permissions; the missing grant here forced parsing `bq ls -j`, capped at about 4,000 jobs.
- **Reduce.** Partition and cluster, incremental builds on a reliable watermark (Ch 1.2), test on cloned slices, `--defer` and `--empty`.
- **Cancel is not undo.** Cancelling a dbt run left running BigQuery jobs; 14 had to be cancelled by hand and bytes already processed were billed.

*What a per-query cap would have done here, by my analysis.* The largest single model scan was about 5.4 TiB (*F-COST* Plan B table). A about $180 step was about 723 queries, each below that; a cap set above 5.4 TiB passes all of them. The about $48 leak was an approval and hand-off error, not one big query. Only the one outlier job of 38.76 TiB (another developer, same project and day, *F-*) would have been refused by a cap of, say, 10 TiB. So the real fix for my overruns is the **estimate-from-precedent gate** plus a **daily quota**, with the per-query cap as a backstop.
*In my project:* every row of the ledger in section 4, item 4.

### 6.5 Small batches, trunk-based development, and why joint merges fail
**Little's law:** work in progress = throughput × cycle time. If throughput is fixed, a bigger batch means a longer cycle time and later feedback. Large batches also raise variance, risk and the cost of delay (Reinertsen). **DORA** measures delivery with four keys: deployment frequency, lead time for changes, change failure rate, time to restore. Small, frequent changes improve all four. **Trunk-based development** means short-lived branches merged often. **Stacked PRs** keep a chain small when work depends on the previous piece.

Why a joint merge of *k* changes is fragile: if each is fine with probability *pᵢ*, all are fine with ∏ pᵢ. With four MRs at 0.9 each that is 0.9⁴ ≈ 0.66 (an illustration, not a measurement). One blocking comment holds all four. A squash-merge of 8 checkpoints reverts as one unit, so a bug in the lowest-risk-looking piece removes the rest. Review quality drops with size (commonly cited: defect finding falls past a few hundred lines per review, *check*). Unmerged work is inventory: it delivers nothing, ages against `develop`, and is lost if the author leaves, which is what happened.

The tension: my proof method was a **build** (about 10 min, about $2.5 per pipeline run at about $5/TiB), so many small MRs would multiply cost. The way out is to use the **free layers first**: compile-diff (byte-identical SQL, zero data cost, Ch 1.3 Layer 1) and unit tests need no warehouse bytes. Mechanical, behaviour-preserving MRs can ship on those alone; only behaviour-changing ones need a data diff.
*In my project:* A, B, C, F as one review package; F could have gone alone.

## 8. Glossary

| Term | One-line definition |
|---|---|
| Unit test (dbt) | YAML test with fixed input rows and expected output rows for one model |
| Data test | A check on the real table: unique, not-null, accepted values |
| Oracle | The known-correct expected result a test compares against |
| MC/DC | Branch coverage rule: at least *n* + 1 cases for a predicate with *n* conditions |
| Model contract | Enforced list of a model's column names and types; the build fails on mismatch |
| Breaking change | A schema change that can make an existing consumer fail |
| Data diff | Comparison of two table versions by key, with per-column change counts |
| Source pinning | Reading inputs as of a fixed time (snapshot or time travel) |
| Time travel | BigQuery's ability to read a table as of a past time within its retention window |
| Dry run | A BigQuery request that returns estimated bytes without running or billing |
| `maximum_bytes_billed` | Per-query limit; the query fails, free, if its estimate is higher |
| Custom quota | Daily limit on query usage per project or user |
| On-demand vs Editions | Pay per TiB read vs pay per slot-hour |
| Batch size | Amount of change delivered per merge |
| Trunk-based development | Short-lived branches merged to the main line often |
| Stacked PRs | A chain of small PRs, each based on the previous one |
| DORA metrics | Deployment frequency, lead time, change failure rate, time to restore |

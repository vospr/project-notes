# Course 13 · Chapter 13.10: Keeping a team of agents safe, controlled and measurable

_Andrey Popov's project notes: how it works, why it was built this way, and the theory behind it._

**In short:** Controls for agent teams: least privilege, separation of duties, caps, approvals, injection defence, kill switches, per-step logging with receipts, and how to evaluate a team by outcome, cost and time.

## 2. The problem (business view, plain English)

A single agent can make a mistake. A team can make the same mistake **in parallel**, **pass it along**, **loop on it** and **bill you for every round**. The risks multiply: more tools, more permissions, more places where untrusted text enters, more cost, more places to hide a bug. Without controls, nobody can answer simple questions: what did the agents do, who allowed it, what did it cost, and did it work?

Analogy: letting five new staff handle company money. You give each only the access their job needs, set spending limits, require a second signature for large items, keep a ledger, and check the results.

## 4. How it works

### 4.1 What goes wrong in a team
| Failure | Plain description |
|---|---|
| **Runaway loops** | Agents keep handing work back and forth, or re-planning, until the budget is gone |
| **Prompt injection** | Text in a web page, file or another agent's reply tells an agent to do something the user never asked |
| **Over-permission** | An agent that only needs to read can also write, send or delete |
| **Silent failure** | An agent can't use a tool and **makes up an answer** instead of failing loudly |
| **Conflicting work** | Helpers make incompatible choices (13.2) |
| **Cost blow-up** | Full history passed to every helper; groups of agents debating at length |
| **Unverifiable "done"** | The agent says finished; nobody can prove it (13.4, 13.7) |
| **Data leakage** | Personal or confidential data sent to a helper or a remote agent that shouldn't get it |

### 4.2 The controls, in the order I'd add them
| # | Control | What it does | Example |
|---|---|---|---|
| 1 | **Least privilege** | Each agent gets only the tools and rights its job needs, enforced by the platform not by the prompt | Planner can read and write specs but not application code; verifier can run tests but not edit files; deploy rights only for the release agent |
| 2 | **Separation of duties** | The checker is not the author | Verify agent cannot fix, only report |
| 3 | **Caps** | Limits on rounds, tokens, time, tool calls, spend per run and per day | Max 8 rounds in group chat; stop after "no progress" twice |
| 4 | **Human approval for irreversible actions** | The run pauses until a person approves | Sending email, merging, deploying, paying, deleting |
| 5 | **Validation of every hand-over** | Typed results; reject and retry malformed ones | `status` must be done/blocked/failed (13.4) |
| 6 | **Untrusted-input handling** | Treat web pages, files, tool results and other agents' replies as data, never as instructions | Strip or flag instructions in retrieved text; no tool access to untrusted-content agents |
| 7 | **Data minimisation** | Send each agent / remote agent only what it needs | Remove personal data before calling an outside agent (13.6) |
| 8 | **Kill switch and circuit breaker** | Stop one agent or all, and stop calling a failing tool | Feature flag; stop after N consecutive errors |
| 9 | **Identity per agent** | Separate identity so logs show which agent acted | Entra identity for each agent (13.5) |

Rule: **rules in code and platform settings, not only in prompts.** A prompt is a request; a permission is a lock.

### 4.3 What to record (observability)
For every step of every agent:
- run id, step id, **attempt number** (retries must not double count)
- agent name and identity, model used
- inputs (or a hash), outputs, tool calls and their results
- tokens in/out (including cache reads), cost, time
- the **receipt**: success state, evidence (commit, report), who approved
This gives you traces to debug a team, a cost per agent and per task, and an audit trail. Foundry supports tracing and evaluations; Agent Framework exposes telemetry hooks; you can add your own with OpenTelemetry-style tracing.

### 4.4 How to evaluate a team
1. **Outcome first.** Did the task get done correctly? Use a fixed set of test tasks with known good answers or a rubric. Judge the final result, not each step.
2. **Compare configurations.** One agent vs team; sequential vs group chat; strong vs cheap helper model. Same tasks, measure **quality, cost and time**.
3. **Check the hand-overs.** Sample the briefs and results between agents: were they complete? any invented facts?
4. **Failure injection.** Break a tool, send a prompt-injection page, return a malformed result; confirm it fails loudly and safely.
5. **Watch distributions, not averages.** Median, 90th percentile cost per task; the worst runs matter (3.3).
6. **Re-run after any change** to a prompt, model or framework version.

### 4.5 A launch checklist
- [ ] Each agent's tools listed; nothing extra enabled (checked in the **compiled/deployed** config)
- [ ] Irreversible actions need approval
- [ ] Caps on rounds, tokens, spend, time
- [ ] Untrusted content never given tool rights
- [ ] Hand-over formats validated
- [ ] Logs with run, step, attempt, agent, tokens, receipt
- [ ] Evaluation set run; cost per task known
- [ ] Kill switch tested
- [ ] Owner named for each agent

## 5. Why it was built this way (decisions and trade-offs)

| Decision | Alternatives | Why this one | Cost / risk |
|---|---|---|---|
| Permissions enforced by platform/code | Prompt rules only | Prompts can be ignored or overridden by injected text | Setup work per agent |
| Human approval for irreversible steps | Fully automatic | Cheap insurance for rare big mistakes | Slower; approver fatigue |
| Caps on rounds and spend | Trust the agents to stop | Loops and debates are the main cost risk | A cap may stop a task that needed more |
| Outcome-based evaluation | Judge each message | Teams can reach good results by different paths | Needs a good test set |
| Attempt ids and receipts | Count events | Retries and failures don't inflate success counts | More plumbing |

## 6. Theory behind it (the "lecture" part)

### 6.1 Defence in depth
Several independent layers, so one failure doesn't cause harm: permissions, validation, approvals, caps, monitoring.
*In this chapter:* §4.2 is a stack of layers.

### 6.2 Least privilege and blast radius
Give the minimum rights; then a compromised or confused agent can only do limited damage. "Blast radius" is how much can break if one part fails.
*In this chapter:* control 1; one agent per risk level.

### 6.3 Confused deputy and prompt injection
A "deputy" (the agent) with powers can be tricked by someone without those powers (text in a web page) into using them. The defence is to separate agents that read untrusted content from agents that hold powers.
*In this chapter:* control 6, and why a research agent shouldn't also have deploy rights.

### 6.4 Idempotency and exactly-once effects
An operation is idempotent if doing it twice has the same effect as once. Retries are normal in agent systems, so actions and records need ids that make a repeat harmless.
*In this chapter:* attempt numbers and receipts.

### 6.5 Evaluating systems vs components
Component tests (does this prompt work?) don't tell you whether the whole team works. System evaluation uses end-to-end tasks, cost and failure injection.
*In this chapter:* §4.4.

## 8. Glossary

| Term | One-line definition |
|---|---|
| Least privilege | Give only the minimum rights needed for the job |
| Blast radius | How much can go wrong if one part fails |
| Separation of duties | Doer and checker are different parties |
| Cap | A hard limit on rounds, tokens, time or spend |
| Circuit breaker | Stops calling something after repeated failures |
| Kill switch | A way to stop an agent or all agents immediately |
| Prompt injection | Untrusted text that tries to give the agent new instructions |
| Confused deputy | A powerful agent tricked into misusing its powers |
| Receipt | Evidence record that a step finished and how |
| Idempotent | Safe to repeat; the second time changes nothing |
| Trace | A recorded path of everything an agent run did |
| Failure injection | Deliberately breaking things to test safe behaviour |
| Human-in-the-loop | A person approves before the run continues |

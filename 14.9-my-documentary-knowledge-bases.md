# Course 14 · Chapter 14.9: My documentary knowledge bases, project by project

_Andrey Popov's project notes: how it works, why it was built this way, and the theory behind it._

**In short:** Andrey's documentary knowledge bases: lexical-first engagement knowledge base with catalogue and authority tiers, the gated Verdaca wiki update, Library one-way rule, digest archive, session full-text index, this chatbot's router, and memory notes.

## 2. The problem (business view, plain English)

Over months, an AI-assisted project produces handoffs, decisions, research, daily news and code. If it all sits in folders, each new session starts by hunting for context, or worse, trusts an old summary. I built several small knowledge systems to fix different parts of this: one for a client engagement, one for my own product, one for research, one for a daily feed, one for this portfolio's chatbot, and a small memory for the coding agent. The common design: raw material is kept as it was, curated pages are written from it with approval, indexes are cheap and rebuildable, and the agent reads a small map first.

## 4. How it works

### 4.1 The engagement knowledge base: lexical, layered, authority-aware
```
raw immutable notes ──(gated wiki-update skill, approval)──► curated wiki pages
code repos ──(parser)──► code graphs (separate system, 14.8)
runtime memory (per tool, not shared)
        │
 catalogue (policy → path, tier, hash, time, commit)  ──► route by question type
        │
 agent: read tiny index → pick file → read one section (point read) → grep if unsure → confirm in source
```
Core principle in the research file: no vector database, no embeddings; speed comes from never loading more than needed. The comparison appendix scores this lexical approach against hybrid retrieval on ten parameters (volume, velocity, variety, freshness, query type, language, sovereignty, latency, explainability, operations). It is better or equal on small volume, high churn, exact symbols, freshness, local-only and operations; worse on very large corpora, fuzzy prose, cross-language and multi-hop.

The action plan orders work: P0 routing and truth metadata (catalogue, precedence, isolate untrusted material, stop repeated graph injection, generated graph state, freshness preflight); P1 lexical baseline (44 questions, routed search, heading-aware full-text index, citation validation); P2 code-graph value; P3 dense retrieval only if failures are semantic; P4 regression and runbook. Deferred: a universal vector index over everything, documentary GraphRAG, a default reranker.

### 4.2 The gated wiki update (Verdaca)
```
1. freshness: read each page's "Compiled" date; list handoffs and docs newer than the oldest
   (or use the FTS5 index with --index)
2. read: one cheap model per new file, all in parallel, extracting a fixed list (stage, ratifications,
   findings, architecture changes, constraints, remaining work, HEAD commit)
3. synthesise: one strong model per affected page produces a TARGETED PATCH, not a rewrite,
   marking doubts as "(uncertain - verify)"
4. present: show patches; the user replies "go", "go <page>" or "skip"
5. apply: update Compiled date and HEAD; optional graph rebuild
```
Hard rule in the skill: never write to the wiki without an explicit "go".

### 4.3 Library: awareness without copies
Four sibling folders (product code, Library, the job-search pipeline, the digest archive). **One-way rule:** Library reads about the others; the others do not read from Library. Product status lives in thin pointer cards, not copies. Findings flow outward by *promotion by copy with provenance*. The decisions log has dated entries with source, decision, action taken, caveat and product impact.

### 4.4 digest-archive: a feed plus saved queries
Two routines push a daily news digest and tooling digest. A seen-URL file de-duplicates. Per-tag rollup files (`_index/tags/<tag>.md`) are saved queries: newest first, with a short "why it matters" per item. Query by reading a tag file or by `grep`.

### 4.5 This portfolio's chatbot KB: a small lexical retrieval system with tests
```
visitor question ──► router: tf-idf word score + keyword phrase boost + project-alias boost
                       attach top note if score ≥ 2.5; add runner-up if ≥ 70% of top
notes (kb-index.json: summary, 8-14 keywords, 3 questions each) ──► export keeps only public sections
check_kb.py: syllabus = note files = index; every course has a project entry; site pages published;
             allowlist; redaction scope; at least one routing test per course
```
It is the same philosophy as the engagement system: a curated index, keyword scoring and consistency checks, no embeddings.

### 4.6 Agent memory
Each memory is one file with a name, description, type and body; a short index file is loaded at session start. Used for stable facts and decisions, not for project truth.

## 5. Why it was built this way (decisions and trade-offs)

| Decision | Alternatives | Why this one | Cost / risk |
|---|---|---|---|
| Lexical-first, curated indexes | Vector database / hybrid now | Small, fast-changing, exact-symbol corpus; local-only; nothing to re-embed | Weaker on paraphrase and multi-hop; benchmark pending |
| Raw immutable, wiki compiled by a gated skill | Edit pages directly | Provenance and a human check on silent errors | Slower; wiki can lag (it does) |
| Cheap readers in parallel, strong model synthesises, patch not rewrite | One model rewrites the page | Cost; smaller diffs to review | Two-stage orchestration |
| Pointer cards and one-way rule in Library | Copy status into Library | No duplicated facts to rot | Must follow the pointer |
| Tag rollups as saved queries | Search every time | Fast repeated queries | Rollups must be regenerated |
| Keyword router plus tests for the chatbot | Embeddings | Deterministic, free, testable | Keywords need curating; collisions between courses |
| Memory kept small | Store everything | Easy to review | Not shared across tools |

## 6. Theory behind it (the "lecture" part)

### 6.1 Raw, derived and curated
Raw: the evidence as it happened. Derived: computed from raw by a script (catalogue, graph, tag rollups), always rebuildable. Curated: written by a person or a gated model (wiki). Keep the three kinds apart and label them.
*In this course:* every store above is one of the three.

### 6.2 Progressive disclosure
Give the model a small map first and the detail only on request; the top of the map is cheap and always loaded.
*In this course:* the index file, the memory index and the graph report excerpt all work this way.

### 6.3 Immutability and append-only logs
Never edit evidence; add dated records. Corrections are new entries.
*In this course:* handoffs and the decisions log.

### 6.4 One-way dependencies
If A reads B but B never reads A, there are no loops and no circular staleness.
*In this course:* the Library rule.

### 6.5 Saved queries (materialised views)
Precompute a frequent query and store it as a file. Fast reads, with the risk of staleness.
*In this course:* tag rollups.

### 6.6 Consistency checks as tests for a knowledge base
Small scripts that assert that indexes, files and routing tests agree.
*In this course:* `check_kb.py` is the only consistency check I found that runs across a whole knowledge base; I found none for the wikis.

## 8. Glossary

| Term | One-line definition |
|---|---|
| Handoff | A dated note written at the end of a work session |
| Wiki compile | Turning raw handoffs into curated pages |
| Gate | A step that waits for explicit human approval |
| Targeted patch | A small proposed change to a page instead of a rewrite |
| Catalogue | A generated inventory of files with hash, tier and time |
| Authority tier | A rank for how far a source can be trusted for a question |
| Point read | Reading one section of one file |
| Pointer card | A short page that says where the truth lives |
| One-way rule | A folder may read another but not the reverse |
| Tag rollup | A file that collects all items under one tag, newest first |
| Seen-URL list | A file that prevents duplicate entries in a feed |
| FTS5 | SQLite's full-text search module |
| Persona file | An instruction file describing an agent role |

**In short:** The routing evaluation: 40 labelled queries, three arms. Rules only 52.5%, with Opus 62.5%, with Haiku 65.0%; the 2.5-point gap is one row, not a result, and the whole LLM gain is 4-5 rag rows. Covers sample size and intervals.

## 2. The problem (business view, plain English)

The first review found the project's headline claim, "hybrid routing is accurate and cost-effective", had **no evidence behind it**: no labelled set, no accuracy figure, no cost measurement (*Review §4*: "Hypothesis 3: no evaluation exists"). The review asked for 60 to 100 labelled queries, a confusion matrix, and cost and latency for keywords-only, LLM-only and hybrid. The redo built a smaller version: 40 rows, rules-only vs rules+Opus vs rules+Haiku.

Finance analogy: back-testing a trading rule. One backtest on 40 observations can show that a rule is not obviously broken. It cannot tell you that strategy A beats strategy B by 2.5 points. And if you wrote the test scenarios yourself, you must say so.

## 4. How it works (technical walkthrough)

```
routing_labels.yaml (40 rows: text, route)
        │
        ▼
 run_arm(rows, use_llm, model)  ── builds DispatcherAgent, wraps Stage 2 (count calls) and
        │                           response parsing (read usage.input/output_tokens)
        │   for each row: agent.run(fresh state) → update["route"] or "fallback"
        ▼
 score: n, overall, per-route {n, correct, accuracy}, confusion[true][pred]
        │   (+ usage and cost_usd for LLM arms; + stage1_decided, llm_calls)
        ▼
 merge into evals/results/routing_eval.json ──► README table (checked by a test)
```

**Labelled set** (`CC:routing_labels.yaml`). 40 rows: 11 `rag`, 10 `research`, 9 `booking_stub`, 10 `fallback`. The header defines each route in one line: rag = answerable from the mock destination file; research = current or external information; booking_stub = book, reserve, change or cancel; fallback = out of domain, chit-chat or too vague (`:1-7`). The set includes deliberate hard cases: no keyword ("Tell me about Phuket"), booking without a booking word ("Get me two nights in Koh Samui, I'm ready to pay"), a collision ("I want to secure a room at the Alpine Vista", labelled booking, which the property rule sends to rag), and out-of-domain rows that contain a rule word ("Should I invest in Tesla stock?").

**Harness** (`CC:routing_eval.py:109-158`). It drives the real `DispatcherAgent.run` on a fresh state per row (`:142-144`), so the eval measures the production code path including the fallback behaviour. `_env_key(use_llm)` removes the API key for the rules-only arm, so it cannot call a model (`:85-96`, tested at `test_routing_eval.py:42-51`). Stage 2 is wrapped to count calls, and response parsing is wrapped to add up `usage.input_tokens` and `output_tokens` (`:119-135`). Cost = (input tokens × input price + output tokens × output price) / 1,000,000 (`:155-157`), with prices in USD per million tokens: Opus 4.6 (5, 25), Haiku 4.5 (1, 5) (`:36-40`). The model is pinned per arm (`:215`) so the committed Opus result stays reproducible even though the policy default is now Haiku.

## 5. Why it was built this way (decisions and trade-offs)

| Decision | Alternatives | Why this one | Cost / risk |
|---|---|---|---|
| 40 rows, 4 routes roughly balanced | 60–100; real logs | Fast, cheap, one sitting ||
| Labels from route definitions, "not from the regexes" | Labels from rule output; real user data | Avoids grading the rules against themselves | Unverified claim; AI labeller; no agreement measure |
| Drive the real `DispatcherAgent.run` | Re-implement routing in the harness | Eval = production path, including fallbacks | Needs care to stop real API calls in the rules arm (done via key removal) |
| Accuracy + per-route + confusion matrix | One number | Shows which route fails | Per-route counts are 9–11; recall only, no precision |
| Measure tokens from `usage`, price from a table | Read the billing page | Cheap and reproducible | Prices can go stale; not billed cost |
| One run per arm | 3–5 runs, temperature 0 | Cost and time | No variance estimate |
| Commit the JSON; test that rules-only re-runs identically; test that README numbers equal the JSON | Paste numbers in README | Docs cannot drift from data | LLM arms cannot be re-verified offline |
| Switch the default to Haiku on a "no gain" result | Keep Opus; run more first | Cheaper model, same measured accuracy | A null result on 40 rows is weak support (6.4) |

## 6. Theory behind it (the "lecture" part)

### 6.1 Designing an evaluation set
An eval set must represent the **population you care about** (construct validity), be large enough for the decision, and have **correct labels**. Steps: write an annotation guideline (what each class means, how to treat ambiguity); include easy, hard and out-of-scope cases on purpose; label with at least two annotators on a sample; measure agreement with **Cohen's κ** = (p_o − p_e) / (1 − p_e), where p_o is observed agreement and p_e is agreement expected by chance. κ above about 0.8 is strong. Disagreement is also information: it bounds the best accuracy anyone can reach. Keep a **dev** set for tuning prompts and rules and a **held-out test** set for the final number; once you tune on a set it is a dev set. Check for **contamination**: test items copied into prompt examples.

*In my project:* one AI annotator, no κ, no split. Because nothing has been tuned on the 40 rows yet, they are still usable as a test set once. If I now edit rules or prompts to raise this score, I need new rows.

### 6.2 Metrics for classification, including abstention
From a confusion matrix: **accuracy** = correct / n; per class **recall** = TP / (class size) and **precision** = TP / (predicted as class); **F1** = 2PR / (P + R); **macro-F1** averages F1 over classes, so small classes count equally. Always compare with a **majority-class baseline** (here "always fallback" = 25%). When a class is the default or "abstain" bucket, its recall is trivially high; its **precision** tells you how much junk lands there.

*In my project:* "per-route accuracy" in the README is recall. Macro-F1 for the Haiku arm is 0.65 (my arithmetic).

### 6.3 Sampling error and confidence intervals
A measured accuracy p̂ on n independent items has standard error SE = √(p̂(1 − p̂)/n). At p̂ = 0.65, n = 40: SE = 0.075, so ±1.96 SE ≈ ±15 points. The **Wilson interval** is better at small n: centre (p̂ + z²/2n) / (1 + z²/n), half-width z·√(p̂(1 − p̂)/n + z²/4n²) / (1 + z²/n).

To compare two classifiers on the **same** items use a paired design. Let b = items only A got right, c = items only B got right. Under "no difference", b ~ Binomial(b + c, ½): the **exact McNemar test**. The SE of the accuracy difference is √(b + c − (b − c)²/n) / n. Pairing helps when the models agree on most items; it cannot help when they differ on many.

**Power:** to detect a true gap δ between two independent accuracies near p̄ at 80% power and 5% two-sided, n per arm ≈ 2(1.96 + 0.84)² p̄(1 − p̄) / δ². For p̄ = 0.6: δ = 10 points needs about 380 per arm; δ = 2.5 points needs about 6,000. Turned around: at n = 40, the smallest unpaired gap you can reliably detect is 2.8·√(2p̄(1 − p̄)/n) ≈ 31 points.

*In my project:* a 2.5-point gap is nine times smaller than the 31-point detectable gap. The data cannot rank the models.

### 6.4 Comparing models: null results, non-inferiority and cost
"No significant difference" is not "equivalent". To claim a cheaper model is good enough you state a **non-inferiority margin** Δ (say, "at most 5 points worse") in advance and show the lower bound of the interval for (cheap − expensive) is above −Δ. With the Haiku-vs-Opus interval here (about −12 to +17 in the worst case, −2 to +7 in the best) you could only support Δ of about 12 points, which is not a tight claim.

Defaulting to the cheaper model can still be **rational**: if costs are 3x apart and no evidence favours the dear one, you pick the cheap one and keep a switch. That is a decision under uncertainty, not a finding. Say it that way.

Other discipline: same prompt, same data, **pinned model versions**, fixed temperature (0 for classification), **several repeats** to estimate run-to-run variance, and report mean ± sd. When picking the best of k arms, the best one's score is biased upwards (winner's curse).

*In my project:* the README states the right framing ("no measurable gain ... not 'Haiku is better'"); the CV bullet and page compress it.

### 6.5 Baselines, floors and ceilings
Good evals include arms that bound the answer: a **floor** (majority or rules-only), a **ceiling** (strongest model, LLM-only, or human), and an **oracle** (the router's best possible choice). If all strong arms sit at the same low score, suspect the **harness or prompt** (a "floor effect"), not the models. Use an **ablation**: change one thing (the prompt's label list) and see if the whole group moves.

*In my project:* Opus and Haiku both only ever produced `rag` or `fallback`. That points at the shared prompt and label map. There is no LLM-only arm and no oracle.

### 6.6 Measuring cost
Cost per call = tokens_in × price_in + tokens_out × price_out. Two models differ in price **and** in verbosity; compare **measured** tokens, not only price lists. Report cost per decision, per correct decision, and per *additional* correct decision against a baseline. Add latency (p50, p95) because a cheap model that is slow may not be cheaper to run. Prompt caching helps long repeated prefixes only above a minimum length (check current limits).

*In my project:* 157 input tokens per call, so input cost is tiny; output tokens decide the ratio: 22 (Opus) vs 51 (Haiku) per call.

### 6.7 Eval hygiene and reproducibility
Commit the dataset and the results; version the prompt; save **per-item predictions and raw outputs** (otherwise no paired test and no error analysis); make the harness fail loudly rather than skip (`LlmUnavailable`); never leak keys into results; let tests pin the docs to the data. Re-run on every prompt or model change, ideally in CI with a small cheap subset.

*In my project:* strong on reproducibility of the rules-only arm and key hygiene; weak on saved per-row outputs.

## 8. Glossary

| Term | One-line definition |
|---|---|
| Labelled set / gold set | Utterances with a human-decided correct route |
| Arm | One configuration under test (rules-only, rules+Opus, rules+Haiku) |
| Per-route accuracy | Correct / rows of that true route, i.e. recall for that route |
| Confusion matrix | Counts of true route against predicted route |
| Precision / recall / F1 | Share of predictions right / share of true cases found / their harmonic mean |
| Macro-F1 | Average F1 over classes, each class weighted equally |
| Standard error | Typical sampling spread of a measured rate: √(p(1 − p)/n) |
| Wilson interval | Confidence interval for a proportion that behaves well at small n |
| McNemar test | Paired test on the items where two classifiers disagree |
| Discordant pair | An item that exactly one of two classifiers got right |
| MDE | Smallest true gap a test of given n can detect at set power |
| Non-inferiority | Showing a cheaper option is not worse than a margin Δ |
| Floor effect | Strong and weak arms look equal because all hit the same low ceiling |
| Cohen's κ | Inter-annotator agreement corrected for chance |
| Contamination | Test items appearing in prompts or training data |
| Winner's curse | The best of several noisy scores is biased upwards |

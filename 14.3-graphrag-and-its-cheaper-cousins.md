## 2. The problem (business view, plain English)

Plain retrieval answers "what does document 12 say about X?". It fails on "what are the main themes across all 2,000 reports?" because no single passage contains the answer; the answer is a view across everything. GraphRAG was designed for that second kind. The price: an expensive build step, where a language model reads every document, and an index that must be refreshed when sources change.

Analogy: a market analyst. For one company, you open its filing (retrieval). For "what are the sector trends?", the analyst first writes a one-page summary per company, then per sub-sector, then reads those summaries (GraphRAG). Writing all those summaries up front is the cost.

## 4. How it works

### 4.1 Classic GraphRAG (Microsoft, 2024)
```
documents -> split into chunks
          -> LLM extracts entities + relationships + short descriptions
          -> graph is clustered into communities (groups, in levels)
          -> LLM writes a summary for each community          <- the expensive part
query     -> each community summary gives a partial answer
          -> partial answers are combined into the final answer (map-reduce)
```
It targets "global" questions over corpora of about a million tokens, judged on how comprehensive and diverse the answers are versus a plain RAG baseline.

### 4.2 The query modes you will hear
| Mode | Best for | How |
|---|---|---|
| **Local** | Questions about specific entities | Start at the entity, fan out to neighbours and the text units attached |
| **Global** | Whole-corpus questions | Map-reduce over community summaries (costly) |
| **DRIFT** | Exploratory, multi-hop questions | Starts from a global-style primer, then follows local leads iteratively |
| **Basic** | Plain vector similarity | Ordinary RAG for comparison |

### 4.3 LazyGraphRAG: pay later, pay less
Same idea, different timing:
- **Index time:** no LLM summarisation at all. Extract noun phrases with ordinary text processing, link phrases that co-occur, find communities with graph statistics. Microsoft states the indexing cost equals vector RAG and is 0.1% of full GraphRAG's.
- **Query time:** an LLM breaks the query into sub-queries and tests relevance on a budget. The budget is the dial between cost and quality.
- **Reported results (their evaluation):** at vector-RAG-like query cost it beats the other methods on local queries; with one configuration it reaches quality comparable to GraphRAG global search at over 700 times lower query cost; at about 4% of GraphRAG global search's query cost it beats all compared methods on local and global queries.

### 4.4 The decision rule
```
Mostly single-fact or section lookups?                   -> lexical or hybrid retrieval (14.5)
Repeated whole-corpus "themes / risks / patterns" ask?   -> a summary-based method (GraphRAG, or LazyGraphRAG if the index cost hurts)
Repeated multi-hop questions that lighter methods miss?  -> measure that first, then consider a graph
Corpus changes daily?                                    -> be wary of any expensive pre-built index
```

## 5. Why it was built this way (decisions and trade-offs)

| Decision | Alternatives | Why this one | Cost / risk |
|---|---|---|---|
| Community summaries up front (GraphRAG) | Retrieve passages only | Global questions have no single passage | Large one-time LLM cost; summaries go stale |
| Defer the LLM to query time (LazyGraphRAG) | Summarise everything | Cheap index, pay per question, tunable budget | Query cost and latency vary; one vendor evaluation so far |
| Several query modes | One mode | Local and global questions are different problems | More to configure |
| For my own workspace: do not adopt yet | Build documentary GraphRAG now | No measured multi-hop deficit; an earlier attempt was left unfinished; high upkeep | Might miss a real gap; the benchmark will tell (14.7) |

## 6. Theory behind it (the "lecture" part)

### 6.1 Query-focused summarisation
Answering a broad question by condensing many sources toward the query, rather than quoting one. GraphRAG frames global questions this way, which is why it is judged on comprehensiveness and diversity rather than exact-match accuracy.
*In this course:* a different success measure than lookup accuracy; do not compare them with the same metric.

### 6.2 Map-reduce
Do a small job on each piece (map), then combine the results (reduce). Community summaries are the map; the final answer is the reduce.
*In this course:* the same pattern as a lead agent combining helpers' findings (Course 13).

### 6.3 Index-time vs query-time cost
Work done once when indexing is cheap per question but goes stale; work done per question is always fresh but repeated. GraphRAG leans index-time; LazyGraphRAG moves most of it to query-time.
*In this course:* choose by how often the corpus changes and how often it is queried.

### 6.4 Community detection
Algorithms that split a graph into groups of tightly linked nodes (the idea behind the "communities" in a code-graph report too).
*In this course:* in my code graphs a community is a cluster of related code, not a summary.

## 8. Glossary

| Term | One-line definition |
|---|---|
| GraphRAG | Retrieval using a model-built entity graph and community summaries |
| Community summary | A short model-written description of one cluster of the graph |
| Global search | Answering a whole-corpus question by combining community summaries |
| Local search | Answering about specific entities by expanding from them |
| DRIFT | Exploratory search mixing a global primer with iterative local follow-up |
| LazyGraphRAG | A variant that skips up-front summaries and defers LLM use to query time |
| Query-focused summarisation | Condensing many sources toward a specific question |
| Map-reduce | Process pieces separately, then combine |
| Index-time cost | Cost paid once when building the index |
| Sense-making question | A question about overall patterns across a corpus |

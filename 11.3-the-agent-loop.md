# Course 11 · Chapter 11.3: The agent loop

_Andrey Popov's project notes: how it works, why it was built this way, and the theory behind it._

**In short:** The agent loop in flutter_agent_harness: two nested loops, steering vs follow-up queues, four hooks, tool-call pairing repair, the tool-misuse circuit breaker, stuck-call supervision with heartbeats, and the FinalizeGate task ledger (including the #1516 leak into interactive sessions).

## 2. The problem (business view, plain English)

The textbook agent loop is six lines: call the model, run its tools, append results, repeat until it stops. A loop that survives real use needs much more. The user types a correction while a tool is running; a tool hangs for ten minutes; the model sends the same broken call fifteen times; the model declares victory without checking; a corrupted history makes the provider reject every request forever; a model returns a blank answer. None of that is exotic. Each item below exists in this repo because it happened (the code comments cite incident numbers).

Finance analogy: the loop is the order-management state machine. The happy path (new → filled) is trivial. The real code is amendments while in flight (steering), orders stuck at the venue (stuck supervision), repeated rejects (breaker), and the end-of-day reconciliation before you sign off (FinalizeGate).

## 4. How it works (technical walkthrough)

### 4.1 Two nested loops (*AL* `_runAgentLoop`, lines 1042-1202)

```
agent_start; first turn_start; prompt messages as events
pending = poll steering                     ← user may have typed while we waited
while true:                                  ← OUTER: follow-ups
  while hasMoreToolCalls or pending:         ← INNER: tools and steering
     turn_start
     inject pending messages (steering/follow-up) into context
     message = stream assistant response     ← section 4.3
     retry once if "degenerate empty"
     terminal? (error / aborted) → return
     run tool phase → tool results           ← section 4.4
     turn_end; prepareNextTurn hook (may swap context or config)
     pending = poll steering (capped)
  follow-ups = getFollowUpMessages
  if any: pending = follow-ups; continue
  pending = poll steering                    ← last drain (issue #314)
  if any: continue
  break
finalize gate: parse task ledger from the final answer  (if enabled)
agent_end
```

The run ends only when the model made no tool calls, **and** there are no follow-ups, **and** no steering message is waiting.

### 4.2 Steering and follow-up queues (*AG* lines 45-60, 396-427; *AL* lines 1066-1076)
- **Steering** = the user (or another agent) injects a message **while the run is going**. It is delivered at the next turn boundary, before the next model call. In the interactive CLI, "typed input steers the agent".
- **Follow-up** = a message queued to be processed **after** the agent would otherwise stop. It starts a new inner round without a new user prompt.
- `QueueMode.all` drains every queued message at a drain point; `oneAtATime` injects only the oldest (*AG* lines 45-54).
- **Cap:** `maxSteeringTurns` (default 20) limits "steering extensions". A chatter loop where each inbound message triggers a reply that triggers the next inbound message cannot keep the run alive forever; the undelivered steering stays queued for the next run (*AL* lines 1062-1076).
- **Soft yield:** while tools are running, the first steering arrival (an in-process notification, or an external probe polled every 2 seconds) cancels a *yield token* held in a Dart `Zone`. Yield-aware tools (the shell) finish early *without stopping their work*, so the user's message is delivered at the upcoming step boundary instead of after the whole tool call (*AL* lines 1271-1316). The long command continues as a background job (chapter 11.5).
- **Headless drain (gh-1459):** a headless `fa -p` run used to exit while a background shell job was still running, orphaning the result the model was waiting for. Now live shell jobs drain like subagents, with one wall-clock ceiling (`headless.shellJobDrainMs`, default 30 minutes) and periodic liveness notices (*CL* 1.0.508).

### 4.3 One model request (*AL* lines 1406-1535)
In order: (1) if the token is already cancelled, return a synthetic aborted turn without calling the provider; (2) build the request context: apply `transformContext`, **repair tool pairing**, attach any pending misuse note (`_buildRequestContext`, line 1705); (3) emit a `ToolPairingRepairEvent` if anything was repaired; (4) estimate request tokens and, if over the window, run the over-window guard (chapter 11.2); (5) emit a `ModelRequestEvent` capture; (6) call the `StreamFunction`; (7) consume the stream, keeping the partial message in the context up to date; (8) if the provider answered with a pairing 400, heal once and retry; (9) if the stream closed without a terminal event, synthesise an error.

### 4.4 The tool phase (*AL* lines 1319-1356, 2128-2330)
1. If the message stopped with `length`, **fail every tool call** with an error result; arguments may be cut off.
2. Otherwise choose **sequential** or **parallel**. Parallel is the default, but one tool declaring `executionMode: sequential` forces the whole batch sequential.
3. For each call: emit `ToolExecutionStartEvent`, then **prepare**: does the tool exist? is the exact call **refused by the misuse breaker**? run the `beforeToolCall` hook (it may `block` with a reason, which becomes an error tool result the model sees; a throw is also converted to an error result).
4. **Execute** through the injected `ToolExecutor`, under stuck-call supervision (4.7). Parallel mode starts all prepared calls concurrently; `ToolExecutionEndEvent`s come in *completion* order, but the tool-result messages are emitted in the assistant's *source* order after all settle (*AL* lines 163-175).
5. **Finalize**: the `afterToolCall` hook may rewrite the result. Feed the outcome to the misuse breaker.
6. If any result sets `terminate`, the loop does not continue with tool turns (`_shouldTerminateToolBatch`).
Schema validation sits one layer down in the `ToolRegistry`'s executor adapter: arguments are validated and **coerced** against the tool's JSON schema subset (`"42"` becomes `42`, `"true"` becomes a boolean, defaults injected, unknown keys passed through); keywords like `pattern`, `minimum`, `anyOf` are *ignored*, not enforced (*PV* lines 1-24; *TR* lines 1-25).

### 4.5 Tool-call pairing repair (*TP* lines 1-40)
Strict providers reject a request in which a `tool_result` has no matching `tool_use` in the **immediately preceding** assistant message, or the reverse. One such corruption (an interrupted run, a steering message wedged between call and result, an orphan after compaction) makes *every* later request a 400: the session is dead. `repairToolPairing` runs **on the outbound request only** (the transcript is never rewritten):
- a result without its call → dropped, replaced by a one-line user-role note so the model is "not gaslit about missing work";
- a call without its result → a synthetic "interrupted" result;
- a result displaced from its call (steering interleave) → hoisted back next to it;
- duplicate tool-call ids → suffix-renamed on **both** sides.
Every non-empty repair emits a `ToolPairingRepairEvent`: "silent context surgery is how the wedge happened in the first place." If the provider still returns a pairing 400, the loop re-repairs and retries once (issue #85).

### 4.6 The tool-misuse circuit breaker
Incident ("the luna incident", 2026-09-23): a model re-sent the byte-identical malformed `edit` call 15 times in 15 turns, was hard-rejected every time, then hallucinated success. The breaker keys on **(tool name, canonical arguments JSON)**. After `noteThreshold = 3` consecutive identical failures it arms a corrective note that is injected into the **next request**; after `stopThreshold = 6` the loop refuses to execute that exact call for the rest of the run, with an honest error naming the misuse. A different call, a different error, or a success resets that tool's state. Counters are per tool and per run. It is a pure state machine with no I/O.

### 4.7 Stuck-call supervision (gh-1054; *ST*, *SUP*)
Problem: in an unattended run a hung tool call used to produce total silence; the only net was an *external* watchdog killing the whole leg after 10 minutes without trace updates. The mid-run layer now does:
- **threshold** = `max(declaredTimeoutFactor × declared timeout, floorSeconds)` with defaults factor 2 and floor 300 s, so a legitimately long `flutter test` (declared 15 minutes) is not pestered at minute two;
- **heartbeats**: once a call runs past half the threshold, cheap append-only records (tool, args, elapsed, output size) go to the session ledger every `heartbeatSeconds` (default 60) so external watchers can tell *alive-busy* from *dead*;
- **autonomous follow-up** at the threshold: cancel the call, wait a bounded grace (10 s) for it to notice, **retry once**; if the retry also exceeds the threshold, **convert it to a background job** (the shell's soft-yield path) so the turn continues with a job id and log path;
- if recovery cannot succeed, a session-visible escalation names the call, duration and partial output: "Never die silently";
- `advisory` mode only emits the stuck event (interactive comfort; a kill switch for the autonomy).
The 300-second floor is chosen to sit inside the external watchdog's 10-minute window so the heartbeats and follow-up land first.

### 4.8 FinalizeGate and TaskLedger (gh-1412; *FG*)
"An unattended agent must stop declaring success on intent and start declaring it on re-verified state." Two pieces:
- the **FinalizeGate** is a *prompt contract* (`prompts/cli/finalize_gate.md`, rendered into the system prompt in unattended and bench mode): before the final summary the agent re-quotes every explicit requirement as a checklist, verifies each item with a real command against the produced state, and fixes or reports each unmet item;
- the **TaskLedger** is that checklist in a fenced block named `task-ledger` in the final message. The loop parses it from the **last assistant message only** and only if the run *ends* on that message (a ledger quoted in an earlier turn, or a run that stopped on tool calls, does not count), emits `TaskLedgerEvent`, and hosts persist it as a hidden session record. Item status is `pass`, `fail` or `fixed`; a missing or unrecognised status parses as `fail`, "an unverified item must never silently count as verified".
It is the harness-level version of "check your work", and it creates data: the bench summary reports near-miss proximity (items verified over checks passed).

### 4.9 Events out (*AL* lines 570-890)
The loop reports through a sealed `AgentEvent` family: `AgentStart/End/Settled`, `TurnStart/End`, `MessageStart/Update/End`, `ToolExecutionStart/Update/End`, `ModelRequest`, `ToolPairingRepair`, `TaskLedger`, `ToolCallHeartbeat`, `ToolCallStuck`. `AgentEventStream` is an `EventStream<AgentEvent, List<Message>>`: iterate it for live events or await the list of new messages. Hosts, the session writer, the trajectory ledger and the wire protocol (chapter 11.6) all consume this one stream.

## 5. Why it was built this way (decisions and trade-offs)

| Decision | Alternatives considered | Why this one | Cost / risk |
|---|---|---|---|
| Keep control flow close to pi's `agent-loop.ts` | Redesign in Dart idiom | Upstream fixes port cleanly (*AL* header) | Inherits upstream structure; 2,718 lines in one file (split with a `part` file) |
| Tools and provider injected as callbacks (`ToolExecutor`, `StreamFunction`) | Loop owns a registry and HTTP | The loop is unit-testable with no network and no registry (*AL* lines 11-17) | More wiring in the host |
| Steering delivered at turn boundaries with a soft yield for long tools | Interrupt mid-tool; or wait for the whole tool call | Responsive without killing work | Interleaving complexity (hence the pairing repair) |
| Repair pairing on the **request**, not the transcript | Rewrite history | The transcript stays a truthful record | The same repair runs again on every request |
| Misuse note first, refusal later (3 then 6) | Hard stop at the first repeat | Gives the model a chance to correct itself, then stops the burn | Two thresholds to tune; per-run reset |
| Stuck follow-up is autonomous by default | Ask the user | Unattended runs have nobody to ask | A retry can repeat a non-idempotent tool call; the design relies on cancel-then-retry-once and background conversion |
| FinalizeGate as a **prompt** contract plus a parsed ledger | Enforce with code checks | Works for any task type; yields measurable data | The agent grades itself; it is evidence, not proof |
| Parallel tool execution by default | Sequential | Faster when calls are independent (reads) | Needs per-tool opt-out for mutating tools |

## 6. Theory behind it (the "lecture" part)

### 6.1 The agent loop as a state machine
Formally an agent is a policy π mapping the history h_t to an action a_t (a message, or tool calls), followed by an observation o_t (tool results). ReAct (Yao et al., 2022) interleaves reasoning text and actions. The loop is the controller: it owns *termination*, *error handling* and *what the model sees next*. The model only proposes. This is the same separation as Course 2.4 (producer proposes; deliberation loop and receipts decide).

*In my project:* Course 2.4's loop is a three-role graph; here it is a single-agent loop with guards.

### 6.2 Event-driven design and the observer pattern
Instead of returning one big result, the loop emits events as things happen. Many consumers subscribe independently: UI, persistence, metrics, protocol bridges. The cost is ordering rules (here: tool results are emitted in source order even if execution finished in a different order) and back-pressure. A fully awaited `emit` makes listeners part of the run's settlement: the agent is not idle until awaited listeners finish (*AG* lines 62-71).

*In my project:* the trajectory ledger and the NDJSON wire protocol are two more consumers of the same stream.

### 6.3 Idempotency and retrying tool calls
A function is idempotent if running it twice has the same effect as once. Reading a file is; appending to a log or sending a message is not. Supervisors that retry (stuck-call follow-up) must know the difference, or limit themselves to *cancel, retry once, escalate*. Converting to a background job avoids a third attempt.

*In my project:* the design bounds retries (one retry, then background) instead of proving idempotency.

### 6.4 Supervision and the "let it crash" idea
Erlang/OTP supervisors detect a failing process and restart it with limits (max restarts in a time window), escalating to the parent when limits are exceeded. The stuck-call stage machine has the same shape: detect (threshold), restart (retry once), degrade (background), escalate (visible message). Heartbeats are the liveness signal, the same as in cluster health checks: a missing heartbeat means *dead*, a present one with no progress means *stuck*.

*In my project:* the external CI watchdog (10 minutes without trace updates) is the second supervisor level.

### 6.5 Circuit breakers and loop detection
A circuit breaker opens after N failures so a doomed call stops being attempted. For agents the signature of failure is repetition: the same call, the same error. Keying on the canonical JSON of the arguments makes "same" precise. Notes injected into the context are a soft intervention (the model may self-correct); refusal is the hard one.

*In my project:* the first line of defence is a hint, the second a refusal that names the misuse.

### 6.6 Verification before declaring success
Models report completion based on what they *intended*. Process controls from other fields apply: a checklist (aviation, surgery), independent verification (maker-checker), and post-conditions (design by contract). The ledger records the checklist; a real command per item gives the evidence. The weakness is self-grading: the same model that did the work checks the work, a point I made in my Verdaca review about self-critique limits (Course 2.7).

*In my project:* a finance parallel is a control self-assessment sheet: useful, cheap, and worth less than an independent test.

### 6.7 Cooperative cancellation and Zones
Dart `Zone`s carry values down an async call tree, like thread-local state. Here a yield token is put in the zone for the duration of the tool phase, so any tool can ask "was I asked to yield?" without an extra parameter. It is implicit context, convenient and a little magical.

*In my project:* `currentYieldToken` in `cancel_token.dart` is read by the shell tool.

## 8. Glossary

| Term | One-line definition |
|---|---|
| Turn | One model request plus its tool executions |
| Steering message | User/agent input injected during a run, delivered at the next turn boundary |
| Follow-up message | Input queued to start a new round after the agent would stop |
| `prepareNextTurn` | Hook that can replace the context or config between turns |
| `beforeToolCall` / `afterToolCall` | Hooks that can block a call / rewrite its result |
| `transformContext` | Hook that rewrites the context before every provider call |
| Yield token | Zone-carried cancel signal asking long tools to hand back early |
| Pairing | The rule that each `tool_result` matches a `tool_use` in the previous assistant message |
| Misuse breaker | Per-tool counter that warns after 3 and refuses after 6 identical failures |
| Stuck threshold | `max(2 × declared timeout, 300 s)` by default |
| Heartbeat | Periodic record proving a long call is still alive |
| FinalizeGate | Prompt contract: re-verify every requirement before the final answer |
| TaskLedger | The checklist block parsed from the final answer |
| `terminate` | Tool result flag that stops further tool turns |
| Degenerate-empty | A normal stop with no tool calls and no text |

# Course 5 · Chapter 5.3: Merge safety in an AI-assisted team: silent-revert guard, CI gates, test wiring

_Andrey Popov's project notes: how it works, why it was built this way, and the theory behind it._

**In short:** Merge safety for a team landing about five AI-written PRs a day: a silent-revert guard using git blame and ancestry, and wiring 575 frontend tests that never ran into CI. Both gates were proven able to fail and fail closed.

## 2. The problem (business view, plain English)

The team merged about five pull requests per working day, written mostly by AI coding agents under human direction. With that many branches open at once, a branch is often rebased, force-pushed or squashed before merge. If the rebase is resolved the wrong way (taking the stale side of a conflict), the pull request quietly deletes work that other people already merged. GitHub does not warn: the branch looks current, and the removed lines look like ordinary intended deletions in the diff. A second, quieter risk: tests that exist but never run give a false sense of safety.

Finance analogy: restoring the ledger from last week's backup. Everything balances, nothing looks wrong, but every entry posted since the backup is gone. The control is to compare the restored ledger with the last signed-off close and flag any line that existed at the sign-off and is now missing without a journal explaining it.

## 4. How it works (technical walkthrough)

```
PR head ─┬─ merge-base(head, origin/main) = BASE          (the PR's diff is BASE..head)
         └─ ORIGIN: where the branch was really cut
              no force-push ─► merge-base of main and the branch's OLDEST commit
              force-pushed  ─► ask GitHub for the head BEFORE the first force-push,
                               take its merge-base with main
For every removed line in `git diff -U0 BASE head`:
   skip if a similar line was added in the same file   (token overlap ≥ 0.7: a rewrite)
   blame the line at BASE  ─► commit C that introduced it
   if C is an ancestor of ORIGIN ─► the branch had it: deliberate delete, OK
   else if (PR, path, line fingerprint) is allowlisted ─► OK
   else ─► finding: "main gained this after you branched, and you deleted it"
no findings ─► pass.   cannot resolve ORIGIN / blame / GitHub ─► FAIL (closed)
```

**Why not timestamps.** A squash rewrites commit dates, so an author date can fall after the content it clobbers. A pull request's creation time can be rewritten the other way, because a PR can be opened long after the branch was cut. Taking the minimum of two late signals is still late. The guard therefore uses **pure ancestry**: `git merge-base --is-ancestor C ORIGIN`. If ORIGIN cannot be recovered, it fails rather than guess. This design came from my fix commit 9b673a8f ("resolve the branch origin from ancestry, not timestamps").

**Diff parsing.** It tracks the old and new path separately so that whole-file deletions (`+++ /dev/null`) and renames are not missed; removed lines are blamed under the old path. Trivial lines (a lone brace) are ignored, but short meaningful lines such as `deny: true` are not (no length threshold). Tokenising is Unicode-aware so non-Latin text counts.

**Rewrite test.** For each removed line, the fraction of its tokens that reappear in any added line of the same file. At or above 0.7 it is a rewrite, below it is a loss. Fail-closed: a line with no tokens has overlap 0.

**Allowlist.** Entries are a PR number, a file path, an optional line fingerprint and a reason. Scoped to one PR and optionally to one line (SHA-1 prefix of the trimmed content). A bare path is deliberately not supported, because it would exempt that file in every future PR, including the files the original incident hit.

**CI wiring.** A separate job "Silent Revert Guard", full history (`fetch-depth: 0`) because blame needs it, runs the script's own unit tests first, then the check with the PR number, head SHA and a read-only token. Skipped for docs-only PRs through the shared path filter.

**Frontend test wiring.** Before: the `src/` folder had vitest and jsdom installed and 50 test files, but no `test` script and no job that entered `src/`; every test step in the workflow was inside `api/`. After: a `test` script, `environment: 'jsdom'`, and a job "Frontend Unit Tests (ACA PR)" with the same path filter. I proved the job could fail by breaking an assertion on purpose. Promoted to required on 2026-08-07 by the repo owners.

**Other gates I added.** The enclosure guard (#1364) scans the chat view for durable state changes that bypass a single durable-state-change seam; its tests include a scanner test so that the detector itself is verified. The seed-slot audit (#2077) unions every uuid `id` in every table through `information_schema` and asserts that each exported seed constant resolves; the commit records a mutation proof: green with the dedupe intact, red with it bypassed, green again.

## 5. Why it was built this way (decisions and trade-offs)

| Decision | Alternatives considered | Why this one | Cost / risk |
|---|---|---|---|
| Check **content** removed by a PR, using blame + ancestry | Compare file sizes; a path-protection list; require "up to date" branches; rely on code review | Nothing else sees it: the branch is current, the diff looks intentional | Needs full history and GitHub API; false positives on moves |
| Origin from ancestry / force-push history | Author dates; PR creation date; `min` of both | Dates are rewritten by squash, PR date can be late | Depends on GitHub's timeline events |
| Fail closed everywhere (blame, ancestry, GraphQL) | Fall back to a heuristic | A gate that guesses when blind passes the case it was built for | A flaky API blocks merges |
| Allowlist scoped to PR + line fingerprint | Bare path exemptions | Bare paths would permanently unguard the clobbered files | Authors must add entries for legitimate moves |
| Ship as visible-but-advisory first | Required from day one | No ruleset change needed to land; admins promote after trust builds (commit body) | Not binding until promoted; later done by admins |
| Separate CI job with full checkout | Add to the lint job | Lint job is shallow and fast | One more job (~full clone) |
| Prove a gate can go red | Assume it works | "A CI job that cannot fail is not a CI job" (commit 531096ef) | A few extra minutes of work |
| Wire existing tests before writing new ones | Rewrite the frontend suite | Biggest value per line: three lines made 575 tests count | Reveals no quality information by itself |

## 6. Theory behind it (the "lecture" part)

### 6.1 Git history: merge-base, rebase, squash, force-push
A commit graph is a DAG. The *merge-base* of two commits is their nearest common ancestor; a PR diff is normally head versus merge-base. *Rebase* rewrites a branch's commits onto a new base (new hashes); *squash-merge* collapses a branch into one new commit on the target; *force-push* replaces a remote branch head, discarding the old history from the branch's view. After a rebase or squash, author and committer dates no longer say when the content was first written. `git merge-base --is-ancestor A B` answers "is A reachable from B" using the graph only, which is immune to date rewriting.
*In my project:* the guard compares the introducing commit of a removed line with the branch's true origin by ancestry, not by dates.

### 6.2 Line attribution with blame and its limits
`git blame` maps each line of a file at a revision to the commit that last changed it. It follows the file's history but a moved or reformatted line is attributed to the commit that moved it. So blame answers "who last touched this line", which is only a proxy for "who introduced this content". Heuristics (similarity thresholds, move detection) trade false positives against false negatives.
*In my project:* a code move that left shims behind made blame point to a later commit and triggered a false alarm (PR 2609).

### 6.3 Similarity by token overlap (containment)
Represent a line as a set of tokens A. For a removed line A and an added line B the *containment* is |A ∩ B| / |A| (how much of the old line survives); Jaccard similarity is |A ∩ B| / |A ∪ B| and penalises long additions. Containment is the right direction when asking "did this content survive somewhere". A threshold t splits the lines into rewrite (≥ t) and loss (< t). Raising t increases alarms (more false positives), lowering it hides real losses (false negatives). Example: removed line `deny: true` has 2 tokens; an added line `deny: false` keeps 1 of 2, containment 0.5, so it counts as a loss.
*In my project:* t = 0.7, chosen from merged PRs and "unretuned" since the footer convention it was tuned against was deleted.

### 6.4 CI gates, required checks and bypass
A *status check* reports pass/fail on a commit; branch protection or a ruleset can mark checks *required*, blocking merge until they pass. An *advisory* check is visible but not binding. A *bypass actor* can merge regardless. A control's strength is the weakest of: it exists, it runs on every change, it is required, and nobody can skip it silently. Also: a check that never fails gives no information, so prove it can fail (inject a defect).
*In my project:* both of my gates started advisory, were promoted by admins, and are bypassable by the code owners.

### 6.5 Tests that exist but do not run
Assurance comes from tests *executed* on every change, not from tests *written*. Typical causes: a missing script, a wrong working directory, a path filter that excludes the folder, a skipped suite. Detection: count executed tests in CI output, make "zero tests found" a failure, and review the list of jobs against the list of test folders. Related: a test that passes vacuously (nothing asserted, or asserting an empty set) is the same failure; guard with a positive control or a mutation (break the code, expect red).
*In my project:* 50 files and 575 frontend tests passed the first time they ran, because nobody had run them in CI before.

### 6.6 Concurrency and conflicts in a high-throughput trunk
With k pull requests in flight and a pairwise chance q that two of them touch overlapping lines, the chance that a given PR overlaps at least one other is 1 − (1 − q)^(k−1). It grows quickly with k, so a team that merges several PRs a day with AI help gets more rebases, more conflicts and more chances for a wrong resolution. Mitigations: small PRs, merge queues (test the merge result), re-running gates after a rebase, and content-based guards like this one.
*In my project:* my merge-skill fix (#1971) re-runs invalidated gates before retrying a rebased merge; the guard is the content-level backstop.

### 6.7 Least-exemption design
Any gate needs an escape hatch, and the hatch should be as narrow as the justification: scoped by change (PR), by object (line fingerprint) and by time (it stops applying when the PR merges), with a mandatory reason.
*In my project:* allowlist entries are a PR number, a file path, a line fingerprint and a reason; two file-scoped entries exist only for PR 2609.

## 8. Glossary

| Term | One-line definition |
|---|---|
| Silent revert / stale-rebase clobber | A PR that deletes already-merged content because of a wrong rebase or old branch copy |
| Merge-base | Nearest common ancestor commit of two branches |
| Ancestry test | `merge-base --is-ancestor A B`: is A reachable from B |
| Origin (of a branch) | The commit it was originally cut from, before any rewriting |
| Squash merge | Merging a branch as one new commit; rewrites dates and hashes |
| Force-push | Replacing a remote branch head; discards earlier history from that branch |
| Blame | Mapping each line to the commit that last changed it |
| Containment | |A ∩ B| / |A|: share of old tokens that survive in new text |
| Fail-closed | When uncertain, the check fails rather than passes |
| Required status check | Check that must pass before merge |
| Advisory check | Visible result that does not block |
| Bypass actor | Account allowed to merge without meeting the rules |
| Allowlist (here) | PR-scoped, line-scoped exemption with a reason |
| Mutation proof | Break the code on purpose and show the test goes red |
| Path filter | CI rule that runs jobs only when certain folders change |

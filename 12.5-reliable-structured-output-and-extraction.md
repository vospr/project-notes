**In short:** Reliable structured output and document extraction: schema-constrained output, semantic errors and how to fix them, conflicting values with provenance, validate-and-retry with the error, long documents, batch scheduling against an SLA, and routing human review.

## 2. The problem (business view, plain English)

Extraction turns documents (invoices, contracts, CVs, transcripts) into rows a downstream system accepts. Downstream systems are strict: a missing field, a string where a number belongs, or a total that does not add up gets rejected or, worse, booked. Prompting "return only JSON" works most of the time; the failures arrive as malformed JSON, invented values, the wrong one of two conflicting numbers, and quiet drops on long documents.

Finance analogy: accounts-payable capture. A good AP clerk copies what is on the invoice, writes "not stated" rather than guessing, checks that the lines sum to the total, flags amended terms with the amendment date, and passes only the doubtful invoices to the senior accountant. The pipeline should behave the same way.

## 4. How it works (an extraction pipeline)

```
 documents ─► pre-check (size, type, language) ─┬─ fits ─────────────► extract (schema-constrained)
                                                 └─ too long ─► chunk ─► extract per chunk ─► merge + dedupe
                                                                                  │
                                       validate (schema + business rules: sums, dates, ranges)
                                         ├─ pass ─► confidence / ambiguity check ─┬─ clear ─► store
                                         │                                       └─ doubtful ─► human review queue
                                         └─ fail ─► retry with the exact validation error (max 2) ─► still failing ─► review
                                                                                  │
                         reviewer corrections ─► error analysis ─► few-shot examples, schema fixes ─► eval set
```

Batch path: documents accumulate for a fixed window, are submitted as a Message Batch (half price, results within 24 hours), results are matched back by `custom_id`, failed items are fixed and resubmitted alone.

## 5. Why it is done this way (decisions and trade-offs)

| Decision | Alternatives | Why this one | Cost / risk |
|---|---|---|---|
| Schema-constrained output (structured outputs or a strict tool) | Prompt JSON, regex, prefill | Guarantees syntactically valid, schema-shaped output | Schema features are limited (some keywords unsupported); check current |
| Nullable fields, "not stated" allowed | All fields required | Removes pressure to invent values | Downstream must handle nulls |
| Raw text + normalised value | Normalised only | "2 to 3" or "a handful" kept verbatim; no invented precision | Two fields to maintain |
| Multiple values with source and effective date | Single field, precedence rule | Conflicts and amendments stay visible; downstream applies policy | More complex schema |
| Calculated vs stated total, flag mismatch | Trust either; auto-adjust | Catches OCR and model errors without falsifying | Review workload |
| Retry with the validation error | Blind retry, bigger model | The model fixes the specific problem | Extra call; cap it |
| Chunk, extract, merge for long documents | One pass; summarise first | Accuracy on scattered facts | Merge and dedupe logic |
| Route review by uncertainty | Random sample; by entity type; after downstream failure | Puts scarce reviewers where errors are | Needs a reliable uncertainty signal; keep a small random sample to measure |

## 6. Theory (the lecture)

### 6.1 Ladder of output control
| Level | What it guarantees |
|---|---|
| Instructions ("return JSON with fields ...") | Nothing |
| Few-shot example of the exact JSON | Better format adherence; shows field semantics |
| JSON mode (some providers) | Valid JSON, any shape |
| Tool use with an input schema | The model fills a schema-shaped object; validation still advisable |
| **Constrained decoding**: Claude structured outputs (`output_config.format` with a JSON schema) or a tool with `strict: true` | Output validates against the schema |
| Your validation (Pydantic, JSON Schema, business rules) | Semantic and cross-field checks |

Constrained decoding removes syntax and shape errors. It does not make values right: an array can be validly empty, a required string can be validly invented. That is the semantic layer.

For a classifier with fixed labels ("In Stock" / "Out of Stock") the prompt must state the input, the task and exactly the allowed outputs; in 2026 an enum in a structured output makes the label set binding.

### 6.2 Semantic errors and how to fix them
- **Information present but in varied formats** (inline citations vs bibliography; methodology inside the introduction): few-shot examples that show each variant and where to find the field.
- **Fabrication under pressure** (informal measurements turned into exact amounts, or left empty): allow and show verbatim extraction ("a handful") and nulls; add a field for the measurement type if downstream needs it.
- **Inconsistent numbers** (line items do not sum to the total in 18% of invoices, from OCR or model errors): extract the stated total and compute the sum separately; when they differ, flag for review. Never adjust amounts to make them agree.
- **Conflicting values in the source** (summary says 4000 mAh, spec table 4200 mAh): capture every value with its source location; let downstream apply precedence. The same for **amendments**: each value with its source and effective date, so "current" is a rule, not a guess.

### 6.3 Validate and retry
A validation failure is information. Send the model its previous output and the exact error ("`quantity`: expected float, got '2 to 3'") and ask for a corrected output; often the right fix is a schema change (a range, or raw text plus min/max). Retrying the same request without the error reproduces the same output. Cap the loop (one or two repairs), then route to review. A larger model for failures is a fallback, not the first fix; preprocessing the source to "standardise" formats moves the extraction problem into brittle code.

### 6.4 Long documents
Even when a document fits the window, accuracy drops when the facts are scattered (94% on short transcripts vs 68% on long ones in one practice scenario). Pattern: split into chunks with some overlap along natural boundaries (topics, sections), extract per chunk with the same schema, merge, deduplicate, and resolve conflicts with provenance. A summarise-first step loses detail before extraction starts. For documents beyond the window, split to a safe share of it (around 80%), process each part, and aggregate (map-reduce).

### 6.5 Dependent steps
If enrichment needs a value from extraction (a DOI), order the steps in code: call 1 extracts (structured outputs), call 2 enriches with the extracted value and the enrichment tools. Forcing a specific tool on every call stops enrichment from ever running; `tool_choice: any` only forces some tool; tool order in the array is not a priority signal.

### 6.6 Message Batches (Claude API)
Batches cost **50% less**, accept up to 100,000 requests or 256 MB per batch, usually finish within an hour, and **expire after 24 hours**: that is a deadline, not an SLA. Results arrive in any order, so key them by `custom_id`. Scheduling rule: worst-case latency = time a document waits for the next submission + 24 h. With a 30-hour SLA, submitting every 4 hours gives 28 h worst case; every 6 hours gives exactly 30 h with no margin; once a day breaks the SLA. User-facing work stays on the real-time API.

Recovering failures: resubmit **only** the failed items after fixing their cause (`context_length_exceeded` → chunk those documents and combine the partial extractions). Re-running the full batch pays twice for 97% of the work; `max_tokens` controls output length, not input. Prompt caching can be combined with batches for a shared system prompt.

### 6.7 Human review with limited capacity
With capacity for about 5% of volume, route by **uncertainty**: low model-reported confidence, failed cross-checks (sums, dates), conflicting or ambiguous sources, unusual document types. Add a small random sample so you can measure the error rate of what is *not* reviewed (otherwise you only see the errors you predicted). Routing all financial figures regardless of confidence overwhelms reviewers; waiting for downstream failures finds problems after damage.

Reviewer corrections are the best training signal you have: analyse them by pattern (23% of corrections were informal measurements), fix the prompt and schema (examples, verbatim fields), and add the cases to the eval set. Fine-tuning on a few hundred corrections is rarely the first move.

### 6.8 Measuring extraction
Report schema-valid rate, field-level precision and recall (exact or normalised match), document-level all-fields-correct rate, and the share routed to review; weight money and date fields as zero-tolerance (10.1).

## 8. Glossary

| Term | One-line definition |
|---|---|
| Structured outputs | API feature that constrains the response to a JSON schema |
| Strict tool use | Tool arguments guaranteed to match the schema |
| Constrained decoding | Generation restricted to tokens that keep output valid for a grammar or schema |
| JSON mode | Output is valid JSON but any shape |
| Prefill | Starting the assistant's reply for it; removed on current Claude models |
| Validation-retry loop | Sending the exact validation error back for a corrected output |
| Provenance | Where in the source a value came from |
| Effective date | Date from which an amended term applies |
| Self-consistency check | Cross-field rule such as line items summing to the total |
| Map-reduce extraction | Extract per chunk, then merge |
| Message Batches | Asynchronous API at half price with a 24-hour expiry |
| `custom_id` | Your key for matching batch results to requests |
| Uncertainty routing | Sending low-confidence or conflicting cases to human review |

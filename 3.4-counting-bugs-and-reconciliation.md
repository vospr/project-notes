# Course 3 · Chapter 3.4: Counting bugs and reconciliation: double-counting, session resumes, frozen snapshots, retraction

_Andrey Popov's project notes: how it works, why it was built this way, and the theory behind it._

**In short:** The token-counting bugs found before publishing any cost: Claude totals about 2x too high (usage repeated per content block) and Codex too low (counter resets on resume). Fixes, hashed frozen snapshots, an independent audit script and a public retraction.

## 2. The problem (business view, plain English)

Before any cost figure could be published, the token counts had to be right. They were not. The first Claude figures were about twice too high. The first Codex figures were too low. Both errors were found by re-running the collectors, not by anyone outside. If I had published a cost per ticket on those counts, I would have been wrong by a factor and would not have known.

Finance analogy: a sub-ledger that double-posts every invoice line, and a feeder system whose counter resets at month-end so the closing balance misses the earlier runs. You do not publish the P&L. You find the posting rule that causes it, fix it, reconcile the sub-ledger to a control total, and restate anything already circulated.

## 4. How it works (technical walkthrough)

```
Claude JSONL  ── record per content block ──► group by (message.id, else uuid, else line)
   parent files + subagent files                  one canonical event per key, first usage wins
                                                 subagent event dropped if its id is in a parent file
                                                 filter by record timestamp in [since, until)
                                                 sum 4 buckets per (licence, scope, ticket, model)

Codex JSONL  ── cumulative total_token_usage ──► delta = current − previous
   rollout appended across resumes                if any bucket decreases → reset: delta = current
                                                 filter by record timestamp in [since, until)

Capture ► freeze JSON + SHA-256 ► next adjacent capture [cut, end) ► sum rows with identical dimensions
              │                                                       do NOT sum session counts
              └── independent audit script recomputes events and tokens → must match exactly
```

**Claude, defect and fix.** Claude Code writes one record per content block (thinking, text, tool call). Every record repeats the whole message's usage object. Summing per record multi-counts. Fix: key each record by `message.id` (the API response id, the unit that bills), then `uuid`, then line number as fallbacks, keep one canonical event per key, and drop later copies (`read_usage_from_bytes`, *TS.py:228–300*). Measured: about 30,000 records carried about 15,000 distinct ids, and cache-read fell from 7.93 billion to 3.94 billion.

**Parent and subagent files.** Subagent logs are separate files. If a subagent event has an explicit id that already appears in any parent file, the subagent copy is suppressed ("parent-first"). This happens before the time filter, so even an out-of-window parent id suppresses a matching in-window subagent event. Fallback ids (uuid, line number) never reconcile across files. The first check had said "no id appears in more than one file", which was true for parent files only; 24 ids recur only among subagent files and are each counted per file.

**Codex, defect and fix.** `total_token_usage` is cumulative per process, but a rollout file is appended across resumes and the counter restarts at zero. The old rule "take the last value" drops earlier runs. The new rule is a running delta: if any bucket decreases, the stream has reset, and that emission's delta is its current value (`read_session`, *CX.py:102–172*). This equals the sum of each run's final value. Never sum every emission: that over-counts 111×. Resets do not line up with the `compacted` markers; the signal is a decrease in the counter. The old rule was right for the 469 of 481 sessions that never reset.

**Half-open windows and record time.** Each period is `[start, end)`. Records are bucketed by their own timestamp, never by file modification time, because sessions are resumed across period boundaries (a file in the 10 August directory had an mtime of 18 August). Adjacent captures use `[start, cut)` and `[cut, end)` with `cut` identical, so there is neither a gap nor an overlap. A Codex test fixes this: the record timestamp wins over a contradictory mtime.

**Additivity across captures.** Tokens and events add only across rows with identical `(surface, licence, scope, ticket, model)`. Session counts do not add, because one file can have records on both sides of the cut.

**Frozen snapshots and digests.** Every capture is stored as JSON with the exact command, collector path and SHA-256, the interval, the capture time and aggregate diagnostics, and no transcript text. A test pins the digests of the real frozen artifacts.

**Reconciliation checks.** (a) An audit script recomputes events and tokens without importing the collector and must match exactly. (b) Four adjacent September captures were compared with a fresh full-month run: cache-read tokens and canonical events differed by 0 for both tools. (c) Zero invalid timestamps, missing models or unreadable roots in the full-month run.

## 5. Why it was built this way (decisions and trade-offs)

| Decision | Alternatives | Why this one | Cost / risk |
|---|---|---|---|
| Key by message id | Count records; key by uuid | The id is what bills; records repeat usage per block | Relies on an undocumented log format |
| First usage wins for conflicting copies | Max, last, or drop conflicts | Deterministic, byte-stable output ||
| Parent-first suppression of subagent copies | Global de-dup across all files | Subagent files are billed independently; global de-dup could remove real events | 24 subagent-only reused ids are counted per file |
| Reset-aware delta for Codex | Last value; max; sum of all | Matches how the counter behaves; reduces to the old rule when no reset | Any bucket decrease triggers a reset; edge cases unknown |
| Record timestamp, half-open windows | File mtime; closed intervals | Resumed sessions; no gap or double edge | Records with bad timestamps are excluded and counted in diagnostics |
| Adjacent captures plus full-month check | Single capture at month end | Logs expire at about 30 days; capture early | More artifacts to manage |
| Independent audit script | Trust the collector | A second implementation catches coding errors ||
| Withdraw and re-state, label "not currency" | Quietly fix | Anything already shown stays traceable | Embarrassing but cheap |

## 6. Theory behind it (the "lecture" part)

### 6.1 Idempotent counting and natural keys
When the same fact can be recorded more than once (retries, per-part records, replays), counting rows over-counts. The standard cure is a **natural key** that identifies the real-world event, then **deduplicate on the key** so that processing the same input twice gives the same result. Choose the key from the unit that matters downstream: here, what bills. Define a rule for conflicting duplicates (first, last, max) and count the conflicts.

*In my project:* the key is `message.id`; fallbacks are `uuid` then line number; conflicts are counted in diagnostics.

### 6.2 Cumulative counters and resets
A **cumulative counter** only increases within one process lifetime and restarts at zero when the process restarts. To get usage in an interval, compute **deltas** and treat a decrease as a reset (the new value is the amount since restart). Monitoring systems do the same when computing rates from counters. Taking the last value, or the max, ignores earlier runs. Summing every reading counts the same usage many times.

*In my project:* the Codex rule is exactly "delta, with reset detection". Edge case: a decrease in one bucket resets all five.

### 6.3 Event time versus processing time; half-open intervals
**Event time** is when the thing happened (record timestamp). **Processing time** is when your system saw or stored it (file mtime, ingest time). Reports for a period must use event time, otherwise late or resumed data lands in the wrong period (a **cut-off error** in accounting). Use half-open intervals `[a, b)` so adjacent periods partition the timeline exactly.

*In my project:* every collector filters on record timestamps with `[since, until)`; a test shows record time beating a contradictory mtime.

### 6.4 Additive and non-additive measures
A measure is **additive** if the total over a partition equals the sum of the parts. Sums of tokens and events are additive across disjoint time slices with identical dimensions. A **distinct count** (sessions) is not: an item that appears in two slices is counted twice. Averages and percentiles are not additive either.

*In my project:* tokens and events add across the two chunks; sessions and qualifying-session diagnostics do not.

### 6.5 Reconciliation, control totals and independent verification
**Reconciliation** compares two computations of the same quantity that should agree (sub-ledger to general ledger; chunked run to full run). A **control total** is a figure computed separately to check completeness. Value comes from **independence**: different code, different inputs, or a different method. Weakness: **common-mode failure**, where both computations share the same wrong assumption and agree on a wrong answer. Only an external source (the vendor's own usage report, the invoice) breaks common-mode failure.

*In my project:* the audit script and the full-month run catch implementation and chunking errors. Nothing here checks the log-semantics assumptions against the provider.

### 6.6 Immutability, provenance and hashing
A **cryptographic hash** (SHA-256) of an artifact detects any later change. Combined with the exact command, tool version hash and interval, a frozen output is **provenance-complete**: someone else can tell what produced it. A frozen snapshot is the only way to keep a number reproducible when its source is deleted.

*In my project:* every snapshot has the command, collector digest and interval, and the artifact digest is recorded in the notes.

### 6.7 Restatement and retraction
When a published number is found wrong, the professional response is a **restatement**: say that it was wrong, by how much, which direction, why, and which documents are affected; then correct. Distinguish a **correction** (error) from a **revision** (new information). Keep the old text visible with a banner rather than deleting it.

*In my project:* two banners ("every absolute figure below is wrong"; "every token figure below is wrong"), a list of invalidated documents with what is wrong in each, and the observation that one finding survives because both errors moved in directions that widen the gap.

## 8. Glossary

| Term | One-line definition |
|---|---|
| Canonical event | The single kept record for one message id |
| `message.id` | The API response identifier; the unit that bills |
| Content block | One part of an assistant message (thinking, text, tool call); one log record each |
| Parent / subagent file | The main session log / the log of a delegated agent; billed independently |
| Parent-first suppression | Drop a subagent event whose explicit id already occurs in a parent file |
| Cumulative counter | A total that only rises while a process lives |
| Counter reset | The counter returns to zero (here: on resume) |
| Monotonic run | A stretch of a cumulative stream with no decrease |
| Half-open interval | `[start, end)` |
| Frozen snapshot | A stored capture with command, interval and SHA-256 |
| Additive vs non-additive | Sum of parts equals total / does not (distinct counts) |
| Cold oracle | A second, independently written implementation used to check the first |
| Common-mode failure | Two checks fail the same way because they share an assumption |
| Restatement | Publicly correcting a figure with the reason and the size of the error |

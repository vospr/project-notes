# Course 8 · Chapter 8.3: Hooks that really block: the hook contract and how to verify it

_Andrey Popov's project notes: how it works, why it was built this way, and the theory behind it._

**In short:** Hooks that actually block: the first version could never fire (wrong config shape, env vars instead of stdin JSON, exit 1 instead of 2). The fix has a red-then-green record (5 pass, 26 fail, then 31/31) and a live session where a write was blocked.

## 2. The problem (business view, plain English)

Rules written in a prompt are requests. A model can ignore them under pressure or in a long session. For the few rules that must hold ("do not write outside these folders", "no code before there is a plan") the template wanted something outside the model that says no. The first version had such scripts, but none of them could ever fire, and the README advertised them as an "enforcement layer". The October revision made them work and proved one of them blocks a real session (*Redo* item 1).

Finance analogy: a pre-trade limit check in the order system versus a policy memo. The memo says "do not exceed 5 million". The limit check rejects the order. And if the limit check was never connected to the order flow, then a green dashboard "limit check: OK" means nothing. Auditors test it by sending an order that should be rejected and showing that it was.

## 4. How it works (technical walkthrough)

**Config (nested, current).** Each event holds matcher groups; each group holds a `hooks` array of `{type: "command", command}` (; *DOCS* "Hook configuration"). The old file put `command` directly on the matcher entry (`git show e9e1b2d:.claude/settings.json`), which is not the current shape. Check H1 asserts the shape with `jq`.

**Input (stdin JSON).** Per *DOCS*, command hooks read one JSON object on stdin: common fields (`session_id`, `cwd`, `hook_event_name`, …); `tool_name` and `tool_input` for PreToolUse; inside a subagent also `agent_id` and `agent_type`; `last_assistant_message` for SubagentStop. The repo's own header says the same. The old scripts read `$TOOL_NAME`/`$TOOL_INPUT` environment variables instead (`git show e9e1b2d:.claude/hooks/enforce-paths.sh` lines 9, 16); with those variables empty, they hit "empty input, exit 0" at once. Check H2 greps the new scripts for those names. The live proof records the real payload: `hook_event=PreToolUse tool_name=Write file_path=…/src/evil.txt` (*EV-live* line 11), so the field names for PreToolUse/Write are observed, not assumed.

**Exit codes.** Per *DOCS*: `exit 0` = success; `exit 2` = blocking error on events that can block, and stderr is fed back as the reason; any other non-zero code (including 1) is a non-blocking error and "Claude doesn't see it". The old scripts used `exit 1` (`git show e9e1b2d:.claude/hooks/enforce-paths.sh` lines 45, 53), so even with the right input they would not have blocked. A script can also deny through JSON on exit 0 (`permissionDecision: "deny"`); the template uses the exit-code route.

**Which events can block**: PreToolUse (blocks the call), UserPromptSubmit, Stop and SubagentStop (prevent stopping), and several others. PostToolUse cannot block, because the tool has already run. SubagentStop on exit 0 does not reach the model, which is why the two advisory hooks write files that `CLAUDE.md` Step 6a tells the dispatcher to read.

**The four hooks.**

| Hook | Event / matcher | Effect | Evidence level |
|---|---|---|---|
| `enforce-paths.sh` | PreToolUse `Write\|Edit` | Resolves `..` and symlinks, compares to the allowlist, `exit 2` with a message that names the allowed folders | Unit (H3–H5) **and live run** |
| `enforce-sequencing.sh` | PreToolUse `Agent\|Task` | Blocks `subagent_type == implementer` if no `planning-artifacts/*plan-*.md` | Unit (H6–H7) only |
| `warn-dor-dod.sh` | SubagentStop (4 agents) | Logs missing citations, missing `AC-n`, nonexistent cited paths to `hook-warnings.log`; always `exit 0` | Unit (H8–H9) only |
| `extract-knowledge.sh` | SubagentStop (6 agents) | If at least 5 signal lines, appends `EXTRACT_KNOWLEDGE_SIGNAL` to `.hook-signals`; `exit 0` | Unit (H10) only |

The first two are **preventive** (stop the action). The last two are **detective** (record and warn): they change nothing unless the dispatcher reads their files, which is again an instruction.

**The verification ladder, rung by rung.**

```
1  static shape       H1 (config shape), H2 (no env-var reads)       cheap, proves nothing about behaviour
2  synthetic stdin    H3-H11: pipe handmade JSON into the script      proves the script, given MY belief about the contract
3  live session       LIVE: real claude -p, payload recorder +        proves the PLATFORM sends what I assume
                      tool_result is_error=true + file absent          and honours exit 2
4  re-run on upgrade  not built                                       catches contract drift
```

- **Rung 2 design.** `run_hook` pipes a JSON payload into the script in a throwaway copy of `.claude/`, with `CLAUDE_PROJECT_DIR` set. The checks assert `RC == 2` and "BLOCK" on stderr for the blocking cases.
- **Rung 3 design.** The sandbox gets a copy of `.claude/`, an extra PreToolUse hook that only records the payload and always exits 0, so a block can only come from `enforce-paths`. It asks the model to write `src/evil.txt`, with `--allowedTools Write` so that the permission system will not stop it first, then prints three things: the payload, the `tool_result` blocks (`is_error=true` with the BLOCK text and the allowed folders), and the final message; finally whether the file is absent (; *EV-live* lines 11, 14-16, 30). That shows the whole loop: payload in, exit 2, stderr returned to the model, action not performed.
- **Before/after discipline.** The checks were committed with the baseline run (5 pass, 26 fail) before the fix commit (`b8e2c8d` then `2826233`, both on 2026-10-01), and the final run is 31/31. That is a red-then-green record.

## 5. Why it was built this way (decisions and trade-offs)

| Decision | Alternatives | Why this one | Cost / risk |
|---|---|---|---|
| Block with `exit 2` and a human-readable stderr | JSON `permissionDecision: deny` | Simplest; stderr is returned to the model so it can correct itself | Exit-code contract is easy to get wrong (it was) |
| Shared `lib.sh` reading stdin once | Each script parses itself | One place for the contract; `jq` with a grep fallback | The fallback is untested |
| Fail-open on empty or malformed input | Fail-closed (block when unsure) | A hook must never wedge a session on a bad payload | Silent loss of the guard on contract drift |
| Fail-closed when the allowlist cannot be loaded | Allow | "Refusing to guess" | Misconfiguration blocks all writes |
| Allowlist on Write/Edit only | Sandbox / permissions | Cheap guard against accidents | Bash and other tools bypass it |
| Advisory hooks write files | Print to stdout | SubagentStop stdout never reaches the model | Works only if the dispatcher reads the files |
| Checks written before the fix, baseline logged | Fix then test | Shows the checks can fail | Some checks passed vacuously |
| Live proof in a sandbox copy with a payload recorder | Trust the unit checks | Tests the platform assumption | One tool, one run, one version |

## 6. Theory behind it (the "lecture" part)

### 6.1 A hook is a process contract
A command hook is a small program run with a defined **interface**: input on stdin, output on stdout/stderr, and an **exit status**. POSIX defines exit 0 as success and non-zero as failure; it does not say which non-zero value means what. The host application assigns meaning (here: 2 = block). That is a Unix-filter-style contract, simple but weak on types: nothing stops you writing `exit 1` and believing it blocks. Rules for a robust consumer: validate input shape, define behaviour for every exit code, and test against the host's real behaviour, not only your reading of the docs.

*In my project:* the first version broke three parts of the contract at once: config shape, input channel (env vars instead of stdin) and exit code (1 instead of 2). Any one of them was enough to make the guard inert.

### 6.2 Enforcement points: preventive and detective controls
Access-control systems separate the **policy decision point** (PDP, decides allow or deny) from the **policy enforcement point** (PEP, makes it stick). A hook is a PDP. The platform's tool call is the PEP, and it only enforces if it is wired to the PDP and honours its answer. Controls are **preventive** (stop it happening) or **detective** (find out afterwards). A pre-trade limit check is preventive; end-of-day reconciliation is detective. Good designs have both: detective controls tell you when a preventive control has a hole.

Also: a check that happens before use (`check`) and an action that happens later (`use`) can disagree if the world changes in between (time-of-check to time-of-use). The path hook resolves a symlink at check time; the tool writes later.

*In my project:* `enforce-paths` and `enforce-sequencing` are preventive; `warn-dor-dod` and `extract-knowledge` are detective but only effective if the dispatcher reads their files. There is no detective control for the holes (Bash writes), such as a post-run `git status` outside the allowlist.

### 6.3 Fail-open versus fail-closed (again)
The same trade-off as in chapter 1.4 (NULL in SQL). A guard that cannot evaluate its input must pick a side. Fail-closed is safer for security; fail-open is safer for availability. A hook runs in the user's interactive loop, so a crash that blocks every tool call is very costly, which is why most hooks fail open on malformed input. The cost: **silent degradation**. Mitigation is a canary: a regular check that the guard still blocks a known bad case.

*In my project:* fail-open on empty input (by design), fail-closed on an unreadable allowlist. The missing piece is the canary.

### 6.4 Testing a guard: positive, negative, vacuous
A guard has two behaviours. **Block** the bad case, **allow** the good case. Tests must cover both, and the block tests carry the proof. A test suite where every test expects "allow" passes on a guard that does nothing: this is a **vacuous pass**. Good practice is the red-green record: run the new tests on the old code and show that they fail, then fix and show that they pass. A cruder cousin is **mutation testing**: break the code on purpose and check that some test notices.

Then there is the **test oracle** problem: synthetic payloads encode *your belief* about the platform. A unit test of the script proves the script handles that payload. An integration test with the real platform proves the belief. Version pinning matters: record the platform version with the result, and re-run after upgrades.

*In my project:* the baseline log shows 3 vacuous passes and 26 genuine failures, and the live run closes the belief gap for one hook.

### 6.5 Calibrating a claim to its evidence
A claim should be no stronger than the weakest link in its evidence chain. "Hook X blocked tool Y in session S on version V" is an observation. "Hooks work" is a generalisation over hooks, tools, versions and sessions. Ladders like 6.4's name the step each claim has reached.

*In my project:* site wording ("the path hook is verified blocking a live session") is calibrated; the CV bullet's plural is slightly looser.

## 8. Glossary

| Term | One-line definition |
|---|---|
| Hook | A command or other handler Claude Code runs at a lifecycle event |
| PreToolUse | Event fired before a tool call; can block it |
| SubagentStop | Event fired when a subagent finishes; exit 2 stops it from finishing |
| Matcher | The filter on a hook group: tool name for tool events, agent type for subagent events |
| Exit code 2 | The blocking code; stderr is fed back as the reason |
| Non-blocking error | Any other non-zero exit; the action goes ahead and the model is not told |
| `CLAUDE_PROJECT_DIR` | Env var with the project root, exported to hook processes |
| PDP / PEP | Policy decision point / policy enforcement point |
| Preventive / detective control | Stops the event / finds it afterwards |
| Fail-open / fail-closed | Allow / deny when the guard cannot decide |
| Vacuous pass | A test that passes even if the thing under test does nothing |
| Red-green | Show the test failing on the old code, then passing on the fix |
| Canary | A recurring known-bad probe that proves the guard still works |
| TOCTOU | Time-of-check to time-of-use gap |
| `disableAllHooks` | Setting that turns off all hooks at once; no per-hook switch |

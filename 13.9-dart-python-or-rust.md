# Course 13 · Chapter 13.9: Why `fa` chose Dart, what a Python version would look like, and is Rust faster?

_Andrey Popov's project notes: how it works, why it was built this way, and the theory behind it._

**In short:** Why flutter_agent_harness uses Dart (one core for seven hosts, sealed event types), what a Python version would look like, the 2026 Python agent stack, and whether Rust would be faster (mostly no; where it helps).

## 2. The problem (business view, plain English)

Teams spend weeks arguing about which language to build their agent in. They usually argue about speed. But an agent spends almost all of its time **waiting**: for the model to answer, for Jira to respond, for a web page to load. The language decides other things: **where the agent can run** (server, phone, browser, laptop), **how cheaply you can run many of them**, **how easy it is to install**, and **which libraries you get for free**. Those are the real questions.

Analogy: choosing between a car, a van and a motorbike for a trip where you spend 95% of the time stuck at border control. The vehicle doesn't change the arrival time much. It changes how many people you can carry, where you can park, and what fuel costs.

## 4. How it works

### 4.1 Why `fa` is written in Dart: one core, seven places
`fa` wants **one** agent engine that runs in seven places: the terminal, macOS, iOS, Android, the web browser, a browser extension and an Outlook add-in (`11.1` §4.6). Dart is one of very few languages that does all of these well:

- **Flutter** (Dart's UI toolkit) builds phone and desktop apps from one codebase.
- Dart compiles **to native code** for the terminal and apps, and **to JavaScript or WebAssembly** for the browser.
- So the rule "no `dart:io` in the core" (`11.1` §4.2) is how they keep the engine browser-safe: anything touching files or processes sits behind one interface (`ExecutionEnv`).

The second reason is **safety by the compiler**. Events such as "text arrived", "tool call finished" and "error" are *sealed* types: a closed list the compiler knows about. If someone adds a new event type, every piece of code that handles events **refuses to compile** until it handles the new one too. The bug shows up on the developer's screen, not in production at 3 a.m.

The third reason is history: `fa` is a port of a TypeScript design (pi-mono), and its author's earlier assistant was already in Dart.

**What is *not* the reason:** speed of the agent loop. Dart is faster than Python at raw computing, but the agent waits on the model just as long.

### 4.2 The same harness in Python: block by block
| What `fa` needs | Dart way | Python way | What you lose or gain |
|---|---|---|---|
| A closed list of event types the code must handle | `sealed` classes + exhaustive `switch` (compiler enforces) | Pydantic models or dataclasses in a union, `match` statement, plus a type checker (pyright or mypy) with `assert_never` | Python only warns if you **run the type checker** in CI; the program itself still runs with a missing case |
| Many things waiting at once (model stream, tools, timers) | single-threaded event loop, `Future`, `Stream` | `asyncio` event loop, `async`/`await`, async generators | Almost identical idea. Python's `asyncio` and Dart's event loop are cousins |
| Stop everything when the user presses Esc | `CancelToken` passed down by hand | `asyncio` cancellation: `task.cancel`, `TaskGroup` (3.11+) cancels all children when one fails, `asyncio.timeout` | Python's is built in and structured; you get it nearly for free |
| Truly parallel CPU work | **isolates**: separate workers with their own memory, talking by messages | processes (`multiprocessing`), or 3.14's optional no-GIL build | Both push you towards "no shared memory, send messages", which is also how agent teams should talk (13.4) |
| Run in a browser | compiles to JS / WebAssembly, small and fast | Pyodide (Python compiled to WebAssembly): works, but a large download and slow start | **Big loss.** This alone is why `fa` could not be Python |
| Phone apps | Flutter, first-class | possible (BeeWare, Kivy), niche | **Big loss** |
| AI libraries, SDKs, evals, data tools | small ecosystem; `fa` writes its own provider adapters | the biggest ecosystem: every model vendor's SDK first, LangGraph, Agent Framework, Pydantic AI, evaluation tools | **Big gain** |
| Hiring and examples | few Dart AI engineers | almost every AI engineer reads Python | **Big gain** |

Small Python picture of "a closed list of events":
```python
Event = TextDelta | ToolCallEnd | Done | Error      # a union of small data classes
match event:
    case TextDelta: ...
    case Done: ...
    case _: assert_never(event)   # the type checker flags the forgotten ToolCallEnd/Error
```

### 4.3 What the latest Python agent stack looks like (2026)
If `fa` were rebuilt in Python today, it would probably not write everything by hand. It would pick from:
- **Microsoft Agent Framework (Python)**: orchestration patterns, checkpoints, middleware; hosts on Foundry (13.3, 13.5).
- **LangGraph**: graph of steps with saved checkpoints and merge rules per state key (13.8, Course 7).
- **Claude Agent SDK / OpenAI Agents SDK**: ready-made agent loop with tools and subagents, light to use.
- **Pydantic AI**: typed inputs and outputs, validation built in.
- **Temporal (durable execution)**: the whole run survives crashes and restarts, because every step is recorded. Used under several production coding agents.
- **`uv`** to install everything in seconds, **`ruff`** to lint, **pyright** to type-check (the part that replaces Dart's compiler checks).

### 4.4 Is Rust faster? Where the time actually goes
Rough sizes for **one agent step** (typical orders of magnitude, not my measurements):

| Part of the step | Typical time | Would Rust make it faster? |
|---|---|---|
| Waiting for the model's answer | 1–30 seconds | **No.** Rust waits exactly as long as Python |
| Network calls to tools (Jira, search, APIs) | 0.1–3 seconds | **No**, also waiting |
| The loop's own code (build request, read reply, save state) | a few milliseconds in Python | Yes, but it saves milliseconds out of seconds |
| Heavy local work inside a tool (search a big codebase, parse files, diffs, tokenizing) | can be seconds | **Yes, clearly** |

So a Rust agent finishes the same task in **almost the same time**. More than 95% of the time is waiting for the model, and no language makes that faster.

**Where Rust really wins:**
1. **Many agents on one machine.** An idle Python agent with a framework loaded typically sits at tens of MB of memory; a Rust one at a few MB. At 500 agents per server that is real money.
2. **Startup time.** A Rust command-line agent starts instantly; a Python one can need a second or two just to load its libraries. Users feel that in a coding tool.
3. **Easy to ship and lock down.** Rust compiles to one file with nothing else to install, and it is easier to sandbox (limit what the agent's tools may touch). OpenAI rewrote its Codex command-line tool from TypeScript to Rust in 2025 mainly for these reasons, not for raw speed.
4. **Heavy tool work**: code search, indexing, diffing, tokenizing.

### 4.5 The "fusion": Python on top, Rust inside
This mix already exists, and you use it every day without noticing. Many of the Python libraries an agent depends on are written in Rust underneath:
- `pydantic-core` (data validation), `tiktoken` and Hugging Face `tokenizers` (splitting text into tokens), `orjson` (fast JSON), `polars` (data tables)
- the developer tools `uv` (installer) and `ruff` (linter)

The pattern: **readable orchestration in Python, the slow repetitive parts in Rust.** The link between the two is a bridge library (PyO3), so a Python function call runs Rust code. For most teams this is the best of both: Python's speed of writing and its AI ecosystem, Rust's speed where it actually matters.

```
 your agent code (Python)  ── orchestration, prompts, tools, glue
        │ calls
        ▼
 libraries (Rust inside)    ── validation, tokenizing, JSON, search, data
        │ waits on
        ▼
 the model API (network)    ── where 95% of the time goes, whatever the language
```

## 5. Why it was built this way (decisions and trade-offs)

| Decision | Alternatives considered | Why this one | Cost / risk |
|---|---|---|---|
| `fa` in Dart | TypeScript, Python, Rust | One core for terminal, phone, desktop and browser; compiler-checked event types | Small AI ecosystem; must write its own provider adapters; fewer people can contribute |
| A server-side agent team in Python (my default) | Dart, Rust, TypeScript | Every model SDK and framework is Python-first; Azure Agent Framework and Foundry support it; easy hiring | Type safety only if a type checker runs in CI; more memory per agent |
| A shipped command-line agent in Rust (Codex's choice) | TypeScript, Python | Instant start, one file to install, strong sandboxing, small memory | Slower to write and change; smaller AI library ecosystem |
| Python + Rust libraries (the usual mix) | Pure Python, pure Rust | Fast where it matters, easy everywhere else | Two languages in the stack; building Rust extensions needs a toolchain |

## 6. Theory behind it (the "lecture" part)

### 6.1 I/O-bound vs CPU-bound
A program is **CPU-bound** when it is busy computing (training a model, compressing a file) and **I/O-bound** when it is mostly waiting (network, disk, a model API). A faster language only helps CPU-bound work. Agents are I/O-bound, which is why every agent framework is built around an **event loop**: one worker juggling many waiting tasks, instead of one worker per task.
*In this chapter:* Dart's event loop and Python's `asyncio` are the same idea; Rust's equivalent is `tokio`.

### 6.2 Compiled vs interpreted, and "checked before running"
Dart and Rust check a lot of mistakes **before the program runs** (the compiler refuses). Python checks types only if you run an extra tool (pyright, mypy); otherwise a mistake shows up when that line runs. For agents this matters at the **edges**: model output and tool results are untrusted, so you validate them at runtime anyway (Pydantic), whatever the language.
*In this chapter:* `fa`'s sealed events ≈ Python's union + `match` + type checker in CI.

### 6.3 The GIL and parallelism, in one paragraph
Standard Python has a lock (the **GIL**) that lets only one thread run Python code at a time. That hurts CPU-heavy work, not waiting. Python 3.14 made a no-GIL build **officially supported but optional** (PEP 779); it is not the default and many libraries are still catching up. For agents, which mostly wait, this changes little.
*In this chapter:* see 13.8 for what this means for agent teams.

### 6.4 Memory per agent
Every running agent costs memory: the language runtime, the loaded libraries, and the conversation it keeps. Python's runtime and big frameworks make the first two large; Rust's are tiny. But the **conversation** (the context window, measured in tokens) is the same size in any language, and that is usually where the money goes (13.8, "three memory systems").
*In this chapter:* Rust saves server RAM, not model tokens.

## 8. Glossary

| Term | One-line definition |
|---|---|
| Dart | Google's language behind Flutter; compiles to native code, JavaScript and WebAssembly |
| Flutter | Dart's toolkit for one codebase across phone, desktop and web apps |
| Sealed type | A closed list of subtypes; the compiler makes you handle all of them |
| Isolate | Dart's parallel worker with its own memory; talks only by messages |
| `asyncio` | Python's built-in event loop for many waiting tasks at once |
| `TaskGroup` | Python 3.11+ way to run tasks together and cancel all of them if one fails |
| Pyright / mypy | Python type checkers; they catch type mistakes before running, if you run them |
| Pydantic | Python library for typed data models with validation (Rust core since v2) |
| GIL | Python's lock that lets one thread run Python code at a time |
| Free-threaded Python | Optional 3.14 build without the GIL (PEP 779) |
| Rust | Compiled, memory-safe systems language; small, fast, single-file programs |
| `tokio` | Rust's event loop for many waiting tasks (the `asyncio` equivalent) |
| PyO3 | The bridge that lets Python call Rust code |
| I/O-bound | Mostly waiting on network or disk; a faster language barely helps |
| Durable execution | Every step is recorded so a run survives crashes and restarts (e.g. Temporal) |

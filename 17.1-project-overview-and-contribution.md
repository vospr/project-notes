## 2. The problem (business view, plain English)

A manager sees a forecast alert and asks which evidence and rule explain it. A plausible paragraph can attach the wrong period, model or meaning to a correct-looking number, so the answer needs an inspectable trail. I defined the requirements, decisions and acceptance boundaries and directed AI-assisted implementation and review; I do not claim manual authorship of every line. The case uses synthetic data: historical Databricks execution is proven for one wheel, later explanation and Fabric-adapter work is locally verified with mocks, and actual current-source Fabric integration remains unproven. Live LLM and Teams implementation are deferred; neither production users nor business uplift is established.

## 4. How it works (technical walkthrough)

```text
supported question + pinned target + explicit evidence
                    |
           route / refuse / clarify
                    |
      evidence eligibility + deterministic specialists
                    |
             checked host plan
                    |
       optional explanation callback (local mock)
                    |
       full validation -> checked answer
             failure -> deterministic fallback
```

First separate the forecasting producer from its explanation consumer. Historical forecasting followed prepare, train, register, score and monitor. The explanation does not rerun that pipeline. It receives an explicit bounded synthetic packet and answers only supported questions about the supplied evidence. Current source references below are local study pointers, not a claim that the repository is public or that this exact source ran historically.

`src/forecast/orchestrator.py:40` defines `AnswerRequest`: question, evidence, target, mode and caller-supplied time. `_route` at line 121 checks the minimal question envelope, prohibited operations and the closed intent table. Unknown wording clarifies; a request containing a prohibited action refuses. This is intentionally narrower than an unrestricted conversational assistant.

`src/forecast/evidence.py:39` represents the pinned identity, including model/version and acceptance scope. `validate_evidence` at line 628 checks the packet and topic eligibility. Correct shape is only the beginning: periods, sources, completeness, conflicting claims and freshness also matter. A missing quality-check result cannot become an observed pass because training succeeded.

`src/forecast/specialists.py:316` builds assertions for data quality, comparison and commentary. These are ordinary deterministic functions, not three autonomous LLM agents. Comparison uses validation scores; commentary computes the written monitoring rule. The target model remains explicit even if another candidate ranks first.

`src/forecast/explanations.py:460` builds the host plan. The plan binds eligible assertions, operands, citations and qualifications before any callback. `context_digest` at line 174 ties a response to that canonical plan. The framework coordinates route, plan and terminal executors; it does not choose facts or establish their external authenticity.

`src/forecast/explanation_language.py:343` parses a complete sentence in the bounded grammar. `validate_generated` in `explanations.py:948` checks response structure, context and assertion bindings. A wrong meaning rejects the whole generated draft, even with valid citations. The deterministic rendering preserves eligible facts and their limitations. This is not arbitrary-English verification.

The retained local demonstrations used real framework execution but mocked provider transport and constructed response bytes. Fabric adapters in `src/forecast/io.py` have local synthetic/mock proof, not actual Fabric service proof. Live LLM and Teams remain deferred. The existing portfolio chatbot is a separate Gemini retrieval application and does not inherit this B-v1 validation guarantee.

## 5. Why it was built this way (decisions and trade-offs)

| Decision | Alternatives considered | Why this one | Cost / risk |
| --- | --- | --- | --- |
| Synthetic explicit packets | Start with company data or automatic discovery | Inspectable, reproducible case without confidential rows | Not evidence of enterprise ingestion readiness |
| Fixed routing and ordinary functions | Model-selected tools and autonomous specialists | Keep authority and calculations explicit | Narrow question vocabulary |
| Bounded English validation | Citation checks alone or unrestricted model judgment | Bind sentence meaning to approved assertions | Less expressive language |
| Whole-draft fallback | Repair individual sentences with another call | Avoid mixing unchecked and checked fragments | Less polished wording on rejection |
| Environment code in IO | Platform checks throughout the core | Separate reasoning from runtime dependencies | Real adapters still need integration proof |
| Distinct evidence scopes | Present every green result as one deployment | Preserve artifact identity and uncertainty | Requires precise communication |

I owned the decisions and acceptance framing; implementation was AI-assisted. Accepted offline step 7 does not complete the pending Stage 6 learning checkpoint. Historical Databricks success, applied local Fabric adapters and actual Fabric integration are separate claims; the last remains unproven, with LLM/Teams delivery deferred.

## 6. Theory behind it (the lecture part)

### 6.1 A data product starts with a decision

A data product connects information to a user's decision, not merely to an interface. Define the user, question, available evidence and consequence of error before choosing a model. "Explain why this threshold fired" is different from "explain the cause of falling demand"; the second requires causal evidence the first does not. In this case, I chose bounded quality, comparison and monitoring explanations rather than an assistant authorised to act on forecasts.

### 6.2 Separate the control plane from the data plane

A control plane decides permitted configuration and operations; a data plane performs the work on concrete inputs. In an explanation application, the host's routing and eligibility rules are part of control, while processing an allowed packet supplies facts. Model text is an output candidate, not a new policy. In this case, an explanation cannot grant itself the right to retrain or select using test data.

### 6.3 Functional core and imperative shell

A functional core computes from explicit inputs; the surrounding shell handles clocks, files, networks and environment. This separation reduces hidden dependencies and makes tests repeatable. It does not eliminate operational risk: the shell must still establish real context and handle service failures. In this case, evidence and specialist logic are separated from environment-specific `io.py` behaviour, whose Fabric integration remains unproven.

### 6.4 Provenance is more than a citation

Provenance records where a claim came from and under which identity, time and scope it is valid. A citation that resolves is insufficient if it refers to another model, version or period. Think of a fact as a tuple: subject, measurement, unit, period, source, observation time and status. In this case, these bindings prevent a locally simulated observation from becoming current live evidence.

### 6.5 Prediction error, parity and impact answer different questions

For nonnegative demand with positive total actual demand, WAPE is `sum(abs(actual - predicted)) / sum(actual)`. It summarises error relative to volume; it can exceed one and can conceal segment weaknesses. Parity measures whether two implementations produce equivalent outputs for the same inputs and saved estimator. Business impact asks whether using the result improves a decision and usually requires additional outcome evidence. In this case, the historical 960-prediction parity audit is not proof of future accuracy or business uplift.

### 6.6 Validation is a chain of distinct checks

Syntax asks whether data has the allowed shape. Semantics asks whether its meaning and calculations agree. Eligibility asks whether the evidence may support the requested conclusion at all. A perfectly parsed sentence can still use stale evidence; a correct number can still describe the wrong subject. In this case, B-v1 combines these checks within a closed language rather than claiming a general truth detector.

### 6.7 Generality has a price

A broad interface accepts many user expressions and therefore needs stronger ambiguity handling, evaluation and authority boundaries. A bounded interface sacrifices coverage for predictable behaviour. The useful question is whether the supported set serves a real purpose, not whether it sounds as capable as unrestricted chat. In this case, exact routes and grammar make the contract inspectable but leave broader natural-language use for separately reviewed extensions.

### 6.8 Ownership includes knowing the limits

Engineering ownership is responsibility for decisions, understanding, verification and operational consequences. It does not require personally typing every line, but it does require distinguishing generated implementation from one's own judgment. A successful demonstration is evidence about what happened under its conditions, not a blanket completion certificate. In this case, my defensible contribution is owner-led specification, AI-assisted delivery and evidence-based acceptance; Stage 6 understanding is still unassessed.

## 8. Glossary

| Term | One-line definition |
| --- | --- |
| Evidence packet | Explicit claims and sources with identity, time and scope |
| Specialist | Ordinary deterministic function producing domain assertions here |
| Host plan | Approved catalogue of assertions and bindings before wording |
| B-v1 | Bounded English explanation and validation contract |
| Fallback | Local rendering replacing an unavailable or rejected explanation |
| WAPE | Sum of absolute errors divided by total actual demand |
| Parity | Agreement between implementations on the same saved-estimator task |
| Acceptance scope | Conditions and capabilities an acceptance actually covers |
| Mock transport | Simulated provider boundary, not a real model call |
| Fabric integration | Actual target-platform behaviour, still unproven here |

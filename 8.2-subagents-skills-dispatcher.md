# Course 8 · Chapter 8.2: Subagents, skills, dispatcher: least privilege and pipeline depth

_Andrey Popov's project notes: how it works, why it was built this way, and the theory behind it._

## 2. The problem (business view, plain English)

One agent that plans, codes, reviews and tests its own work marks its own homework. It also carries every file and every instruction in one window. The template splits the work into roles with separate windows and different rights, and puts a coordinator in front that decides who runs, on which model, and when to stop.

Finance analogy: a trading floor with desks. Front office (implementer) can book trades but not approve them. Middle office (reviewer) can read positions but not change them. Compliance (blind reviewer) sees only the trade ticket, not the story behind it. The head of desk (dispatcher) allocates the work and escalates when a limit is hit. Small trades do not need all four desks. That is the sizing idea.

## 4. How it works (technical walkthrough)

**Privilege matrix** (from the frontmatter; `✓` = in `tools`, `–` = absent; `disallowedTools` repeats the exclusions):

| Agent | Model | Read/Grep/Glob | Write | Edit | Bash | Web | Task tools | Preloaded skills |
|---|---|---|---|---|---|---|---|---|
| researcher | haiku | ✓ | ✓ | – | – | ✓ (+ docs MCP) | – | none |
| planner | sonnet | ✓ | ✓ | – | – | – | Create, Update, List | spec-protocol |
| architect | opus | ✓ | ✓ | – | – | – | – | architecture-principles |
| implementer | sonnet | ✓ | ✓ | ✓ | ✓ | – | Update | coding-standards, git-workflow |
| reviewer | sonnet | ✓ | – | – | – | – | – | review-checklist, architecture-principles, spec-protocol |
| blind-reviewer | sonnet | ✓ | – | – | – | – | – | none |
| tester | sonnet | ✓ | ✓ | – | ✓ | – | Create | testing-strategy, spec-protocol |

Source: `tools`, `model`, `skills`, `disallowedTools` lines of each file. I checked that no tool is in both `tools` and `disallowedTools` for any agent.

**What the matrix shows.** The pattern is sensible: only the implementer can Edit; only the researcher can reach the web; reviewers are read-only; the architect has no Bash; the planner cannot touch code. The deny list repeats the allow list's complement, so it is a second layer (belt and braces), not new information. Rights that are broad: `Bash` for implementer and tester, and `Write` for five of seven agents.

**The dispatcher as a decision chain**:
1. Standards check (Step 0), read state (Step 1), pick the lowest unblocked task (Step 2).
2. **Match:** score the top two agents on task type, tool access, output format (0–2 each); dispatch at 4/6 or more; otherwise ask the user or let the planner classify.
3. **Size:** Micro / Small / Medium / Large sets model and pipeline. Review composition by tier: Micro none; Small standard review; Medium and Large add blind review in parallel and the tester.
4. **Gate:** for Medium and Large each step must be demoable, context-bounded, independently verifiable and revert-cheap, else sub-slice; five or more sub-steps re-classify as Large.
5. **Dispatch:** inject warnings, trace ID, and a max-turns hint (Micro 5, Small 15, Medium 25, Large 40).
6. **Parse:** the `Machine-Readable Summary` YAML decides the next step; flags such as `ARCHITECTURE_IMPACT`, `NEEDS_RESPEC`, `ESCALATED` route to the planner or re-size (max 1 escalation per task).
7. **Stop conditions:** 3 worker-reviewer cycles, then BLOCKED and escalate; every 10 tasks check for cascade failure (>3 blocked), dispatch loop (>5 dispatches of one task), plan explosion (>15 tasks).

**Conflict matrix.** Two reviewers, three statuses each: nine cells. Any BLOCKED+BLOCKED halts. Any single NEEDS_CHANGES or BLOCKED means that reviewer's issues get fixed; both disagreeing means both lists get fixed. Unknown status (SKIPPED, PARSE_ERROR, typo, timeout) counts as NEEDS_CHANGES from that reviewer. The blind reviewer returns SKIPPED on diffs under 5 lines, so for small changes the default row turns a skip into NEEDS_CHANGES. That is an interaction I did not see addressed. Medium tasks can have small diffs.

**Skills.** Ten `SKILL.md` files; `description` starts with a purpose and a "Use when" clause so that the model can choose them (check S1). Agents can preload skills by name via `skills:`; some skills are also referenced by path in `CLAUDE.md`.

```
 task ─► match (score) ─► size ─┬─ Micro ──► implementer(haiku)
                                ├─ Small ──► implementer ─► reviewer
                                ├─ Medium ─► planner ─► implementer ─► reviewer ║ blind ─► tester
                                └─ Large ──► (architect opus) ─► … same as Medium
```

## 5. Why it was built this way (decisions and trade-offs)

| Decision | Alternatives | Why this one | Cost / risk |
|---|---|---|---|
| Per-role tool lists plus deny lists | One agent with all tools | Least privilege; read-only reviewers; no web for coders | Reviewers cannot write their own report; Bash undercuts it |
| Blind reviewer with diff only | A second normal reviewer | Lower correlation with the spec-aware reviewer; catches what anchored reviewers pass | Blind by instruction only; the diff has to be supplied by someone |
| 9-cell conflict matrix | Majority vote; ask the user on any conflict | Mechanical, repeatable, testable | Never tested with a real conflict; SKIPPED interaction |
| Size tiers set depth and model | One depth for all tasks | Cost control; small tasks skip review | Classification is a model call; depth stays heavy by default |
| Max 3 review cycles | Unlimited loop | Stops runaway loops; escalates to a human | Three is a guess; no data on how often it fires |
| Parse a YAML block, not free text | Read the prose | Reliable routing; a missing block is an explicit error | Models sometimes omit or break YAML; the recovery is another dispatch |
| Skills as files, not in `CLAUDE.md` | Everything in `CLAUDE.md` | Keeps the kernel under 300 lines; load on demand | A 1,457-line skill is preloaded into 3 agents (8.|
| Haiku for scouts and Micro | Sonnet everywhere | Cheapest model for read-and-summarise | Summaries can drop detail; unmeasured savings |

## 6. Theory behind it (the "lecture" part)

### 6.1 Principle of least privilege
Saltzer and Schroeder (1975): every program and user should operate with the least set of privileges necessary to do the job. It limits the damage from mistakes (an agent that misreads a task) and from attacks (prompt injection through a web page the agent fetched). Practical rules: allowlist (name what is allowed) beats denylist (name what is forbidden); enforce in the platform, not in the prompt; check privileges at the boundary where the action happens. A common failure is the **confused deputy**: a low-privilege party gets a high-privilege component to act for it.

For LLM agents the twist is that the "program" can be talked into things. Instruction text ("never modify code") is a request; a missing tool is a fact. Only the second counts as a control.

*In my project:* `tools` allowlists are real controls (reviewer has no Write tool). "NEVER modify code", "MUST NOT read planning-artifacts" are requests. `Bash` is a hole through the file-path control.

### 6.2 Separation of duties and independent review
Same idea as maker–checker in finance: the one who produces is not the one who approves. Independence is measured by **error correlation**. For two reviewers with miss probabilities m₁ and m₂ and correlation ρ, the chance that both miss is about m₁·m₂ + ρ·√(m₁(1−m₁)m₂(1−m₂)). With m = 0.4 each: independent 0.16, fully correlated 0.40. Methods to reduce ρ: different information (diff only), different model, different prompt, different time. A 9-cell policy table then turns two verdicts into one action.

*In my project:* the standard reviewer sees spec and intent; the blind one sees only the diff. If the "blind" one can read the spec, ρ rises and the second reviewer adds cost, not independence.

### 6.3 Orchestration patterns for agents
Three common shapes: a **router** (one hop to a specialist), an **orchestrator–workers** pattern (a coordinator decomposes and delegates, then merges), and a **pipeline** (fixed stages, each hands off). The template is an orchestrator with a sized pipeline. Design questions are always the same: who owns state, how do results come back (structured, parseable), when does it stop, and who is the human gate. A coordinator that must **never** do the work keeps its context small but becomes a bottleneck and a single point of failure.

Handoffs through structured output (a schema) are more reliable than parsing prose, but a schema only helps if a missing or invalid block is treated as an error.

*In my project:* orchestrator-workers with a YAML summary contract; PARSE_ERROR triggers a recovery dispatch.

### 6.4 Sizing pipeline depth: expected cost
Let a task of tier s take stages with costs c₁…c_k and let each review stage catch a defect with probability r. Expected cost is Σcᵢ plus the expected rework cost. Extra stages pay off only when the cost they avoid, q · L (probability that a defect exists times the loss if it escapes), is larger than the stage cost. For tiny mechanical changes q is small and L is small, so a review costs more than it saves. For a new subsystem q and L are large. That is the whole case for sizing.

Example (illustrative): reviewing a typo fix costs 20k tokens, a bug that escapes costs 5k to fix later, and the escape probability is 2%. Expected saving is 100 tokens against a cost of 20k. Skip the review. For a feature: review 40k tokens, escape probability 30%, fix cost 150k: expected saving 45k against 40k. Review pays.

*In my project:* the tiers encode this reasoning, but I never estimated q or L. The one data point (A vs C) says that on a small task the heavy pipeline did not pay.

### 6.5 Tool descriptions as interface: matching and routing
The dispatcher chooses an agent from its `description` field. With few candidates and clear descriptions this works; with overlapping ones (reviewer vs blind reviewer, planner vs architect) routing errors appear. The standard remedy is a rules-first step with a model fallback, plus a confidence floor.

*In my project:* the 4/6 score is a confidence floor written in prose. It has never been measured. Course 7 (routing evals) shows how I would test it today.

## 8. Glossary

| Term | One-line definition |
|---|---|
| Subagent | A role with its own window, system prompt, tools and model |
| `tools` / `disallowedTools` | Allowlist / denylist of tools in a subagent's frontmatter |
| Least privilege | Give each component only the rights its job needs |
| Confused deputy | A privileged component tricked into acting for a less privileged party |
| Blind review | Review by someone who sees the change but not the intent or spec |
| Triage consensus matrix | The 9-cell table turning two reviewer verdicts into one action |
| Circuit breaker | A hard stop after N failures or loops |
| Pipeline sizing | Choosing pipeline depth and model by task size |
| Step-sizing gate | Five checks a step must pass before implementation |
| Machine-Readable Summary | The YAML block each agent ends with; the dispatcher parses it |
| SDD | Spec-driven development: assertions are written before code |
| Orchestrator–workers | One coordinator delegates sub-tasks to specialists and merges results |
| Maker–checker | Producer and approver are different parties |

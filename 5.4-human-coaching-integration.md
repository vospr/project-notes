# Course 5 · Chapter 5.4: Human-coaching integration (my main slice): service auth, booking consistency, error mapping, video

_Andrey Popov's project notes: how it works, why it was built this way, and the theory behind it._

## 2. The problem (business view, plain English)

The product is sold as hybrid coaching: the AI partner works between sessions and can hand the participant to a real human coach. Human coaches, their calendars and their video rooms live in a **separate operations platform** with its own team, its own release cadence (daily on its dev environment, roughly every five weeks on the others, *ADR*) and its own login system. Our side had to: authenticate to it as a service, ask it for matching coaches, show free slots, book and cancel without double-booking the coach, tell the user what went wrong in words that fit the screen, and join a video call. The hard part is not the HTTP calls. It is that two systems with independent releases must agree about who holds which time slot.

Finance analogy: a company books travel through a corporate card system run by another team. You hold a service account, you reserve a seat, and later cancel it. If your cancel request quotes your own booking reference but the card system issued its own, the cancel silently fails and the budget stays blocked. Month-end shows a reserved amount nobody can explain. This chapter's central bug is exactly that.

## 4. How it works (technical walkthrough)

```
 browser ─► our API (same origin) ─► mapping layer ─► partner platform
                │                      <ops>ErrorMapping        ├─ IAM token endpoint   (client credentials)
                │                      status+code+fixed text   ├─ people service       person → country
                │                                               ├─ matching service      matched coaches (≤3)
                │                                               ├─ calendar service      external-sessions (block a slot)
                ▼                                               └─ client API            test call / video join
         booking (partner-first):  prepare(journal=pending) → create block at partner → commit (session row, journal=confirmed)
         cancel  (ours-first):     cancel our row → delete the partner block by the PARTNER'S id → cleanup worker retries
         video:  join handler → ACS room + token (4 fields) → CallComposite in the browser
```

**1. Service auth.** OAuth2 client credentials: our service holds a client id and secret and exchanges them at the partner's token endpoint for a short-lived bearer token, one cache slot per partner service (and per coach where a grant is coach-scoped, #2532). The cache stores the **in-flight promise** and writes it synchronously before the first `await`, so N concurrent first callers cause one grant, not N. A rejected grant is evicted under an identity guard so a late rejection cannot clear a newer entry. Refresh skew is per token, `min(60 s, lifetime/2)`, so a short-lived token is not "expired on arrival". A failed early refresh keeps serving the still-valid old token. `expires_in` must be finite, positive and below one year, or the response is rejected as malformed. Hygiene: no redirect follow on the token POST (a 307/308 would replay the secret); 10 s deadline on every call via an abort signal; log only service, status and the OAuth error code from a closed list, never the body. Status 514 means a scheduled maintenance window, 429 is "rate limited, credentials fine", other 4xx are auth failures.

**2. Config and capability gate.** The three shared credentials are all-or-nothing: none set means "not configured here" (valid), a partial set is a configuration error naming every missing variable. Each service's base URL is optional, and a set URL must be absolute HTTPS. A single enable-list variable gates each partner-dependent capability: unset or blank means nothing enabled; unknown, mis-cased or empty elements make the whole list malformed and enable nothing. This is the "tolerance" mechanism the ADR argues for: independent release cadences cannot be aligned away, so one failing capability must be switchable alone.

**3. Matching (#2391).** The server derives every input (the client sends none), calls the people service for the participant's country, then the matching service, and returns at most three candidates; nothing is stored. Two postures on purpose: the country lookup rejects the whole response on any malformed or duplicate entry (a wrong mapping would route a person to the wrong market); the matching call rejects only identity fields and degrades unknown enrichment fields to null with a warning, because none of those 16 fields had been seen live (commit body).

**4. Error mapping.** Partner errors are typed (config, auth, maintenance, request) and never extend the HTTP error class, so a leak becomes an opaque 500 rather than a wrong message. The mapping function builds a fixed sentence per case and attaches the original only as `cause`, so no upstream text or variable name reaches the client. It is **service-aware**: a 400 from the matching service is an actionable rejected request, a 400 from the people service is an integration fault folded into "unavailable", except an unmapped country, which gets its own code so staff stop retrying. It is **screen-aware**: the same error reads "Coach matching ...", "Session booking ..." or "Video call join ..." depending on route or an explicit flow argument. A 409 on booking becomes the slot-conflict error code: "That time slot is no longer available.". A failure telemetry line is logged with categorical fields only, because the HTTP error class suppresses the framework's own error log. A non-partner throwable is rethrown, not relabelled as "partner down".

**5. Booking and cancel consistency.** The partner owns the coach's calendar; we are the booking surface. Booking is partner-first in three steps with no database transaction open across the HTTP call (the pool has 3 connections): prepare (lock, validate, write a `pending` journal row), call the partner, commit (re-validate, insert the session, mark journal `confirmed`). Ambiguous outcomes (timeout, 5xx) leave the journal `pending` for a cleanup worker; a daily sweep recovers stale claims and raises an alert for stuck rows. That design is the architect's and a teammate's. **My fix (#2629):** the partner creates its own server-side `id` for a block and never echoes our our own session reference. Our cancel deleted by our id, got 404, and a standing "404 means already gone, success" rule swallowed it, so every cancelled session kept the coach's slot blocked. Fix: store the partner's real id at booking (nullable column), delete by it, and for older rows look it up by query and match the exact start and end instants (parsed, because the partner omits milliseconds), never guessing among several candidates. The architect's design doc was corrected in place with the probe evidence.

**6. Org to company link (#2758).** A write path under one org-row lock enforces one active company per org and one active org per company. Admin tools list, add and delete the link; refusals are curated codes that never echo the company id; two support events record link and unlink without the id. The API checks UUID syntax only and does not confirm that the company exists at the partner (commit body).

**7. Choose-coach wizard (#2834).** Three steps: match, slot, confirm and book. Steps 1 and 2 write nothing. Step 3 confirms the relationship, then books. If booking fails after confirm, it never re-confirms or rolls back; a local recovery state does a fresh journey read before any retry, asks for a new slot when stale, and does not retry on an exhausted allowance.

**8. Video (#1614 proof; #2559 shipped).** The proof defined a token-provider seam: four fields a user id, a display name, a token and a room id, a credential object with proactive refresh, a build-time gate so production bundles contain neither route nor chunk, and a finding that the legacy call UI is already React so Microsoft's composite can be used directly (*ACSDOC*, commit body). The shipped surface consumes exactly those four fields and adds the backend join with ACS provisioning.

## 5. Why it was built this way (decisions and trade-offs)

| Decision | Alternatives considered | Why this one | Cost / risk |
|---|---|---|---|
| Cache the in-flight token promise | Cache the resolved token; lock | The grant is an async HTTP call, so `await` yields and N callers would each fire a grant | Subtle; needs four tests (dedup, eviction, per-service key, refresh dedup) |
| All-or-nothing shared credentials; optional per-service URL | One flag per service | "Not configured" must be a valid state so one service can ship dark | More states to document |
| One positive enable-list, fail-closed | One flag per capability; a denylist | Switch one capability off without breaking QA; a typo must not half-enable | Operators must edit a string |
| No new environment; QA and PR previews target the partner's dev | Align UAT with partner QA; add a dev tier | Promotion tracking cost outweighs closer alignment; alignment cannot remove drift anyway | UAT/staging/prod pairings unconfirmed |
| Typed partner errors, fixed sentences, `cause` only | Pass the upstream message through | Upstream text can leak variable names or data | Less detail in the UI; detail goes to logs |
| Map by service and status, then by screen | One flat status switch | Same status means different things per service | More tests (138 lines added in #2610) |
| Persist the partner's id; refuse to guess on legacy rows | Delete by time window alone | Wrong DELETE would remove an unrelated booking | Some legacy slots stay blocked |
| Booking partner-first with a journal | Our DB first, then call | The partner is the authority for the calendar and a lock across both systems (*MAPDOC* D2) | Phantom/ambiguous states need a cleanup worker |
| Org link under one lock | Allow many-to-many | Enforces the business rule in one place | Does not verify the company exists |
| Keep the ACS proof on a branch | Merge it gated | Repo policy: inert proofs do not enter `main` | Work not visible in `main` history |

## 6. Theory behind it (the "lecture" part)

### 6.1 OAuth 2.0 client credentials and token caching
The client-credentials grant (RFC 6749 §4.4) lets a confidential client obtain an access token for itself, without a user, by presenting a client id and secret to the token endpoint, usually with a scope. The response has `access_token` and `expires_in`. Good clients cache the token until shortly before expiry (refresh skew), do not follow redirects on the token request, never log secrets, and classify failures: 400/401 on the token endpoint are credential problems, 429 and 5xx are retryable. Caching asynchronously fetched values has a classic race, the *cache stampede*: if the cache holds the value, N callers racing on a miss each start a fetch. Remedy: cache the promise (single-flight).
*In my project:* one grant per service key regardless of concurrency; early refresh keeps the old token if the refresh fails.

### 6.2 Integration across independently released systems
When two systems release on different schedules, you cannot rely on lock-step versions. Standard tools: explicit contracts (a typed boundary), tolerant readers (accept unknown fields, reject only what you rely on), feature gating per capability, and contract tests against the real counterpart. Environment alignment (our QA to their QA) does not remove drift because the pairing that matters is production to production.
*In my project:* tolerant reading of enrichment fields, an enable-list per capability, and an ADR that says aligning environments only moves the mismatch.

### 6.3 Idempotent operations, "404 as success", and verification
A DELETE is idempotent: deleting an absent resource leaves the same end state. Treating 404 as success is a common, reasonable rule for retries. It becomes dangerous when 404 can also mean "wrong key" or "wrong route": the state you wanted (slot released) is not achieved, but the code reports success. The fix is to verify the identity of what you delete (use the system's own id, check by a read-after-write) and to separate "already gone" from "never addressed". In general, success must be defined by the postcondition, not by the absence of an error.
*In my project:* the partner issues its own id; deleting by ours returned 404 on every call and a swallow rule hid it.

### 6.4 Saga, compensation and the outbox/journal pattern
A transaction spanning two systems cannot be atomic. A *saga* splits it into local steps with compensating actions. A *journal* (or outbox) records intent before the external call, so that after a crash or timeout a worker can resolve ambiguous outcomes: confirm, retry or compensate. Two principles: never hold a database transaction open across a remote call (it ties up pool connections), and make every step idempotent.
*In my project:* prepare / call / commit with a `pending` journal row, a cleanup worker, and a daily sweep (team code); my fix repaired the delete leg.

### 6.5 Error taxonomy and mapping to a public contract
Separate *what happened* (internal typed errors with cause) from *what the client may know* (a stable status, a code and a fixed message). Rules: never forward upstream text, log categorical fields, give distinct codes only where the caller can act differently (retry later, pick another slot, stop retrying), and keep unknown cases in a safe default bucket. Message wording depends on the screen, so presentation context selects wording while classification stays keyed on provenance.
*In my project:* stable integration error codes for config, auth, maintenance, request rejected, not found, slot conflict, country unsupported, and generic unavailable.

### 6.6 Allowlists, denylists and failing closed
A denylist blocks known-bad things and allows the rest; an allowlist allows only known-good things. Under uncertainty (typo, partial value) a fail-closed allowlist is safer for enabling capabilities; a fail-open denylist is safer for emergency stops (see 5.2). The two are complementary: enable-list to turn things on carefully, kill switch to turn them off quickly.
*In my project:* the capability list is a strict positive allowlist; the generation kill switch is a fail-open flag.

### 6.7 Real-time media with ACS Rooms (high level)
Azure Communication Services separates *identity and tokens* (minted server-side from a connection string, never in the browser), *rooms* (a scheduled space with presenter and attendee roles) and *clients* (a UI composite that joins with a user id, token and room id). Tokens are short-lived credentials designed to sit in the browser, but the resource keys that mint them must not. A rotating token can be refreshed in place by the SDK credential (proactive refresh) or by rebuilding the call, which drops participants briefly.
*In my project:* four-field seam, tokens minted by the backend join handler, composite in the browser.

## 8. Glossary

| Term | One-line definition |
|---|---|
| Partner platform | The separate coaching-operations system that owns coaches, calendars and rooms |
| Client credentials | OAuth grant where a service authenticates as itself with id + secret |
| Single-flight | Many callers share one in-flight request instead of each starting one |
| Refresh skew | Safety margin before expiry when a token is renewed |
| Enable-list | One positive list of capabilities allowed to run in an environment |
| Tolerant reader | Accepts unknown extra fields; rejects only what it depends on |
| External session | A block placed on a coach's partner-side calendar for one of our bookings |
| Journal (outbox) | Table recording intent before an external call, for recovery |
| Saga / compensation | Multi-step process with undo steps instead of one atomic transaction |
| Idempotent | Repeating the operation leaves the same end state |
| Screen-aware error | Same error, wording chosen by the screen that shows it |
| Presentation flow | matching, booking or call-join; selects the wording only |
| ACS | Azure Communication Services: identity, rooms, calling |
| Token-provider seam | The four-field shape the call component needs: user id, name, token, room id |

| Probe | A manual live call used to learn the partner's real behaviour |

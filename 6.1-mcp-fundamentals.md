# Course 6 · Chapter 6.1: MCP fundamentals (tools, resources, prompts, transports, structuredContent)

_Andrey Popov's project notes: how it works, why it was built this way, and the theory behind it._

**In short:** MCP basics and how the spike works: JSON-RPC, tools versus resources versus prompts, stdio and Streamable HTTP, Zod schemas with structuredContent, and a stub coaching backend with two tools. Notes that the booking tool is not idempotent.

## 2. The problem (business view, plain English)

An AI-coaching product wanted its coaching to appear inside the AI tools employees already use: Copilot, ChatGPT Enterprise, Claude, Teams. One custom integration per platform means N integrations to build and maintain ( option D). MCP is a shared protocol: build one server, and any MCP client can connect.

Finance analogy: a broker that wants to be reachable by many trading venues. It can write one adapter per venue, or publish one FIX endpoint that every venue already speaks. MCP is the FIX of AI assistants. The standard fixes the message format; it does not decide who may trade or how much (that is auth, chapter 6.4).

The deliverable was a one-day decision memo plus a small working server that proves the "MCP surface".

## 4. How it works (technical walkthrough)

```
Host app (Claude Desktop / Copilot Studio / ChatGPT)  ── contains an MCP client
        │  JSON-RPC 2.0 messages
        ├── stdio:  child process, stdin/stdout, one JSON message per line     stdio.ts:12-17
        └── HTTP:   POST /mcp, new server + transport per request              http.ts:27-35
                                │
                  createCoachingMcpServer                                    server.ts:33
        ┌──────────────┬───────┴────────┬──────────────┬───────────────┐
     tools (2)    resources (4+1)    prompt (1)    instructions    stub backend
   model decides  host/user attaches  user picks   string to client  coaching-data.ts
```

**One factory, two entry points.** `createCoachingMcpServer` builds the `McpServer` and registers everything (`server.ts:33-291`). `stdio.ts` connects it to `StdioServerTransport` (`stdio.ts:12-17`) and logs only to `stderr` (`stdio.ts:16`). `http.ts` builds a fresh server and a fresh `StreamableHTTPServerTransport` per request (`http.ts:28-33`). `index.ts` re-exports the factory and defaults to stdio (`index.ts:7-10`).

**Tools (model-controlled).** `single-turn-advice` takes `question` and optional `theme` and returns `response`, `detectedCue`, `suggestedTheme`, `phase` (`server.ts:56-92`). Both input and output are Zod schemas; the SDK turns them into JSON Schema for `tools/list`. `book-session` takes `date`, `timeSlot`, `coachType` (enum `ai|human|hybrid`) and returns `confirmed`, `sessionId`, … (`server.ts:94-123`). The handler returns `content` (text) plus `structuredContent` (the object).

**Resources (application-driven).** Four static JSON documents: `coaching://themes`, `cues`, `phases`, `model` (`server.ts:127-221`) and one template `coaching://themes/{themeId}` with a `list` callback so clients can enumerate the five themes (`server.ts:224-250`).

**Prompt (user-controlled).** `coaching-question` expands to a user message that tells the model to read the model resource, call the tool, reflect the answer and ask one follow-up (`server.ts:254-288`).

**Instructions.** A string sent to the client at connect time that tells the model when to use what (`server.ts:40-47`). uses it as a fallback for clients that ignore resources.

**Stub backend.** `generateCoachingResponse` lower-cases the question, picks a theme by substring match (default `priorities`), detects a cue by keyword, and returns one of five canned questions (`coaching-data.ts:40-80`). `bookSession` always returns `confirmed: true` (`coaching-data.ts:83-100`). So the "intelligence" is a lookup table; the spike proves the interface shape only.

**A tool call on the wire (2025/26-era HTTP, simplified).**
```json
{"jsonrpc":"2.0","id":2,"method":"tools/call",
 "params":{"name":"single-turn-advice","arguments":{"question":"…","theme":"priorities"}}}
```
The reply carries `result.content[0].text` and `result.structuredContent` (`server.ts:81-90`). Under 2026-07-28 each request also carries `_meta` with protocol version and client capabilities; this code predates that (chapter 6.2).

## 5. Why it was built this way (decisions and trade-offs)

| Decision | Alternatives | Why this one | Cost / risk |
|---|---|---|---|
| Reference data as resources, actions as tools, guided flow as a prompt | Everything as tools | Matches who controls what; read-only context should not be callable "actions" | Clients that do not surface resources hide the context |
| Advice and booking as tools | Booking as a resource | Booking changes state, so it is a model-invoked action | No annotations, not idempotent |
| `outputSchema` + `structuredContent` on both tools | Free text only | Typed result clients can validate and parse | Text block carries only part of the data |
| Official TypeScript SDK 1.29 + Zod | Hand-rolled JSON-RPC | Same language as the client's backend; SDK does schema plumbing | Pinned to an April-2026 spec era |
| stdio **and** Streamable HTTP | HTTP only | stdio for Claude Desktop/Inspector, HTTP for remote clients | Two entry points to keep alike; HTTP has no auth |
| Stub backend | Call the real coaching API | No credentials needed; shows the interface shape | "Connect live API is mostly a backend swap" is oversold: auth, errors, latency |
| Server `instructions` string | Rely on tool descriptions only | Fallback for clients that ignore resources | Not verified in any real client |

## 6. Theory behind it (the "lecture" part)

### 6.1 JSON-RPC 2.0 as the wire format
JSON-RPC 2.0 is a stateless remote-call format. A **request** has `jsonrpc`, `method`, `params`, `id`. A **response** has the same `id` and either `result` or `error` (`code`, `message`). A **notification** has no `id` and expects no reply. The `id` lets a client run several requests in parallel and match answers. Reserved codes: `-32601` method not found, `-32602` invalid params, `-32603` internal error (general knowledge; check the JSON-RPC 2.0 text). MCP adds its own code ranges.

*In my project:* every call in is a JSON-RPC request; the SDK builds and parses the envelopes, so no line of `server.ts` touches `id` or `error` directly.

### 6.2 Client, server, capabilities
An MCP **host** (the AI app) contains one MCP **client** per connected **server**. A server declares what it offers as **capabilities** (`tools`, `resources`, `prompts`, …; *SPEC-TOOLS "Capabilities"*). Capability declarations are a contract: a server that declares `tools` MUST answer `tools/list`, and the list MUST NOT vary per connection (it MAY vary with the authorization presented; *SPEC-TOOLS*). Under 2026-07-28 capabilities are advertised via `server/discover` and per-request `_meta`, not an `initialize` handshake.

*In my project:* the SDK derives the capabilities from the `register*` calls; the one manual declaration is the unused `logging` (`server.ts:48-50`).

### 6.3 The control hierarchy: tools, resources, prompts
The three primitives differ by **who decides to use them**:

| Primitive | Controlled by | Analogy (HTTP) | Spec wording |
|---|---|---|---|
| Tool | the **model** | POST: may change state | "model-controlled … SHOULD always be a human in the loop with the ability to deny" |
| Resource | the **application** | GET: read-only context | "application-driven, with host applications determining how to incorporate context" |
| Prompt | the **user** | slash command | "user-controlled … the user being able to explicitly select them" |

Design rule: put side effects in tools, stable read-only context in resources, reusable workflows in prompts. The protocol does not enforce the split ("free to expose through any interface pattern"); clients differ.

*In my project:* `book-session` is a tool; themes/phases are resources; `coaching-question` is a prompt.

### 6.4 Tools: schemas, structured output and two error channels
A tool has a `name`, `description`, `inputSchema` (JSON Schema) and optionally `outputSchema` and `annotations`. If an `outputSchema` exists, the server MUST return conforming `structuredContent` and clients SHOULD validate it. `structuredContent` was added in the 2025-06-18 revision. For backward compatibility a tool returning structured content SHOULD also return the serialized JSON in a text block. Two error channels exist: **protocol errors** (JSON-RPC `error`: unknown tool, malformed request) and **tool execution errors** (`isError: true` in a normal result: API failure, validation, business rules), which the model can read and correct. Annotations such as `readOnlyHint` describe behaviour but "clients MUST consider tool annotations to be untrusted unless they come from trusted servers". Zod is a schema library: one declaration yields a runtime validator and a JSON Schema.

Principle: *parse, don't validate*. Turn untyped input into a typed value at the boundary, once, so everything behind the boundary can trust the type.

*In my project:* both tools declare `outputSchema`; neither uses `isError` or annotations; input constraints beyond type (date format) are not enforced.

### 6.5 Safe and idempotent operations
A **safe** operation has no side effects (HTTP GET). An operation is **idempotent** if repeating it gives the same state as doing it once: f(f(x)) = f(x) for the state change (HTTP PUT, DELETE). Retries are everywhere in agent systems (timeouts, model re-planning), so a non-idempotent tool double-executes. The standard fix is an **idempotency key**: the caller sends a unique key; the server stores the result under it and returns the stored result on repeat.

Finance analogy: a payment instruction carries a unique end-to-end reference; the bank rejects a second instruction with the same reference rather than paying twice.

*In my project:* `book-session` creates a new ID per call (`coaching-data.ts:91`), so it is neither safe nor idempotent. The review's "if built today" adds an idempotency key and a confirmation step.

### 6.6 Transports: stdio and Streamable HTTP
**stdio:** the client launches the server as a subprocess. Messages are newline-delimited JSON-RPC with no embedded newlines on stdin/stdout. The server MUST NOT write anything to stdout that is not a valid MCP message; logs go to stderr. One stray `console.log` corrupts the stream. The authorization spec says stdio servers SHOULD NOT follow it and take credentials from the environment (chapter 6.4).
**Streamable HTTP:** one endpoint accepting POST; each JSON-RPC message is its own POST; the server answers with a JSON object or an SSE stream scoped to that request. Servers MUST validate `Origin` (DNS rebinding), SHOULD bind to localhost when local, SHOULD authenticate. The older HTTP+SSE transport is deprecated; MCP has no WebSocket transport.

*In my project:* `stdio.ts:16` logs with `console.error`, as required. `http.ts` binds to `127.0.0.1` (`http.ts:42`) but has no Origin check.

### 6.7 Tool definitions are prompt text
The model sees tool names, descriptions and schemas as part of its context on every turn. So (a) descriptions steer behaviour, (b) every tool costs tokens: context cost per turn ≈ Σ over tools of tokens(name + description + schema) (an estimate, not a spec formula), and (c) a malicious or sloppy description is an injection surface. This is why the memo moves critical context into `instructions` and tool descriptions.

*In my project:* `single-turn-advice`'s description tells the model that the answer is "questions, not advice" (`server.ts:61-62`), which shapes how the model presents it.

## 8. Glossary

| Term | One-line definition |
|---|---|
| MCP | Model Context Protocol: an open protocol for AI apps to call external tools and read context |
| Host / client / server | AI app / its protocol connector / the program exposing capabilities |
| JSON-RPC 2.0 | Request/response/notification envelope MCP messages use |
| Tool | Model-invoked action with a typed input (and optional output) schema |
| Resource | URI-addressed, read-only context chosen by the application |
| Resource template | A parameterised resource URI such as `coaching://themes/{themeId}` |
| Prompt | User-selected message template provided by the server |
| `structuredContent` | Machine-readable JSON result of a tool, validated against `outputSchema` |
| `isError` | Flag in a tool result marking an execution error the model can read |
| Annotations | Hints about a tool (read-only, destructive, idempotent); untrusted by default |
| stdio | Transport where the client spawns the server and talks over stdin/stdout |
| Streamable HTTP | Transport using POST to one endpoint, replies as JSON or SSE |
| SSE | Server-Sent Events: a one-way HTTP stream |
| Zod | TypeScript schema library giving validation and JSON Schema |
| Idempotent | Repeating the call leaves the same state as one call |
| `instructions` | Server-supplied text telling the client's model how to use the server |

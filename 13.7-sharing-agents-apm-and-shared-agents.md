# Course 13 · Chapter 13.7: Sharing agents across teams: APM and the shared-agents approach

_Andrey Popov's project notes: how it works, why it was built this way, and the theory behind it._

**In short:** APM (Agent Package Manager) and the shared-agents approach: manifest, lock file, targets, primitives, a Plan, Implement, Verify pipeline, portability gaps between tools and why a stop signal is not a completion receipt.

## 2. The problem (business view, plain English)

A company with 30 service repositories wants every team to use the same AI helpers: a planning agent, an implementing agent, a verifying agent, code review rules, Terraform and pipeline experts. Copying files into each repo creates 30 slightly different versions that drift apart. Teams also use different tools (GitHub Copilot, Claude Code, Codex, Cursor), and each tool wants its files in different folders and formats.

Analogy: shared templates in a company. You don't email the template to everyone; you publish one version, and everyone installs updates from it.

## 4. How it works

### 4.1 What APM is
**APM (Agent Package Manager)** is an open-source Microsoft dependency manager for AI-agent context, "like npm, but for agent instructions". The project declares what it needs in a manifest, and one command installs it for every AI tool the team uses.
| File / concept | Plain meaning |
|---|---|
| `apm.yml` | The manifest: name, version, target tools, and dependencies (other packages, MCP servers) |
| **Primitives** | The things APM distributes: **agents**, **skills**, **instructions**, **prompts**, plugins, MCP servers (hooks in newer versions) |
| `apm install` | Fetches packages (from GitHub, GitLab, Azure DevOps, Bitbucket or any git server) and places each primitive where each target tool expects it |
| **Targets** | Copilot, Claude Code, Codex, Cursor, OpenCode, Gemini, Windsurf, Kiro and others |
| `apm.lock.yaml` | Pins exact versions and content hashes, so a fresh clone gets the same content |
| `apm-policy.yml` | Governance rules enforced at install, including transitive MCP servers. Policies can only be **tightened** as they pass from enterprise to org to repo |
| Security scan | Install checks for hidden Unicode and blocks undeclared transitive MCP servers |

### 4.2 The shared-agents package: what is inside
```
 shared-agents repo (the producer)
   .apm/agents/        6 agents: plan, implement, verify, ci/cd, infrastructure, infrastructure-verify
   .apm/skills/        ~22 reusable procedures (fetch ticket, create branch, write tests, code review, create PR ...)
   .apm/instructions/  always-on rules: coding standards, working agreements, infrastructure patterns
   apm.yml             also declares MCP servers: work tracking, DevOps, cloud CLI, Terraform, browser tests,
                       code quality, design tool
        │  apm install (versioned)
        ▼
 service repo (a consumer)  gets the agents, skills, instructions and MCP config in the right folders per tool
```
| Primitive | What it is | Example |
|---|---|---|
| **Agent** | A role with allowed tools and a required workflow | "plan agent: read the ticket, make a branch, write spec files; may not write application code" |
| **Skill** | A reusable, named procedure an agent calls | "create pull request linked to the ticket" |
| **Instruction** | Always-on rules for a folder or file type | "backend code style", "never put secrets in commits" |
| **MCP server config** | Which tool servers the agents may use | ticket system, pipeline system |

### 4.3 The delivery loop: Plan → Implement → Verify
| Agent | Does | Must not | Hands over |
|---|---|---|---|
| **Plan** | Reads the ticket and code, creates a branch, writes proposal / design / tasks, opens a draft PR | Write application code; create a branch without a ticket key | Spec files on the branch → **human reviews the spec** |
| **Implement** | Does only the listed tasks; writes code and tests | Go beyond the task list | Code on the branch |
| **Verify** | Builds, tests, reviews against the spec, creates the PR linked to the ticket | **Write or modify application code**: report failures and stop | A PR for human peer review |

Rules baked in: separate session per agent, hand over **artifacts** not chat history (13.4), cheapest model that works with escalation (13.10), smaller models for summaries and bigger ones for architecture.

### 4.4 What the target tools see
APM turns the same source files into the format each tool expects. In my July check:
- **Skills** (the open `SKILL.md` format, adopted by 30+ tools) came out **byte-identical** for Claude and Codex: genuinely portable.
- **MCP servers** are a real protocol, so also portable.
- **Agents and instructions** have **no shared standard** across tools: each tool has its own way to say "this agent may only use these tools". This is where translation breaks.

## 5. Why it was built this way (decisions and trade-offs)

| Decision | Alternatives | Why this one | Cost / risk |
|---|---|---|---|
| A package manager for agent files | Copy files, git submodules, wiki | Versioned, reproducible, one command, policy-checked | New tool to learn; young project |
| One source, many targets | One folder per tool maintained by hand | Teams can use Copilot, Claude Code or Codex from the same source | Translation gaps for agents and instructions |
| Roles split into three agents with different rights | One all-purpose agent | Separation of duties; verifier can't "fix" its way to green | Hand-overs must be explicit |
| Spec files reviewed before code | Review only the PR | Cheaper to correct a plan | Slower start |
| Lock file + content hashes | Floating versions | Same content on every machine; tamper-evident | Updates are a deliberate step |

## 6. Theory behind it (the "lecture" part)

### 6.1 Dependency management and supply chain
Packages bring code or instructions from outside your repo. Good practice: pin versions, check hashes, review updates, restrict what a package may pull in. Instructions for agents are executable in effect (they steer actions), so they are part of the **software supply chain**.
*In this course:* APM's lock file, hash pinning, Unicode scan and policy file are exactly these controls.

### 6.2 Convention over configuration, and its limits
Shared defaults (naming, spec layout, quality gates) make teams consistent and onboarding fast. Too rigid and teams route around them.
*In this course:* consumers can extend or override instructions with their own files.

### 6.3 Least privilege and separation of duties for agents
Each agent gets only the tools its job needs; the checker is not the author (13.2). A restriction written in a file is only as good as the tool that **enforces** it.
*In this course:* the verifier can't edit code **if** the target tool honours the restriction (see §7).

### 6.4 Receipts and evidence
A claim of completion needs evidence tied to the work: ticket, attempt, commit, test report. A raw "stop" signal from a runtime says the agent stopped talking, not that the business step succeeded.
*In this course:* the gap found in my 2026-10-14 check (§7).

## 8. Glossary

| Term | One-line definition |
|---|---|
| APM | Agent Package Manager: installs agents, skills, instructions, prompts and MCP config as versioned packages |
| `apm.yml` | The manifest listing targets and dependencies |
| `apm.lock.yaml` | Lock file with exact versions and content hashes |
| `apm-policy.yml` | Install-time governance rules that can only be tightened downwards |
| Primitive | One kind of distributable item: agent, skill, instruction, prompt, plugin, MCP server |
| Target | The AI tool APM writes files for (Copilot, Claude Code, Codex ...) |
| Skill | A reusable named procedure in the open `SKILL.md` format |
| Instruction | Always-on rules that apply in a scope |
| OpenSpec | Lightweight spec format: proposal, design, tasks per change |
| Hook | A script the tool runs at an event (session start, agent stop, tool use) |
| Receipt | Evidence record that a step completed, with ticket, attempt and artifact |
| Idempotency | Doing the same operation twice has the same effect as once |

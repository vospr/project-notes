# Course 13 · Chapter 13.3: The five team shapes (orchestration patterns) in Microsoft Agent Framework

_Andrey Popov's project notes: how it works, why it was built this way, and the theory behind it._

**In short:** The five orchestration patterns in Microsoft Agent Framework (sequential, concurrent, handoff, group chat, Magentic): analogies, who decides the next step, when to use each, and where human approval fits.

## 2. The problem (business view, plain English)

Once you decide a job needs several agents (13.2), you must decide **how they work together**: in a line, all at once, passing the customer along, in a meeting, or under a manager who keeps re-planning. Teams that skip this choice end up with an improvised mix that is hard to test. Microsoft Agent Framework gives five named, tested shapes, so the choice becomes a design decision you can explain and review.

Analogy: five ways to run office work: an assembly line, asking several experts at once, a call centre transfer, a moderated meeting, and a project manager with a whiteboard.

## 4. How it works

### 4.1 The five shapes at a glance
| Pattern | Everyday analogy | Who decides the next step | Use it when | Avoid when |
|---|---|---|---|---|
| **Sequential** | Assembly line: draft → edit → approve | **Code** (fixed order) | Steps are known and each builds on the last | Steps could run in parallel, or the order depends on the content |
| **Concurrent** | Ask three experts the same question at once, then compare | **Code** (fan out, then gather) | Independent views or checks on the same input; speed | Answers depend on each other |
| **Handoff** | Call centre: the first agent transfers you to billing or tech support | **The agents** (each decides whom to pass to) | Routing to specialists; the conversation moves around | You need a guaranteed path or audit of every step |
| **Group chat** | A moderated meeting: the chair picks who speaks next | **A manager** (picks the next speaker) | Agents need to build on each other's points; review and debate | Simple jobs; it is the most expensive per answer |
| **Magentic** | A project manager with a whiteboard who re-plans when stuck | **A manager agent** with a plan and a progress check | Open-ended, complex tasks where the plan must change | Anything predictable; hard to test and costly |

Rule of thumb: **move down the table only when the row above can't do the job.** Control and predictability fall as you go down; flexibility and cost rise.

### 4.2 Pictures
```
 Sequential   in ─► [A] ─► [B] ─► [C] ─► out

 Concurrent        ┌─► [A] ─┐
              in ──┼─► [B] ─┼──► gather ─► out
                   └─► [C] ─┘

 Handoff      in ─► [triage] ──"billing issue"──► [billing] ──"needs refund"──► [refunds]

 Group chat   [manager] ─ picks ─► A speaks ─► manager ─ picks ─► C speaks ─► ... ─► done

 Magentic     [manager]: task ledger (facts, plan) + progress ledger (are we stuck? who next?)
                 └─► assigns A ─► checks progress ─► stuck? rewrite plan ─► assigns B ...
```

### 4.3 Each one, plainly
- **Sequential.** Each agent gets the previous agent's output. Predictable, easy to test. Example: write a release note → check facts → shorten for Slack.
- **Concurrent.** The same input goes to several agents in parallel; the results are collected and combined (by code or by a final agent). Example: a support ticket goes to sentiment, category and priority agents at the same time.
- **Handoff.** No central boss. Each agent can hand the conversation to another it's allowed to reach. Good for customer conversations that move between topics. Can also hand to a **human**.
- **Group chat.** A manager (rule-based like round-robin, or an LLM) picks who speaks next in a shared conversation. Good for "writer + critic" refinement loops. Can pause to ask a human.
- **Magentic.** From Microsoft Research's Magentic-One. A manager keeps a **task ledger** (facts and plan) and a **progress ledger** (what's done, are we looping, who's next). After every round it checks progress and **re-plans** if the team is stuck. Most flexible, least predictable.

### 4.4 Underneath: workflows
All five are built on Agent Framework **Workflows**: a graph of steps (agents or plain functions) connected by edges, with **checkpoints** (the run can pause and resume) and **human-in-the-loop** requests (the workflow stops and waits for an approval). You can also draw your own graph when none of the five fits. In Foundry, workflows can be built visually or in YAML and run as hosted agents (13.5).

### 4.5 Where the human fits
In every pattern you can mark a tool as **approval-required**: when an agent wants to call it, the workflow pauses, saves its state, and waits for a person. Because state is saved (checkpointed), the approval can come hours later (13.8 explains why that works).

## 5. Why it was built this way (decisions and trade-offs)

| Decision | Alternatives | Why this one | Cost / risk |
|---|---|---|---|
| Offer five named patterns | Only a free-form graph | Common shapes are tested, documented and easy to review | Teams may force a job into a pattern that doesn't fit |
| Patterns on top of one workflow engine | Separate engines per pattern | Same checkpoints, approvals and tracing everywhere | Learning the engine is still needed for custom shapes |
| Include Magentic (manager-led re-planning) | Leave open-ended tasks to custom code | Hard tasks need re-planning; Microsoft Research tested it | Least predictable; highest cost; hardest to evaluate |
| Human-in-the-loop as a built-in pause | Ask humans outside the system | Approval becomes part of the record | Waiting runs must be stored and expired properly |

## 6. Theory behind it (the "lecture" part)

### 6.1 Orchestration vs choreography
In **orchestration**, one conductor tells each part what to do (sequential, concurrent, group chat, Magentic). In **choreography**, each part knows whom to pass to, with no conductor (handoff). The terms come from microservices design.
*In this course:* orchestration is easier to audit; choreography is more flexible.

### 6.2 Fan-out / fan-in
Send the same work to many workers (fan-out), then collect and combine (fan-in). The combining step needs a **merge rule**: vote, pick best, concatenate, or summarise.
*In this course:* concurrent orchestration is fan-out / fan-in; 13.8 shows the Python side of merge rules.

### 6.3 Control vs autonomy
Each pattern is a point on a scale from "code decides everything" (sequential) to "a model decides everything" (Magentic). More autonomy handles surprises but is harder to predict, test and price.
*In this course:* the rule of thumb in §4.1.

### 6.4 Plan, act, reflect
Magentic is the classic "plan → act → check progress → re-plan" loop, applied to a team. The progress check is what stops an endless loop.
*In this course:* the same idea as the to-do tool in a single deep agent (13.1), lifted to team level.

## 8. Glossary

| Term | One-line definition |
|---|---|
| Orchestration pattern | A standard shape for how agents work together |
| Sequential | Agents run in a fixed order, each using the previous output |
| Concurrent | Agents run in parallel on the same input; results are combined |
| Handoff | Agents pass control to each other without a central boss |
| Group chat | A manager picks the next speaker in a shared conversation |
| Magentic | A manager agent plans, assigns, tracks progress and re-plans (from Magentic-One) |
| Task ledger | Magentic's record of facts and the current plan |
| Progress ledger | Magentic's record of progress, loops and the next assignment |
| Workflow (Agent Framework) | A graph of steps with checkpoints and human pauses that patterns are built on |
| Human-in-the-loop | The run pauses until a person approves or answers |
| Fan-out / fan-in | Send to many in parallel, then gather and combine |

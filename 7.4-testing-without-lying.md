_Andrey Popov's project notes: how it works, why it was built this way, and the theory behind it._

## 2. The problem (business view, plain English)

The first version of the repo had 487 tests and a command-line app that printed no answer and sent every turn after the first down the wrong route. The test count looked like rigour but was not. About 50 tests checked repo tidiness or documentation layout; every end-to-end test used a fresh state and called the graph directly, never the real entry point; one test asserted the sticky-route bug as correct.

Finance analogy: control testing in an audit. A weak test checks that the policy manual says "payments need two approvers". A real test tries to push a one-person payment and watches it get blocked. The first gives you comfort and no assurance. The repo had many of the first and too few of the second.

## 4. How it works (technical walkthrough)

```
what a test can fake                     what stays real
────────────────────────────────         ──────────────────────────────────
anthropic module (sys.modules)           DispatcherAgent, rules, thresholds, parsing
search_duckduckgo (function patch)       guardrail, synthesis, graph wiring, state
API key (env var removed / dummy)        main._run_loop (in the CLI test)
stdin (scripted input_reader)            stdout (captured with capsys)
session write (stubbed in CLI test)      the YAML config files
```

**Suite shape**: 497 collected, 0 skipped: 198 unit, 296 e2e, 3 top-level. All offline, about 3 s. Passing on Python 3.11 and 3.12 locally; green on GitHub for PR #1. The README states what the suite does not show: "it does not measure answer quality".

**Layer 1: the offline guard** (`CC:tests/conftest.py:16-28`). An autouse fixture replaces `search_duckduckgo` with a function that raises "network disabled in tests" and deletes `ANTHROPIC_API_KEY`. Tests that need either set them again themselves. `test_suite_is_offline.py` asserts both effects.

**Layer 2: fakes for the model.** Two patterns. (a) A fake module put into `sys.modules["anthropic"]` with a client whose `messages.create` returns a canned object with `.content[0].text` (`CC:test_story_3_4_*.py:11-27`, `test_routing_eval.py:74-82`). (b) A recorder variant that also stores the call's kwargs, so a test can assert `model == "claude-haiku-4-5"` and `max_tokens == 128` (`test_story_3_4_*.py:40-50`). Eval-cost tests add a fake `usage` object and check that tokens and dollars add up (`test_routing_eval.py:93-117`).

**Layer 3: steering without lying.** After the fix, tests no longer pre-set `state["route"]`. The `force_route` fixture patches Stage 1 to return a chosen route (`CC:conftest.py:61-76`), so topology tests exercise the real dispatcher entry.

**Layer 4: the session test.** `test_cli_three_turns.py` scripts three input lines, fakes search, stubs only the session write, sets a dummy key plus `SKIP_API_PROBE=1`, runs `main.main` and asserts on stdout order (`CC:test_cli_three_turns.py:23-67`). All three lines are Stage-1 hits, so no model fake is needed. This is the test that would have caught both original defects.

**Layer 5: docs pinned to data.** `test_readme_claims.py::test_committed_rules_only_result_matches_a_fresh_run` (`:54-58`): the rules-only arm needs no model, so it is re-run offline and compared with the committed JSON.

**A taxonomy of the tests, by what they would catch** (my classification, by reading file names and samples):

| Kind | Example | Catches a behaviour bug? |
|---|---|---|

## 5. Why it was built this way (decisions and trade-offs)

| Decision | Alternatives | Why this one | Cost / risk |
|---|---|---|---|
| Fully offline suite, no real model or web | Live tests in CI | Free, fast, deterministic, CI has no key ||
| Fake the `anthropic` module via `sys.modules` | Fake at HTTP level (recorded cassettes) | Simple, no new library | Fake shape can drift from the SDK; no request validation |
| Delete the wording and removed-layout tests | Keep them for the count | Count should reflect value; README says so | Tidiness tests partly remain |
| Pin README numbers to code and data in a test | Trust the author | Docs cannot silently go stale on numbers | Couples README to test count; prose unguarded |
| Fix the test for the sticky route by replacing it, add a session-level test | Only patch the code | The old suite blessed the bug | One session test covers 3 mixed turns, Stage-1 only |
| ruff + strict mypy on source only; tests excluded | Annotate tests too | 77 strict errors in tests, mostly missing annotations | "Strict" is not project-wide |
| Evals separate from tests (7.3) | Assert accuracy in a test | LLM quality is a measurement, not a pass/fail | Eval not in CI; one manual run |

## 6. Theory behind it (the "lecture" part)

### 6.1 What a test proves: oracles and assurance
A test has an **oracle**: the rule that decides pass or fail. A good oracle is independent of the code under test (a known answer, an invariant, a second implementation). A bad oracle copies the implementation, so the test passes by construction. Tests show the **presence** of bugs, never their absence (Dijkstra). Confidence comes from the **breadth of what you tried to break**, not from the count of tests. Useful measures: assertion quality, mutation score (does the suite fail when the code is deliberately broken?), and whether tests run through real entry points.

*In my project:* the stale-RAG test and the edge-tuple test are tautological; the 3-turn CLI test has an independent oracle (stdout order).

### 6.2 Test doubles: dummy, stub, fake, spy, mock
Standard vocabulary (Meszaros): a **stub** returns canned answers; a **fake** has a simplified working implementation; a **spy** records how it was called; a **mock** has expectations set in advance and verifies them. People say "mock" for all of them. The risk is **fidelity**: a double that is easier than the real thing hides integration bugs. Manage it with **contract tests** (run the same checks against the double and the real service) or an occasional live smoke test.

*In my project:* the `anthropic` doubles are stubs/spies. Their output format is a guess about the real model; no contract test compares it with a real reply.

### 6.3 Mocks hide the assumptions you most need to test
The rule of thumb: **do not mock what you do not own without also testing the contract**. For an LLM, the contract is: "given this prompt, the reply parses and contains an allowed label". That is exactly what the unit tests assume and what the eval's first run called into question (7.2, 7.3). Remedies: structured output with an enum (the label set is enforced by the API), a small **golden set** run against the live model on demand, and logging raw replies in production.

*In my project:* green unit tests plus a research route the live model never chose.

### 6.4 Testing stateful, multi-step systems
State leaks between steps. Test the **sequence**: arrange a polluted state, run step k+1, assert the invariant. Use the real entry point and fake only the edges (network, clock, disk). Include failure in the middle (a node raises on turn 2). Property-based testing generates many sequences (Hypothesis) and checks invariants such as "turn-scoped fields independent of the previous turn".

*In my project:* one 3-turn test; no failure-in-the-middle test (7.

### 6.5 Documentation tests: good and bad
Two different things get called "docs tests".
- **Behaviour-backed doc checks** (good): extract a claim from the doc and verify it against code or data. Examples: numbers in a README table equal the committed results; every local link exists; the stated KB size equals the file. Doctests and executable examples are the same idea. They stop **doc drift**.
- **Layout or wording checks** (poor): assert a section title, a line count or a sentence exists. They freeze prose, break on harmless edits and prove nothing about behaviour. A **change-detector test** is any test that fails when the implementation changes without a behaviour change.

Also: a test that a doc contains a *prediction* ("expected confidence 0.84") verifies the text, not the prediction.

*In my project:* `test_readme_claims.py` is the good kind; the demo-script text test and the 3-to-5-lines test are the poor kind.

### 6.6 Separate tests from evals
A **test** answers "does the code do what I specified?" on deterministic inputs; pass/fail. An **eval** answers "how good is the model's output on a representative set?" and returns a distribution, often with noise; it informs a decision. Mixing them either makes CI flaky (live model in tests) or hides quality (mocked model in tests, no eval). Standard practice: offline tests in CI on every commit; evals on demand or nightly, with stored per-item results and tracked over time.

*In my project:* the split is right (offline tests; one-off eval). Missing: the eval is not repeatable cheaply and does not store per-row outputs.

### 6.7 The test pyramid and honest reporting
Many fast unit tests, fewer integration tests, few end-to-end tests. Report **what the suite covers and what it does not**, not only a count. A count is meaningful only with context: how many are parametrised copies, how many check behaviour. Coverage tools measure lines executed, not assertions made; a line can be covered by a test that asserts nothing.

*In my project:* the redo README does this well ("they do not measure answer quality"; "far more than the 9 files" explained by parametrisation). The review's original "54 tests" was wrong by ten times (487 collected, 55 files).

## 8. Glossary

| Term | One-line definition |
|---|---|
| Oracle | The rule that decides whether a test's result is correct |
| Tautological test | A test that cannot fail because it asserts what it just set |
| Change-detector test | A test that fails on any change to the code or config, even harmless |
| Stub / fake / spy / mock | Canned answers / simplified working version / records calls / checks expected calls |
| Mock drift | The double no longer matches the real service, so tests stay green while integration breaks |
| Contract test | A test run against both the double and the real service to check they agree |
| Golden set | A fixed set of inputs with accepted outputs, used for repeatable checks |
| Autouse fixture | A pytest fixture applied to every test without being requested |
| `monkeypatch` | pytest tool to replace attributes, env vars and modules for one test |
| Doc drift | Documentation that no longer matches the code |
| Mutation testing | Breaking the code on purpose to see whether the tests notice |
| Test pyramid | Many unit tests, fewer integration tests, few end-to-end tests |
| Eval vs test | Measure of quality on a sample vs pass/fail check of specified behaviour |
| Parametrised test | One test function run with many inputs; one function, many collected tests |

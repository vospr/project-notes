# Course 13 · Chapter 13.1: From chatbot to agent to "deep agent"

_Andrey Popov's project notes: how it works, why it was built this way, and the theory behind it._

**In short:** What a deep agent is: an agent loop plus a written plan, a scratch file system, subagents with clean memory and a detailed prompt, and why that keeps long tasks on track. Compares chatbot, workflow, agent and deep agent.

## 2. The problem (business view, plain English)

A chatbot answers one question. A simple agent can use tools in a loop: search, read, answer. That is enough for "what is the status of ticket 123?". It breaks on **long tasks**: "research our three competitors and write a 10-page comparison", or "implement this feature across 20 files and make the tests pass". After 30 or 40 steps the simple agent forgets what it planned, its memory (the context window) is full of old search results, and it either stops too early or wanders off.

Analogy: a junior employee who is brilliant for 10 minutes but has no notebook, no to-do list, and can't delegate. Give them a notebook (files), a to-do list (plan), the right to hand parts to colleagues (subagents), and a thick onboarding manual (detailed prompt), and they can run a two-week project. That is a deep agent.

## 4. How it works

### 4.1 Four levels, one picture
```
 Chatbot        question ──► model ──► answer
 Workflow       fixed steps written by a developer: A ──► B ──► C   (the model fills in each box)
 Agent          model ──► picks a tool ──► reads result ──► picks next tool ... ──► answer
 Deep agent     agent + a plan + a scratch file system + helpers (subagents) + a long manual
```
- A **workflow** is predictable: the developer decides the path.
- An **agent** decides its own path, step by step, in a loop.
- A **deep agent** is an agent with the extra structure needed to keep going for hours without losing the thread.

### 4.2 The four ingredients
| Ingredient | What it is, plainly | Problem it solves |
|---|---|---|
| **1. A plan / to-do list** | A tool the agent uses to write down its steps and tick them off ("write_todos" in `deepagents`, the to-do list in Claude Code) | Forgetting the goal halfway; stopping early; skipping steps |
| **2. A scratch file system** | The agent saves notes, drafts and big tool results to files and reads back only what it needs | The context window filling up with raw data; losing work if the session restarts |
| **3. Subagents (helpers)** | The main agent hands a sub-task to a helper that starts with a **clean memory**, does the job, and returns only a short summary | One context full of everything; doing independent jobs one by one instead of in parallel |
| **4. A detailed system prompt** | A long, careful manual: how to plan, when to delegate, how to use each tool, what "done" means | The model improvising its own process every time |

The key insight: **ingredients 2 and 3 are both about memory.** A file system moves information *out* of the context window; a subagent does messy work in *its own* context window and hands back only the result. Deep agents are deep because they manage memory well, not because the model is different.

### 4.3 What a subagent hand-back looks like
```
 Main agent context:  goal, plan, short summaries        (stays small and clean)
        │  "research competitor B pricing, return 10 bullet points + sources"
        ▼
 Subagent context:    40 web pages, dead ends, raw notes  (thrown away afterwards)
        │
        ▼  returns: 10 bullets + 5 links
 Main agent context:  + 10 bullets                        (not the 40 pages)
```
This is called **context isolation** (LangChain says "context quarantine").

### 4.4 Three real deep agents
| Product | Plan | Files | Subagents | Long prompt |
|---|---|---|---|---|
| **Claude Code** | to-do list tool | the real project folder, plus memory files like `CLAUDE.md` | `Task` tool spawns helpers | very long system prompt + project instructions |
| **Deep Research** (Anthropic, OpenAI, Google) | the lead agent writes a research plan and saves it to memory | notes and citations stored outside the chat | parallel search helpers | prompt teaches how to split and when to stop |
| **LangChain `deepagents`** (Python and JS library) | `write_todos` tool | a virtual file system (in memory, or a real backend) | a `task` tool to call named helpers | built-in prompt you extend |

## 5. Why it was built this way (decisions and trade-offs)

| Decision | Alternatives | Why this one | Cost / risk |
|---|---|---|---|
| Write the plan down as a tool call | Keep the plan "in the model's head" | The plan becomes visible, checkable and survives long contexts | A few extra tokens per step |
| Save big results to files | Keep everything in the conversation | The context stays small; you can resume after a crash | The agent must remember to read the file back; files can go stale |
| Delegate to helpers with clean memory | One agent does everything | Clean context per job; parallel work | Helpers can't see each other's decisions (13.2); more tokens |
| Long, explicit prompt | Short prompt, trust the model | Consistent behaviour across runs | Prompt becomes a document to maintain and test |

## 6. Theory behind it (the "lecture" part)

### 6.1 The agent loop (ReAct)
The basic pattern: **think → act (call a tool) → observe the result → repeat**, until the model answers without calling a tool. Introduced as ReAct (Yao et al., 2022). Everything in this course is built on this loop.
*In this course:* a deep agent is still this loop; the four ingredients are extra tools and instructions around it.

### 6.2 Context window = working memory
The model only "knows" what is in the current request: instructions, history, tool results. That space is limited and gets **worse** as it fills (models pay less attention to the middle of a long context, sometimes called "context rot"). Managing what goes in is called **context engineering**.
*In this course:* plan, files and subagents are three context-engineering moves: **write it down, move it out, isolate it**.

### 6.3 Workflow vs agent: the control question
Who decides the next step? In a **workflow**, your code does. In an **agent**, the model does. Deep agents mix both: the model plans and acts, but code enforces limits (maximum steps, approvals, budgets).
*In this course:* 13.3's orchestration patterns are a menu of how much control code keeps.

### 6.4 Breadth vs depth
"Deep" also means the task has many layers: a goal, sub-goals, sub-sub-tasks. Planning turns a deep task into a tree; subagents take the branches.
*In this course:* 13.2 asks when branching into many agents is worth the cost.

## 8. Glossary

| Term | One-line definition |
|---|---|
| Agent | A model in a loop that chooses and calls tools until the task is done |
| Workflow | A fixed sequence of steps decided by code; the model fills in each step |
| Deep agent | An agent with a plan, a scratch file system, subagents and a detailed prompt, built for long tasks |
| Subagent | A helper agent started by another agent, with its own clean context, returning a summary |
| Context window | Everything the model sees in one request; its working memory |
| Context isolation | Doing messy work in a separate context so the main one stays clean |
| Context engineering | Deciding what goes into the context window, when, and in what form |
| ReAct | The think → act → observe loop behind most agents |
| To-do tool | A tool the agent uses to write and update its own plan |
| Virtual file system | Files that live in the agent's state or a store, not necessarily on disk |
